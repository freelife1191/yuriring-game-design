# 실무 패턴

책의 방법을 요청별 산출물로 재구성했다. 아래 빈 양식과 새 적용 예시는 책의 원본 서식을 복제한 것이 아니다. 자세한 사례·쪽 근거는 연결된 장에서 확인한다.

## 문제에서 경험까지 의도 정리

**언제:** 새 기능의 도입 이유가 “리텐션·매출·만족도 향상” 수준에 머물 때.

**방법:** 대상과 문제를 좁히고 시스템의 역할, 의도한 감정, 플레이 흐름을 연결한다. 6가지 논리 질문으로 시점·우선순위·결과·차이·리스크·근거를 보강하고, 초기·설계·검토 단계마다 다시 점검한다(ch04, 책 72–73쪽 / PDF 74–75쪽).

**작성 양식:** `대상 / 기존 문제 / 전체 게임에서의 역할 / 의도한 감정 / 행동 흐름 / 기대 변화 / 근거·검증 필요 사항`

**트레이드오프:** 기대 효과를 구체화하되 실제 데이터가 없는 인과는 가설로 남긴다(스킬 정리). 관련 원문: [ch04](chapters/ch04-intent-design.md), 책 58–74쪽 / PDF 60–76쪽.

## 기능과 속성을 분해한 뒤 연결

**언제:** 길드·우편·숙소처럼 많은 기능이 얽힌 시스템을 설계할 때.

**방법:** 행위·동작은 기능으로, 대상의 정보·차이값은 속성으로 정리한다. 각 기능의 입력·조건·결과·예외를 적고 다른 기능으로 넘어가는 정보와 영향을 연결한다.

**작성 양식:** `기능 / 대상 객체 / 필요 속성 / 조건 / 처리 결과 / 예외 / 연동 대상`

**트레이드오프(스킬 적용 주의):** 공통 구조는 재사용하되 목적이 다른 규칙까지 억지로 같은 모듈에 넣지 않는다. 분해·모듈화의 근거는 [ch05](chapters/ch05-system-decomposition.md), [ch06](chapters/ch06-system-composition.md).

## 정상 흐름과 예외를 함께 명세

**언제:** 구매·등록·보상 수령처럼 실패와 상태 변화가 생기는 기능.

**방법:** 의도를 설계 기준으로 바꾸고 기능을 나눈 뒤 판정 정보·결과·예외를 설계한다. 검증 순서, 실패 안내, 취소·충돌 시 결과를 함께 적는다.

**새 적용 양식:** `시작 행위 / 판단 조건 / 정상 처리 / 실패·취소 처리 / 플레이어 안내 / 종료 상태`

**QA 적용 보완:** 스킬이 덧붙인 점검 방법이다. 확정 정책의 필수 결과와 미정 정책별 조건부 결과를 나눈다. 예를 들어 “동일 요청은 한 번만 지급”이 확정이면 재요청으로 추가 지급되지 않아야 한다. 재요청에 성공 응답을 돌려줄지 오류를 안내할지는 별도 미정 정책으로 남긴다. 규칙과 UI가 충돌하면 모순과 결정 질문을 적고 하나의 기대 결과를 임의로 만들지 않는다. 시나리오 작성과 실제 실행 결과도 구분한다.

**QA 작성 양식:** `사전 조건 / 입력 / 확정 정책의 필수 결과 / 미정 정책별 조건부 결과 / 결정 질문`

**트레이드오프:** 악용 방지 제약과 이용 편의를 함께 평가한다. 책의 거래소 수수료·건수·대기 시간은 사례 값이다. [ch07](chapters/ch07-rule-components.md), [ch08](chapters/ch08-rule-design.md).

## 분기를 플로 차트로 점검

**언제:** 저자 기준으로는 '조건 판정이 중요한가', '예외가 많은가' 두 질문에 YES가 나올 때다(ch09, 책 153쪽 / PDF 155쪽). 두 질문 모두 YES로 읽는 것이 자연스럽지만 원문이 '모두'를 따로 적지는 않는다. 그렇지 않으면 텍스트 설명으로 충분하다. 말로 적은 조건이 여러 해석을 낳을 때 점검용으로 그려 보는 것은 스킬의 적용 방법이다.

**방법:** 시작 → 판정 → 분기별 처리·안내 → 다음 프로세스 또는 종료로 연결한다. 각 분기가 어디로 가는지 확인하고 세부 명세는 글·표로 보완한다.

**트레이드오프:** 전체 시스템을 하나의 거대한 차트에 넣으면 가독성이 떨어진다. 하위 프로세스로 나눠 연결한다. [ch09](chapters/ch09-flowcharts.md).

## 객체·반복 정보·참조 분리

**언제:** 보상 회차가 늘 때 칼럼이 계속 증가하거나 메타 정보가 반복될 때.

**방법:** 한 행이 뜻하는 대상을 먼저 정의한다. 출석부 메타 정보와 회차별 보상을 분리하고 출석부 키로 연결한다. 보상 아이템은 기존 아이템 키로 참조한다.

**설계·검수 양식:** `테이블 / 한 행의 의미 / 기본 키 / 중복 금지 범위 / 단일 행 참조·그룹 조회 / 검증 규칙`

업무상 중복 범위 점검은 스킬이 덧붙인 적용 보완이다. 아래 예시의 요청별 유일성 제약을 책의 직접 서술이나 원본 스키마로 인용하지 않는다.

**새 적용 예시:** 자동 편성 결과를 선택 캐릭터별 행으로 관리한다면, 요청 한 건과 선택 후보 한 명의 행을 구분한다. 선택 행의 고유 ID가 달라도 같은 요청에서 같은 캐릭터나 순위가 반복될 수 있으므로, 해당 중복이 금지된 정책에서는 `요청 ID + 캐릭터 ID`, `요청 ID + 순위`의 유일성을 따로 검증한다. 요청 ID는 요청 한 행을 참조하는 동시에 선택 테이블의 여러 행을 조회하는 기준이 될 수 있다. 인원수·ID 생성 방식·배열 등 다른 저장 구조의 채택은 프로젝트에서 정하며, 그 구조에 맞게 행·중복·조회 규칙을 설명한다.

**원문 사례의 구조 재구성:**

| 테이블 | 한 행의 의미 | 핵심 연결 |
|---|---|---|
| 출석부 | 출석 이벤트 하나 | 고유 출석부 키 |
| 출석 보상 | 해당 이벤트의 회차별 보상 | 출석부 키·아이템 키 |
| 아이템 | 아이템 정의 하나 | 고유 아이템 키 |

**트레이드오프:** 원문은 분리로 반복을 없애고 키로 연결하는 효과를 설명한다([ch11](chapters/ch11-table-design.md), 책 176–181쪽 / PDF 178–183쪽). 분리하면 입력·참조 작업이 늘 수 있으니 실제 관리 흐름과 유지 보수 비용을 함께 본다는 판단은 스킬 정리다.

## UI 요소의 행동까지 정의

**언제:** 화면은 있지만 개발자가 클릭 결과나 상태 보존을 알 수 없을 때.

**방법:** 정보 구조도·화면 전환·와이어프레임으로 범위를 정리하고 요소별 역할과 해당되는 동작·기본값·저장 여부를 작성한다. 정적 제목·설명에는 입력·저장 조건을 강제하지 않는다.

**작성 양식:** `요소 이름 / 역할 / 해당되는 입력·상호 작용·기본값·변경 결과·저장 여부 / 관련 규칙`

**트레이드오프:** 화면 밀도와 정보 탐색, 조작 편의 사이의 균형을 본다([ch14](chapters/ch14-visual-interaction.md), 책 235–236쪽 / PDF 237–238쪽). 예쁜 화면만으로 작동 명세를 대신하지 않는다. [ch15](chapters/ch15-ux-ui-design.md), [ch16](chapters/ch16-ui-components.md).

## 기능별 협업 문서 묶기

**언제:** 규칙·표·UI가 멀리 흩어져 구현자가 문서를 반복 탐색할 때.

**방법:** 개요에서 의도·대상·효과를 설명하고 기능별로 규칙·예외·데이터·UI·요청 리소스를 모은다. 개발 중 변경 이유와 결과를 반영한다.

**트레이드오프:** 기능별 독립성을 높이면서 공통 정의를 중복하지 않도록 참조한다. 문서의 길이는 시스템 규모에 맞춘다. [ch17](chapters/ch17-document-purpose.md)–[ch20](chapters/ch20-production-lifecycle.md).

## AI 초안을 검토 재료로 사용

**언제:** 발상이 막히거나 기능·의도·예외가 섞인 메모를 정리할 때.

**방법:** 목표·전제·문제와 원하는 산출물을 전달한다. 후보·분류·논리 보완·문장 교정을 받고 원본의 조건·예외와 대조한다. 사실과 효과 주장은 별도 근거가 확인되기 전까지 가설로 둔다.

**트레이드오프:** 초안 작성은 빨라지지만 표현의 설득력만으로 사실성을 판단하면 위험하다. 책의 AI 활용에 검증 절차를 보완한 적용 지침이다. [ch19](chapters/ch19-document-quality.md), 책 329–336쪽 / PDF 331–338쪽.
