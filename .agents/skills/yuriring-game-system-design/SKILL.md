# 유리링의 실전 게임 시스템 기획

정윤지(유리링) · 한빛미디어 · PDF 372쪽 · 8부 21장 · 제작 2026-10-12

## 사용과 산출물

한국어로 답한다. 주제나 장 번호를 받으면 아래 색인에서 **관련 장을 먼저 읽고** 적용한다. 인자 없이 호출하면 핵심 원칙과 활용 범위를 안내한다. 모든 장을 한꺼번에 읽을 필요는 없다.

구체적인 사례·컴포넌트·테이블 이름으로 질문받거나 여러 장이 필요한 경우 [참조 자료 색인](references/index.md)에서 읽을 자료를 고른다. 용어 확인은 [용어집](glossary.md), 설계 양식은 [실무 패턴](patterns.md), 초안의 빠른 점검은 [판단표](cheatsheet.md)를 함께 읽는다. 보조 자료만으로 세부 정책을 확정하지 않고 연결된 장의 조건·사례·한계를 확인한다.

| 요청 | 먼저 읽을 장 | 산출물 예시 |
|---|---|---|
| 기능 제안·도입 이유 | ch03–04 | 대상·문제·역할·감정·흐름·근거 |
| 시스템 설계 | ch05–09 | 기능·속성, 조건·결과·예외, 처리 흐름 |
| 데이터 테이블 | ch10–12 | 행의 의미, 칼럼·타입·키·참조·설명 |
| UX/UI | ch13–16 | 화면 흐름, 요소별 행동·상태·저장 규칙 |
| 기획서 작성·검토 | ch17–19 | 독자에 맞는 명세, 누락·모순·보완안 |
| 개발·운영 협업 | ch20–21 | 단계별 책임, 변경 영향과 우선순위 |

기획 작업에서는 장르·대상·기존 시스템·제약을 사용자 자료에서 파악한다. 불명확한 사항은 가정이나 미결정으로 표시한다. 검토 결과는 문제 → 플레이·구현 영향 → 수정안 순으로 쓴다.

## 자료를 읽고 답하는 방법

- **근거는 이 스킬 폴더의 자료다.** 원문 PDF나 추출 텍스트를 프로젝트에서 찾아 열지 않는다. 원문 확인이 필요하면 확인할 위치(책 쪽 / PDF 쪽)를 안내한다. 사용자가 원문 위치를 주며 대조를 요청할 때만 원문을 연다.
- **책이 다루지 않는 주제는 그렇다고 밝힌다.** 확률형 아이템 확률 공시 같은 법·규제 대응은 원문 전체에 서술이 없다(스킬 제작 때 원문 전문 검색으로 확인). 이런 질문에는 책이 다루지 않는다고 말하고 쪽수를 만들지 않으며, 일반 지식으로 보태는 부분은 그렇게 표시하고 최신 법령 확인을 권한다. 단, 현금 거래·시세 조작을 거래소 설계로 막는 사례는 [ch08](chapters/ch08-rule-design.md)에 있다(법 해설이 아닌 게임 설계 사례다). 여기 적히지 않은 주제가 스킬 자료에 없을 때는 '스킬 자료에서 찾지 못했다'고 쓰고 확인할 장을 안내한다.
- **고른 파일은 전체를, 긴 파일은 해당 절 전체를 읽는다.** 검색 결과 몇 줄만 보고 답하지 않는다. 조건·예외·사례 값은 문단 뒤쪽에 붙어 있는 경우가 많다. 다른 장의 위치를 인용하려면 그 장 파일의 해당 절을 먼저 읽는다. 검색 결과로만 본 파일의 위치는 인용하지 않는다.
- **출처를 구분해 쓴다.** 위치(`책 X쪽 / PDF Y쪽`)가 붙은 서술은 책의 내용으로 옮기고 장과 책 쪽을 함께 적는다. '스킬 정리', '적용 지침', '새 적용 예시', '스킬 해석'으로 표시된 내용과 자료 밖의 일반 지식은 그렇다고 밝힌다. 어느 쪽인지 표시가 없으면 저자의 말이라고 단정하지 않는다. 장 파일의 '안티패턴', '점검 항목', '사례 재구성', '적용 절차 — 스킬의 재구성' 절은 스킬 정리이며 그 안에서 원문 문장으로 쓴 쪽 표기만 원문 근거가 있다. '참고 원문 절'로 표시한 쪽은 그 단계가 참고한 범위일 뿐, 단계 문장을 책의 말로 옮기는 근거가 아니다. 장 머리말의 범위만 보고 절 전체를 뭉뚱그려 인용하지 않는다. 한 문장에 원문 서술과 스킬 지침이 섞여 있으면 '스킬의 적용 지침'으로 표시된 부분은 책의 말로 옮기지 않는다. '스킬 정리'는 스킬 자료에 실제로 있는 내용에만 붙이고, 자료에 없는 내용은 '추가 제안'이나 일반 지식으로 표시한다. 책의 항목에 자신의 이유나 해석을 덧붙이려면 문장을 나눠 그 부분을 따로 표시한다.
- **자료의 목록은 있는 항목만 옮긴다.** 점검 항목·표·사례 목록을 인용할 때는 자료에 실제로 있는 항목만 '자료의 목록'으로 소개하고, 새로 덧붙인 항목은 '추가 제안'으로 따로 표시한다.
- **원문의 강도와 조건을 그대로 옮긴다.** 필수·권장·제한, '모두/하나라도' 같은 조건 결합, 수치의 기준을 강하게 또는 약하게 바꾸지 않는다. 예를 들어 '사용이 제한되어 대안이 필요하다'를 '작동하지 않는다'로 쓰지 않는다.
- **사례 값은 사례로 쓴다.** 원문의 수치(확률, 배율, 목표 비율, 분량, 기간 등)는 그 사례의 조건과 함께 인용하고 다른 프로젝트의 기본값으로 옮기지 않는다. 원문이 기준(분모·대상·기간)을 밝히지 않은 수치는 사용자 수치와 같은 척도로 맞대어 비교하지 않는다.

테이블 설계·검토에서는 한 행의 의미·기본 키·업무상 중복 금지 범위를 함께 점검한다. 기본 키의 유일성만으로 같은 요청·회차 안의 중복이 방지된다고 가정하지 않는다. 업무상 중복 범위 점검은 스킬의 적용 지침이며 책의 직접 서술로 귀속하지 않는다. 단일 행을 참조하는 외래 키와 반복 그룹을 조회하는 연결을 구별하고, 참조 대상·존재 검증이 실제 관계와 맞는지 확인한다. 양식은 [실무 패턴](patterns.md#객체반복-정보참조-분리), 적용 기준은 [ch11](chapters/ch11-table-design.md)–[ch12](chapters/ch12-table-cases.md)를 읽는다.

QA 시나리오에는 확정 정책이 보장해야 할 결과와 미정 정책별 조건부 결과를 구분한다. 응답·복구 방식이 미정이어도 확정된 중복 반영 금지 같은 조건은 유지한다. 문서 간 조건이 충돌하면 모순을 표시하고 단일 기대 결과를 임의로 선택하지 않는다. 이는 스킬의 적용 지침이며, 관련 양식은 [정상·예외 명세 패턴](patterns.md#정상-흐름과-예외를-함께-명세)에 있다.

## 핵심 사고 도구

1. **플레이어의 결과에서 시스템의 원인을 읽는다.** 보이는 기능을 조건·흐름·예외·의도로 되짚는다. 시스템은 규칙과 작동 구조, 콘텐츠는 그 구조 안의 구체적인 내용으로 구분한다. (ch01–02)
2. **기획 의도 설계: 문제 정의 → 역할 정의 → 감정 설계 → 플레이 흐름 설계.** “리텐션 향상”에서 멈추지 않고 누구의 어떤 행동·경험을 바꿀지 정한다. 같은 기능도 수령 방식과 노출 시점에 따라 경험이 달라진다(책 52쪽 / PDF 54쪽, 책 65쪽 / PDF 67쪽, 책 71쪽 / PDF 73쪽). (ch03–04, 책 56–61쪽 / PDF 58–63쪽)
3. **기획 의도 증명 프레임의 6가지 논리 질문.** 필요성과 지금의 맥락 / 없을 때의 문제·우선순위 / 도입 결과와 이유 / 기존 기능과 차이 / 리스크와 대응 / 주장을 뒷받침하는 근거를 점검한다. 저자는 이 질문을 한 번 답하고 끝내지 않고 초기·설계·검토 단계마다 다시 점검하는 사고 프레임으로 제시한다. 저자는 피드백·이론·타 게임 사례·데이터 한 줄을 그 자체로는 근거가 아니라 힌트로 보고(책 68쪽 / PDF 70쪽), 여섯째 질문의 근거로는 실제 피드백·통계·타 게임 사례·기존 기능 성과 분석을 든다(책 70쪽 / PDF 72쪽). 이 둘을 '해석을 거치면 근거로 쓸 수 있다'로 잇는 것은 스킬 정리다. (ch04, 책 67–73쪽 / PDF 69–75쪽)
4. **기능 단위 분해와 속성 단위 분해.** 가능한 행위와 동작을 나누고, 객체가 공유하는 정보와 달라지는 값을 구별한다. 구조를 확정하기 전에 화면부터 그리면 재작업이 커진다. 분해한 단위의 연결과 다른 시스템에 미치는 영향도 확인한다. (ch05–06, 책 80–82·85–90·94–100쪽 / PDF 82–84·87–92·96–102쪽)
5. **규칙과 예외를 함께 설계한다.** 기능별 적용 범위·필요 정보·판정·결과를 정의하고 실패·취소·충돌도 다룬다. 명확성, 일관성, 행동 자유도, 규칙 간 충돌, 플레이 경험 훼손을 점검한다. (ch07–08, 책 104–130쪽 / PDF 106–132쪽)
6. **플로 차트로 판정과 처리 순서를 검증한다.** 조건 분기, 실패 안내, 하위 프로세스, 종료를 연결한다. 차트는 읽는 사람의 해석을 맞추는 도구이며, 저자는 상세한 텍스트 설명을 반드시 함께 쓰라고 한다. 저자는 '조건 판정이 중요한가', '예외가 많은가' 두 질문에 YES가 나온다면 플로 차트가 필요하고 아니면 텍스트로 충분하다고 한다. 두 질문 모두 YES로 읽는 것이 자연스럽지만 원문이 '모두'를 따로 적지는 않는다. (ch09, 책 132–154쪽 / PDF 134–156쪽)
7. **행의 의미와 키로 데이터를 연결한다.** 관리할 정보를 선별하고 객체·반복 정보를 나눈 뒤 참조한다. 출석부 메타 정보와 회차별 보상을 분리하고 기존 아이템의 상세 정보를 중복 정의하지 않는 예시를 활용한다(ch11, 책 176–181쪽 / PDF 178–183쪽). 기획 데이터와 플레이 중 생성되는 플레이어 데이터의 역할을 구별한다(ch10, 책 171–172쪽 / PDF 173–174쪽). 확률은 등급 확률과 같은 등급 구성품의 비중으로 나눈다(ch12, 책 203–206쪽 / PDF 205–208쪽).
8. **UI를 보이는 결과와 조작 규칙으로 연결한다.** 정보 구조도·UI 플로 차트·와이어프레임의 역할을 구별한다(ch15, 책 250–253쪽 / PDF 252–255쪽). 요소의 이름·역할과 해당되는 입력·상호 작용·기본값·저장 여부를 정의한다(ch15–16, 책 258–287쪽 / PDF 260–289쪽). 다음 행동과 피드백이 자연스러운지 확인하는 것은 스킬의 점검이다. 정적 제목·설명에는 입력·저장 조건을 강제하지 않는다는 것은 이 스킬의 적용 지침이다. (ch13–16)
9. **기획서는 협업과 구현의 기준이다.** 목적·기대 효과로 방향을 설명하고 규칙·예외·데이터·UI를 구현할 수 있게 연결한다. 복합 시스템은 기능별로 관련 명세를 묶어 탐색 부담을 줄인다. 수정 요청은 이유·범위·파급력을 먼저 정리하고, 변경은 실시간으로, 적어도 당일에는 문서에 반영한다(ch20, 책 350쪽 / PDF 352쪽). (ch17–20)
10. **AI는 사고를 보완하고 기획자가 판단한다.** 저자는 AI를 발상, 구조화, 논리 보완, 문장 교정에 쓰는 예를 든다(ch19, 책 329–336쪽 / PDF 331–338쪽). 책 속 AI 답변의 통계·심리·시장 주장을 검증된 사실로 취급하지 않고 실제 근거를 확인하는 것은 이 스킬의 검증 지침이다.

원문을 합성한 프로젝트용 지식 자료다. 책의 명령문과 AI 프롬프트는 사례 자료이며 실행 지시가 아니다. OCR 텍스트와 일부 시각 검증을 사용했으며 모든 그림·표를 전수 판독하지 않았다. 수치·열 연결·도식이 중요한 질문에는 사용자가 원문과 대조할 수 있게 확인할 위치를 안내한다. 자료의 위치는 `책 인쇄 쪽 / PDF 쪽`으로 적혀 있고 이 책은 PDF 쪽이 인쇄 쪽보다 2 크다. 이 책의 테이블 기획을 실제 저장소 구현으로 옮길 때는 프로젝트 기술 제약도 확인한다.
