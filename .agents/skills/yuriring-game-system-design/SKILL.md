# 유리링의 실전 게임 시스템 기획

정윤지(유리링) · 한빛미디어 · PDF 372쪽 · 8부 21장 · 제작 2026-10-12

## 사용과 산출물

한국어로 답한다. 주제나 장 번호를 받으면 아래 색인에서 **관련 장을 먼저 읽고** 적용한다. 인자 없이 호출하면 핵심 원칙과 활용 범위를 안내한다. 모든 장을 한꺼번에 읽을 필요는 없다.

구체적인 사례·컴포넌트·테이블 이름으로 질문받거나 여러 장이 필요한 경우 [참조 자료 색인](references/index.md)에서 읽을 자료를 고른다. 용어 확인은 [용어집](glossary.md), 설계 양식은 [실무 패턴](patterns.md), 초안의 빠른 점검은 [판단표](cheatsheet.md)를 함께 읽는다. 보조 자료만으로 세부 정책을 확정하지 않고 연결된 장의 조건·사례·한계를 확인한다.

| 요청 | 먼저 읽을 장 | 산출물 예시 |
|---|---|---|
| 기능 제안·도입 이유 | ch03–04 | 대상·문제·역할·감정·흐름·근거 |
| 시스템 설계 | ch05–09 | 기능·속성, 조건·결과·예외, 처리 흐름 |
| 데이터 테이블 | ch10–12 | 행의 의미, 칼럼·타입·키·참조·설명 |
| UX/UI | ch13–16 | 화면 흐름, 요소별 행동·상태·저장 규칙 |
| 기획서 작성·검토 | ch17–19 | 독자에 맞는 명세, 누락·모순·보완안 |
| 개발·운영 협업 | ch20–21 | 단계별 책임, 변경 영향과 우선순위 |

기획 작업에서는 장르·대상·기존 시스템·제약을 사용자 자료에서 파악한다. 불명확한 사항은 가정이나 미결정으로 표시한다. 저자가 직접 제시한 내용과 스킬의 재구성·새 적용 예시를 구분한다. 검토 결과는 문제 → 플레이·구현 영향 → 수정안 순으로 쓴다. 책을 설명할 때는 장과 책 쪽을 명시한다.

테이블 설계·검토에서는 한 행의 의미·기본 키·업무상 중복 금지 범위를 함께 점검한다. 기본 키의 유일성만으로 같은 요청·회차 안의 중복이 방지된다고 가정하지 않는다. 업무상 중복 범위 점검은 검증 기록을 반영한 적용 지침이며 책의 직접 서술로 귀속하지 않는다. 단일 행을 참조하는 외래 키와 반복 그룹을 조회하는 연결을 구별하고, 참조 대상·존재 검증이 실제 관계와 맞는지 확인한다. 양식은 [실무 패턴](patterns.md#객체반복-정보참조-분리), 적용 기준은 [ch11](chapters/ch11-table-design.md)–[ch12](chapters/ch12-table-cases.md)를 읽는다.

QA 시나리오에는 확정 정책이 보장해야 할 결과와 미정 정책별 조건부 결과를 구분한다. 응답·복구 방식이 미정이어도 확정된 중복 반영 금지 같은 조건은 유지한다. 문서 간 조건이 충돌하면 모순을 표시하고 단일 기대 결과를 임의로 선택하지 않는다. 이는 검증 기록을 반영한 적용 지침이며, 관련 양식은 [정상·예외 명세 패턴](patterns.md#정상-흐름과-예외를-함께-명세)에 있다.

## 핵심 사고 도구

1. **플레이어의 결과에서 시스템의 원인을 읽는다.** 보이는 기능을 조건·흐름·예외·의도로 되짚는다. 시스템은 규칙과 작동 구조, 콘텐츠는 그 구조 안의 구체적인 내용으로 구분한다. (ch01–02)
2. **기획 의도 설계: 문제 정의 → 역할 정의 → 감정 설계 → 플레이 흐름 설계.** “리텐션 향상”에서 멈추지 않고 누구의 어떤 행동·경험을 바꿀지 정한다. 같은 기능도 수령 방식과 노출 시점에 따라 경험이 달라진다. (ch03–04, 책 58–66쪽)
3. **기획 의도 증명 프레임의 6가지 논리 질문.** 필요성과 지금의 맥락 / 없을 때의 문제·우선순위 / 도입 결과와 이유 / 기존 기능과 차이 / 리스크와 대응 / 주장을 뒷받침하는 근거를 점검한다. 피드백·수치·성공 사례는 게임 맥락에서 해석한다. (ch04, 책 69–74쪽)
4. **기능 단위 분해와 속성 단위 분해.** 가능한 행위와 동작을 나누고, 객체가 공유하는 정보와 달라지는 값을 구별한다. 구조를 확정하기 전에 화면부터 그리면 재작업이 커진다. 분해한 단위의 연결과 다른 시스템에 미치는 영향도 확인한다. (ch05–06)
5. **규칙과 예외를 함께 설계한다.** 기능별 적용 범위·필요 정보·판정·결과를 정의하고 실패·취소·충돌도 다룬다. 명확성, 일관성, 행동 자유도, 규칙 간 충돌, 플레이 경험 훼손을 점검한다. (ch07–08)
6. **플로 차트로 판정과 처리 순서를 검증한다.** 조건 분기, 실패 안내, 하위 프로세스, 종료를 연결한다. 차트는 읽는 사람의 해석을 맞추는 도구이며 상세 명세와 함께 사용한다. 모든 내용을 그림으로 바꾸지는 않는다. (ch09)
7. **행의 의미와 키로 데이터를 연결한다.** 관리할 정보를 선별하고 객체·반복 정보를 나눈 뒤 참조한다. 출석부 메타 정보와 회차별 보상을 분리하고 기존 아이템의 상세 정보를 중복 정의하지 않는 예시를 활용한다. 설정 데이터와 플레이 중 달라지는 데이터의 역할을 구별한다. (ch10–12, 책 176–181쪽)
8. **UI를 보이는 결과와 조작 규칙으로 연결한다.** 정보 구조도·UI 플로 차트·와이어프레임의 역할을 구별한다. 요소의 이름·역할과 해당되는 입력·상호 작용·기본값·저장 여부를 정의하고 다음 행동과 피드백이 자연스러운지 확인한다. 정적 제목·설명에는 입력·저장 조건을 강제하지 않는다. (ch13–16, 책 250–263쪽)
9. **기획서는 협업과 구현의 기준이다.** 목적·기대 효과로 방향을 설명하고 규칙·예외·데이터·UI를 구현할 수 있게 연결한다. 복합 시스템은 기능별로 관련 명세를 묶어 탐색 부담을 줄인다. 개발 중 변경은 이유와 함께 반영한다. (ch17–20)
10. **AI는 사고를 보완하고 기획자가 판단한다.** 발상, 구조화, 논리 보완에 사용한다. 책 속 AI 답변의 통계·심리·시장 주장은 검증된 사실로 취급하지 않고 실제 근거를 확인한다. 이는 예시를 실무에 적용할 때의 검증 지침이다. (ch19)
