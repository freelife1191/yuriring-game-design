| 성공한 게임과 같은 기능을 넣고 싶음 | 목적·타깃·전체 구조의 유사성을 확인한다 | 겉모습만 같아도 효과는 다름 · ch04 |
| 피드백·수치 하나만으로 도입 주장 | 문제의 범위와 원인을 해석하고 효과를 가설로 둔다 | 단일 힌트는 해석 없이는 인과 근거가 아님(스킬 정리: 해석하면 근거로 쓸 수 있음) · ch04 |
| 큰 시스템에서 시작점을 못 찾음 | 기능과 객체 속성을 나눈 뒤 연결한다 | UI는 구조의 결과 · ch05–06 |

| 분기 설명이 모호함 | 판정 순서와 분기별 결과를 도식화한다 | 처리 우선순위의 해석을 맞춤 · ch09 |
| 회차 증가마다 열이 늘어남 | 메타·반복 보상을 분리하고 키로 연결한다 | 입력 실수·중복 관리 감소 · ch11 |

| UI에서 무엇을 누를지 불명확 | 시각적 우선순위·피드백·다음 행동을 점검한다 | 기능 접근이 경험을 결정 · ch13–16 |
| 정렬·필터 화면만 존재 | 초기 상태·변경 동작·저장 여부를 정한다 | 화면만으로는 구현이 불가능 · ch15 |
| 문서를 읽느라 페이지 왕복 반복 | 기능별 규칙·예외·표·UI를 함께 묶는다 | 독자의 탐색 비용을 줄임 · ch17–19 |
