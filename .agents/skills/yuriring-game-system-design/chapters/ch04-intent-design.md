# 04. 기획 의도 설계: 문제·역할·감정·흐름을 근거로 묶는다

**참고 범위:** 책 56–76쪽 / PDF 58–78쪽. 마지막 PART 03 안내(PDF 79쪽)는 제외했다.

## 핵심 관점

원문은 이 장이 기획 의도가 규칙·예외·데이터·UI 결정으로 구체화되는 과정을 보여 준다고 소개한다(책 56쪽 / PDF 58쪽). 저자는 기획 의도가 단순한 '개발 사유서'가 아니라 설계 기준이자 모든 판단의 중심축이라고 한다(책 65–66쪽 / PDF 67–68쪽). 저자는 **문제 정의 → 역할 정의 → 감정 설계 → 플레이 흐름 설계** 순서로 의도를 구체화하고, 이후 여섯 질문으로 타당성을 검토하라고 제안한다(책 58–61, 69–73쪽 / PDF 60–63, 71–75쪽).

## 의도를 설계하는 네 단계

1. **문제 정의:** 어느 행동/콘텐츠가 왜 필요한지 적는다. 일일 퀘스트라면 접속 유도, 반복의 지루함 완화, 메인 퀘스트 밖 성장 기회의 문제가 출발점이다(책 58쪽 / PDF 60쪽).
2. **역할 정의:** 전체 루프에서 차지할 비중과 연결 대상을 정한다. 일일 퀘스트는 접속 유도뿐 아니라 성장 보조, 초보자 학습, 사용률 낮은 콘텐츠의 트리거가 될 수 있다. 무게 중심을 잡는 메인 콘텐츠는 아니지만 강화·제작·파밍으로 이어지는 리텐션 루프의 핵심 연결 고리가 될 수 있다(책 58–59쪽 / PDF 60–61쪽). 원문은 숙제 콘텐츠 사이에서 이 시스템의 위치와 비중을 시각화하면 설계 방향과 협업 커뮤니케이션이 명확해진다고 한다(책 60쪽 / PDF 62쪽). 목표·보상·해금 조건이 핵심 콘텐츠를 대체하지 않게 정한다는 점검은 이 역할 정의를 적용한 스킬 해석이다.
3. **감정 설계:** 반복이 숙제가 되지 않게 감정을 구체적인 결정으로 정한다. 원문 예는 완료 시 짧고 경쾌한 효과음과 눈에 띄는 연출, 보상 수령 시 물리적 움직임 최소화(자동·일괄 수령), 누적 보상 달성 시 "오늘도 다 해냈다!" 같은 성취 문구다(책 60쪽 / PDF 62쪽).
4. **플레이 흐름 설계:** 원문 일일 퀘스트 흐름은 접속 후 UI 열기(오늘의 목표 인지) → 목록 확인(쉬운 것부터 어려운 것까지 난이도를 섞음) → 하나씩 클리어(다른 퀘스트와 병행할 수 있게 배치, 완료 순서·콘텐츠 순환으로 리듬) → 완료 보상(즉시 지급·클릭 수령·우편 발송 중 방식이 감정에 영향) → 모두 클리어 시 누적 보상(전체 완료라는 상위 목표로 루틴화)이다. 원문은 누적 보상을 '오늘도 다 해냈다'는 자기만족을 주는 핵심 도구로 본다(책 61쪽 / PDF 63쪽).

## 의도 깊이와 설득 규칙

‘리텐션을 높인다’나 ‘매출을 올린다’는 판단 기준이 될 수 없다. 원문의 잘된 기획 의도 예시는 대상 플레이어, 원하는 체험, 설계 방향, 기대 효과를 적는다(책 62–66쪽 / PDF 64–68쪽). 이 항목들이 수치·파괴 위험·보호 장치·성공 연출의 선택을 연결한다는 설명은 스킬 해석이다.

원문의 무기 강화 사례는 같은 '실패 시 파괴' 기능도 의도에 따라 설계가 달라짐을 보인다. 확률을 극도로 낮추거나 비용을 높이는 방식은 도전 자체를 망설이게 만들 수 있고, 확률은 비교적 높고 비용은 낮되 실패 시 파괴되는 구조는 '해볼 만하다'는 인식으로 도전 횟수를 늘리고 도박적 반복을 유도한다. 그러나 파괴 기능만으로 도박성이 생기지는 않는다. 특정 단계까지는 파괴되지 않게 하고 그 이상은 '장비 보호권' 같은 장치로 리스크를 줄이거나 성공률을 높이는 **선택권**, 그리고 성공 시 시각·사운드 연출과 실패 시 다음 전략적 시도를 고민하게 하는 피드백 구조가 핵심이다(책 63–64쪽 / PDF 65–66쪽). 원문은 이 구조의 기대 효과로 플레이어가 강화 성공에 몰입하고 실패 시 재도전을 고민하면서 자연스럽게 과금하거나 재도전하는 흐름을 들고, 이를 단순한 과금 유도 기능이 아니라 플레이 동기와 감정의 흐름을 유도하는 시스템으로 본다(책 64쪽 / PDF 66쪽). 신규 플레이어 출석부 사례는 처음 접속한 지 일주일 이하이고 튜토리얼을 마쳤지만 구조·보상 체계에 아직 익숙하지 않은 플레이어를 대상으로 출석 즉시 지급, 초반 성장에 도움이 되는 보상, 날마다 바뀌는 보상 테마, 우편함이 아닌 환영 연출 전용 화면 지급으로 '환영받는 감정'을 설계한다(책 65쪽 / PDF 67쪽).

저자는 아래 여섯 질문을 한 번 답하고 끝내는 체크리스트가 아니라 기획 전체 과정에서 반복 점검하는 사고 프레임으로 제시한다. 초기 아이디어 단계에서는 '왜 필요한가', 설계 단계에서는 '어떻게 구현할 것인가', 검토 단계에서는 '이 방식이 플레이어 경험에 어떤 영향을 주는가'를 다시 본다(책 72–73쪽 / PDF 74–75쪽). 저자는 여섯 질문을 적용할 때 '어떤 불편이 실제 플레이에서 발생하는가', '그 불편이 언제, 어떤 상황에서 커지는가' 같은 문제의 맥락을 짚는 것이 핵심이고, 기능의 장점뿐 아니라 리스크와 대응 전략도 함께 제시해야 한다고 한다(책 72쪽 / PDF 74쪽). 제안의 규모와 미결정 사항에 맞춰 답변의 설명 깊이를 조정하는 것은 스킬의 적용 지침이다.

1. 왜 이 기능이 필요하며 왜 지금인가? 막연한 편의성 향상이나 신규 콘텐츠 추가만으로는 부족하고, 지금 필요한 맥락을 설명한다.
2. 없으면 어떤 문제가 생기며 왜 지금 해결해야 하는가? 당장 없어도 되는 불편인지, 지금 해결하지 않으면 치명적 리스크인지 우선순위를 구분한다.
3. 도입 뒤 어떤 행동·감정·흐름 변화가 생기고, 왜 긍정적인가?
4. 기존 시스템과 무엇이 다르고 어디와 충돌할 수 있는가? 이미 비슷한 시스템이 있는지 확인하고, 새 기능이 기존 시스템으로는 해결할 수 없는 문제를 해결한다는 점을 밝힌다(책 69쪽 / PDF 71쪽).
5. 악용·피로·균형 붕괴 같은 리스크와 대응은 무엇인가?
6. 위 주장을 뒷받침할 근거는 무엇인가? 원문은 플레이어 피드백, 게임 내 통계, 타 게임 적용 사례, 기존 기능의 성과 분석을 들며, 객관적 근거가 없으면 기획 의도는 '희망사항'이 된다고 한다(책 70쪽 / PDF 72쪽).

질문 본문: 책 69–70쪽 / PDF 71–72쪽. 장비 프리셋 적용 예시: 책 70–72쪽 / PDF 72–74쪽.

원문은 흔히 나오는 약한 설득 근거 네 가지와 보강 방법을 든다(책 67–68쪽 / PDF 69–70쪽). 플레이어 피드백은 같은 불편을 느낀 플레이어가 얼마나 되는지와 실제 이탈 영향을 분석해야 한다. 이론은 참고 수준이며 내 기획 구조와의 연결을 설명해야 한다. 타 게임 성공 사례는 우리 게임에서 같은 효과가 날 구조적 유사점을 설명해야 한다. 데이터 한 줄은 왜 그 지점에서 수치가 나쁜지와 이 기능이 어떻게 개입하는지를 함께 설명해야 한다. 이들은 근거가 아니라 힌트이며, 종합적으로 해석해야 한다.

## 원문 사례를 실무 형식으로 재구성: 장비 프리셋

**원문 사례 재구성** — 다양한 콘텐츠에 장비 세팅을 반복 교체하는 상황의 프리셋 제안이다(책 70–72쪽 / PDF 72–74쪽).

| 층위 | 적용 |
| --- | --- |
| 문제/역할 | 전환 때의 수동 교체·실수 때문에 콘텐츠 진입을 포기하는 문제를 줄여, 여러 콘텐츠를 연결한다. |
| 규칙 | 허용된 장비 세트를 저장·불러오며, 사용 가능 시점·슬롯 수·교체 조건을 정의한다. |
| 데이터 | 프리셋 슬롯, 슬롯별 장비 참조, 해금 조건, 콘텐츠별 제약 여부를 관리한다. |
| UI | 초반에는 부담을 줄이도록 해금 뒤 노출하고, 직관적 이름을 쓴다. 저장/불러오기 결과를 분명히 보여 주는 것은 스킬의 적용 지침이다. |
| 리스크 | 최적 세팅 압박 및 초보자 복잡도는 슬롯 제한, 성장 단계 해금, 안내 방식으로 완화한다. |

표의 문제·리스크·UI 노출 조건은 원문에서 왔고, 규칙·데이터 행은 스킬이 구체화한 것이다.

원문 값은 사례 값이며 기본값이 아니다. 원문 사례는 프리셋 최대 2~3개, 초반 골드·퀘스트로 슬롯 확장, 계정 레벨 20 이상 또는 특정 콘텐츠 해금 뒤 노출, '빠른 장비 교체' 같은 직관적 명칭을 제시한다(책 71쪽 / PDF 73쪽). 근거로는 공식 카페·유튜브 댓글의 불만, 실수로 장비를 분해한 사례, 타 게임 A·B의 도입 후 반응, 2주간 직접 플레이에서 하루 최소 4~5회 반복된 재정렬을 든다(책 72쪽 / PDF 74쪽).

## 레퍼런스 활용과 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **안티패턴: 성공작의 표면을 복사한다.** 장르·대상층·템포·과금·UX 맥락이 다른데 구조만 옮기면 기존 루프와 충돌하거나 피로를 늘린다(책 74–75쪽 / PDF 76–77쪽).
- **양날의 검:** 원문은 레퍼런스의 장점으로 빠른 기획·개발 속도, 커뮤니케이션 비용 절감, 검증된 흐름 차용을, 단점으로 독창성 약화, 맥락 불일치, 지루함의 재생산을 든다(책 74–75쪽 / PDF 76–77쪽).
- **활용 순서:** 그 게임에서 왜 작동했는지(장르·플레이어 층·템포·과금·UX 배경) → 우리 게임에 그대로 적용하면 맥락 차이로 어떤 문제가 생길지 → 표면 구조가 아니라 그 시스템이 주는 감정·리듬·목적을 추출해 무엇으로 변형할지 분석한다(책 75쪽 / PDF 77쪽). "A 게임도 이렇게 해서 잘 됐잖아요"라고 말하려면 반드시 우리 게임의 템포·과금 구조·UX 흐름에 맞게 어떻게 변형할지를 이어서 말해야 한다(책 75쪽 / PDF 77쪽).
- **안티패턴: UI와 보상을 이유 없이 정한다.** 자동/클릭 수령, 보상 아이콘 위치, 7일/28일 기간, 재료 선택 모두 의도에 대한 답을 가져야 한다(책 65–66쪽 / PDF 67–68쪽).

## 연습 문제

원문 연습 문제(책 76쪽 / PDF 78쪽)는 "파티 플레이 콘텐츠 이용률이 낮으니 파티 매칭을 편하게 하고 보상을 높여야 한다"는 요청을 문제 정의, 기획 의도, 설계 방향, 설득력 있는 기획을 위한 근거·사례·리스크로 단계적으로 정리하게 한다. 단순 '편의성 개선'이 아니라 경험·감정 흐름·구조 설계 목적을 중심으로 쓰라는 조건이 붙는다.

## 실무 점검

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- 문제, 시스템 역할, 목표 감정, 플레이 흐름을 서로 다른 문장으로 적었는가?
- 각 규칙·예외·테이블 필드·UI 요소가 네 단계 중 무엇을 지지하는지 설명되는가?
- 여섯 질문에 ‘편해진다’ 같은 추상 표현 없이 관찰 가능한 행동 변화로 답했는가?
- 리스크 대응이 기능 도입 목표를 무너뜨리지 않는가?
- 레퍼런스의 성공 맥락과 우리 게임의 차이를 함께 기록했는가?
