# 07장: 규칙이란 무엇인가?

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 7장, 책 104–115쪽 / PDF 106–117쪽.  
> 던전 & 드래곤 사례의 주사위는 D20(20면체 주사위)이다. 추출 텍스트에는 `D200`으로 깨져 있으나 원문 쪽 렌더(책 109쪽 / PDF 111쪽)로 확인했다.

## 핵심 관점

시스템 기획에서 규칙은 플레이어가 지켜야 하는 게임 룰만이 아니다. 플레이어 행동의 가능 범위, 플레이어가 개입하지 않아도 세계가 변화하는 방식, 시스템 요소끼리 영향을 주고받는 방식을 함께 정하는 **게임 전체의 작동 약속**이다. 기획 의도를 실제 플레이 경험으로 바꾸고 디자인과 개발을 잇는 마지막 논리 층이므로, “가능하다”라는 한 문장으로 끝내면 안 된다.

원문은 규칙을 플레이어가 떠올리기 쉬운 게임 룰(턴제의 한 턴 한 번 공격)뿐 아니라 몬스터 리스폰처럼 플레이어가 의식하지 않아도 작동하는 규칙까지 포함해 설명한다(책 106쪽 / PDF 108쪽). 전자는 선택과 기대를 만들고 후자는 세계의 일관된 질서를 만든다는 대비는 스킬 정리다.

## 저자의 절차와 규칙

### 1. 규칙을 상황에서 예외까지 분해한다

원문은 하나의 규칙을 상황·적용 범위·필요한 정보·행동·정보의 활용·판단·결과·예외 처리로 나누고, 상황에서 결과까지 논리적 단계로 나눠 설계하라고 한다(책 109–110쪽 / PDF 111–112쪽). 아래 표의 '언제/어떻게'와 '필요한 이유' 열, 그리고 이 순서로 채우면 구현·QA·플레이어의 해석 차이가 줄어든다는 설명은 스킬 정리다.

| 항목 | 언제/어떻게 정의하는가 | 필요한 이유 |
| --- | --- | --- |
| 상황·적용 범위 | 규칙이 시작되는 사건과 대상자를 지정 | 규칙의 시작점과 적용 대상을 고정한다. |
| 필요한 정보 | 판정 전에 읽을 값·상태를 열거 | 숨은 의존성이나 누락된 데이터가 드러난다. |
| 행동·정보 활용 | 플레이어 입력과 그 정보의 사용 방식을 적는다 | 입력과 내부 처리를 분리해 설명한다. |
| 판단 | 성공·실패·분기의 기준을 명시 | 결과가 임의로 보이지 않게 한다. |
| 결과 | 판정별 상태 변화, 지급, 무효, 안내를 적는다 | 다음 규칙이 참조할 변경값을 분명히 한다. |
| 예외 처리 | 정상 순서 밖의 입력·상태·타이밍을 별도 설계 | 흐름 중단, 악용, 부당한 이득을 막는다. |

원문의 던전 & 드래곤 명중 규칙은 이 틀을 그대로 채운다. 행동은 D20 굴림, 정보의 활용은 명중치 = 기본 공격 보너스 + 근력 또는 민첩 수정치 + 기타 보정치 + D20, 판단은 명중치가 대상의 방어도를 넘는지, 결과는 성공 시 피해 반영·실패 시 아무 일도 없음이다. 예외 처리는 D20이 1이면 무조건 실패, 20이면 무조건 성공이다(책 109쪽 / PDF 111쪽, 렌더 확인). 헤드샷 사례도 같은 틀이다. 헤드샷은 사격이라는 상황에서 조준 위치·무기·탄환을 읽고, 탄환 궤적과 히트박스를 비교해 판정한 뒤 성공 시 일반 피해의 2배, 실패 시 일반 피해를 적용하며, 특수 헬멧·스킬 효과·캐릭터 특성으로 헤드샷을 무효화하는 예외를 둔다(책 109–110쪽 / PDF 111–112쪽). **새 적용 예시:** 제작 버튼을 누른 사건에서 재료·보유 공간·제작 가능 상태를 읽고, 모두 충족하면 재료 차감과 결과 지급을 수행하며, 보유 공간이 없으면 제작을 시작하지 않고 이유를 안내한다. 이는 원문의 구조를 다른 기능에 적용한 예시다.

### 2. 예외를 “드문 버그”가 아니라 설계 대상으로 취급한다

저자는 버그(코드 실수), 에러(플레이어 행동으로 생긴 문제), 예외(발생 가능성을 예상하여 대비할 상황)를 구별한다. 원문은 기획 단계에서부터 예외 상황을 적극적으로 찾아 설계에 반영해야 한다고 한다(책 111쪽 / PDF 113쪽). 원문은 예외 처리의 효과를 세 가지로 든다(책 112쪽 / PDF 114쪽).

- **플레이어 경험 보호:** 인벤토리가 가득 찬 상태에서 단순히 획득되지 않게 하면 플레이어는 버그로 생각한다. 이유와 다음 행동을 안내한다.
- **시스템 안정성 확보:** 존재하지 않는 아이템 ID로 구매 요청이 오면 ID 존재를 미리 검사하고 지급하지 않는다.
- **악용과 부정행위 방지:** 구매 시도 때 소지금이 충분한지 검사하고, 부족하면 진행하지 않고 알린다.

| 예외 패턴 | 처리 원칙 | 원문 사례 |
| --- | --- | --- |
| 결과값 없음 | 행동을 무효화하고 실패 이유를 안내 | 오프라인 친구에게 귓속말, 존재하지 않는 길드 검색 |
| 사전 조건 미충족 | 조건을 먼저 검증하고 진행하지 않음 | 재료 부족 제작, 사용 중 닉네임, 착용 불가 장비 |
| 상태 불일치·타이밍 | 실행 직전에 상태를 재검증하고 안내 | 스킬 대상이 이미 사망, 경매 상품이 이미 거래 완료 |
| 비정상 접근 | 행동을 무효화하고 보안 로그를 남김 | 이동 속도 조작, 아이템 고유 ID 충돌 |
| 자동 처리 대상 없음 | 스킵 또는 안전 중단 | 대상 없는 랜덤 실드, 참여자보다 많은 랭킹 보상 구간 |

비정상 접근은 행동을 무효화하고 보안 로그를 남기는 것이 좋다. 플레이어에게는 부정행위 가능성을 암시하지 않고 단순히 실패만 안내하는 것이 일반적이며, 그 이유는 부정행위자가 패턴을 바꿔 우회하지 못하도록 단서를 주지 않기 위해서다. 원문 예시는 이동 속도 조작을 서버에서 검증해 위치를 롤백하고 로그를 남긴 뒤 "이동에 실패했습니다."만 보여 주는 처리, 그리고 아이템 복제 시도를 인벤토리 변경 시점의 서버 검증에서 동일 아이템 고유 ID 충돌로 감지해 조치·로그 기록을 하고 플레이어에게는 "오류가 발생했습니다."만 보여 주는 처리다(책 114쪽 / PDF 116쪽). 반면 사전 조건 미충족은 행동을 무효화하고 부족한 조건을 명확히 알려 플레이어가 다음 행동을 알 수 있게 한다(책 113쪽 / PDF 115쪽).

저자는 예외 처리를 플레이어의 실수, 시스템의 비정상 상태, 예측하지 못한 상황을 미리 가정하고 대비하는 과정이자 시스템 기획의 필수적인 책임 영역으로 본다. 예외는 생각지 못한 타이밍, 의외의 조합, 시스템 간 상호 작용에서 생기기 쉬우므로 '일어나지 않을 일'로 넘기지 말고 '만약 이런 상황이 발생하면 어떻게 할 것인가'를 꾸준히 자문하며 설계하라고 한다(책 115쪽 / PDF 117쪽).

## 주요 개념

- **규칙 설계:** 기획 의도대로 시스템 구조가 작동하도록 구체화하는 과정이다.
- **적용 범위:** 한 규칙이 적용되는 주체와 대상의 경계다.
- **판단:** 수집한 정보로 성공·실패·분기를 가르는 기준이다.
- **예외 처리:** 실수, 비정상 상태, 예상 밖 조합에서도 흐름을 안전하게 이어 가는 설계다.
- **보안 로그:** 원문은 비정상 행동을 무효화하면서 보안 로그를 남기라고 권한다(책 114쪽 / PDF 116쪽). 대응·추적에 쓰는 기록이라는 설명은 스킬 해석이다.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **결과만 쓰기:** “구매된다”, “강화한다”만 적으면 필요한 값, 검증 순서, 실패 이후 상태가 사라진다.
- **무반응 실패:** 대상·검색 결과·조건이 없을 때 아무 일도 하지 않으면 플레이어는 버그로 오해한다.
- **클라이언트 표시 상태를 확정값으로 믿기:** 타이밍 경쟁에서는 실제 상태를 다시 검증하지 않으면 이미 소진된 대상에 실행될 수 있다.
- **예외를 기술팀의 사후 일로 넘기기:** 기획에서 실패 이유와 상태 보존·롤백·스킵을 정하지 않으면 경험과 악용 방지가 비어 있다.
- **자동 로직의 빈 대상 방치:** 선택할 대상이 없을 때 반복·오류·과부하로 이어질 수 있다.

## 작은 재구성 산출물

원문의 구매·제작류 규칙 구성 방식을 압축하면 다음과 같다. 이는 책의 항목 구조를 재구성한 것이며, 값과 문구는 프로젝트 규칙으로 확정한 것이 아니다.

```text
[입력: 행동 시도]
  → [판단: 대상/재료/상태가 존재하는가?]
    ├─ 아니오 → [무효화] → [이유 안내] → 종료
    └─ 예
       → [판단: 실행 순간에도 조건이 유효한가?]
         ├─ 아니오 → [무효화·필요 시 복구] → [현재 상태 안내] → 종료
         └─ 예 → [결과 반영] → [성공 결과 안내] → 종료
```
