# 07장: 규칙이란 무엇인가?

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 7장, 책 p.104–115 (PDF p.106–117).  
> 아래의 `D20/D200` 표기는 원문 OCR에서 `D20`, `D200`으로 혼재·훼손되어 있어 주사위 면수의 정확한 표기는 원문 이미지 확인 없이는 확정하지 않는다.

## 핵심 관점

시스템 기획에서 규칙은 플레이어가 지켜야 하는 게임 룰만이 아니다. 플레이어 행동의 가능 범위, 플레이어가 개입하지 않아도 세계가 변화하는 방식, 시스템 요소끼리 영향을 주고받는 방식을 함께 정하는 **게임 전체의 작동 약속**이다. 기획 의도를 실제 플레이 경험으로 바꾸고 디자인과 개발을 잇는 마지막 논리 층이므로, “가능하다”라는 한 문장으로 끝내면 안 된다.

규칙은 플레이어가 알아차리는 것(한 턴에 한 번 공격)과 알아차리지 못해도 적용되는 것(몬스터 사망 뒤 일정 시간 후 리스폰)을 모두 포함한다. 전자는 선택과 기대를 만들고, 후자는 세계의 일관된 질서를 만든다.

## 저자의 절차와 규칙

### 1. 규칙을 상황에서 예외까지 분해한다

행동 규칙을 설계할 때는 다음 항목을 순서대로 채운다. 이렇게 해야 같은 문장을 읽고도 구현·QA·플레이어가 서로 다른 동작을 상상하는 일을 줄일 수 있다.

| 항목 | 언제/어떻게 정의하는가 | 필요한 이유 |
| --- | --- | --- |
| 상황·적용 범위 | 규칙이 시작되는 사건과 대상자를 지정 | 규칙의 시작점과 적용 대상을 고정한다. |
| 필요한 정보 | 판정 전에 읽을 값·상태를 열거 | 숨은 의존성이나 누락된 데이터가 드러난다. |
| 행동·정보 활용 | 플레이어 입력과 그 정보의 사용 방식을 적는다 | 입력과 내부 처리를 분리해 설명한다. |
| 판단 | 성공·실패·분기의 기준을 명시 | 결과가 임의로 보이지 않게 한다. |
| 결과 | 판정별 상태 변화, 지급, 무효, 안내를 적는다 | 다음 규칙이 참조할 변경값을 분명히 한다. |
| 예외 처리 | 정상 순서 밖의 입력·상태·타이밍을 별도 설계 | 흐름 중단, 악용, 부당한 이득을 막는다. |

원문의 명중/헤드샷 사례는 이 틀의 용도를 보여 준다. 예컨대 헤드샷은 사격이라는 상황에서 조준 위치·무기·탄환을 읽고, 탄환 궤적과 히트박스를 비교해 판정한 뒤 일반 피해 또는 추가 피해를 적용하며, 특수 헬멧·스킬·특성에는 별도 예외를 둔다. **새 적용 예시:** 제작 버튼을 누른 사건에서 재료·보유 공간·제작 가능 상태를 읽고, 모두 충족하면 재료 차감과 결과 지급을 수행하며, 보유 공간이 없으면 제작을 시작하지 않고 이유를 안내한다. 이는 원문의 구조를 다른 기능에 적용한 예시다.

### 2. 예외를 “드문 버그”가 아니라 설계 대상로 취급한다

저자는 버그(코드 실수), 에러(플레이어 행동으로 생긴 문제), 예외(발생 가능성을 예상하여 대비할 상황)를 구별한다. 예외는 정상 흐름을 뒤늦게 고치는 일이 아니라 기획 단계에서 먼저 찾는 안정성 설계다.

| 예외 패턴 | 처리 원칙 | 원문 사례 |
| --- | --- | --- |
| 결과값 없음 | 행동을 무효화하고 실패 이유를 안내 | 오프라인 친구에게 귓속말, 존재하지 않는 길드 검색 |
| 사전 조건 미충족 | 조건을 먼저 검증하고 진행하지 않음 | 재료 부족 제작, 사용 중 닉네임, 착용 불가 장비 |
| 상태 불일치·타이밍 | 실행 직전에 상태를 재검증하고 안내 | 스킬 대상이 이미 사망, 경매 상품이 이미 거래 완료 |
| 비정상 접근 | 행동을 무효화하고 보안 로그를 남김 | 이동 속도 조작, 아이템 고유 ID 충돌 |
| 자동 처리 대상 없음 | 스킵 또는 안전 중단 | 대상 없는 랜덤 실드, 참여자보다 많은 랭킹 보상 구간 |

비정상 접근에는 부정행위 가능성을 자세히 드러내지 않고 일반 실패만 보이는 방식도 제시한다. 그 이유는 우회 시도를 위한 단서를 줄이지 않기 위해서다. 반면 일반적인 조건 미충족은 플레이어가 다음 행동을 알 수 있도록 부족한 이유를 명확히 알려야 한다.

## 주요 개념

- **규칙 설계:** 기획 의도대로 시스템 구조가 작동하도록 구체화하는 과정이다.
- **적용 범위:** 한 규칙이 적용되는 주체와 대상의 경계다.
- **판단:** 수집한 정보로 성공·실패·분기를 가르는 기준이다.
- **예외 처리:** 실수, 비정상 상태, 예상 밖 조합에서도 흐름을 안전하게 이어 가는 설계다.
- **보안 로그:** 비정상 요청을 기록해 대응·추적할 수 있게 하는 기록이다.

## 안티패턴

- **결과만 쓰기:** “구매된다”, “강화한다”만 적으면 필요한 값, 검증 순서, 실패 이후 상태가 사라진다.
- **무반응 실패:** 대상·검색 결과·조건이 없을 때 아무 일도 하지 않으면 플레이어는 버그로 오해한다.
- **클라이언트 표시 상태를 확정값으로 믿기:** 타이밍 경쟁에서는 실제 상태를 다시 검증하지 않으면 이미 소진된 대상에 실행될 수 있다.
- **예외를 기술팀의 사후 일로 넘기기:** 기획에서 실패 이유와 상태 보존·롤백·스킵을 정하지 않으면 경험과 악용 방지가 비어 있다.
- **자동 로직의 빈 대상 방치:** 선택할 대상이 없을 때 반복·오류·과부하로 이어질 수 있다.

## 작은 재구성 산출물

원문의 구매·제작류 규칙 구성 방식을 압축하면 다음과 같다. 이는 책의 항목 구조를 재구성한 것이며, 값과 문구는 프로젝트 규칙으로 확정한 것이 아니다.

```text
[입력: 행동 시도]
  → [판단: 대상/재료/상태가 존재하는가?]
    ├─ 아니오 → [무효화] → [이유 안내] → 종료
    └─ 예
       → [판단: 실행 순간에도 조건이 유효한가?]
         ├─ 아니오 → [무효화·필요 시 복구] → [현재 상태 안내] → 종료
         └─ 예 → [결과 반영] → [성공 결과 안내] → 종료
```

## 실무 점검 항목

- [ ] 이 규칙이 행동 범위·세계 변화·시스템 간 영향 중 무엇을 정의하는지 적었는가?
- [ ] 상황, 대상, 필요한 정보, 행동, 정보 활용, 판단, 결과, 예외가 모두 있는가?
- [ ] 실패할 때 변경하지 말아야 할 상태와 플레이어에게 알려 줄 이유를 정했는가?
- [ ] 동시 요청·이미 변경된 대상·대상 없음처럼 실행 순간에 달라지는 상태를 재검증하는가?
- [ ] 비정상 요청은 무효화·기록·표시 메시지의 정책이 분리되어 있는가?
- [ ] 자동 처리에 대상이 없을 때 종료 또는 스킵 경로가 있는가?
