# 05. 시스템 구조 분할: 화면보다 행동과 속성부터 나눈다

**참고 범위:** 책 78–91쪽 / PDF 80–93쪽.

## 핵심 관점

큰 시스템은 UI부터 그리면 안 된다. UI는 기능과 규칙의 결과이므로, 먼저 플레이어/시스템의 **행위**, 그 행위가 요구하는 **조건·데이터·결과·예외**를 기능 단위로 나눈다. 이어 객체의 공통 특성을 속성 단위로 추출해, 콘텐츠가 값만 바꾸어 재사용할 수 있는 생성 공식을 만든다(책 80–84, 85–91쪽 / PDF 82–86, 87–93쪽).

## 기능 단위 분해 절차

원문은 요리 레시피를 적듯이 기능을 분해하라며 1단계 눈에 보이는 기능부터 적기, 2단계 자동으로 처리하는 기능 적기, 3단계 작동에 필요한 정보(재료) 생각하기, 4단계 예외·실패 상황 적기의 저자 절차를 제시하고, 우편 시스템을 주요 기능과 세부 기능으로 분해한다(책 81–82쪽 / PDF 83–84쪽). 아래 1–4단계는 이 저자 절차이고, 5단계만 스킬 정리다. 원문은 길드 시스템도 생성·가입/탈퇴·정보·등급 권한·채팅·공지·경험치·버프·미션·기부·상점 등 주요 기능과 세부 기능의 표로 분해한 뒤 각 기능을 하나씩 기획하라고 한다(책 83–84쪽 / PDF 85–86쪽).

1. **눈에 보이는 입력을 열거한다.** 버튼·메뉴·상호작용을 적는다. 우편이라면 보내기, 읽기, 첨부 수령, 삭제다.
2. **자동 처리도 동등한 기능으로 적는다.** 시스템 발송, 기간 만료 삭제처럼 플레이어가 누르지 않는 트리거도 적는다. 이를 빼면 실제 흐름이 누락된다는 설명은 스킬 해석이다.
3. **각 기능의 재료를 붙인다.** 발신자·수신자·내용·첨부·발송 시간, 수령 시 인벤토리 공간처럼 작동에 필요한 정보를 명시한다.
4. **실패·예외를 별도 기능으로 설계한다.** 인벤토리/우편함 한도, 삭제된 발신자, 만료 우편 클릭, 삭제 불가 시스템 우편 같은 예외를 적고 방지 방법을 함께 정한다(책 81–82쪽 / PDF 83–84쪽). 예외마다 무엇을 보일지까지 정하라는 것은 스킬의 적용 지침이다.
5. **주요 기능과 세부 기능의 호출 관계를 확인한 뒤 UI를 얹는다.** 이렇게 하면 화면 동선도 규칙 흐름을 따라 나온다.

## 속성 단위 분해 절차

속성 분해는 “무슨 행동을 하는가” 대신 “객체가 어떤 특성을 갖는가”를 본다. 직업·아이템·스킬·몬스터 같은 객체에서 서로 다른 외형을 걷어내고, 공통 속성과 가변 값을 추출한다(책 85–87쪽 / PDF 87–89쪽).

- 화염구와 칼날폭풍은 표현은 달라도 ‘대미지 발생’ 속성을 공유한다. 대상 수, 범위, 기준 능력치, 배율을 열로 나누면 콘텐츠는 행으로 추가할 수 있다(책 86쪽 / PDF 88쪽).
- **고정 기획 데이터와 플레이 상태의 의미·책임을 구분한다.** 원문은 기획 데이터는 기획자가, 플레이 중 변하는 상태 값은 서버 프로그래머가 다루는 영역으로 나누고, 레벨별 기본 체력(예: 전사 100/110)과 장비로 달라진 현재 체력(예: 115)을 구분하는 예를 든다. 기획자는 작동 규칙을 설계하고 서버 프로그래머가 DB 저장·불러오기를 구현한다(책 87–88쪽 / PDF 89–90쪽). 실제 적용에서 아키텍처에 맞춰 구현 책임을 정하고 기획이 상태의 의미·변경 조건·보존·복구 요구를 명세한다는 것은 스킬 적용 지침이다.
- 속성에는 반드시 작동 규칙이 붙는다. 지속 대미지의 지속·종료 조건, 회복 상한, 동일 버프 중첩 시 처리처럼 값을 해석하는 법이 없으면 테이블은 데이터 나열에 머문다. 원문 예는 속도·공격력 증가에서 동일한 효과가 중복되면 가장 높은 수치 하나만 적용하는 규칙이다(책 87–89쪽 / PDF 89–91쪽). 원문은 스킬을 이런 속성의 조합으로 보며, 예시 표에서 대부분의 스킬은 속성 하나이고 '전투 재개'만 쿨타임 리셋과 속도 증가를 함께 가진다(책 88쪽 / PDF 90쪽, 렌더 확인). 이 값은 사례이며 모든 게임의 중첩 규칙이 아니다.
- 원문은 속성 분해를 함수로 설명한다. 'X를 Y번 사냥하기'에서 시스템 기획자는 함수가 어떻게 작동하고 X·Y에 어떤 타입을 넣을 수 있는지 설계하고, 콘텐츠 기획자는 재미있는 값을 구상해 넣는다. 타입을 제한하지 않으면 "'10'을 '늑대'번 사냥하기" 같은 퀘스트가 생긴다(책 90쪽 / PDF 92쪽).

## 원문 사례를 실무 형식으로 재구성: 퀘스트 생성 공식

**원문 사례 재구성** — 사냥·수집·대화 퀘스트를 내용별 기능이 아니라 공통 속성으로 분해한다(책 89–90쪽 / PDF 91–92쪽).

| 층위 | 설계 내용 |
| --- | --- |
| 의도 | 콘텐츠 담당자가 다양한 목표를 만들되, 플레이어는 조건과 보상을 일관되게 이해한다. |
| 데이터 | 제목, 조건 종류, 대상, 횟수, 보상, 보상 수량을 분리한다. 조건 종류에 맞는 대상만 넣을 수 있게 한다. |
| 규칙 | 사냥은 인정할 처치 기준과 시작 전 처치 인정 여부, 수집은 획득·버림·완료 시 소모, 대화는 대사 재생 완료 조건을 각각 정의한다. 원문 사례 값은 사냥=대상에게 마지막 타격을 입힌 경우만 카운트·퀘스트 시작 전 처치는 불인정, 수집=어떤 방식으로든 획득할 때마다 +1·가지고 있다가 버리면 −1·완료 시 퀘스트 아이템 삭제, 대화=출력 대사를 모두 재생 완료하면 +1·재생 도중 나가면 불인정이다(책 89–90쪽 / PDF 91–92쪽). |
| UI | 조건 종류와 현재 진행도, 완료/보상 수령 상태를 보여 준다. 수집품 소모처럼 결과가 달라지는 행동은 수령 전 인지시킨다. |
| 예외 | 잘못된 타입의 데이터 입력, 파티 기여, 목표 아이템의 감소, 진행 중 이탈을 조건 종류별로 점검한다. |

표의 의도·UI·예외 행과 파티 기여 항목은 스킬이 덧붙인 점검이며, 원문 값은 데이터·규칙 행의 세 퀘스트 예다.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **UI 선행:** 원문은 기능이 정해지기 전에 UI를 먼저 그리면 기능이 확정된 뒤 UI를 뜯어고치거나 다시 짜야 하는 경우가 많다고 한다(책 80쪽 / PDF 82쪽). 가입 방식·재가입·길드장 탈퇴·권한 규칙이 바뀌는 경우를 예로 드는 것은 스킬 예시다.
- **명사 목록을 분해로 착각:** ‘길드, 길드전, 길드 상점’만 쓰지 말고 생성 조건, 승인 대기열, 권한별 조작, 자원 보존 같은 동작 단위까지 내려간다.
- **속성과 현재 상태를 혼동:** 스킬 적용 지침으로, 기준값의 작동 규칙과 개인 상태의 보존 요구를 구별한다. 계산·중첩·종료 조건은 기획에서 설명한다. 원문은 저장 구현을 서버 프로그래머의 영역으로 보며(책 87–88쪽 / PDF 89–90쪽), 프로젝트 역할 분담에 맞춰 협의한다는 것은 스킬 적용 지침이다.
- **속성값에 규칙이 없음:** “공격력 증가 10%”만으로는 지속 시간, 중첩, 상한, 해제 조건을 알 수 없다.

## 실무 점검

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- 화면의 모든 버튼에 대응하는 규칙과, 화면에 없는 자동 기능을 모두 찾았는가?
- 각 기능에 입력/트리거, 필요 데이터, 성공 결과, 실패 결과, 예외 UI가 있는가?
- 서로 다른 콘텐츠 설명에서 공통 속성과 변형 속성을 추출했는가?
- 테이블 열이 데이터의 의미·허용 타입·참조 대상·적용 규칙을 드러내는가?
- 고정 기획 데이터와 플레이 중 상태를 구분했는가?
- 신규 콘텐츠가 행 추가인지, 새 규칙/새 속성/새 모듈이 필요한지 판단했는가?
