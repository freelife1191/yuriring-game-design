# 21장: 시스템 기획자 레벨 업

> **원문 범위:** PDF 358~366쪽 / 책 356~364쪽. 원문은 기획자를 구조·관계·흐름을 설계하는 사람으로 정의하고, 아래 역량을 실무 훈련 기준으로 제시한다. 원신·랜덤 상점·파견 사례는 특정 게임의 구현을 그대로 복제하라는 처방이 아니라 분석 관점을 보이는 사례다.

## 핵심 관점

좋은 아이디어는 시작일 뿐이다. 시스템 기획 역량은 아이디어를 조건·입력·처리·출력의 작동 구조로 바꾸고, 기존 루프·경제·UI·운영에 미칠 영향을 예측하며, 다른 직군이 한 뜻으로 구현하도록 명세하는 능력이다(PDF 360~366쪽). 기획자는 “왜 필요한가, 플레이어는 왜 하는가, 추가하면 기존 흐름은 어떻게 바뀌는가”를 반복해 의심하고 답으로 남긴다(PDF 360쪽).

## 저자 절차와 판단 기준

### 1. 모든 기능을 조건 → 입력 → 처리 → 출력으로 설명한다

원문의 우편 보상 수령 사례는 미수령 메일이라는 조건, 버튼 클릭이라는 입력, 수령 여부·유효기간·인벤토리·최대 보유량 검사와 지급이라는 처리, 연출과 목록 제거라는 출력을 분리한다(PDF 361쪽). 이 틀은 회의의 구두 설명, 플로, 개발 명세, QA 케이스에 공통으로 쓴다. 한 문장으로 “보상을 받으면 지급”이라고 끝내면 트리거·실패·상태 변경이 사라진다. 기능을 쓰기 전에 각 칸이 비어 있지 않은지 확인한다.

### 2. 레퍼런스를 표면 기능이 아니라 역할로 분해한다

원신의 레진을 예로 들어, 저자는 사용 경로, UX(실시간 충전·저장/보충), 소모 시점, 최대치, 반복 콘텐츠와 성장 재화에 대한 역할, 플레이어의 관리 전략을 나누어 관찰한다(PDF 362~363쪽). 분석 순서는 ‘무엇이 있는가’에서 멈추지 않고 ‘왜 이 순간에 소비시키는가, 어떤 루프·운영 리듬을 통제하는가, 어떤 보완 수단이 있는가’까지 간다. 관찰 결과는 복제품이 아니라, 새 프로젝트의 제약과 타깃에 맞춰 재조합할 **패턴 라이브러리**로 쌓는다.

### 3. 새 기능 전 영향도를 시뮬레이션한다

장비 조각 성장 기능을 추가하기 전, 원문은 기존 성장 루프의 피로와 역할 충돌, 공유/전용 재화가 경제에 주는 영향, 기존 강화 UI·인벤토리와의 충돌, 루프 과포화와 신규 진입 장벽을 검토한다(PDF 363~364쪽). 실무에서는 (1) 영향받는 콘텐츠·재화·상태·화면·로그를 목록화하고, (2) 각 항목의 중복·대체·경쟁 관계를 적고, (3) 하루 루틴과 신규/기존 이용자 시나리오를 따라가며, (4) 제거·통합·단계 공개·보완 UX 중 대안을 비교한다. 목표는 기능 하나를 추가하는 것이 아니라 기존 경험을 지키며 구조를 확장하는 것이다.

### 4. 행동 뒤의 시간·기대·부담을 관찰한다

파견 미션은 보상 지급 기능처럼 보여도, 원문 사례에서는 접속 직후 수령과 재파견, 짧은 미션의 남은 시간이 추가 행동을 유도하는 일일 루틴 장치다(PDF 364~365쪽). 기획자는 직접 플레이하면서 “왜 이 순간에 눌렀는가, 무엇을 기대했는가, 멈추고 싶은데 무엇이 남았는가”를 기록한다. 이는 플레이 시간을 무조건 늘리라는 뜻이 아니라, 의도한 경험과 실제 부담·혼란이 맞는지 추론하기 위한 관찰법이다.

### 5. 모호한 자연어를 테스트 가능한 문장으로 바꾼다

랜덤 상점 사례에서 ‘랜덤 품목 등장’은 전 플레이어 공통인지 개인별인지, 슬롯 수도 랜덤인지가 빠져 개발과 QA를 다른 구현으로 이끈다(PDF 365~366쪽). 명세에는 주체, 범위, 시점, 고정/변동 값, 정렬·동점, 실패·예외를 적는다. 예: “매일 04:00 서버 기준으로 **플레이어별** 목록의 **상품 ID만** 갱신하며 슬롯 수 6개는 고정”처럼 검증 가능한 문장으로 쓴다. 이는 원문 사례를 바탕으로 한 새 문장 예시다.

### 6. 이상안보다 가능한 핵심을 우선한다

2주짜리 이벤트라면 신규 대형 시스템보다 기존 UI·테이블 재사용, 필수 기능 우선, 보조 기능의 다음 패치 이관을 검토한다(PDF 366쪽). 버튼 하나도 텍스트 표시인지 서버 조건·상태 저장·연출을 포함하는지에 따라 비용이 다르다. 구현 이력과 지연 원인을 축적하고 클라이언트·서버의 기초 흐름을 이해해 추정 감각을 교정한다.

## 주요 개념

- **논리적 구조화:** 조건·입력·처리·출력으로 설명 가능한 설계 언어.
- **패턴 라이브러리:** 레퍼런스의 목적·제약·UX·운영 역할을 분해해 축적한 재사용 가능한 관찰 기록.
- **영향도:** 기능 하나가 플레이 루프, 재화, 밸런스, UI, 유지보수, 신규 진입에 주는 연쇄 변화.
- **심리 추론:** 플레이어의 시간 감각, 보상 기대, 선택 부담, 루틴 종결을 행동 관찰로 해석하는 일.
- **구현 가능성:** 일정·리소스·기존 자산·상태 저장·서버 조건까지 고려한 범위 판단.

## 안티패턴과 대응

- **아이디어를 설계로 착각:** 동작 흐름·실현 가능성·연동 영향이 없으면 제안이다. 구조와 예외로 내린다.
- **레퍼런스 외형 복사:** UI나 수치가 아니라 대상 게임에서의 역할·제약·보완책을 분석한다.
- **고립 기능 설계:** 재화·루프·화면·신규 유저 경로를 영향도 표로 먼저 점검한다.
- **모호한 형용사:** ‘랜덤’, ‘적절히’, ‘필요 시’ 대신 조건·주체·범위·상태로 쓴다.
- **일정을 희망으로 추정:** 핵심과 옵션을 나누고 실제 구현 이력으로 비용 가정을 갱신한다.

## 사례 재구성: 신규 ‘장비 조각’ 기능의 사전 리뷰

조건·입력·처리·출력으로 보면, 조건은 조각 보유와 대상 장비의 해금, 입력은 강화 선택, 처리는 재화·조각 차감과 상한 검사, 출력은 단계 상승·스탯 반영·로그다. 다음으로 기존 유물 파밍·스킬 강화와 하루 자원 경쟁, 골드 공유 시 경제 압박, 전용 재화 도입 시 복잡도, 장비 화면에 둘 위치, 신규 유저의 진입 시점을 검토한다. 한 레퍼런스의 ‘파밍 재화’ 화면을 그대로 쓰지 않고, 해당 게임의 일일 루프와 현재 UI에 맞는 접근을 고른다. 출시 일정이 짧다면 1차에는 기존 강화 화면과 재화를 활용하고, 전용 조각·세트 보너스는 후속으로 분리한다. 이 과정에서 어떤 선택이 플레이어에게 새 판단을 주는지와 어떤 선택이 피로만 늘리는지를 플레이 테스트로 확인한다.

## 점검 항목

- [ ] 모든 핵심 기능이 조건·입력·처리·출력과 실패/예외를 갖는가?
- [ ] 레퍼런스 분석에 사용 경로, UX, 규칙, 루프·운영 역할, 보완 수단이 있는가?
- [ ] 영향도 검토에 루프·재화·UI·밸런스·신규 진입·유지보수가 포함되는가?
- [ ] 플레이어 행동의 시간·기대·부담을 실제 관찰이나 테스트로 확인하는가?
- [ ] 명세에서 주체, 범위, 시점, 고정/가변값, 오류 결과를 테스트할 수 있는가?
- [ ] 일정 안의 핵심, 옵션, 후속 범위와 재사용 가능 자산이 구분되는가?
