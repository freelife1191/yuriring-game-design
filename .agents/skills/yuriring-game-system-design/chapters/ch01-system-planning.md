# 01. 시스템 기획: 콘텐츠가 작동할 법칙을 설계한다

**참고 범위:** 책 16–33쪽 / PDF 18–35쪽. 추출 텍스트 안의 다른 장 표지·안내는 본문 근거에서 제외했다.

## 핵심 관점

시스템 기획은 화면이나 아이템 하나를 만드는 일이 아니라, 플레이어 행동이 어떤 **조건·판정·상태 변화·결과**를 거쳐 일관되게 작동할지를 설계하는 일이다. 저자는 콘텐츠를 놀이의 재료, 시스템을 그 재료가 의미를 갖도록 하는 법칙으로 구분한다. 따라서 퀘스트의 문장 하나도 대상 식별, 행동 인정 기준, 보상 지정과 지급 과정, 예외까지 분해해야 한다(책 18–19쪽 / PDF 20–21쪽). 시스템 기획의 범위는 국가·회사·팀의 역할과 구조에 따라 다르다. 해외 게임 회사에서는 보통 동기·리소스 수집·소비·반복 행동으로 이어지는 게임 순환 구조(플레이 루프)를 설계하는 사람을 가리키고, 국내에서는 전투·코어 플레이를 다루는 인 게임 기획과 성장·경제·과금을 다루는 아웃 게임(메타 시스템) 기획으로 나누어 부르기도 한다(책 18쪽 / PDF 20쪽). 사용자가 말하는 '시스템 기획'의 범위가 불분명하면 어느 쪽을 뜻하는지 확인한다.

시스템·콘텐츠·서비스는 분업 이름보다 서로의 제약과 가능성을 이해하는 것이 중요하다. 시스템은 규칙과 데이터 기반을 만들고, 콘텐츠는 그 위에 아이템·NPC·보상 같은 구체 재료를 채우며, 서비스는 제공·판매·운영 방식을 설계한다. 서비스의 ‘하루 1회 상품’도 구매 횟수 저장과 갱신 규칙이 없으면 성립하지 않는다(책 20–23쪽 / PDF 22–25쪽).

## 시스템 기획이 중요한 이유(1.4)

원문은 길드장 승계·출석 보상 사례 외에도 시스템 기획의 역할을 다음처럼 설명한다.

- **플레이어 경험 설계:** 플레이어가 어떤 상황에서 시스템을 처음 접하는가, 어떤 순서로 주요 기능을 익히고 활용하는가, 다음 목표를 어떻게 인식하는가, 반복 플레이가 어떤 흐름인가(책 26쪽 / PDF 28쪽).
- **콘텐츠 창의성의 기반:** 아이템 시스템이 고정 능력치만 지원하면 수치만 바뀐 아이템이 반복된다. 조건부 효과(예: 체력 30% 이하일 때 방어력 증가), 사용 시 발동, 스택 누적, 확률 발동을 지원하면 전략적 선택과 긴장감을 주는 설계가 가능해진다(책 28쪽 / PDF 30쪽).
- **확장성과 수명:** 보상 시스템이 유연하면 시즌 패스·출석·이벤트·업적 보상을 별도 기능 개발 없이 테이블만으로 추가할 수 있다. 하드코딩이면 보상마다 새 로직 개발이 반복된다. 스킬 구조가 잘 분리되어 있으면 신규 캐릭터 추가·능력치 조정이 다른 기능에 영향을 주지 않는다(책 28–29쪽 / PDF 30–31쪽).

## 설계 절차: 행동에서 구현 계약까지

아래 다섯 단계는 원문 1.5의 범위별 질문(기획 의도, 핵심 규칙, 보조 규칙·예외, 테이블, 인터페이스, 개발 전달 문서)을 스킬이 작업 순서로 재배열한 정리다(책 30–33쪽 / PDF 32–35쪽). 각 단계의 질문과 사례는 원문에 있다.

1. **의도와 역할을 먼저 적는다.** 해결하려는 문제, 유도할 플레이 흐름, 다른 시스템에서 맡을 역할을 한 문장으로 정한다. 재접속은 단순 편의가 아니라 신뢰·악용 방지·게임 템포에 영향을 주는 기능이므로, 보존할 정보와 복귀 가능 시점부터 정한다(책 30쪽 / PDF 32쪽).
2. **플레이어 행동을 판정 가능한 규칙으로 쪼갠다.** `시도 조건 → 입력/판정 → 성공·실패·유지 결과 → 상태/보상 반영` 순서로 쓴다. 강화라면 최소 조건, 조건 미충족 시 처리, 성공 판정 방식, 성공·실패 결과를 각각 분리한다(책 21–22쪽 / PDF 23–24쪽). 원문은 가챠도 확률표만이 아니라 시도 조건, 중복 캐릭터 처리, 천장, 보너스 룰(예: 10회 뽑기 시 1회 보너스)까지 설계 범위로 든다(책 31쪽 / PDF 33쪽). 원문 Tip은 운이 나쁜 플레이어가 아무리 뽑아도 원하는 것을 얻지 못할 수 있는 매우 부정적인 경험을 해결하려고 대부분의 게임이 천장을 도입한다고 하며, 천장을 뽑기 횟수 N번 달성 시 특정 등급·캐릭터·아이템이 반드시 등장하는 보증 장치로 설명한다(책 31쪽 / PDF 33쪽).
3. **예외와 무결성을 본 흐름에 포함한다.** 중복 입력, 빠른 클릭, 앱 종료·연결 끊김에도 중복 지급·누락 없이 논리적 일관성이 남는지 정한다(책 31–32쪽 / PDF 33–34쪽). 예외를 뒤에 붙이는 메모로 취급하지 않는다.
4. **데이터와 UI로 번역한다.** 조정·추가가 필요한 수치와 조건은 테이블 항목·참조 관계로, 플레이어 결정에는 활성 조건·입력 순서·취소·확인 메시지로 표현한다. 원문 예시는 장비 ID·강화 단계·옵션 부여 조건·적용 대상을 분리해 테이블로 관리하는 것과(책 32쪽 / PDF 34쪽), 캐릭터 삭제처럼 치명적인 행동에 2단계 확인이나 일정 시간 후 삭제를 두는 것이다(책 33쪽 / PDF 35쪽). 값이 코드에 고정되면 변경 때마다 개발이 필요해 확장과 밸런스 조정 비용이 커진다(책 28–29쪽 / PDF 30–31쪽, 책 32쪽 / PDF 34쪽).
5. **협업자가 구현할 수 있게 전달한다.** 프로그래머에게는 순서·판정·예외, UI 담당자에게는 화면 구조·버튼 상태, 이펙트 담당자에게는 트리거·타이밍을 보이게 한다. 문서만 읽고 구현 흐름을 재구성할 수 있어야 한다(책 33쪽 / PDF 35쪽).

## 판단 규칙과 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **조건을 플레이어에게 강제해 복잡도를 줄일 수 있는가?** 길드장을 무작위로 승계하는 대신, 길드장은 위임 또는 탈퇴 후에만 캐릭터를 삭제하게 하면 예외·유지보수 부담이 줄어든다(책 27쪽 / PDF 29쪽). 스킬 적용 지침: 이 경우 UI가 차단 이유와 해소 행동을 안내해야 한다.
- **시스템이 허용하는 달성 구조가 다양한가?** 사냥만 가능한 퀘스트 구조는 몬스터와 수량만 다른 반복 콘텐츠를 낳는다. 수집·상호작용·탐색·호위·잠입 같은 달성 구조를 시스템이 허용할수록 콘텐츠도 다양해진다(책 24–25쪽 / PDF 26–27쪽).
- **안티패턴: UI부터 그리기.** 원문은 UI가 기능의 결과물이지 출발점이 아니며, 기능과 구조가 정해지기 전에 UI를 먼저 그리면 나중에 뜯어고치거나 처음부터 다시 짜야 하는 경우가 많다고 한다(ch05, 책 80쪽 / PDF 82쪽). 조건·판정·결과가 없으면 버튼 상태와 오류 흐름도 확정할 수 없다는 설명은 스킬 정리다.
- **안티패턴: ‘기능이 된다’만 확인하기.** 출석 보상에서 서버 시간·계정 상태·UI 출력 조건 중 하나만 틀어져도 누락·중복·오작동이 생기고, 상태 이상·넉백 판정이 여러 시스템과 동시에 충돌해 UI가 멈추거나 서버가 다운될 수도 있다. 원문은 이런 문제가 대부분 설계 초기에 예외 처리와 조건 흐름이 정리되지 않았거나 테스트가 어려운 복잡한 구조로 설계됐을 때 생긴다고 한다(책 27쪽 / PDF 29쪽). 정상 경로와 실패 경로를 같은 수준으로 설계한다.
- **안티패턴: 콘텐츠와 시스템의 책임을 섞기.** 원문에서 시스템 기획자는 퀘스트 작동 방식(조건 달성·완료 처리·보상 지급), 콘텐츠 재료의 규칙(예: 누적 사냥 퀘스트는 "이 퀘스트를 받기 전에 사냥한 분량은 카운트되지 않는다"), 데이터 구조(오픈 조건·담당 NPC·달성 조건·대사·보상의 삽입 방식)를 맡는다. 콘텐츠 기획자는 퀘스트 내용 구성(늑대 가죽 10개와 빵 보상), NPC·대사 작성, 보상 아이템 설정을 맡는다(책 24쪽 / PDF 26쪽). '퀘스트는 시스템인가, 콘텐츠인가'라는 질문에 저자는 퀘스트라는 '기능'은 시스템 기획의 산물이고 퀘스트의 '내용'은 콘텐츠 기획의 산물이라고 답한다(책 25쪽 / PDF 27쪽).

## 원문 사례를 실무 형식으로 재구성: 퀘스트 수령 후 사냥

**원문에서 확인한 구조** — “슬라임 10마리 처치 시 보상” 사례는 대상 오브젝트, 처치 인정 조건, 처치 횟수, 보상 지정·지급을 분해한다(책 18–19쪽 / PDF 20–21쪽).

**새 적용 예시** — 아래 표는 그 구조에 의도·UI·실패 처리를 덧붙인 스킬 작성자의 명세 예시다. 추가 항목을 위 페이지의 원문 주장으로 인용하지 않는다.

| 층위 | 결정할 내용 |
| --- | --- |
| 의도 | 사냥 목표를 명확히 보여 주고, 달성 후 보상으로 다음 행동을 만든다. |
| 규칙 | 퀘스트를 수락한 뒤 지정 오브젝트가 인정 기준으로 처치될 때 카운트를 올리고, 목표 달성 시 완료 상태로 전환한다. 기여만 한 경우를 인정할지는 별도 판정으로 명시한다. |
| 데이터 | 대상 오브젝트 식별자, 필요 횟수, 보상 식별자·수량, 수락 가능 조건, 완료 상태를 연결한다. |
| UI | 수락 전/진행 중/완료 상태, 현재 카운트, 보상 수령 가능 여부와 조건 미충족 사유를 표시한다. |
| 예외 | 수락 전 처치 인정 여부, 파티 기여, 보상 지급 중 연결 종료, 인벤토리 제약을 결정한다. |

## 실무 점검

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- 이 시스템이 해결할 문제와 유도할 루프를 한 문장으로 설명할 수 있는가?
- 각 입력에 대해 조건, 판정 주체/시점, 상태 변화, 성공·실패 출력이 있는가?
- 신규 콘텐츠가 추가될 때 코드 변경이 아니라 데이터 추가로 해결되는 항목은 무엇인가?
- 제한·차단·실패를 만난 플레이어가 UI만 보고 다음 행동을 알 수 있는가?
- 중복 입력, 취소, 강제 종료, 재접속에 대한 보상·상태 일관성을 확인했는가?
- 문서에 규칙뿐 아니라 데이터 예시와 화면 상태가 있어 직군별로 해석이 갈리지 않는가?
