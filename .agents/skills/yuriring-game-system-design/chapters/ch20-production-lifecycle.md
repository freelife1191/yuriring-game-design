# 20장: 디자인부터 런칭까지, 시스템 기획의 여정

> **원문 범위:** 책 338–355쪽 / PDF 340–357쪽. 이 장은 시스템 기획자가 문서 작성에서 끝나지 않고 디자인·프리 프로덕션·프로덕션·라이브 서비스까지 기준을 관리해야 한다는 실무 흐름을 제시한다.

## 핵심 관점

시스템 기획의 완료 조건은 기획서 제출이 아니라, 의도한 경험이 구현·검증·운영되고 피드백으로 조정되는 것이다(스킬 정리). 초기에는 플레이어 경험과 방향을 고정하고, 개발 중에는 의도를 보존한 현실적 대안을 제시하며, 출시 뒤에는 로그·지표·정성 피드백으로 가설을 검증한다(책 340–355쪽 / PDF 342–357쪽). 원문은 문서를 프로그래머·아티스트·QA·운영 팀이 모두 참조하는 기준선이라고 하며(책 350쪽 / PDF 352쪽), 이를 단계마다 달라지는 판단을 잇는 기준선으로 넓혀 보는 것은 스킬 정리다.

## 저자 절차와 판단 기준

### 1. 디자인: 기능보다 핵심 경험을 먼저 정한다

‘지휘관이 파티에 패시브를 준다’는 기능 설명보다, 어떤 조합 고민과 전략 감정을 만들지가 핵심 재미다(책 340–341쪽 / PDF 342–343쪽). 원문은 재미가 운에 맡길 대상이 아니라 설계할 대상이며, 핵심 재미 정의는 시스템 구조의 중심축이자 팀이 설계 방향을 공유하는 기준점이라고 한다. 이 방향 설정이 부족하면 디테일이 정교해도 후반부에 설계를 뜯어고치게 된다고 경고한다(책 341–343쪽 / PDF 343–345쪽). 핵심 재미를 플레이어에게 유도할 행동·감정·판단이 보이는 문장으로 정의한 뒤, 선택지 다양성, 연계 효과의 가시성, 상황별 유효성 같은 설계 기준으로 내린다(책 341–342쪽 / PDF 343–344쪽). 이어 시스템 관여도, 타깃의 진입 시점과 난이도, 자동 추천 같은 보조 기능, 성장·수집·사업 구조와의 연결을 판단한다(책 342–343쪽 / PDF 344–345쪽). 관여도의 원문 예는 전투 결과에 30% 이상 영향을 주는 메타 중심 축이면 패시브 파급력을 높게, 10% 미만이면 '편성에 신경 쓰는 사람만 쓰는' 보조 요소로 기획한다는 것이다(책 342쪽 / PDF 344쪽). 이 비율은 가상 사례 값이며 기본값이 아니다.

제안서는 현재 문제→시스템 역할→간략한 흐름→플레이어 경험·사업·개발 측 기대 효과 순으로 쓰며, 흐름 요약에는 가능하면 스토리보드나 UI 스케치를 함께 붙인다(책 343–344쪽 / PDF 345–346쪽). 기대 효과를 희망 문구가 아니라 전제와 기대 변화로 쓰고 개발 부담·기존 자산 활용 가능성을 함께 검토한다는 것은 스킬 보완이다.

### 2. 프리 프로덕션: 범위와 기준선을 합의한다

프리 프로덕션 미팅은 디자인 단계의 기획 방향이 개발 가능한 수준으로 타당한지 확인하고 각 파트의 일정과 리소스 소요를 가늠하는 자리다(책 345쪽 / PDF 347쪽). 이 단계에서 기획자는 디테일보다 전체 기능의 포함 여부와 동작 방식, 플레이어가 겪게 될 흐름을 먼저 정리한다(책 346쪽 / PDF 348쪽). 저자는 가장 중요한 것이 시스템 범위를 오버하지 않는 것이며, 실현 가능한 범위에서 우선순위를 정하고 모든 기능이 지금 당장 필요한지 향후 확장할지를 판단하라고 한다(책 346쪽 / PDF 348쪽). 회의 전 핵심 기능과 있으면 좋은 기능을 구분하고 각 대체안을 준비한다. 회의에서는 필요성, 우선순위, 리스크를 확인하며 리소스·서버 부하·기존 기능 중복의 반론을 사양 조정의 입력으로 쓴다(책 345쪽 / PDF 347쪽). 시스템은 수집, 편성 UI, 효과 발동, 성장처럼 구조 단위로 분해하여 포함/제외와 향후 확장을 결정한다(책 346쪽 / PDF 348쪽).

상세 문서는 기능 단위로 쪼개 기획 의도가 빠짐없이 설명되게 하고 표·도식·UI 프로토타입·데이터 예시를 결합한다. 원문은 실무에서 기획서를 한 번에 일괄 작성하는 경우가 흔하지 않다며, 개발 우선순위가 높은 기능부터 쓰고 확장 가능성이 있는 기능은 별도 문서 또는 ‘기획 예정’으로 분리한다고 설명한다(책 346쪽 / PDF 348쪽). 킥오프는 상세 기획서 초안이 작성된 뒤 열리며, 전체 흐름, 핵심 기능, 논의가 필요한 모호점, 예상 일정과 구현 단계별 목표를 준비한다(책 347쪽 / PDF 349쪽). 완벽한 문서가 아니라 **병렬 작업을 시작할 만큼 명확한 기준선**이 시작 조건이며, 그 전제는 '기획서는 업데이트될 수 있다'는 것을 팀 전체가 공유하는 것이다(책 347쪽 / PDF 349쪽).

### 3. 프로덕션: 이슈를 분류하고 의도를 보존한다

개발 추적에서 확인할 것은 ‘개발자 입장에서 모호한 명세’와 ‘의도를 유지하는 우회안’이다(책 348쪽 / PDF 350쪽). 예를 들어 전투 HUD 공간이 없으면 효과 설명을 전투 전 브리핑에 두고 전투 중에는 아이콘만 보여 주는 방안을 비교한다(책 348–349쪽 / PDF 350–351쪽). 원문의 유형별 대응 사례(책 349–350쪽 / PDF 351–352쪽)를 다음 점검 항목으로 재구성했다. 이는 저자가 제시한 고정 순서가 아니다. 원문은 개발 도중 기획 방향이 바뀌면(전략 수정, 운영·사업·마케팅 요청, 플레이어 피드백·시장 반응, 경쟁작 벤치마킹, 급작스러운 우선순위 변경) 전체를 다시 설계하지 말고 기존 구조에서 변형 가능한 범위를 먼저 분석하고, 변경 사유·수정 범위·영향 시스템·일정을 요약한 내부 공유 문서를 작성하며, 기존 구현 자산을 재활용하는 우회안을 설계해 실시간으로 기획서에 반영하라고 한다(책 349쪽 / PDF 351쪽, 렌더 확인).

원문은 기획서와 구현이 어긋나면 기획서대로 무작정 수정을 요청하기보다 현재 구현을 먼저 파악하고 "지금 구현은 A인데 기획 의도는 B였습니다. 이 구현이 더 효율적이라면 방향을 조정할 여지가 있습니다"처럼 유연하게 대하라고 한다. 버그는 경우에 따라 설계상의 예외 처리를 추가하는 것이 더 빠른 해결책일 수도 있다고 한다(책 349쪽 / PDF 351쪽, 렌더 확인).

1. 변경·불일치·버그·일정 지연 중 유형을 분류한다.
2. 원인, 변경 범위, 영향 시스템, 일정, 재현 조건을 정리한다. 확인된 사실과 가설의 구분은 스킬이 보완한 적용 기준이다.
3. 핵심 경험을 유지하는 축소·재활용·단계 배포안을 만든다.
4. 결정과 새 사양을 문서에 반영하고 관련 파트에 알린다. 방향이 바뀌면 '어디까지 바뀌었고 어디는 그대로'인지 전 파트에 명확히 설명한다(책 349쪽 / PDF 351쪽).

원문의 일정 지연·구현 난이도 상승 대응은 세 가지다. 개발 담당자와 소통해 어떤 부분이 어렵고 시간이 걸리는지 정확히 확인하고, 우선순위를 나눠 배포하거나 1차 버전에서 제외할 기능을 협의하며, 기획 의도와 기능 완성도 중 무엇이 더 중요한지 선택해야 할 때도 있다. 저자는 이슈를 라이브에 미치는 영향과 개발 리스크로 우선순위를 관리하고, 지금 수정할 것·나중에 고쳐도 되는 것·절대 빠지면 안 되는 핵심 요소를 구분하라고 한다(책 350쪽 / PDF 352쪽, 렌더 확인).

수정 요청이 들어오면 세 가지를 빠르게 정리한다. 수정이 필요한 이유(설계 미비·구현 문제·외부 요청), 수정의 범위(문장 수정·기능 재정의), 파급력(다른 시스템 연결·기존 구현 사양과의 충돌)이다. 변경은 그때그때 반영해야 하며, 원문은 **실시간으로, 적어도 당일에는** 반영하는 것을 원칙으로 삼으라고 한다. 미루면 QA 단계에서 사양이 어긋나고 운영·유지보수 단계에서 혼선이 생긴다(책 350쪽 / PDF 352쪽).

데이터 입력, 조건 분기, 엔진 파라미터, 밸런스 시뮬레이션을 기획자가 다룰 수 있으며, 구현 뒤에는 직접 빌드를 확인한다(책 350–351쪽 / PDF 352–353쪽). QA는 시스템 기능을 테스트할 뿐 기획 의도의 재미나 구조적 완성도까지 보장하지 않고, QA 리소스는 한정적이어서 단순 텍스트 오류·데이터 누락에 시간을 쓰면 예외 상황 검증 같은 중요한 테스트를 못 한다(책 351쪽 / PDF 353쪽). 기획자의 자체 테스트로 단순 텍스트 오류·데이터 누락을 먼저 걸러 내고 자체 테스트를 QA의 대체가 아니라 그 앞 단계로 두라는 것은 스킬 정리다. 반복 조정될 값은 툴/테이블로 만들고, 출시 뒤 확인할 사용·효과 로그는 이 시점에 요청한다(책 351–352쪽 / PDF 353–354쪽).

### 4. 라이브: 결과와 이유를 함께 읽고 폴리싱한다

패치 노트는 운영 팀이 쓰는 경우가 많아도, 시스템 기획자는 최소한 자신이 담당한 시스템의 변경 내역을 직접 쓰거나 구조와 내용을 제시해야 하고, 어떤 내용까지 공개할지와 어떤 표현이 오해를 낳는지는 기획자가 결정한다(책 353쪽 / PDF 355쪽). 공개 여부는 선별하되 플레이어가 체감하는 요소는 투명하게 명시하는 것이 좋고, 톤앤매너는 게임에 맞추되 핵심 메시지는 명확해야 한다(책 354쪽 / PDF 356쪽). 원문은 '왜 바꿨는가'가 가장 중요하다고 하고, 중요한 변화일수록 변경 전/후, 영향 대상, 기대 효과, 예시로 구조를 나눠 명확히 쓰라고 한다(책 353–354쪽 / PDF 355–356쪽). 원문 지휘관 사례의 지표는 슬롯 사용률(원문은 이를 "지휘관을 편성하지 않은 플레이어 비율은 어느 정도인가?"로 묻는다), 분포도(특정 지휘관 편중), 편성 변경 빈도(바꿔 쓰는 경험)다(책 354쪽 / PDF 356쪽). 지표는 결과를 보일 뿐 원인을 말하지 않으므로, 편성률이 낮으면 진입 조건이 너무 뒤에 있는지, UI가 눈에 띄지 않는지, 효과가 체감되지 않는지 같은 가설을 세워 확인한다(책 354–355쪽 / PDF 356–357쪽). 초반 마케팅·튜토리얼 효과가 섞일 수 있으므로, 원문은 첫 주의 단면보다 2~3주 차 추이를 보고 커뮤니티·리뷰·CS 같은 정성 피드백을 함께 해석하라고 권한다(책 354–355쪽 / PDF 356–357쪽). 이 기간 권고도 게임의 주기·표본·이벤트를 고려해 적용한다는 단서는 스킬 정리다.

폴리싱은 버그 수정에 한정되지 않는다. 사용 흐름과 UX를 다듬고 진입 장벽을 낮추며, 필요하면 기능을 재설계·제거하거나 구조를 바꾸는 일이다. 원문 예는 편성 슬롯 이동·미편성 알림(UI 개선), 튜토리얼 맵의 지휘관 선택 유도(튜토리얼 추가), 효과 발동 연출 추가(효과 가시성 강화)다(책 355쪽 / PDF 357쪽).

## 주요 개념

- **핵심 재미:** 플레이어가 하게 될 선택과 감정으로 표현한 설계 중심축.
- **기준선:** 병렬 개발이 가능한 수준으로 합의된 사양과 미확정 지점.
- **우회안:** 구현 제약 아래에서도 의도를 최대한 유지하는 축소·대체 설계.
- **로그 선행 설계:** 출시 후 질문에 답할 이벤트와 속성을 출시 전에 요청하는 일(스킬 정리, 근거는 위 3절의 로그 요청).
- **폴리싱:** 사용 흐름·UX·진입 장벽을 조정해 설계를 실제 경험에 맞추는 작업.

## 안티패턴과 대응

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **기능 목록을 핵심 재미로 오인:** 플레이어의 선택·감정·행동으로 다시 정의한다.
- **모든 기능을 이번 버전에 고집:** 핵심/선택/후속을 분리하고 재사용·단계 배포안을 만든다.
- **불일치를 무조건 문서대로 되돌림:** 현재 구현의 장점과 비용을 확인한 뒤 의도와 기준선을 재결정한다.
- **QA에 자체 검증 위임:** 기획자는 데이터와 의도 흐름을 직접 확인한다.
- **지표 하나로 원인 단정:** 기간 추이, 세그먼트, 정성 피드백, 튜토리얼·마케팅 맥락을 결합한다.

## 사례 재구성: 장비 프리셋의 출시 전후

디자인 단계에서 장비 프리셋의 핵심 재미를 ‘콘텐츠 직전의 빠른 준비와 상황별 세팅 선택’으로 정한다. 프리 프로덕션에서 전투 중 전환은 1차 범위에서 제외하고 편성 화면 전환, 저장/삭제, 장비 누락 예외, 전환 로그를 확정한다. HUD 공간 문제가 아니라 저장 용량 문제가 발견되면 프리셋 수를 축소하되 핵심 경험이 유지되는지 검토하고 변경 사유·영향·테스트 케이스를 문서에 남긴다. 출시 뒤에는 프리셋 생성률, 콘텐츠별 전환률, 저장 실패 원인, 세팅 화면 이탈과 피드백을 같이 보고, 발견성 부족이라면 튜토리얼·추천 진입점을 폴리싱한다. 이는 지휘관 사례의 라이프사이클을 새 기능에 적용한 재구성이다.

## 점검 항목

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- [ ] 핵심 재미가 기능 목록이 아니라 플레이어 행동·판단·감정으로 정의됐는가?
- [ ] 핵심/선택/후속 범위와 제약 발생 시 대체안이 있는가?
- [ ] 킥오프에 기준선, 모호점, 담당별 결정 사항, 단계별 목표가 있는가?
- [ ] 이슈마다 원인·범위·영향·재현·결정·문서 반영이 연결되는가?
- [ ] 기획자 자체 테스트와 QA 테스트가 서로 다른 목적을 갖고 있는가?
- [ ] 출시 전 로그가 운영 질문과 연결되고, 지표와 정성 피드백을 함께 해석하는가?
