# 20장: 디자인부터 런칭까지, 시스템 기획의 여정

> **원문 범위:** PDF 340~357쪽 / 책 338~355쪽. 이 장은 시스템 기획자가 문서 작성에서 끝나지 않고 디자인·프리 프로덕션·프로덕션·라이브 서비스까지 기준을 관리해야 한다는 실무 흐름을 제시한다.

## 핵심 관점

시스템 기획의 완료 조건은 기획서 제출이 아니라, 의도한 경험이 구현·검증·운영되고 피드백으로 조정되는 것이다. 초기에는 플레이어 경험과 방향을 고정하고, 개발 중에는 의도를 보존한 현실적 대안을 제시하며, 출시 뒤에는 로그·지표·정성 피드백으로 가설을 검증한다(PDF 342~357쪽). 문서는 단계마다 달라지는 이 판단을 연결하는 기준선이다.

## 저자 절차와 판단 기준

### 1. 디자인: 기능보다 핵심 경험을 먼저 정한다

‘지휘관이 파티에 패시브를 준다’는 기능 설명보다, 어떤 조합 고민과 전략 감정을 만들지가 핵심 재미다(PDF 342~343쪽). 이를 행동·감정·판단이 보이는 문장으로 정의한 뒤, 선택지 다양성, 연계 효과의 가시성, 상황별 유효성 같은 설계 기준으로 내린다(PDF 344쪽). 이어 시스템 관여도, 타깃의 진입 시점과 난이도, 자동 추천 같은 보조 기능, 성장·수집·사업 구조와의 연결을 판단한다(PDF 344~345쪽).

제안서는 현재 문제→시스템 역할→간략한 흐름→플레이어 경험·사업·개발 측 기대 효과 순으로 쓴다(PDF 345~346쪽). 기대 효과는 희망 문구가 아니라, 어떤 전제에서 어떤 변화를 기대하는지로 쓰고 실제 개발 부담·기존 자산 활용 가능성도 함께 검토한다.

### 2. 프리 프로덕션: 범위와 기준선을 합의한다

회의 전 핵심 기능과 있으면 좋은 기능을 구분하고 각 대체안을 준비한다. 회의에서는 필요성, 우선순위, 리스크를 확인하며 리소스·서버 부하·기존 기능 중복의 반론을 사양 조정의 입력으로 쓴다(PDF 347쪽). 시스템은 수집, 편성 UI, 효과 발동, 성장처럼 구조 단위로 분해하여 포함/제외와 향후 확장을 결정한다(PDF 348쪽).

상세 문서는 기능 단위로 쓰고 표·도식·UI 프로토타입·데이터 예시를 결합한다. 우선순위가 높은 기능부터 작성하고 미래 기능은 별도 문서 또는 ‘기획 예정’으로 분리한다(PDF 348~349쪽). 킥오프에는 전체 흐름, 핵심 기능, 논의가 필요한 모호점, 단계별 목표를 준비한다. 완벽한 문서가 아니라 **병렬 작업을 시작할 만큼 명확한 기준선**이 시작 조건이다(PDF 349쪽).

### 3. 프로덕션: 이슈를 분류하고 의도를 보존한다

개발 추적에서 확인할 것은 ‘개발자가 해석할 수 없는 명세’와 ‘의도를 유지하는 우회안’이다(PDF 350쪽). 예를 들어 전투 HUD 공간이 없으면 효과 설명을 전투 전 브리핑에 두고 전투 중에는 아이콘만 보여 주는 방안을 비교한다. 원문의 유형별 대응 사례(PDF 351~352쪽)를 다음 점검 항목으로 재구성했다. 이는 저자가 제시한 고정 순서가 아니다.

1. 변경·불일치·버그·일정 지연 중 유형을 분류한다.
2. 원인, 변경 범위, 영향 시스템, 일정, 재현 조건을 정리한다. 확인된 사실과 가설의 구분은 스킬이 보완한 적용 기준이다.
3. 핵심 경험을 유지하는 축소·재활용·단계 배포안을 만든다.
4. 결정과 새 사양을 즉시 문서에 반영하고 관련 파트에 알린다.

데이터 입력, 조건 분기, 엔진 파라미터, 밸런스 시뮬레이션을 기획자가 다룰 수 있으며, 구현 뒤에는 직접 빌드를 확인한다. QA는 기획 의도까지 자동 보증하지 않으므로, 기획자의 자체 테스트는 QA를 대체하는 일이 아니라 명세·데이터 누락을 먼저 제거하는 일이다(PDF 352~353쪽). 반복 조정될 값은 툴/테이블로 만들고, 출시 뒤 확인할 사용·효과 로그는 이 시점에 요청한다(PDF 353~354쪽).

### 4. 라이브: 결과와 이유를 함께 읽고 폴리싱한다

패치 노트에는 무엇이 바뀌었는지뿐 아니라 왜 바꿨는지, 변경 전/후, 영향 대상, 기대 효과, 예시를 구조화한다. 플레이어가 체감하는 요소는 투명하게 알리되 공개 범위는 판단한다(PDF 355~356쪽). 출시 후 사용률·분포·변경 빈도 같은 지표는 결과를 보일 뿐 원인을 말하지 않는다. 초반 캠페인·튜토리얼 효과가 섞일 수 있으므로, 원문은 첫 주의 단면보다 2~3주 차 추이를 보고 커뮤니티·리뷰·CS 같은 정성 피드백을 함께 해석하라고 권한다(PDF 356~357쪽). 이 기간 권고도 게임의 주기·표본·이벤트를 고려해 적용한다.

폴리싱은 버그 수정에 한정되지 않는다. 노출 위치, 안내, 튜토리얼, 효과 가시성, 진입 장벽을 조정하고 필요하면 기능을 재설계·제거하는 일이다(PDF 357쪽).

## 주요 개념

- **핵심 재미:** 플레이어가 하게 될 선택과 감정으로 표현한 설계 중심축.
- **기준선:** 병렬 개발이 가능한 수준으로 합의된 사양과 미확정 지점.
- **우회안:** 구현 제약 아래에서도 의도를 최대한 유지하는 축소·대체 설계.
- **로그 선행 설계:** 출시 후 질문에 답할 이벤트와 속성을 출시 전에 요청하는 일.
- **폴리싱:** 사용 흐름·UX·진입 장벽을 조정해 설계를 실제 경험에 맞추는 작업.

## 안티패턴과 대응

- **기능 목록을 핵심 재미로 오인:** 플레이어의 선택·감정·행동으로 다시 정의한다.
- **모든 기능을 이번 버전에 고집:** 핵심/선택/후속을 분리하고 재사용·단계 배포안을 만든다.
- **불일치를 무조건 문서대로 되돌림:** 현재 구현의 장점과 비용을 확인한 뒤 의도와 기준선을 재결정한다.
- **QA에 자체 검증 위임:** 기획자는 데이터와 의도 흐름을 직접 확인한다.
- **지표 하나로 원인 단정:** 기간 추이, 세그먼트, 정성 피드백, 튜토리얼·마케팅 맥락을 결합한다.

## 사례 재구성: 장비 프리셋의 출시 전후

디자인 단계에서 장비 프리셋의 핵심 재미를 ‘콘텐츠 직전의 빠른 준비와 상황별 세팅 선택’으로 정한다. 프리 프로덕션에서 전투 중 전환은 1차 범위에서 제외하고 편성 화면 전환, 저장/삭제, 장비 누락 예외, 전환 로그를 확정한다. HUD 공간 문제가 아니라 저장 용량 문제가 발견되면 프리셋 수를 축소하되 핵심 경험이 유지되는지 검토하고 변경 사유·영향·테스트 케이스를 문서에 남긴다. 출시 뒤에는 프리셋 생성률, 콘텐츠별 전환률, 저장 실패 원인, 세팅 화면 이탈과 피드백을 같이 보고, 발견성 부족이라면 튜토리얼·추천 진입점을 폴리싱한다. 이는 지휘관 사례의 라이프사이클을 새 기능에 적용한 재구성이다.

## 점검 항목

- [ ] 핵심 재미가 기능 목록이 아니라 플레이어 행동·판단·감정으로 정의됐는가?
- [ ] 핵심/선택/후속 범위와 제약 발생 시 대체안이 있는가?
- [ ] 킥오프에 기준선, 모호점, 담당별 결정 사항, 단계별 목표가 있는가?
- [ ] 이슈마다 원인·범위·영향·재현·결정·문서 반영이 연결되는가?
- [ ] 기획자 자체 테스트와 QA 테스트가 서로 다른 목적을 갖고 있는가?
- [ ] 출시 전 로그가 운영 질문과 연결되고, 지표와 정성 피드백을 함께 해석하는가?
