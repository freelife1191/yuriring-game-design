# 08장: 규칙의 설계

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 8장, 책 116–130쪽 / PDF 118–132쪽. PDF 133쪽은 빈 쪽이다.  
> 거래소의 레벨 10, 동일 아이템 5건, 취소 10분, 재등록 5분, 시세 ±200%, 수수료 10%, 새로고침 5초는 모두 **원문 거래소 사례 수치**다. 프로젝트 기본값으로 쓰지 않는다. 원문은 구매 완료 시 판매 금액 전송과 판매자 정산 버튼 지급을 함께 서술하므로 지급 시점은 확정하지 않는다.

## 핵심 관점

좋은 규칙 설계는 조건을 나열하는 작업이 아니라, “왜 이 시스템이 필요한가”에서 시작해 플레이어 경험과 운영 위험을 함께 해결하는 과정이다. 저자는 거래소를 사례로 **기획 의도 → 설계 기준 → 기능 단위 분해 → 상세 규칙 → 검토·보완**의 순서를 제시한다. 작동만 하는 거래소가 아니라 자원 순환, 신뢰, 부정 거래 방지를 동시에 만족하는지를 되묻는 방식이다.

## 저자의 절차와 규칙

### 1. 먼저 기획 의도를 문장으로 고정한다

거래가 가능해야 한다는 기능 요구만으로는 거래소, 개인 거래, 개인 상점 중 무엇이 맞는지 판단할 수 없다. 원문은 거래소를 설계할 때 가장 먼저 이 기능이 왜 필요하고 왜 이 방식이어야 하는지를 생각하라고 하며, 기획 의도 설계를 이 시스템이 왜 필요한지, 어떤 문제를 해결하고 어떤 플레이 경험을 만들고 싶은지 명확히 하는 과정으로 설명한다(책 118쪽 / PDF 120쪽). 원문은 거래소의 의도를 자원 순환, 편리하고 신뢰 가능한 거래, 현금 거래·시세 조작·독점·투기 방지로 둔다(책 118–119쪽 / PDF 120–121쪽). 이 의도를 뒤의 제한을 정당화하는 기준으로 삼아 각 규칙이 어느 의도를 지지하는지 연결하라는 것은 스킬의 적용 지침이다.

### 2. 의도를 검증 가능한 설계 기준으로 바꾼다

| 기획 의도 | 원문의 설계 기준 | 왜 필요한가 |
| --- | --- | --- |
| 자원 흐름 | 간결한 등록·구매, 묶음 거래, 수수료 | 거래 마찰을 줄이고 재화 소비·공급을 순환시킨다. |
| 신뢰·편의 | 단계별 결과 안내, 시세 정보, 검색·정렬, 서버 기준 재고 검증 | 실패 원인과 실제 상태를 납득하게 한다. |
| 부정 거래 방지 | 시세 검증·지연 등록, 취소/재등록 제한, 등록 제한, 계정 제한, 거래 기록·이상 감지 | 자유 거래가 경제를 훼손하지 않게 한다. |

원문은 시세 검증 기준·범위·허용치를 운영 도구에서 조정 가능하게 두라고 권한다(책 120쪽 / PDF 122쪽). 이를 모든 수치를 운영 도구에 노출하라는 요구로 읽지 않고, 제한을 악용 억제와 정상 거래 기회 사이에서 검토하라는 것은 스킬 해석이다.

### 3. 복합 시스템을 기능 단위로 쪼갠 뒤 각 단위의 정상·예외 흐름을 쓴다

원문 거래소 분해는 등록, 검색·열람, 구매, 수수료 처리, 아이템·재화 수령, 취소, 시세 검증·지연 등록이다. 단위를 나누면 빠지는 규칙과 위험 구간을 조기에 찾을 수 있다. 원문은 각 기능을 기본 흐름과 예외 처리로 나눠 쓴다. 여기에 7장의 상황–정보–판단–결과–예외 틀을 함께 적용하는 것은 스킬 정리다.

| 기능 | 원문의 기본 흐름 요약 | 핵심 예외/점검 |
| --- | --- | --- |
| 등록 | 아이템·수량·가격 입력 → 검증 대기 → 시세 검증 → 확정/거부. 검증 대기 중에는 다른 플레이어에게 노출되지 않는다(책 121쪽 / PDF 123쪽). | 거래 불가, 수량 부족, 계정·등록 건수 제한 |
| 취소 | 판매 목록 선택 → 취소 가능 상태 확인 → 취소 | 이미 거래됨, 취소 가능 시간, 반복 취소 제한 |
| 지연 등록 | 평균가 허용 범위 확인 → 초과 시 거부 | 대기 중 회수, 검증 기준 변경 시 대기 건 재검토 |
| 구매 | 서버 재고 확인 → 수량·총액·소지금 확인 → 완료·지급 | 품절, 잔액 부족, 미확정 거래의 취소·환불·재고 복구. 다른 플레이어와 구매가 충돌하면 첫 시도자가 우선이고 후속 시도자에게는 재고 없음을 안내한다(책 123쪽 / PDF 125쪽). |
| 수수료 처리 | 판매 금액에서 수수료를 차감 | 원문 사례는 수수료율 고정(예: 10%), 소수점이 생기면 반올림이다(책 123쪽 / PDF 125쪽). |
| 검색·열람 | 카테고리/정렬/검색어로 결과 표시. 원문 사례의 정렬은 서브 카테고리 선택 시 아이템 등급순 > 이름순, 개별 아이템 선택 시 낮은 가격순 > 오래된 등록순, 검색어는 완전 일치 > 부분 일치다(책 124쪽 / PDF 126쪽). | 새 등록 강제 갱신 방지, 결과 없음·빈 검색어·특수문자 처리 |

**지급 시점 한계:** 원문 책 123쪽 / PDF 125쪽은 구매 완료 뒤 판매자에게 수수료 차감 금액을 전송한다고 쓰고, 같은 쪽의 정산 규칙에서는 판매자가 정산 버튼을 누르면 지급한다고 쓴다. 두 서술의 관계(전송 뒤 정산 대기 상태인지 등)는 원문이 밝히지 않는다. 자동 정산/수동 정산 어느 하나로 단정하지 말고, 프로젝트에서는 판매 대금의 상태와 지급 시점을 하나로 일관되게 정한 뒤 구매·정산·최대 보유 금액 예외에 같은 정의를 적용해야 한다.

### 4. 의도와 실제 규칙의 간극을 검토하고 보완한다

완성 뒤에는 “동작하는가”보다 “의도한 경험을 전달하는가”를 확인한다(책 124–125쪽 / PDF 126–127쪽). 원문은 방향까지 준다. 수수료 차감을 정산 시점이 아닌 등록 시점에 두면 소지금이 부족할 때 거래소를 쓸 수 없어 자원 흐름이 지체될 수 있고, 구매품을 우편함이 아닌 인벤토리로 지급하면 인벤토리 부족 검증에서 막혀 원하는 때 수령할 수 없다. 등록 취소 후 재등록 쿨타임이 없거나 짧으면 시세를 흔드는 반복이, 너무 길면 가격 조정 기회 상실이 생기므로 양쪽을 함께 본다(책 125쪽 / PDF 127쪽). 원문은 수수료 시점이 자금 부족으로 거래 이용을 막지 않는지, 지급 위치가 인벤토리 부족으로 수령을 막지 않는지, 실패 안내·시세·재고 정보가 투명한지, 제한이 정상 거래까지 과도하게 막지 않는지를 묻는다. 원문은 자원 흐름을 왜곡하거나 일부 플레이어만 이득을 보는 설계는 없는지, 시세 검증 로직의 허용 범위가 현실적이면서 악용을 막는 수준인지, 이상 패턴 감지 로직과 GM 검토 시스템이 연동되는지도 점검 질문으로 든다(책 125쪽 / PDF 127쪽).

### 5. 규칙 설계 시 다섯 기준으로 점검한다(8.2)

저자는 규칙 설계 시 반드시 고려해야 할 요소로 다섯 가지를 든다(책 126–130쪽 / PDF 128–132쪽).

| 기준 | 원문의 판단과 사례 |
| --- | --- |
| 명확성과 직관성 | “공격 시 10% 확률로 기절”은 스킬 공격 포함 여부, 도트·반사 피해 포함 여부, 다단히트의 타격별/스킬 단위 계산이 모두 갈린다. 예측 가능한 부분은 간결하게, 혼동 여지가 있는 부분은 구체적으로, 모든 경우를 나열하기보다 오해하기 쉬운 지점만 짚는다. 지속 피해가 공격으로 취급되어 온 게임이면 그 점을 명시한다(책 126–127쪽 / PDF 128–129쪽). |
| 일관성 | 구매 퀘스트는 이전 구매를 인정하고 강화 퀘스트는 인정하지 않으면 플레이어는 규칙을 외워야 한다. 비슷한 규칙은 같은 방식으로 처리하고, 예외가 있으면 이유를 알 수 있게 설명한다(책 127–128쪽 / PDF 129–130쪽). |
| 행동의 자유도 | 스킬 트리 초기화 불가는 빌드 실험을 막고 인터넷 공략을 외우는 플레이를 고착시킨다. 무제한 개방만이 답은 아니며 초기화 비용 같은 절제된 제한이 효과적이다(책 128–129쪽 / PDF 130–131쪽). |
| 규칙 간 충돌 방지 | '넉백 중 이동 불가'와 '돌진은 어떤 상태에서도 가능'이 만나면 우선순위를 미리 선언하고 일관되게 적용한다. 서로 다른 시스템 간 상호 작용에서 예상 못한 연쇄 충돌이 많으므로 규칙을 단편적으로 보지 않고 시스템 전체 흐름에서 검토한다(책 129쪽 / PDF 131쪽). |
| 플레이 경험 훼손 줄이기 | 경험치 분배는 첫 타격자·마지막 타격자·최다 피해자·딜량 비례(90:10)·균등(50:50) 중 무엇이든 기준을 설명하지 않으면 억울함이 남는다. 딜량 비례면 힐러가 경험치를 전혀 받지 못한다(책 129–130쪽 / PDF 131–132쪽). |

**플레이어에게 얼마나 설명할지:** 원문은 '얼마나 설명할 것인가'를 게임의 설계 방향과 플레이어의 기대치를 기준으로 정하라고 한다(책 127쪽 / PDF 129쪽). 구현용 명세에는 필요한 조건·예외를 모두 정의하고 플레이어용 설명은 그보다 줄여 쓴다는 구분은 이 원칙을 문서 작업에 적용한 스킬 정리다.

## 주요 개념

- **설계 기준:** 기획 의도를 각 기능의 의사결정에 적용하기 위한 판단 기준.
- **지연 등록:** 등록을 즉시 노출하지 않고 검증 대기 상태를 거치는 보호 장치.
- **서버 기준 검증:** 화면의 오래된 표시가 아니라 실제 재고·잔액으로 확정하는 방식.
- **규칙 충돌:** 동시에 적용되는 규칙의 결과가 양립하지 않는 상태. 우선순위를 선언해야 한다.
- **행동 자유도:** 제한 안에서도 플레이어가 실험·선택할 수 있는 여지. 제한 해제와 동일하지 않다.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **기능부터 만들기:** 의도 없이 제한을 붙이면 왜 필요한지 검토할 기준이 없고, 기능 대체 가능성도 놓친다.
- **사례 수치를 보편 규칙으로 복사하기:** 원문의 시간·건수·수수료·시세 범위는 거래소 사례일 뿐이다.
- **비슷한 규칙을 다르게 처리하고 이유를 숨기기:** 과거 행동 인정 여부가 퀘스트마다 다르면 플레이어는 규칙을 외워야 한다.
- **무제한과 과도한 제한 사이만 고르기:** 스킬 초기화처럼 비용 등 절제된 제한으로 실험 기회와 경제를 함께 다룰 수 있다.
- **충돌 우선순위 미정:** 넉백 중 이동 불가와 어떤 상태에서도 돌진 가능이 만날 때 어느 쪽이 우선인지 정해져 있지 않으면 불신이 생긴다.
- **불투명한 손해:** 보상 분배처럼 실패·손해의 이유를 설명하지 않으면 학습이 아니라 억울함이 남는다.

원문 절차를 거래소가 아닌 일반 기능 검토표로 재구성했다. 값은 **새 적용 예시**이며 원문 기본값이 아니다.

| 의도 | 기능 단위 | 성공 전 검증 | 실패 시 보존할 상태 | 플레이어 피드백 |

- [ ] 모든 단위에 입력, 실제 상태 재검증, 성공 처리, 실패 처리, 안내가 있는가?
- [ ] 제한값은 조정 주체·검토 근거와 함께 정의했는가?
- [ ] 동시 요청·서버 오류·대기 중 기준 변경·새로고침 상태를 점검했는가?
- [ ] 판매 대금의 생성, 보관, 지급 시점을 하나로 명세했는가? 원문 사례의 겹친 서술을 그대로 구현 결론으로 쓰지 않았는가?
- [ ] 규칙 충돌 시 우선순위와 플레이어가 알아야 할 설명을 정했는가?
- [ ] 플레이어용 설명은 오해하기 쉬운 지점을 짚으면서, 예측 가능한 경우까지 불필요하게 나열하지 않는가?
- [ ] 비슷한 유형의 규칙이 같은 방식으로 처리되고, 예외는 이유와 함께 안내되는가?
- [ ] 되돌릴 수 없는 선택이 실험을 막지 않는지, 절제된 제한(비용 등)으로 자유도를 줄 수 있는지 검토했는가?
- [ ] 분배·실패 같은 손해 결과의 기준을 플레이어가 스스로 설명할 수 있게 안내하는가?
