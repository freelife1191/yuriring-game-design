# 08장: 규칙의 설계

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 8장, 책 p.116–131 (PDF p.118–133).  
> 거래소의 레벨 10, 동일 아이템 5건, 취소 10분, 재등록 5분, 시세 ±200%, 수수료 10%, 새로고침 5초는 모두 **원문 거래소 사례 수치**다. 프로젝트 기본값으로 쓰지 않는다. 원문은 구매 완료 시 판매 금액 전송과 판매자 정산 버튼 지급을 함께 서술하므로 지급 시점은 확정하지 않는다.

## 핵심 관점

좋은 규칙 설계는 조건을 나열하는 작업이 아니라, “왜 이 시스템이 필요한가”에서 시작해 플레이어 경험과 운영 위험을 함께 해결하는 과정이다. 저자는 거래소를 사례로 **기획 의도 → 설계 기준 → 기능 단위 분해 → 상세 규칙 → 검토·보완**의 순서를 제시한다. 작동만 하는 거래소가 아니라 자원 순환, 신뢰, 부정 거래 방지를 동시에 만족하는지를 되묻는 방식이다.

## 저자의 절차와 규칙

### 1. 먼저 기획 의도를 문장으로 고정한다

거래가 가능해야 한다는 기능 요구만으로는 거래소, 개인 거래, 개인 상점 중 무엇이 맞는지 판단할 수 없다. 원문은 거래소의 의도를 자원 순환, 편리하고 신뢰 가능한 거래, 현금 거래·시세 조작·독점·투기 방지로 둔다. 이 의도는 뒤의 제한을 정당화하는 기준이다. 따라서 시스템을 시작할 때는 해결할 문제와 만들 경험을 먼저 쓰고, 각 규칙이 어느 의도를 지지하는지 연결한다.

### 2. 의도를 검증 가능한 설계 기준으로 바꾼다

| 기획 의도 | 원문의 설계 기준 | 왜 필요한가 |
| --- | --- | --- |
| 자원 흐름 | 간결한 등록·구매, 묶음 거래, 수수료 | 거래 마찰을 줄이고 재화 소비·공급을 순환시킨다. |
| 신뢰·편의 | 단계별 결과 안내, 시세 정보, 검색·정렬, 서버 기준 재고 검증 | 실패 원인과 실제 상태를 납득하게 한다. |
| 부정 거래 방지 | 시세 검증·지연 등록, 취소/재등록 제한, 등록 제한, 계정 제한, 거래 기록·이상 감지 | 자유 거래가 경제를 훼손하지 않게 한다. |

원문은 시세 검증 기준·범위·허용치를 운영 도구에서 조정 가능하게 두라고 권한다(책 120쪽 / PDF 122쪽). 모든 수치를 운영 도구에 노출하라는 요구는 아니다. 제한은 강할수록 좋은 것이 아니라, 악용 억제와 정상 거래 기회 사이에서 검토해야 한다.

### 3. 복합 시스템을 기능 단위로 쪼갠 뒤 각 단위의 정상·예외 흐름을 쓴다

원문 거래소 분해는 등록, 검색·열람, 구매, 수수료 처리, 아이템·재화 수령, 취소, 시세 검증·지연 등록이다. 단위를 나누면 빠지는 규칙과 위험 구간을 조기에 찾을 수 있다. 각 기능에는 7장의 상황–정보–판단–결과–예외 틀을 적용한다.

| 기능 | 원문의 기본 흐름 요약 | 핵심 예외/점검 |
| --- | --- | --- |
| 등록 | 아이템·수량·가격 입력 → 검증 대기 → 시세 검증 → 확정/거부 | 거래 불가, 수량 부족, 계정·등록 건수 제한 |
| 취소 | 판매 목록 선택 → 취소 가능 상태 확인 → 취소 | 이미 거래됨, 취소 가능 시간, 반복 취소 제한 |
| 지연 등록 | 평균가 허용 범위 확인 → 초과 시 거부 | 대기 중 회수, 검증 기준 변경 시 대기 건 재검토 |
| 구매 | 서버 재고 확인 → 수량·총액·소지금 확인 → 완료·지급 | 품절, 잔액 부족, 동시 구매, 미확정 거래의 취소·환불·재고 복구 |
| 검색·열람 | 카테고리/정렬/검색어로 결과 표시 | 새 등록 강제 갱신 방지, 결과 없음·빈 검색어·특수문자 처리 |

**지급 시점 한계:** 원문 p.123은 구매 완료 뒤 판매자에게 수수료 차감 금액을 전송한다고 쓰면서, 같은 쪽의 정산 규칙에서 판매자가 정산 버튼을 누르면 지급한다고도 쓴다. 자동 정산/수동 정산 어느 하나로 단정하지 말고, 프로젝트에서는 판매 대금의 상태와 지급 시점을 하나로 일관되게 정한 뒤 구매·정산·최대 보유 금액 예외에 같은 정의를 적용해야 한다.

### 4. 의도와 실제 규칙의 간극을 검토하고 보완한다

완성 뒤에는 “동작하는가”보다 “의도한 경험을 전달하는가”를 확인한다. 원문은 수수료 시점이 자금 부족으로 거래 이용을 막지 않는지, 지급 위치가 인벤토리 부족으로 수령을 막지 않는지, 실패 안내·시세·재고 정보가 투명한지, 제한이 정상 거래까지 과도하게 막지 않는지를 묻는다.

**플레이어에게 얼마나 설명할지:** 구현용 명세에는 필요한 조건·예외를 정의하되, 플레이어에게 모든 경우를 장황하게 나열하지 않는다. 기존 게임의 규칙과 이용 경험으로 예측 가능한 부분은 간결하게 쓰고, 오해하기 쉬운 적용 범위·판정 단위는 구체적으로 설명한다. 같은 ‘공격 시’ 효과도 지속 피해가 공격으로 취급되어 온 게임인지에 따라 추가 설명의 필요성이 달라진다. 설명의 밀도는 게임의 설계 방향과 플레이어의 기대에 맞춘다(책 126–127쪽 / PDF 128–129쪽).

## 주요 개념

- **설계 기준:** 기획 의도를 각 기능의 의사결정에 적용하기 위한 판단 기준.
- **지연 등록:** 등록을 즉시 노출하지 않고 검증 대기 상태를 거치는 보호 장치.
- **서버 기준 검증:** 화면의 오래된 표시가 아니라 실제 재고·잔액으로 확정하는 방식.
- **규칙 충돌:** 동시에 적용되는 규칙의 결과가 양립하지 않는 상태. 우선순위를 선언해야 한다.
- **행동 자유도:** 제한 안에서도 플레이어가 실험·선택할 수 있는 여지. 제한 해제와 동일하지 않다.

## 안티패턴

- **기능부터 만들기:** 의도 없이 제한을 붙이면 왜 필요한지 검토할 기준이 없고, 기능 대체 가능성도 놓친다.
- **사례 수치를 보편 규칙으로 복사하기:** 원문의 시간·건수·수수료·시세 범위는 거래소 사례일 뿐이다.
- **비슷한 규칙을 다르게 처리하고 이유를 숨기기:** 과거 행동 인정 여부가 퀘스트마다 다르면 플레이어는 규칙을 외워야 한다.
- **무제한과 과도한 제한 사이만 고르기:** 스킬 초기화처럼 비용 등 절제된 제한으로 실험 기회와 경제를 함께 다룰 수 있다.
- **충돌 우선순위 미정:** 넉백 중 이동 불가와 어떤 상태에서도 돌진 가능이 만날 때 어느 쪽이 우선인지 없으면 불신이 생긴다.
- **불투명한 손해:** 보상 분배처럼 실패·손해의 이유를 설명하지 않으면 학습이 아니라 억울함이 남는다.

## 작은 재구성 산출물

원문 절차를 거래소가 아닌 일반 기능 검토표로 재구성했다. 값은 **새 적용 예시**이며 원문 기본값이 아니다.

| 의도 | 기능 단위 | 성공 전 검증 | 실패 시 보존할 상태 | 플레이어 피드백 |
| --- | --- | --- | --- | --- |
| 신뢰 | 보상 수령 | 대상 존재, 수령 가능 상태, 동시 변경 여부 | 보상·재화의 중복/소실 없음 | 현재 실패 이유와 재시도 가능 조건 |
| 경제 | 교환 등록 | 대상 소유, 허용 범위, 등록 제한 | 원본 소유권·대기 상태 일관성 | 등록/대기/거부 상태와 근거 |
| 악용 방지 | 반복 요청 | 요청 유효성, 변경된 실제 상태 | 부당 이득 없음, 필요한 기록 | 일반 실패 안내(세부 탐지 기준은 노출하지 않음) |

## 실무 점검 항목

- [ ] “왜 이 기능인가, 왜 이 방식인가”를 한 문장 이상으로 적었는가?
- [ ] 설계 기준이 자원·신뢰·위험 중 어떤 의도를 지지하는지 연결했는가?
- [ ] 등록·변경·구매·취소·정산·검색처럼 서로 다른 책임을 분리했는가?
- [ ] 모든 단위에 입력, 실제 상태 재검증, 성공 처리, 실패 처리, 안내가 있는가?
- [ ] 제한값은 조정 주체·검토 근거와 함께 정의했는가?
- [ ] 동시 요청·서버 오류·대기 중 기준 변경·새로고침 상태를 점검했는가?
- [ ] 판매 대금의 생성, 보관, 지급 시점을 하나로 명세했는가? 원문 사례의 겹친 서술을 그대로 구현 결론으로 쓰지 않았는가?
- [ ] 규칙 충돌 시 우선순위와 플레이어가 알아야 할 설명을 정했는가?
- [ ] 플레이어용 설명은 오해하기 쉬운 지점을 짚으면서, 예측 가능한 경우까지 불필요하게 나열하지 않는가?
