# 11장: 데이터 테이블 설계

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 11장, 책 174–191쪽 / PDF 176–193쪽.  
> `EVENT_SANTA`, `LoginBonusID`, `MONTHLY` 등은 원문 출석부 사례의 명명 예시다. 특히 책 178쪽 / PDF 180쪽의 “서로 다른 출석부 3개”는 이 사례에서 **행이 출석부 자체를 의미하게 설계했을 때의 결과**이며, 모든 데이터 엔진의 불변 규칙으로 일반화하지 않는다.

## 핵심 관점

테이블 설계는 표 칸을 채우는 일이 아니라 게임 규칙을 데이터 구조로 바꾸는 일이다. 저자는 출석부를 통해 데이터 선별, 칼럼 나열, 객체 분리와 키 연결, 칼럼 네이밍·작동 규칙·사용 규칙, 가데이터 검증으로 이어지는 흐름을 보인다(장 로드맵, 책 175쪽 / PDF 177쪽). 이를 '무엇을 직접 관리할지 고르고 한 행의 의미를 고정한 뒤 반복을 분리해 키로 잇고 규칙을 쓰고 가데이터로 검증하는 흐름'으로 한 문장에 묶은 것은 스킬 정리다. 좋은 구조는 보기 좋음보다 한 객체를 명확히 다루고 변경·검증·협업을 쉽게 한다.

## 저자의 절차와 규칙

### 1. 시스템 책임에 따라 데이터를 선별한다

원문은 구현할 기능마다 기획자가 직접 관리해야 할 데이터를 표로 짝지어 고른다(책 176쪽 / PDF 178쪽). 출석부에서 직접 관리할 것은 기간, 회차별 보상, 이름·이미지 같은 메타·리소스 정보다. 보상 아이템의 이름·아이콘·등급·효과는 이미 아이템 테이블의 책임이므로 출석부에 복사하지 않고 아이템 ID를 참조한다(책 177쪽 / PDF 179쪽). 이 단계의 원칙은 **시스템과 직접 관련된 정보만 소유하고, 다른 시스템의 상세 정보는 외래 키로 참조한다**는 것이다(책 177쪽 / PDF 179쪽).

### 2. 완성된 기능을 칼럼으로 나열하되, 반복 구조를 발견한다

원문은 출석부 하나에 1~7일 보상과 수량을 모두 열로 두면 회차가 늘수록 가로가 과도하게 넓어진다고 지적한다. 30일 월간 출석부라면 보상·수량 2열×30일로 열이 60개 이상이 되고, 옆으로 스크롤하며 입력하다 실수하기 쉽다(책 178쪽 / PDF 180쪽). 반대로 회차마다 행을 만들면서 출석부 이름·기간·이미지를 반복하면, 원문은 표로는 출석부가 하나처럼 보여도 게임은 각 행을 독립된 출석부로 처리해 서로 다른 출석부 3개로 인식한다고 한다(책 178쪽 / PDF 180쪽). 이를 행이 출석부 자체를 의미하는 설계에서 생기는 **행 의미** 문제로 일반화하는 것은 스킬 해석이다.

### 3. 한 테이블에 한 객체를 두고, 반복은 별도 행으로 분리해 연결한다

| 테이블 | 한 행의 의미 | 핵심 열 | 관계 |
| --- | --- | --- | --- |
| 출석부 | 출석부 하나의 메타 정보 | 출석부 키, 제목 키, 시작/종료, 배너, 리셋 | 출석부 키를 보상 테이블이 참조 |
| 출석부 보상 | 특정 출석부의 특정 회차 보상 | 보상 키, 출석부 키, 회차, 보상 아이템 키, 수량 | 출석부·아이템 테이블을 참조 |
| 아이템 | 아이템 하나의 상세 정보 | 아이템 키, 이름/아이콘/등급 등 | 보상 테이블의 아이템 키가 참조 |
| 스트링 | 언어별 텍스트 하나 | 스트링 키, 언어별 값 | 제목·아이템 이름 키가 참조 |

ERD로 테이블·기본 키·외래 키를 선으로 그려 관계를 검토한다. 보상 테이블은 출석부 키와 아이템 키를 함께 참조해야 “어느 출석부의 어느 회차에 무엇을 얼마 지급하는가”가 정해진다. 모든 테이블에는 각 행을 고유하게 식별하는 기본 키가 있어야 하므로 출석부 보상 테이블에도 '출석부 보상 키'를 둔다(책 183쪽 / PDF 185쪽). 텍스트는 테이블에 직접 쓰지 않고 스트링 키만 넣는다. 그러면 언어별 텍스트 수정과 번역 누락·문자열 길이 제한 같은 문제를 한곳에서 관리할 수 있다(책 183쪽 / PDF 185쪽).

### 4. 이름, 자료형, 작동 규칙, 사용 규칙을 함께 명세한다

원문 사례의 열별 자료형은 출석부 키·제목 스트링 키·배너가 STRING, 시작일·종료일이 DATETIME, 리셋 주기가 ENUM이고, 보상 테이블은 출석부 키·보상 아이템 키가 STRING(각각 출석부·아이템 테이블 참조), 회차·수량이 INTEGER다(책 185–186쪽 / PDF 187–188쪽).

원문은 코드·도구 연동을 이유로 영문 칼럼명을 권장하고, 의미가 간결하게 전달되면 `CharNameStr` 같은 줄임말도 허용한다(책 184쪽 / PDF 186쪽). 기존 프로젝트에 명명·스키마·도구 규약이 있으면 그 규약과의 관계를 먼저 확인한다(스킬 정리). 대상이 드러나게 구체화하고, `Item1`처럼 번호 열이 과도해지면 칼럼 또는 테이블 분리를 고려한다(책 184쪽 / PDF 186쪽). 원문의 `LoginBonusID`, `RewardItemID`, `RewardCount`는 역할 중심 명명의 사례다. 각 칼럼에는 자료형과 의미를 쓰고, 필요한 입력 형식과 게임 동작을 덧붙인다. 자료형 정의와 작동 규칙 정의는 반드시 함께 한다(책 185쪽 / PDF 187쪽). 원문 출석부의 작동 규칙은 다음과 같다(책 185–186쪽 / PDF 187–188쪽).

- `StartDate`·`EndDate`: 연/월/일 형식. **기간 제한이 없는 출석부는 이 칸을 비워 둔다.** 최대 출석 횟수보다 운영 기간(시작일~종료일)이 긴 경우가 많다(예: 7일 출석부를 14일 동안 운영).
- `BannerResource`: `파일명.확장자`, 경로 `Assets/LoginBonusBanner/`.
- `Reset`: `MONTHLY` 매월 1일 0시 초기화, `WEEKLY` 매주 월요일 0시 초기화, `NONE` 초기화하지 않음(1회성 출석부).

이 값은 원문 사례의 규칙이다. 다른 프로젝트에 적용할 때 초기화 시각·시간대를 바꿀 수 있지만, 바꾼 값도 같은 방식으로 작동 규칙에 적는다.

여러 기획자가 함께 쓰는 테이블은 칼럼마다 **사용 규칙**도 명시한다. 원문 출석부의 사용 규칙은 다음과 같다(책 188쪽 / PDF 190쪽, 렌더 확인).

| 칼럼 | 원문 사용 규칙 |
| --- | --- |
| `LoginBonusID`, `LoginBonusRewardID` | 중복 불가, NULL(빈 값) 불가. 발번 `EVENT_이벤트명`, `EVENT_이벤트명_회차` |
| `TitleString` | 스트링 테이블에 키가 존재해야 함 |
| `StartDate` / `EndDate` | 시작일은 종료일보다 빨라야 하고 종료일은 시작일보다 늦어야 함 |
| `BannerResource` | 이미지 파일이 존재해야 함 |
| `Reset` | `MONTHLY`, `WEEKLY`, `NONE` 값만 입력 가능 |
| `LoginBonusID`(보상) / `RewardItemID` | 출석부 테이블·아이템 테이블에 키가 존재해야 함 |
| `Num` | 중복 불가, 0이나 NULL 불가 |
| `RewardCount` | 0이나 NULL 불가 |

`Num`의 "중복 불가"가 테이블 전체인지 같은 출석부 안인지는 원문이 밝히지 않는다. 출석부마다 1회차가 따로 있는 사례 구조와 함께 보면 업무상 중복 범위를 따로 정해야 하며, 이 점검은 SKILL.md의 적용 지침이다.

기본 키 발번 규칙도 정한다. 원문은 `EVENT_이벤트명`, `EVENT_이벤트명_회차` 같은 사례로 문자 기반 키의 협업 이점을 설명하며, 장점으로 이름만 봐도 데이터를 알 수 있음, 검색·필터가 쉬움, 접두어로 시스템 구분, 오타·중복 키 예방을 든다(책 187쪽 / PDF 189쪽). 원문은 아이템 키를 `ITEM_아이템종류_이름`처럼 발번하는 예도 들고, 실무에서 쓰이는 숫자 ID(예: 10111)는 어떤 항목인지 알기 어렵고 잘못 참조하거나 중복될 위험이 높아 기획자 중심의 관리가 필요한 테이블일수록 문자 기반 ID가 실용적이라고 한다(책 187쪽 / PDF 189쪽). 이를 모든 프로젝트에서 숫자 키를 금지하는 규칙으로 보지 않는다는 것은 스킬 해석이다.

### 5. 가데이터로 구조와 설명을 함께 검증한다

가데이터는 실제 입력 전에 구조가 충분한지, 칼럼 명세·참조가 맞는지, 개발자가 같은 의미로 읽는지 확인하는 데이터다. 원문은 모든 행에 해설을 붙일 필요 없이 2~5행 정도, 특히 의도가 애매하거나 조건이 걸린 데이터를 골라 해설하라고 한다(책 189쪽 / PDF 191쪽).

## 주요 개념

- **객체 단위:** 한 테이블의 한 행이 대표하는 대상. 출석부와 회차 보상은 서로 다른 객체다.
- **정규화에 가까운 분리:** 반복되는 고정 정보를 한 번만 두고 ID 참조로 연결하는 구조. 원문은 이 표현 대신 “하나의 객체”와 “반복 제거” 원칙으로 설명한다.
- **ERD:** 테이블과 키 관계를 시각화한 엔티티 관계도.
- **발번 규칙:** 기본 키에 용도·범위·순서를 반영하는 네이밍 약속.
- **가데이터:** 구조·작동·참조 관계를 검증하고 커뮤니케이션하는 시험 입력값.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **한 테이블에 모든 정보를 밀어넣기:** 회차 보상처럼 반복 데이터가 열로 늘어 유지 보수가 어려워진다.
- **상세 속성 중복:** 보상 테이블에 아이템 이름·아이콘·등급까지 재입력하면 수정 불일치가 생긴다.
- **관계 없는 분리:** 보상만 따로 두고 출석부 키가 없으면 어느 이벤트 소속인지 알 수 없다.
- **자료형만 있고 동작 규칙 없음:** `StartDate`, `Reset`, 리소스 값이 어떤 형식·시점·경로로 동작하는지 구현자가 추측하게 된다.
- **임의 ID와 가데이터 생략:** 중복·잘못된 참조·경계 날짜 같은 오류를 개발 뒤에 발견한다.

## 작은 재구성 산출물

원문의 출석부 관계를 ID·값을 바꾼 **새 적용 예시**로 축약했다. 이 ID는 원문 예제가 아니며 프로젝트 명명 규칙도 아니다.

```text
LoginEvent[PK: EVENT_SPRING]
  └─ LoginReward[PK: EVENT_SPRING_01, FK: LoginEventID=EVENT_SPRING,
                 Num=1, FK: RewardItemID=ITEM_TOKEN, RewardCount=3]
                                      └─ Item[PK: ITEM_TOKEN]
```

이 산출물은 한 이벤트가 여러 보상 행을 갖고, 각 보상은 기존 아이템 하나를 참조한다는 관계만 보인다. 기간·리셋·사용 규칙은 위 원문 사례 규칙을 출발점으로 쓰고, 프로젝트에서 바꾸는 값(시간대, 키의 문자/숫자 형태 등)은 바꾼 이유와 함께 명세한다.
