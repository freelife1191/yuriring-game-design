# 11장: 데이터 테이블 설계

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 11장, 책 p.174–191 (PDF p.176–193).  
> `EVENT_SANTA`, `LoginBonusID`, `MONTHLY` 등은 원문 출석부 사례의 명명 예시다. 특히 책 p.178/PDF p.180의 “서로 다른 출석부 3개”는 이 사례에서 **행이 출석부 자체를 의미하게 설계했을 때의 결과**이며, 모든 데이터 엔진의 불변 규칙으로 일반화하지 않는다.

## 핵심 관점

테이블 설계는 표 칸을 채우는 일이 아니라 게임 규칙을 데이터 구조로 바꾸는 일이다. 저자는 출석부를 통해 “무엇을 직접 관리할지 고르고, 한 행이 무엇을 뜻하는지 고정하고, 반복되는 정보를 분리해 키로 연결하고, 각 칼럼의 입력·동작·검증 규칙을 쓰고, 가데이터로 관계를 검증하는” 흐름을 제시한다. 좋은 구조는 보기 좋음보다 한 객체를 명확히 다루고 변경·검증·협업을 쉽게 한다.

## 저자의 절차와 규칙

### 1. 시스템 책임에 따라 데이터를 선별한다

출석부에서 직접 관리할 것은 기간, 회차별 보상, 이름·이미지 같은 메타·리소스 정보다. 보상 아이템의 이름·아이콘·등급·효과는 이미 아이템 테이블의 책임이므로 출석부에 복사하지 않고 아이템 ID를 참조한다. 이 단계의 원칙은 **시스템과 직접 관련된 정보만 소유하고, 다른 시스템의 상세 정보는 외래 키로 참조한다**는 것이다.

### 2. 완성된 기능을 칼럼으로 나열하되, 반복 구조를 발견한다

원문은 출석부 하나에 1~7일 보상과 수량을 모두 열로 두면 회차가 늘수록 가로가 과도하게 넓어진다고 지적한다. 반대로 회차마다 행을 만들면서 출석부 이름·기간·이미지를 반복하면, 그 행이 출석부라는 의미를 갖는 설계에서는 한 출석부가 여러 독립 행으로 해석된다. 이는 원문 사례의 **행 의미** 문제다.

### 3. 한 테이블에 한 객체를 두고, 반복은 별도 행으로 분리해 연결한다

| 테이블 | 한 행의 의미 | 핵심 열 | 관계 |
| --- | --- | --- | --- |
| 출석부 | 출석부 하나의 메타 정보 | 출석부 키, 제목 키, 시작/종료, 배너, 리셋 | 출석부 키를 보상 테이블이 참조 |
| 출석부 보상 | 특정 출석부의 특정 회차 보상 | 보상 키, 출석부 키, 회차, 보상 아이템 키, 수량 | 출석부·아이템 테이블을 참조 |
| 아이템 | 아이템 하나의 상세 정보 | 아이템 키, 이름/아이콘/등급 등 | 보상 테이블의 아이템 키가 참조 |
| 스트링 | 언어별 텍스트 하나 | 스트링 키, 언어별 값 | 제목·아이템 이름 키가 참조 |

ERD로 테이블·기본 키·외래 키를 선으로 그려 관계를 검토한다. 보상 테이블은 출석부 키와 아이템 키를 함께 참조해야 “어느 출석부의 어느 회차에 무엇을 얼마 지급하는가”가 정해진다.

### 4. 이름, 자료형, 작동 규칙, 사용 규칙을 함께 명세한다

원문은 코드·도구 연동을 이유로 영문 칼럼명을 권장한다(책 184쪽 / PDF 186쪽). 실제 적용은 기존 프로젝트의 명명·스키마·도구 규약을 우선한다. 대상이 드러나게 구체화하고, `Item1`처럼 번호 열이 과도해지면 테이블 분리를 검토한다. 원문의 `LoginBonusID`, `RewardItemID`, `RewardCount`는 역할 중심 명명의 사례다. 각 칼럼에는 자료형과 의미를 쓰고, 필요한 입력 형식과 게임 동작을 덧붙인다. 원문의 배너에는 파일명·확장자·리소스 경로를, 리셋 ENUM에는 초기화 시각을 적는다.

기본 키 발번 규칙도 정한다. 원문은 `EVENT_이벤트명`, `EVENT_이벤트명_회차` 같은 사례로 사람이 읽고 검색할 수 있는 문자 기반 키의 협업 이점을 설명한다. 이는 모든 프로젝트에 숫자 키를 금지한다는 뜻이 아니라, 기획 중심 관리에서 오타·중복·참조 실수를 줄이는 한 방법이다.

### 5. 가데이터로 구조와 설명을 함께 검증한다

가데이터는 실제 입력 전에 구조가 충분한지, 칼럼 명세·참조가 맞는지, 개발자가 같은 의미로 읽는지 확인하는 데이터다. 모든 행에 장문 주석을 달기보다 원문처럼 2~5개, 특히 조건이 모호한 행을 골라 해설한다.

## 주요 개념

- **객체 단위:** 한 테이블의 한 행이 대표하는 대상. 출석부와 회차 보상은 서로 다른 객체다.
- **정규화에 가까운 분리:** 반복되는 고정 정보를 한 번만 두고 ID 참조로 연결하는 구조. 원문은 이 표현 대신 “하나의 객체”와 “반복 제거” 원칙으로 설명한다.
- **ERD:** 테이블과 키 관계를 시각화한 엔티티 관계도.
- **발번 규칙:** 기본 키에 용도·범위·순서를 반영하는 네이밍 약속.
- **가데이터:** 구조·작동·참조 관계를 검증하고 커뮤니케이션하는 시험 입력값.

## 안티패턴

- **한 테이블에 모든 정보를 밀어넣기:** 회차 보상처럼 반복 데이터가 열로 늘어 유지 보수가 어려워진다.
- **상세 속성 중복:** 보상 테이블에 아이템 이름·아이콘·등급까지 재입력하면 수정 불일치가 생긴다.
- **관계 없는 분리:** 보상만 따로 두고 출석부 키가 없으면 어느 이벤트 소속인지 알 수 없다.
- **자료형만 있고 동작 규칙 없음:** `StartDate`, `Reset`, 리소스 값이 어떤 형식·시점·경로로 동작하는지 구현자가 추측하게 된다.
- **임의 ID와 가데이터 생략:** 중복·잘못된 참조·경계 날짜 같은 오류를 개발 뒤에 발견한다.

## 작은 재구성 산출물

원문의 출석부 관계를 ID·값을 바꾼 **새 적용 예시**로 축약했다. 이 ID는 원문 예제가 아니며 프로젝트 명명 규칙도 아니다.

```text
LoginEvent[PK: EVENT_SPRING]
  └─ LoginReward[PK: EVENT_SPRING_01, FK: LoginEventID=EVENT_SPRING,
                 Num=1, FK: RewardItemID=ITEM_TOKEN, RewardCount=3]
                                      └─ Item[PK: ITEM_TOKEN]
```

이 산출물은 한 이벤트가 여러 보상 행을 갖고, 각 보상은 기존 아이템 하나를 참조한다는 관계만 보인다. 기간 제한 없음, 종료 시각, 리셋 방식, 키의 문자/숫자 형태는 프로젝트 명세에서 별도로 결정해야 한다.

## 실무 점검 항목

- [ ] 각 테이블의 한 행이 표현하는 객체를 한 문장으로 말할 수 있는가?
- [ ] 다른 시스템이 이미 소유한 이름·아이콘·설명·성능을 복사하지 않고 키로 참조하는가?
- [ ] 반복되는 열 또는 반복되는 메타 정보가 테이블 분리 신호인지 검토했는가?
- [ ] 모든 기본 키의 중복·빈값 금지와 발번 규칙이 있는가?
- [ ] 외래 키마다 대상 테이블·칼럼과 존재 조건이 명시되었는가?
- [ ] 칼럼명, 자료형, 입력 형식, 실제 작동, 사용 규칙을 함께 적었는가?
- [ ] ERD가 참조 관계를 빠짐없이 나타내는가?
- [ ] 가데이터와 2~5개의 설명 행으로 날짜·리셋·참조·경계 사례를 검증했는가?
