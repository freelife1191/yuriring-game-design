# 10장: 데이터 테이블이란 무엇인가?

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 10장, 책 156–173쪽 / PDF 158–175쪽.  
> 원문은 하드코딩 비교를 설명하기 위해 코드 조각을 보이나, 이 문서는 책의 코드 예제를 재현하지 않는다. 테이블 형식(CSV/JSON/XML)과 특정 동작은 프로젝트 구현에 따라 달라진다.

## 핵심 관점

데이터 테이블은 보기 좋은 기획서 표가 아니라, 게임이 읽어 실제로 작동하는 데이터 구조이며 코드와 맺는 약속이다. 캐릭터 능력치, 가격, 퀘스트 조건처럼 자주 조정되는 값을 코드 밖에서 관리하면 기획·운영이 값 수정에 참여하고, 밸런스·이벤트 대응을 빠르게 할 수 있다. 빌드나 클라이언트 재다운로드 없이 수정 사항을 반영할 수 있어 라이브 서비스에서 특히 유리하며, 원문은 이 밖에 기획자·운영자의 직접 수정, 재사용성·확장성, 실수 원인 추적, 자동화·도구 연동을 이점으로 든다(책 161쪽 / PDF 163쪽). 다만 테이블은 만능이 아니다. 원문은 테이블이 정적인 수치·문자열·조건식에 강한 반면 복잡한 타이밍 조절이나 공간 좌표, 연출 시퀀스에는 적합하지 않다고 한다(책 162쪽 / PDF 164쪽).

## 저자의 절차와 규칙

### 1. 먼저 테이블화할 가치가 있는 데이터를 선별한다

| 관리 방식 | 적합한 원문 사례 | 판단 기준 |
| --- | --- | --- |
| 데이터 테이블 | 직업/레벨별 능력치, 가격, 조건, 이벤트 값 | 반복적으로 조정·추가·검증하며 여러 담당자가 관리할 값 |
| 코드 상수 | 고정되어 있고 향후 변경 가능성도 없는 값(원문의 전투 참가 캐릭터 수 6개 사례, 책 163쪽 / PDF 165쪽) | 테이블화의 초기 비용이 하드코딩보다 클 수 있으므로 필요한 데이터만 선별한다 |
| 전용 도구 | 사용 로직이 복잡하거나 시점·상황별로 분기하는 보스 스킬(Behavior Tree·FSM 같은 AI 도구), 몬스터·채집물 좌표(레벨 에디터), 프레임 단위 정확도가 필요한 애니메이션·카메라·사운드 타이밍(시퀀스 도구) | 시간·공간·복잡한 분기를 정밀하게 제어해야 하는 값(책 162쪽 / PDF 164쪽) |

테이블 제작은 원문의 네 단계를 거친다(책 162–163쪽 / PDF 164–165쪽). **기획 단계**에서 관리할 기획 데이터와 항목을 정하고 각 칼럼의 의미·자료형·작동 규칙·테이블 간 관계를 설계한다. **제작 단계**에서 스프레드시트로 작성하고 CSV·JSON·XML 포맷으로 변환해 개발 환경에 맞게 준비한다. **구현 단계**에서 각 속성이 게임에서 어떻게 동작할지 프로그래머와 약속하고 연동 규칙을 구현한다. **사용 단계**에서 규격에 맞는 데이터를 유지 보수하고 실제 로직과 맞춰 테스트한다. 파일에 값을 넣는 것만으로 자동 반영된다고 가정하지 않는 것이 핵심이다. 테이블화에는 하드코딩보다 큰 초기 비용이 들 수 있으므로 필요한 데이터를 선별한다(책 163쪽 / PDF 165쪽).

### 2. 행·열·키·자료형을 작동 규칙으로 정의한다

- **열(속성):** 같은 종류의 값을 담는 세로 단위다. 설계의 핵심은 각 열 값이 게임에서 어떻게 쓰이는지 정하는 일이다.
- **행(레코드):** 하나의 캐릭터·아이템·퀘스트처럼 한 데이터 덩어리를 뜻한다.
- **필드:** 행과 열이 만나는 한 셀이다.
- **기본 키(Primary Key):** 각 행의 주소다. 저자는 기본 키 설계에서 반드시 지켜야 할 원칙으로 ① 한 테이블 안에서 기본 키 값은 중복되면 안 되고 ② 기본 키 칼럼은 비워 두면 안 되며 ③ 각 테이블에는 반드시 하나의 기본 키 칼럼이 있어야 한다는 세 가지를 든다(책 166쪽 / PDF 168쪽). 기본 키가 있으면 오류가 난 행을 정확히 특정할 수 있고, 같은 아이템도 기간 한정·패키지·주간 상점처럼 조건과 가격이 다르게 팔리므로 아이템 ID가 아닌 상품 ID 단위로 판매 지표를 봐야 운영 판단이 가능하다(책 166쪽 / PDF 168쪽). 기존 프로젝트가 복합 키 같은 다른 스키마 규약을 쓰고 있다면 그 규약과의 관계는 프로젝트에서 확인한다(스킬 정리).
- **외래 키(Foreign Key):** 다른 테이블 기본 키를 가리키는 참조다. 요리 테이블은 재료의 이름·아이콘을 복사하지 않고 재료 ID를 참조한다. 참조 대상 테이블과 칼럼을 명시하고, 존재하지 않는 값을 넣지 않는다(책 167–168쪽 / PDF 169–170쪽).

| 자료형 | 원문의 용도와 설명 | 스킬 점검 포인트 |
| --- | --- | --- |
| INTEGER | 레벨, 체력, 가격 | 정수 범위와 0 허용 여부 |
| FLOAT | 드롭 확률, 스킬 계수. 소수점 7자리까지의 수이며, 원문은 보통 INT를 쓰고 백분율·천분율·만분율로 환산하는 경우가 더 많다고 한다. | 소수 사용 여부와 정수 환산 단위 |
| BOOLEAN | 콘텐츠 사용 가능 여부, TRUE(1)/FALSE(0)만 사용 | 두 값의 의미 |
| STRING | 스트링 키, 이름, 리소스 파일명. 메모리를 가장 많이 쓰므로 숫자만 쓸 칼럼이면 INT를 쓴다. | 문자 사용 필요성, 형식·길이 |
| DATETIME | 이벤트 시작/종료, `YYYY-MM-DD HH:MM:SS`. STRING으로 두고 코드에서 환산하기도 한다. | 입력 형식과 시간 경계 |
| ENUM | 속성, 캐릭터 타입, 스킬 분류. 사용할 목록과 각 값의 동작을 함께 정의한다(예: 출석 리셋 `MONTHLY` 매월 1일·`WEEKLY` 매주 월요일·`NONE`, 아이템 등급별 아이콘 배경색). 선택의 폭이 넓지 않으면 STRING으로 대체할 수 있다. | 허용 목록과 각 값의 게임 동작 |

자료형 근거: 책 168–169쪽 / PDF 170–171쪽. 원문은 자료형을 적절하게 설계하지 않으면 게임 실행 시 PC 메모리를 과도하게 차지해 처리 속도가 느려지고, 유지 보수 때 검증·수정 작업에 더 많은 시간이 든다고 한다(책 169쪽 / PDF 171쪽). 표의 셋째 열은 스킬이 덧붙인 점검 항목이다.

### 3. 분리·통합은 관리와 변경의 맥락으로 판단한다

직업과 레벨을 하나의 테이블로 관리할지 별도로 나눌지에 절대적인 정답은 없다. **사용 빈도·업데이트 빈도·수정 범위·재사용성**을 비교하고, 현재 프로젝트에서 선택한 구조의 이유를 설명한다(책 172쪽 / PDF 174쪽). 값 목록만 정하는 데서 멈추지 않고 언제 어떻게 작동하는지도 명세한다. 원문의 월간 패키지 사례는 매월 수동으로 상품을 새로 등록하게 설계한 탓에 1일이 일요일이던 날 담당 운영 직원이 패키지 갱신을 위해 휴일에 출근해야 했던 일을 들며, 구매 횟수의 월 단위 초기화 규칙이 설계에 빠진 문제를 보여 준다(책 171쪽 / PDF 173쪽). 저자는 테이블 구현은 프로그래머가 맡아도 어떤 데이터를 어떤 구조로 설계할지는 기획자의 영역이며, '무슨 데이터가 필요한가'만이 아니라 '그 데이터가 언제, 어떻게 동작해야 하는가'까지 기획자가 정의해야 한다고 강조한다(책 171쪽 / PDF 173쪽). 설계가 어렵게 느껴질 때는 저자가 제시한 생각 순서를 따른다. 어떤 데이터를 게임에 넣고 싶은가 → 그 데이터에 어떤 속성이 필요한가 → 데이터가 어떤 규칙으로 동작하는가 → 나중에 수정하기 쉬운 구조인가(책 172쪽 / PDF 174쪽). 월간 초기화의 시간대처럼 원문이 정하지 않은 세부 기준은 현재 프로젝트에서 별도로 정한다.

## 주요 개념

- **하드코딩:** 데이터를 소스 코드에 직접 입력하는 방식. 수정 시 코드 변경·빌드/재시작이 필요할 수 있다.
- **기획 데이터:** 게임의 동작 원칙을 정하는 데이터(예: 전사 레벨 3의 공격력).
- **플레이어 데이터:** 플레이 중 생성·저장되는 개인 상태(예: 특정 플레이어의 현재 경험치·장착 장비). 기획 데이터와 구분한다(책 171–172쪽 / PDF 173–174쪽).
- **참조 무결성(스킬 용어):** 외래 키가 실제 대상 키를 가리키는 상태. 원문은 존재하지 않는 재료 값 입력을 금지하는 예로 설명한다.
- **작동 규칙:** 칼럼 값을 게임이 어떤 방식으로 읽고 적용할지에 대한 약속.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **표를 발표 자료처럼 꾸미기:** 원문은 셀 병합·구분선 같은 장식을 CSV/JSON 변환 때 병합 셀 아래가 빈 값이 되거나 데이터가 한 칸씩 밀릴 수 있으므로 절대 해서는 안 된다고 한다(책 170쪽 / PDF 172쪽).
- **모든 값을 테이블화하기:** 전용 도구가 더 적합하거나 상수인 값을 표에 넣으면 복잡성과 초기 구현 비용만 늘어난다.
- **키 없는 행:** 오류와 로그의 대상을 정확히 찾을 수 없고 참조도 불안정해진다.
- **외래 키에 임의 텍스트 입력:** 참조 대상에 없는 값은 연결을 끊는다.
- **자료형 이름만 정하기:** ENUM의 허용값·행동을 적지 않거나 날짜 경계를 모호하게 두면 구현마다 다른 해석이 나온다.
- **플레이어 상태를 기획 테이블에 넣기:** 개인 저장값과 설계값의 수정 주체·수명·저장 방식이 다르다.

## 작은 재구성 산출물

원문의 재료–요리 참조 예시를 구조만 남겨 재구성했다. ID와 값은 **새 적용 예시**다.

| 재료 테이블 (기본 키) | 이름 키 | 아이콘 |
| --- | --- | --- |
| `MAT_HERB` | `NAME_HERB` | `ICON_HERB` |

| 제작 테이블 (기본 키) | 재료 ID (외래 키) | 수량 |
| --- | --- | --- |
| `CRAFT_TONIC` | `MAT_HERB` | 2 |

이 구조에서 이름·아이콘 변경은 재료 테이블 한 곳에서 하고, 제작 테이블은 필요한 대상과 수량만 가진다. 단, 실제 테이블명·ID 규칙·파일 포맷은 프로젝트에서 별도로 합의해야 한다.

## 실무 점검 항목

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- [ ] 값이 자주 조정·추가·검증되는가, 아니면 코드/전용 도구가 더 적합한가?
- [ ] 각 행이 어떤 대상 하나를 의미하는지, 각 열이 어떤 값을 의미하는지 설명 가능한가?
- [ ] 기본 키가 중복·빈값 없이 각 행을 식별하는가?
- [ ] 외래 키마다 참조할 테이블·칼럼과 존재 검증 규칙이 있는가?
- [ ] 자료형뿐 아니라 입력 범위·NULL/빈값·ENUM 목록·시간 경계를 적었는가?
- [ ] 칼럼값이 게임에서 반영되는 구현 약속과 테스트 경로가 있는가?
- [ ] 기획 데이터와 플레이어 저장 데이터를 분리했는가?
- [ ] 테이블 분리·통합의 이유를 사용·업데이트 빈도, 수정 범위, 재사용성으로 설명할 수 있는가?
