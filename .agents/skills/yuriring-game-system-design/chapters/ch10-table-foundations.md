# 10장: 데이터 테이블이란 무엇인가?

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 10장, 책 p.156–173 (PDF p.158–175).  
> 원문은 하드코딩 비교를 설명하기 위해 코드 조각을 보이나, 이 문서는 책의 코드 예제를 재현하지 않는다. 테이블 형식(CSV/JSON/XML)과 특정 동작은 프로젝트 구현에 따라 달라진다.

## 핵심 관점

데이터 테이블은 보기 좋은 기획서 표가 아니라, 게임이 읽어 실제로 작동하는 데이터 구조이며 코드와 맺는 약속이다. 캐릭터 능력치, 가격, 퀘스트 조건처럼 자주 조정되는 값을 코드 밖에서 관리하면 기획·운영이 값 수정에 참여하고, 밸런스·이벤트 대응을 빠르게 할 수 있다. 다만 테이블은 만능이 아니다. 정적인 수치·문자열·조건식에 강할 뿐, 정밀 타이밍·공간 배치·복잡한 AI 흐름에는 적합하지 않을 수 있다.

## 저자의 절차와 규칙

### 1. 먼저 테이블화할 가치가 있는 데이터를 선별한다

| 관리 방식 | 적합한 원문 사례 | 판단 기준 |
| --- | --- | --- |
| 데이터 테이블 | 직업/레벨별 능력치, 가격, 조건, 이벤트 값 | 반복적으로 조정·추가·검증하며 여러 담당자가 관리할 값 |
| 코드 상수 | 바뀔 가능성이 없는 고정값(원문의 전투 참가 캐릭터 수 6개 사례) | 변경 가능성과 운영 가치가 낮아 초기 테이블 비용이 더 큰 값 |
| 전용 도구 | 복잡한 보스 스킬 타이밍, 몬스터·채집물 좌표, 애니메이션·카메라·사운드 타이밍 | 시간·공간·복잡한 분기를 정밀하게 제어해야 하는 값 |

테이블로 관리하기로 했다면 다음 순서로 진행한다. (1) 관리할 기획 데이터와 항목을 정한다. (2) 각 칼럼의 의미, 자료형, 작동 규칙, 테이블 간 관계를 설계한다. (3) 스프레드시트로 작성하고, (4) 프로그래머와 각 속성이 게임에서 작동하는 연동 규칙을 약속·구현한다. (5) 규격에 맞는 데이터를 유지 보수하고 실제 로직과 맞춰 테스트한다. 파일에 값을 넣는 것만으로 자동 반영된다고 가정하지 않는 것이 핵심이다.

### 2. 행·열·키·자료형을 작동 규칙으로 정의한다

- **열(속성):** 같은 종류의 값을 담는 세로 단위다. 설계의 핵심은 각 열 값이 게임에서 어떻게 쓰이는지 정하는 일이다.
- **행(레코드):** 하나의 캐릭터·아이템·퀘스트처럼 한 데이터 덩어리를 뜻한다.
- **필드:** 행과 열이 만나는 한 셀이다.
- **기본 키(Primary Key):** 각 행의 주소다. 원문은 기획 테이블 사례에서 중복·빈값이 없는 **단일 ID 기준 칼럼**을 둔다고 설명하며, 이를 통해 오류 위치와 판매 지표를 특정한다. 이는 책의 예시 방식이며, 실제 프로젝트의 복합 키·스키마 선택을 이 문장만으로 배제하지 않는다.
- **외래 키(Foreign Key):** 다른 테이블 기본 키를 가리키는 참조다. 요리 테이블은 재료의 이름·아이콘을 복사하지 않고 재료 ID를 참조한다. 참조 대상 테이블과 칼럼을 명시하고, 존재하지 않는 값을 넣지 않는다.

| 자료형 | 원문의 용도 | 설계 시 명시할 점 |
| --- | --- | --- |
| INTEGER | 레벨, 체력, 가격 | 정수 범위와 0 허용 여부 |
| FLOAT | 드롭 확률, 스킬 계수 | 소수 사용 여부와, 정수 환산 단위 사용 여부 |
| BOOLEAN | 콘텐츠 사용 가능 여부 | TRUE/FALSE 두 값의 의미 |
| STRING | 스트링 키, 이름, 리소스 파일명 | 문자 사용 필요성, 형식·길이 |
| DATETIME | 이벤트 시작/종료 | 입력 형식과 시간 경계 |
| ENUM | 속성, 등급, 스킬 분류 | 허용 목록과 각 값의 게임 동작 |

### 3. 분리·통합은 관리와 변경의 맥락으로 판단한다

직업과 레벨을 하나의 테이블로 관리할지 별도로 나눌지에 절대적인 정답은 없다. **사용 빈도·업데이트 빈도·수정 범위·재사용성**을 비교하고, 현재 프로젝트에서 선택한 구조의 이유를 설명한다(책 172쪽 / PDF 174쪽). 값 목록만 정하는 데서 멈추지 않고 언제 어떻게 작동하는지도 명세한다. 원문의 월간 패키지 사례는 매월 수동으로 상품을 새로 등록한 결과 운영 작업이 발생했으며, 구매 횟수의 월 단위 초기화 규칙이 설계에 빠진 문제를 보여 준다(책 171쪽 / PDF 173쪽). 자동 초기화의 구체적인 기준 시각·시간대는 현재 프로젝트에서 별도로 정한다.

## 주요 개념

- **하드코딩:** 데이터를 소스 코드에 직접 입력하는 방식. 수정 시 코드 변경·빌드/재시작이 필요할 수 있다.
- **기획 데이터:** 게임의 동작 원칙을 정하는 데이터(예: 전사 레벨 3의 공격력).
- **플레이어 데이터:** 플레이 중 생성·저장되는 개인 상태(예: 특정 플레이어의 현재 경험치·장착 장비). 기획 데이터와 구분한다.
- **참조 무결성:** 외래 키가 실제 대상 키를 가리키는 상태. 원문은 존재하지 않는 재료 값 입력을 금지하는 예로 설명한다.
- **작동 규칙:** 칼럼 값을 게임이 어떤 방식으로 읽고 적용할지에 대한 약속.

## 안티패턴

- **표를 발표 자료처럼 꾸미기:** 셀 병합·장식은 CSV/JSON 변환 때 빈 값·열 밀림을 만들 수 있다.
- **모든 값을 테이블화하기:** 전용 도구가 더 적합하거나 상수인 값을 표에 넣으면 복잡성과 초기 구현 비용만 늘어난다.
- **키 없는 행:** 오류와 로그의 대상을 정확히 찾을 수 없고 참조도 불안정해진다.
- **외래 키에 임의 텍스트 입력:** 참조 대상에 없는 값은 연결을 끊는다.
- **자료형을 이름만 정하기:** ENUM의 허용값·행동을 적지 않거나 날짜 경계를 모호하게 두면 구현마다 다른 해석이 나온다.
- **플레이어 상태를 기획 테이블에 넣기:** 개인 저장값과 설계값의 수정 주체·수명·저장 방식이 다르다.

## 작은 재구성 산출물

원문의 재료–요리 참조 예시를 구조만 남겨 재구성했다. ID와 값은 **새 적용 예시**다.

| 재료 테이블 (기본 키) | 이름 키 | 아이콘 |
| --- | --- | --- |
| `MAT_HERB` | `NAME_HERB` | `ICON_HERB` |

| 제작 테이블 (기본 키) | 재료 ID (외래 키) | 수량 |
| --- | --- | --- |
| `CRAFT_TONIC` | `MAT_HERB` | 2 |

이 구조에서 이름·아이콘 변경은 재료 테이블 한 곳에서 하고, 제작 테이블은 필요한 대상과 수량만 가진다. 단, 실제 테이블명·ID 규칙·파일 포맷은 프로젝트에서 별도로 합의해야 한다.

## 실무 점검 항목

- [ ] 값이 자주 조정·추가·검증되는가, 아니면 코드/전용 도구가 더 적합한가?
- [ ] 각 행이 무엇 하나를 의미하는지, 각 열이 어떤 값을 의미하는지 설명 가능한가?
- [ ] 기본 키가 중복·빈값 없이 각 행을 식별하는가?
- [ ] 외래 키마다 참조할 테이블·칼럼과 존재 검증 규칙이 있는가?
- [ ] 자료형뿐 아니라 입력 범위·NULL/빈값·ENUM 목록·시간 경계를 적었는가?
- [ ] 칼럼값이 게임에서 반영되는 구현 약속과 테스트 경로가 있는가?
- [ ] 기획 데이터와 플레이어 저장 데이터를 분리했는가?
- [ ] 테이블 분리·통합의 이유를 사용·업데이트 빈도, 수정 범위, 재사용성으로 설명할 수 있는가?
