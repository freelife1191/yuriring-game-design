# 09장: 규칙의 도식화

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 9장, 책 p.132–155 (PDF p.134–157).  
> 원문 도식의 숫자·세부 표기는 OCR 훼손 가능성이 있어, 아래는 흐름의 의미를 짧게 재구성했다. 154쪽 연습문제의 성공 확률·실패 포인트 등은 연습 조건이며 프로젝트 기본값이 아니다.

## 핵심 관점

플로 차트는 화면 이동도, 코드의 복사본도, 플레이어 감정선도 아니다. 저자가 말하는 목적은 **어떤 상황에서 어떤 조건을 판단하고 어떤 처리를 거쳐 어떤 결과를 내는지**를 팀이 동일하게 읽게 하는 것이다. 자연어는 조건의 대상·순서·우선순위를 생략하기 쉽고, 플로 차트는 그 빈칸을 분기와 화살표로 드러낸다. 따라서 좋은 플로 차트는 규칙의 핵심 로직을 압축하고, 상세한 값·문구·근거는 텍스트 명세가 맡는다.

## 저자의 절차와 규칙

### 1. “그려야 할 흐름”을 먼저 고른다

조건 판정이 중요하거나 예외가 많은 흐름은 플로 차트 대상이다. 한 방향으로 단순히 나열되는 작업은 텍스트가 더 낫다. 예를 들어 거래소 구매의 재고·소지금·동시 구매는 분기와 예외가 있어 도식화 가치가 크다. 반대로 로비에서 여러 화면으로 들어가는 모든 UI 이동을 붙이면 핵심 조건이 묻힌다.

### 2. 차트 전에 범위와 텍스트 흐름을 정리한다

1. **대상과 목적을 쓴다.** “무엇을 설명하는가”, “왜 도식화하는가”를 먼저 정한다. 원문은 거래소 구매의 재고 충돌 방지용 서버 처리 흐름을 예로 든다.
2. **정상 흐름을 텍스트로 나열한다.** 입력 → 재고 확인 → 소지금 확인 → 거래 완료처럼 먼저 논리를 검토한다. 그림부터 그리면 누락과 혼동이 커진다.
3. **입력·처리·판단·출력을 구분한다.** 버튼 클릭은 입력, 재고/소지금 확인은 판단, 차감·지급은 처리, 팝업은 출력이다.
4. **기호와 레이아웃을 적용한다.** 위에서 아래로 읽히게 배치하고, 반복은 되돌아가는 화살표로 명확히 한다.
5. **예외를 붙이고 가독성을 검수한다.** 서버 오류, 재고 부족, 중복 요청 같은 실패 경로도 끝까지 닫는다. 같은 기호·색·박스 크기, 겹치지 않는 화살표, 명시된 분기 라벨을 확인한다.

| 기호/역할 | 사용할 때 | 피해야 할 혼동 |
| --- | --- | --- |
| 시작/종료 | 프로세스의 경계를 표시 | 어디서 읽고 어디서 끝나는지 생략 |
| 입력 | 플레이어의 클릭·명령·값 입력 | 시스템 내부 처리와 혼합 |
| 출력 | 결과·안내를 사용자에게 표시 | 실패 처리 없이 팝업만 둠 |
| 처리 | 저장·차감·지급·상태 갱신 | 코드 변수/디버그 세부 사항을 전부 나열 |
| 비교/판단 | 조건에 따라 갈래가 나뉨 | YES/NO의 대상이나 우선순위 생략 |
| 다른 프로세스 연결 | 공통 하위 절차로 분리 | 같은 긴 절차를 여러 차트에 복제 |

### 3. 공통 효과는 스킬마다 반복해서 그리지 않는다

턴제 RPG 사례에서 저자는 ‘운명 조작’이라는 개별 스킬 자체보다 공통 효과인 불사·수면의 규칙을 분리해 도식화한다. 같은 효과를 다른 스킬도 사용할 수 있기 때문이다. 불사는 치명 피해 시 효과 보유 여부를 확인하여 HP 회복, 상태 제거, 쿨타임 초기화, 연출, 1회 효과 해제 또는 일반 사망으로 갈린다. 수면은 행동 불가, 피해 시 해제, 턴 경과에 따른 지속 턴 감소·자동 해제로 구성된다. 이처럼 공통 규칙을 효과 단위로 두면 같은 로직의 중복 명세와 리밸런싱 누락을 줄인다.

## 주요 개념

- **프로세스:** 결과뿐 아니라 결과까지 도달하는 조건·처리 순서 자체.
- **분기:** 비교/판단 결과에 따라 서로 다른 처리를 타는 지점.
- **서브 프로세스:** 반복되거나 공통인 절차를 별도로 관리해 연결하는 흐름.
- **완결성:** 승패 판정 뒤 전투 동작 중지, 결과 UI·연출처럼 결과 이후의 필요한 처리를 닫는 성질.
- **효과 단위 설계:** 개별 스킬이 아닌 재사용 가능한 효과의 작동 규칙을 한 곳에 두는 방식.

## 안티패턴

- **심리를 조건으로 넣기:** “좋은 장비를 얻었는가 → 강화한다”는 시스템이 감정을 판정하는 것처럼 보인다. 행동·입력·시스템 상태만 다룬다.
- **모든 UI 흐름을 넣기:** 로비부터 모든 메뉴를 그리면 강화 조건 같은 핵심 로직이 사라진다.
- **실제 코드와 1:1로 쓰기:** 변수 선언, 내부 초기화, 디버그 세부는 기획 의도 전달을 흐린다.
- **차트만 제공하기:** 박스 안에 확률, 문구, 테이블 참조, 우선순위를 억지로 넣지 말고 텍스트 명세를 병행한다.
- **YES만 그리기:** 파티 초대 거절, 동시 처치, 매칭 실패처럼 실패·동시 상태를 빼면 예외가 구현 밖으로 밀린다.

## 작은 재구성 산출물

원문의 거래소 구매 도식을 의미 단위로 재구성했다. 실제 가격·재고·지급 정책은 정하지 않는다.

```text
시작 → [입력: 구매 요청]
      → ◇ 실제 재고가 남았는가?
        ├─ 아니오 → [출력: 판매 완료 안내] → 종료
        └─ 예 → ◇ 실제 소지금이 충분한가?
              ├─ 아니오 → [출력: 소지금 부족 안내] → 종료
              └─ 예 → [처리: 거래 확정에 필요한 상태 변경]
                    → [출력: 완료 안내] → 종료
```

원문의 3매치 사례는 “이동 → 매칭 판정 → 실패면 원위치 복귀, 성공이면 파괴·특수 블록·낙하 → 추가 매칭이면 반복”처럼 루프의 종료 조건을 반드시 그려야 함을 보인다. 승패 판정 사례는 양쪽 동시 파괴처럼 자명해 보이는 규칙에도 우선순위·무승부 여부·전투 중단 시점을 따로 검토해야 함을 보인다.

## 실무 점검 항목

- [ ] 이 차트의 대상과 작성 목적을 한 문장으로 적었는가?
- [ ] 그림 전 텍스트 순서가 있고, 입력·판단·처리·출력이 구분되는가?
- [ ] 모든 판단 분기에 라벨과 종료 또는 다음 처리가 있는가?
- [ ] 서버 오류, 재고 부족, 동시 요청, 실패 뒤 복구 같은 예외 경로를 포함했는가?
- [ ] 반복에는 재진입 조건과 종료 조건이 모두 있는가?
- [ ] 공통 효과·공통 검증을 별도 프로세스로 추출할 수 있는가?
- [ ] UI 탐색·심리·코드 세부를 핵심 로직 차트에서 제외했는가?
- [ ] 확률값, 안내 문구, 데이터 참조, 우선순위는 차트 밖 명세에도 있는가?
