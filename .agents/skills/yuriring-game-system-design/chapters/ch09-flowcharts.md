# 09장: 규칙의 도식화

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 9장, 책 132–154쪽 / PDF 134–156쪽. PDF 157쪽은 다음 부 표지다.  
> 원문 도식의 숫자·세부 표기는 OCR 훼손 가능성이 있어, 아래는 흐름의 의미를 짧게 재구성했다. 연습 문제(책 154쪽 / PDF 156쪽)의 성공 확률·실패 포인트 등은 연습 조건이며 프로젝트 기본값이 아니다.

## 핵심 관점

플로 차트는 화면 이동도, 코드의 복사본도, 플레이어 감정선도 아니다. 저자가 말하는 목적은 **어떤 상황에서 어떤 조건을 판단하고 어떤 처리를 거쳐 어떤 결과를 내는지**를 팀이 동일하게 읽게 하는 것이다. 원문은 '아보카도가 있으면 아보카도를 6개 사고 우유는 1개만 산다'는 의도가 '아보카도가 있으면 우유를 6개 산다'로 전달되는 예로 말에서 조건의 우선순위가 사라지는 문제를 보인다(책 134–135쪽 / PDF 136–137쪽). 자연어는 조건의 대상·순서·우선순위를 생략하기 쉽고 플로 차트는 그 빈칸을 분기와 화살표로 드러내므로, 좋은 플로 차트는 규칙의 핵심 로직을 압축하고 상세한 값·문구·근거는 텍스트 명세가 맡는다는 것은 이 장을 묶은 스킬 정리다. 원문 근거는 아래 각 절의 쪽 표기를 따른다.

## 저자의 절차와 규칙

### 1. “그려야 할 흐름”을 먼저 고른다

원문의 판단 기준은 두 질문이다. 원문은 "'조건 판정이 중요한가?', '예외가 많은가?' 이 두 질문에 YES가 나온다면 플로 차트가 필요한 경우고, 그렇지 않다면 텍스트 설명만으로 충분하다"고 쓴다(책 153쪽 / PDF 155쪽). 이를 두 질문 모두 YES인 경우로 읽는 것은 문장의 자연스러운 해석이며, 원문이 '모두'를 따로 적지는 않는다. 바로 앞 문단은 플로 차트가 분기와 예외가 많거나 조건이 복잡하게 얽힌 흐름에 가장 효과적이라고 한다(책 152쪽 / PDF 154쪽). 한 방향으로 단순히 나열되는 작업은 텍스트가 더 낫다. 원문의 다른 절에 나오는 두 사례를 이 기준에 대어 본 스킬의 적용 예시로, 거래소 구매의 재고·소지금·동시 구매는 분기와 예외가 있어 도식화 가치가 크고, 로비에서 여러 화면으로 들어가는 모든 UI 이동을 붙이면 핵심 조건이 묻힌다.

### 2. 차트 전에 범위와 텍스트 흐름을 정리한다

1. **대상과 목적을 쓴다.** “무엇을 설명하는가”, “왜 도식화하는가”를 먼저 정한다. 원문은 거래소 구매의 재고 충돌 방지용 서버 처리 흐름을 예로 든다.
2. **정상 흐름을 텍스트로 나열한다.** 입력 → 재고 확인 → 소지금 확인 → 거래 완료처럼 먼저 논리를 검토한다. 그림부터 그리면 누락과 혼동이 커진다.
3. **입력·처리·판단·출력을 구분한다.** 버튼 클릭은 입력, 재고/소지금 확인은 판단, 차감·지급은 처리, 팝업은 출력이다.
4. **기호와 레이아웃을 적용한다.** 위에서 아래로 읽히게 배치하고, 반복은 되돌아가는 화살표로 명확히 한다.
5. **예외를 붙이고 가독성을 검수한다.** 서버 오류, 재고 부족, 중복 요청 같은 실패 경로도 끝까지 닫는다. 같은 기호·색·박스 크기, 겹치지 않는 화살표, 명시된 분기 라벨을 확인한다.

원문은 플로 차트 기호에 국제 표준이 있지만 게임 기획서에서는 이를 약간 단순화해 쓰는 경우가 많다고 한다(책 136쪽 / PDF 138쪽).

| 기호/역할 | 사용할 때 | 피해야 할 혼동(스킬 정리) |
| --- | --- | --- |
| 시작/종료 | 프로세스의 경계를 표시. 원문은 모든 플로 차트에 반드시 포함한다고 강조한다(책 137쪽 / PDF 139쪽). | 어디서 읽고 어디서 끝나는지 생략 |
| 입력 | 플레이어의 클릭·명령·값 입력 | 시스템 내부 처리와 혼합 |
| 출력 | 결과·안내를 사용자에게 표시 | 실패 처리 없이 팝업만 둠 |
| 처리 | 저장·차감·지급·상태 갱신 | 코드 변수/디버그 세부 사항을 전부 나열 |
| 비교/판단 | 조건에 따라 갈래가 나뉨 | YES/NO의 대상이나 우선순위 생략 |
| 다른 프로세스 연결 | 공통 하위 절차로 분리 | 같은 긴 절차를 여러 차트에 복제 |

### 3. 공통 효과는 스킬마다 반복해서 그리지 않는다

턴제 RPG 사례에서 저자는 ‘운명 조작’이라는 개별 스킬 자체보다 공통 효과인 불사·수면의 규칙을 분리해 도식화한다(책 146–147쪽 / PDF 148–149쪽). 같은 효과를 다른 스킬도 사용할 수 있기 때문이다. 불사는 치명 피해 시 효과 보유 여부를 확인하여 HP 회복, 상태 제거, 쿨타임 초기화, 연출, 1회 효과 해제 또는 일반 사망으로 갈린다. 수면은 행동 불가, 피해 시 해제, 턴 경과에 따른 지속 턴 감소·자동 해제로 구성되며, 수면 중에는 스킬 쿨타임이 줄지 않는다(책 147쪽 / PDF 149쪽). 저자는 이렇게 효과 단위로 설계하는 방식을 실무에서 매우 권장한다(책 146쪽 / PDF 148쪽). 이처럼 공통 규칙을 효과 단위로 두면 같은 로직의 중복 명세와 리밸런싱 누락을 줄인다(책 146쪽 / PDF 148쪽).

### 4. 원문 실무 사례의 검증 항목

| 사례 | 원문의 검증·흐름 | 설계 포인트 |
| --- | --- | --- |
| MMORPG 파티 초대 | 파티 정원 초과, 상대 오프라인, 상대의 초대자 차단, 자동 거절 옵션, 파티 불가 콘텐츠 이용 중, 이미 다른 파티 합류, 다른 초대 알림 대기 중을 차례로 검증(책 141–142쪽 / PDF 143–144쪽) | 검증 항목을 체크리스트로 나열하지 않고 흐름으로 그려 예외 누락을 막고, 실패마다 안내 메시지를 함께 설계한다. |
| 타워 디펜스 승패 판정 | 플레이어 타워 체력 0 → 상대 타워 체력 0 순으로 확인(책 142–143쪽 / PDF 144–145쪽) | 본문은 양쪽 타워가 동시에 파괴되는 예외까지 언급하며 승리·패배·무승부를 결정한다고 쓰지만(책 143쪽 / PDF 145쪽), 원문 도식은 패배→승리 두 분기만 그리고 동시 파괴·무승부 분기는 없다(PDF 145쪽 렌더 확인). 적용할 때는 동시 파괴의 우선순위를 결정 질문으로 남긴다. 원문 설계 포인트는 승패 판정 후 자원 생산·유닛 이동·연출 재생 등 모든 동작을 멈추고, 판정 로직 외에 결과 연출·UI 제어까지 흐름에 포함하는 것이다(책 143쪽 / PDF 145쪽). |
| 3매치 퍼즐 | 이동 → 매칭 판정 → 실패면 원위치 복귀, 성공이면 파괴·특수 블록·낙하 → 추가 매칭이면 반복(콤보 증가)(책 143–144쪽 / PDF 145–146쪽) | 매칭 실패 처리와 콤보 루프를 함께 설계하고, 각 단계의 결과가 다음 단계의 입력이 된다. |
| 수집형 RPG 전투 입장 | 유닛 슬롯 빈 공간, 입장 재화(예: 스태미너), 인벤토리 여유를 검증한다. 도식은 덱 편성 슬롯이 완전히 비어 있으면 알림 팝업을 띄우고, 꽉 차 있지 않으면 재확인 팝업에서 [확인] 입력을 받은 뒤 다음 검증으로 진행한다(책 145쪽 / PDF 147쪽, 렌더 확인) | 원문 설계 포인트는 각 검증 단계마다 슬롯 채우기·인벤토리 정리 같은 선택지를 안내하고, 실패 시 강제 중단이 아니라 정리하고 다시 시도하게 유도하는 것이다(책 145쪽 / PDF 147쪽). |

반복에는 재진입 조건과 종료 조건을 모두 그려야 한다는 점검은 3매치 사례를 일반화한 스킬 정리다.

### 5. 연습 문제

원문 연습 문제(책 154쪽 / PDF 156쪽)는 무기 제작 규칙을 정리하고 제작 처리 흐름을 플로 차트로 그리게 한다. 연습 조건은 성공 확률 30%, 실패 시 재료 미반환·실패 포인트 1 누적, 실패 포인트 5에 도달하면 다음 시도 확정 성공, 확정 성공 시 실패 포인트 0 초기화, 성공은 대성공(거래소 거래 가능)과 일반 성공(거래 불가, 계정 귀속)으로 나뉜다는 것이다. 확정 성공이 아닌 시도에서 일반 성공이나 대성공이 났을 때 실패 포인트를 초기화하는지, 성공 중 대성공과 일반 성공의 비율, 확정 성공이 대성공·일반 성공 중 무엇인지는 원문이 밝히지 않으므로 결정 질문으로 남긴다.

## 주요 개념

- **프로세스:** 결과뿐 아니라 결과까지 도달하는 조건·처리 순서 자체.
- **분기:** 비교/판단 결과에 따라 서로 다른 처리를 타는 지점.
- **서브 프로세스(하위 프로세스):** 반복되거나 공통인 절차를 별도로 관리해 연결하는 흐름.
- **완결성:** 승패 판정 뒤 전투 동작 중지, 결과 UI·연출처럼 결과 이후의 필요한 처리를 닫는 성질.
- **효과 단위 설계:** 개별 스킬이 아닌 재사용 가능한 효과의 작동 규칙을 한 곳에 두는 방식.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **심리를 조건으로 넣기:** “좋은 장비를 얻었는가 → 강화한다”는 시스템이 감정을 판정하는 것처럼 보인다. 행동·입력·시스템 상태만 다룬다. 원문의 오해 ①이다(책 148–149쪽 / PDF 150–151쪽).
- **모든 UI 흐름을 넣기:** 로비부터 모든 메뉴를 그리면 강화 조건 같은 핵심 로직이 사라진다. 원문의 오해 ②다(책 149–150쪽 / PDF 151–152쪽).
- **실제 코드와 1:1로 쓰기:** 변수 선언, 내부 초기화, 디버그 세부는 기획 의도 전달을 흐린다. 원문의 오해 ③이다(책 150쪽 / PDF 152쪽).
- **차트만 제공하기:** 원문의 오해 ④다. 저자는 기획서에 플로 차트와 함께 상세한 텍스트 설명을 반드시 포함하고, 안내 문구·확률 같은 수치·우선순위 조건은 차트 박스가 아니라 텍스트 설명 영역에 반드시 따로 정리하라고 한다(책 151–152쪽 / PDF 153–154쪽).
- **모든 규칙을 차트로 옮기기:** 원문의 오해 ⑤다. 조건 판정이 중요하고 예외가 많은 흐름만 차트로 그린다(책 152–153쪽 / PDF 154–155쪽).
- **YES만 그리기:** 파티 초대 거절, 동시 처치, 매칭 실패처럼 실패·동시 상태를 빼면 예외가 구현 밖으로 밀린다.

## 작은 재구성 산출물

원문의 거래소 구매 도식을 의미 단위로 재구성했다. 실제 가격·재고·지급 정책은 정하지 않는다.

```text
시작 → [입력: 구매 요청]
      → ◇ 실제 재고가 남았는가?
        ├─ 아니오 → [출력: 판매 완료 안내] → 종료
        └─ 예 → ◇ 실제 소지금이 충분한가?
              ├─ 아니오 → [출력: 소지금 부족 안내] → 종료
              └─ 예 → [처리: 거래 확정에 필요한 상태 변경]
                    → [출력: 완료 안내] → 종료
```

## 실무 점검 항목

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- [ ] 이 차트의 대상과 작성 목적을 한 문장으로 적었는가?
- [ ] 그림 전 텍스트 순서가 있고, 입력·판단·처리·출력이 구분되는가?
- [ ] 모든 판단 분기에 라벨과 종료 또는 다음 처리가 있는가?
- [ ] 서버 오류, 재고 부족, 동시 요청, 실패 뒤 복구 같은 예외 경로를 포함했는가?
- [ ] 반복에는 재진입 조건과 종료 조건이 모두 있는가?
- [ ] 공통 효과·공통 검증을 별도 프로세스로 추출할 수 있는가?
- [ ] UI 탐색·심리·코드 세부를 핵심 로직 차트에서 제외했는가?
- [ ] 확률값, 안내 문구, 데이터 참조, 우선순위는 차트 밖 명세에도 있는가?
