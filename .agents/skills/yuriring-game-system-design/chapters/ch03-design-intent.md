# 03. 기획 의도: 기능 선택을 지키는 판단 기준

**참고 범위:** 책 46–55쪽 / PDF 48–57쪽.

## 핵심 관점

기획 의도는 ‘왜 이 기능이 필요한가’와 ‘왜 이 방식이어야 하는가’를 함께 정한 방향성이다. 해결할 문제, 유도할 플레이 흐름, 전달할 경험·감정을 설계 전에 명확히 해야, 구조·조건·연출·예외를 고를 때 일관된 기준이 생긴다(책 48쪽 / PDF 50쪽). 요청이 위에서 내려온 기능이라도 구체 구조는 기획자의 선택이므로 의도가 필요하다.

## 의도를 설계에 쓰는 방법

1. **문제와 손실을 관찰한다.** 무엇이 불편한지보다 어떤 플레이어가 어느 맥락에서 어떤 감정·행동 손실을 겪는지 적는다.
2. **원하는 경험을 한 문장으로 만든다.** 예: 사망 뒤의 허무를 줄이고, 생존한 팀과 사망한 팀원의 연결을 유지하며, 중후반 교전 리듬을 살린다. 이 문장은 개별 기능의 채택·거절 기준이 된다(책 49쪽 / PDF 51쪽).
3. **각 규칙에 의도 역할을 붙인다.** 규칙이 어떤 감정 또는 행동을 만드는지 설명할 수 없으면, 편의 기능인지 핵심 구조인지 다시 판단한다.
4. **수정 요청을 의도로 검토한다.** 요청이 불편을 줄이더라도, 의도한 상호작용·긴장·팀 연결을 없애는지 확인한다. 거절할 때도 기능 찬반이 아니라 경험 구조가 어떻게 달라지는지 설명한다(책 50–51쪽 / PDF 52–53쪽).
5. **변경·운영 때도 같은 기준을 재사용한다.** 최초 의도 없이 횟수나 보상만 늘리면, 가벼운 루틴이 부담스러운 숙제가 될 수 있다(책 54쪽 / PDF 56쪽).

의도 문장은 기능명이 아니라 다음 빈칸을 채우는 방식으로 검토한다. **“[대상 플레이어]가 [문제 상황]에서 [원하는 감정/행동]을 경험하도록, [핵심 상호작용]을 통해 [게임 전체 흐름의 변화]를 만든다.”** 이 문장에 답하지 못하는 규칙은 제거·보류하거나, 해당 규칙이 지원하는 경험을 다시 명확히 한다. 이는 저자가 부활·출석·구사일생 사례에서 강조한 ‘기능 작동’과 ‘감정 전달’을 함께 보는 실무적 정리다(책 48–55쪽 / PDF 50–57쪽).

## 원문 사례를 실무 형식으로 재구성: 배틀로얄 부활 구조

**원문 사례 재구성** — 저자는 PUBG: 배틀그라운드의 블루칩 부활을 ‘단순 부활’이 아니라 팀 몰입과 전장 리듬을 위한 구조로 읽는다(책 49–51쪽 / PDF 51–53쪽).

| 층위 | 의도에 따른 설계 |
| --- | --- |
| 문제 | 이른 사망의 허무, 긴 관전의 피로, 초반 뒤 교전이 줄어드는 흐름을 완화한다. |
| 규칙 | 사망 시 칩을 남기고, 팀원이 회수해 위험한 송신 지점에 등록하며, 정해진 재진입 흐름에 합류한다. 적의 회수 가능 여부도 상호작용을 만든다. |
| 데이터/상태 | 사망자 식별, 칩 소유·회수 상태, 등록 여부, 재진입 대기 상태를 구분해 흐름이 뒤섞이지 않게 한다. |
| UI/피드백 | 사망자에게 재합류 기대를, 생존자에게 회수·등록 목표와 위험을 인지시킨다. |
| 변경 판단 | ‘적이 칩을 못 가져가게 하자’는 제안은 편의는 높이지만, 회수/저지 전투와 팀 연결이라는 의도를 약화하는지로 판단한다. |

## 의도 부재의 신호와 안티패턴

- **한 줄 KPI를 의도로 삼기:** ‘매출’, ‘리텐션’, ‘만족도’만으로는 보상 위치·수령 방식·횟수·연출을 고를 수 없다. 구체적 대상·경험·행동 흐름이 필요하다(ch04, 책 62쪽 / PDF 64쪽).
- **기능별로 수령 흐름이 제각각인 경우:** 일반/특별/유료 출석 보상이 각각 다른 장소에서 지급되면 플레이어는 정상 동작도 오류로 받아들일 수 있다(책 52쪽 / PDF 54쪽).
- **협업자에게 효과 이름만 전달하기:** 슈퍼아머에서 피격 모션만 없애면 넉백·경직은 남을 수 있다. 전투 흐름을 끊지 않는다는 목적을 적어야 판정, 애니메이션, 이펙트, QA 기준이 함께 정렬된다(책 53쪽 / PDF 55쪽).
- **감정을 피드백 없이 방치하기:** 체력 1 생존이 아무 신호 없이 다음 피격으로 끝나면 극적 생존이라는 의도는 전달되지 않는다. 인지·선택·연출을 포함해야 한다(책 54–55쪽 / PDF 56–57쪽).

**변경 판단 예:** 하루 1회 성장 던전의 보상 공급을 늘려야 할 때, 원래 의도가 바쁜 플레이어도 가볍게 성장하게 하는 것이라면 입장 횟수 증가보다 1회 보상 증가가 의도에 더 맞을 수 있다. 전자는 플레이 시간을 늘려 숙제감을 높일 수 있기 때문이다. 이는 원문의 유지보수 사례를 적용 판단으로 압축한 것이다(책 54쪽 / PDF 56쪽).

## 실무 점검

- 문제를 ‘누가 / 언제 / 무엇을 잃는가’로 적었는가?
- 의도한 경험이 규칙, 상태, 데이터, UI·연출 결정 각각에 연결되는가?
- 개선 요청을 받을 때 유지해야 할 경험과 바꿔도 되는 구현을 구분하는가?
- 후임자가 문서만 보고 보상 수량과 횟수 중 무엇을 바꿔야 할지 판단할 수 있는가?
- QA가 작동 여부 외에 의도한 리듬·몰입·인지까지 검증할 기준을 갖는가?
