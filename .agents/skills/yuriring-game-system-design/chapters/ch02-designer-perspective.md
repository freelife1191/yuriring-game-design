# 02. 시스템 기획자의 시야: 결과를 조건·흐름·피드백으로 되돌린다

**참고 범위:** 책 34–44쪽 / PDF 36–46쪽. 마지막 PART 02 안내(PDF 47쪽)는 본문 분석에서 제외했다.

## 핵심 관점

플레이어는 “먹으면 체력이 찬다”, “돌리면 보상을 얻는다”처럼 결과를 경험한다. 시스템 기획자는 그 결과가 성립하는 조건, 입력 뒤의 처리 순서, 상태값, 예외, 데이터 참조, UI·사운드 피드백까지 설계한다(책 36–38쪽 / PDF 38–40쪽). 결과만 적은 문장은 구현 지시가 아니라 감상에 머문다.

좋은 기획서는 플레이어 시야와 시스템 시야를 겹친다. 먼저 전달할 감정·행동 변화를 정하고, 이를 상태 전환·판정·수치·연출로 바꾼다. 시스템 시야만 있으면 기능은 만들어도 감정을 전달하기 어렵고, 플레이어 시야만 있으면 느낌은 표현해도 게임을 작동하게 만들 수 없다(책 39–40쪽 / PDF 41–42쪽).

## 결과 문장을 설계 문장으로 바꾸는 절차

아래 단계는 스킬 정리이며, 쪽 표기가 붙은 부분만 원문 근거다.

1. **표면 결과를 적는다.** 예: “장애물에 부딪치면 체력이 줄어든다.”
2. **조건과 주체를 명시한다.** 무엇이 장애물인지, 충돌을 어느 시점에 인정하는지, 현재/최대 체력의 초기값은 어디서 오는지를 쓴다.
3. **상태와 처리 순서를 연결한다.** 충돌 → 체력 감소 → 반투명·무적 시간 → 다음 충돌 처리처럼, 같은 장애물에 연속 적용되는지까지 정한다. 원문은 충돌 직후 일정 시간 반투명·무적 처리로 장애물 크기에 따라 체력이 지나치게 줄어드는 것을 막고 충돌 피드백을 명확히 준다고 설명한다(책 37–38쪽 / PDF 39–40쪽). 원문 체력 규칙은 충돌 감소와 별도로 게임 시작 후 일정 시간 간격으로 체력이 계속 줄어드는 감소도 두며, 감소량·속도는 캐릭터나 보물의 능력치에 따라 달라진다. 최대·현재 체력은 화면 중앙 상단에 실시간으로 표시한다(책 38쪽 / PDF 40쪽, 추출 텍스트에서 빠진 줄은 렌더로 확인).
4. **데이터와 표시를 분리해 연결한다.** 젤리의 점수·회복 속성과 값은 데이터 테이블에서 정의하고, 획득 판정 뒤 객체 제거·효과 적용·종류별 획득 사운드를 명시한다. 누적 점수는 세션마다 서버로 정산해 세션 최고 점수와 개인 최고 기록에 쓴다(책 38쪽 / PDF 40쪽).
5. **감정이 실제 피드백으로 남는지 확인한다.** 긴장감은 충돌 모션·사운드·화면 흔들림, 획득감은 오브젝트 삭제·소리로 구현한다(책 39–40쪽 / PDF 41–42쪽). 연출을 판정 결과를 납득시키는 시스템 출력으로 보는 것은 스킬 해석이다.

## 중요 개념과 판단 규칙

- **겉모습과 실제 조작 구조를 구분한다.** 러닝 게임이 ‘앞으로 달린다’고 보이더라도 플레이어 좌표 이동이 아니라 맵 횡스크롤일 수 있다. 조작 축을 줄여 회피에 집중시키려는 의도까지 읽어야 외형만 닮은 다른 게임이 되는 일을 막는다(책 37, 39쪽 / PDF 39, 41쪽).
- **원문 사례 값은 기본값이 아니다.** 원문 진화 사례의 조건은 50레벨 이상과 전용 진화 재료이고(책 41쪽 / PDF 43쪽), 돌림판은 돌리기 버튼을 누르면 이용권 1장을 소모한다(책 42쪽 / PDF 44쪽). 이 값은 원문 사례 값이다.
- **상태는 감정의 구현 단위다(스킬 해석).** 원문의 거인 젤리 사례는 거대화·무적 체험을 상태 전환, 지속 시간, 충돌 대상 처리, 피격 무시, 크기 변화, 사운드·화면 흔들림으로 구체화한다(책 40쪽 / PDF 42쪽).
- **보상은 보이는 멈춤 위치가 아니라 결정 시점이 중요하다.** 돌림판은 시작 시 보상을 확률로 정하고 회전·정지는 그 결과를 보여 주는 연출로 설계할 수 있다. 이때 보상 지급 확인, 서버·클라이언트의 데이터 일치, 중복 방지와 오류 복구까지 함께 본다(책 42–43쪽 / PDF 44–45쪽).

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **결과 서술만 하는 기획서:** “캐릭터가 앞으로 달린다”, “젤리를 먹으면 점수가 오른다”는 좌표/스크롤 방식, 판정, 갱신, 예외가 빠져 구현할 수 없다(책 37쪽 / PDF 39쪽).
- **감정과 로직을 분리하는 기획:** “압도적이어야 한다”만 적으면 게임을 작동하게 만들 수 없고, `무적=true`만 적으면 플레이어에게 감정을 전달하기 어렵다(책 39–40쪽 / PDF 41–42쪽).
- **연출을 실제 결정 처리로 오해하는 설계:** 멈추기 버튼이 실제 보상을 결정하는지, 이미 결정된 보상을 향하도록 보이는지는 구분해야 한다. 원문 돌림판은 돌리기 버튼을 누른 시점에 보상을 랜덤으로 정하고 멈추기 버튼을 누를 때는 이미 결정되어 있게 하며(책 42쪽 / PDF 44쪽, 해설은 '버튼 입력 이전에 확률 테이블에서 결정'으로 표현), 바늘 멈춤 타이밍을 잘 잡은 플레이어의 실력에 달린 것처럼 보이게 연출해 기대감을 높이며 공정하고 몰입감 있게 느껴지도록 설계한다(책 42–43쪽 / PDF 44–45쪽). 결과 결정·지급·확인 책임을 UI에 떠넘기지 않는다는 문장은 스킬 정리다.

## 원문 사례를 실무 형식으로 재구성: 캐릭터 진화

**원문에서 확인한 구조** — 원문의 시스템 시야 기획서는 플레이어 경험·조건·이용 방법 및 과정·결과·데이터 테이블 항목으로 쓴다(책 41–43쪽 / PDF 43–45쪽). 캐릭터 진화 사례는 레벨·재료 조건, 슬롯 입력, 원본·재료 소모, 상위 캐릭터 지급, ID 연결과 재료 부족 경고를 정의한다(책 41–42쪽 / PDF 43–44쪽).

**새 적용 예시** — 아래 표는 원문 구조에 표시·피드백과 추가 실패 검증을 붙인 명세 예시다. 잘못된 슬롯 조합, 인벤토리 반영 실패, 중복 입력 처리는 스킬 작성자의 추가 점검이며 원문 사례의 확정 사양이 아니다.

| 층위 | 결정할 내용 |
| --- | --- |
| 의도 | 목표 레벨 도달 뒤 큰 성장으로 성취감과 다음 성장 동기를 만든다. |
| 규칙 | 대상 캐릭터의 레벨 및 전용 재료 보유를 확인하고, 슬롯 투입·버튼 입력 후 원본/재료를 소모해 상위 캐릭터를 지급한다. 부족하면 지급하지 않고 이유를 알린다. |
| 데이터 | 캐릭터 식별자 → 필요 레벨·재료 식별자/수량·상위 캐릭터 식별자 참조를 둔다. |
| UI/피드백 | 슬롯의 허용 대상, 조건 충족 여부, 소모 예정물과 결과물을 보여 주고, 성공 시 성장 변화가 인지되게 한다. |
| 검증 | 재료 부족, 잘못된 슬롯 조합, 인벤토리 반영 중 실패, 중복 입력에서 소모와 지급이 하나의 결과로 남는지 확인한다. |

## 연습 문제

원문 연습 문제(책 44쪽 / PDF 46쪽)는 “보스를 처치하면 상자가 떨어지고, 상자를 열면 보상을 받는다.”를 시스템 기획자의 시야로 다시 쓰게 한다. 저자의 힌트는 다섯 가지다. 처치 시점을 어떻게 판정하는가, 상자는 즉시 생성되는가 연출이 포함되는가, 상자는 자동으로 열리는가 플레이어가 눌러야 하는가, 보상은 고정인가 확률인가, 파티로 처치하면 보상이 개별인가 공용인가. 이 힌트는 다른 결과 문장을 설계 문장으로 바꿀 때도 점검 질문으로 쓸 수 있다.

## 실무 점검

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- 플레이어가 보는 한 문장마다 ‘언제·무엇이·어떤 조건에서·어떤 순서로’가 답되는가?
- 입력 뒤 바뀌는 상태, 데이터 값, UI 표시, 사운드/이펙트가 서로 같은 결과를 가리키는가?
- 연출 시작·결과 결정·보상 반영·확인 팝업의 시점이 분리되어 있는가?
- 동일 이벤트의 연속 발생, 재입력, 네트워크 실패에서 결과가 중복되거나 사라지지 않는가?
- 플레이어 감정 목표를 최소 한 개의 판정/수치와 최소 한 개의 피드백으로 연결했는가?
