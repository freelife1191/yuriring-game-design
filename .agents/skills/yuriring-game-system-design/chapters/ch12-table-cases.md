# 12장: 데이터 테이블 사례

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 12장, 책 192–218쪽 / PDF 194–220쪽.  
> 이 장의 테이블명·ID·값·확률·비율은 구조를 설명하는 원문 사례다. 예컨대 특정 캐릭터명, 가챠 확률, 성장 배수, 상점 값은 프로젝트 기본값으로 전용하지 않는다. OCR로 열 정렬이 흐린 표는 관계 설명이 본문에서 확인되는 경우에만 정리했다.

## 핵심 관점

테이블 목록은 정답 목록이 아니다. 저자는 장르, 서버 구조, 데이터 흐름, 협업 방식에 따라 스킬과 캐릭터를 합칠 수도, 효과·조건을 분리할 수도 있다고 명시한다(책 194쪽 / PDF 196쪽). 이 장의 가치는 “어떤 시스템에 어떤 종류의 데이터가 필요하고, 반복·다국어·확률·공통 효과·운영 설정을 어떤 단위로 나누어 키로 연결할지”를 판단하는 감각에 있다. 좋은 테이블은 동작만 하는 표가 아니라 여러 직군이 읽고 수정하며 자동화와 서비스 확장을 견디는 구조다.

## 저자의 절차와 규칙

### 1. 데이터 성격으로 테이블 책임을 정한다

| 영역 | 원문의 테이블 구성 | 분리/연결 이유 |
| --- | --- | --- |
| 텍스트 | 스트링, 다이얼로그 챕터, 다이얼로그 | 문자열은 키+언어별 값으로 관리하고 새 언어는 열로 추가한다. 대사는 챕터 소속·재생 순서·화자·표정·음성으로 연결하고, 챕터는 퀘스트 테이블의 챕터 ID로 연결된다(책 195–196쪽 / PDF 197–198쪽). |
| 아이템·제작 | 아이템, 장비, 제작(필요 시 제작 재료) | 아이템 기본 정보와 장비 성능을 나눈다. 아이템 테이블의 등급·카테고리는 아이콘 색상·별 개수 같은 UI 표현과 인벤토리 분류에 쓰이고, 사용 아이템은 사용 시 발동되는 기능과 수치를 정의한다(예: HP 100 회복)(책 198쪽 / PDF 200쪽). 장비 테이블은 아이템 ID를 1:1로 반드시 참조하고 비장비 아이템은 넣지 않으며, 구조가 단순하면 통합할 수도 있다. 최대 스택은 슬롯 한 칸에 쌓이는 수량, 가챠 아이템은 뽑기 풀 지정이며, 장비의 패시브 효과와 효과 값은 작동 규칙을 미리 정의해 둔다. 제작은 대성공 시스템을 넣을 때 대성공 확률·획득 수량 칼럼을, 실패 시스템을 넣을 때 실패 확률 칼럼을 만들어 작동 규칙을 정의한다. 조합 재료가 늘면 반복 재료를 1:N으로 분리한다(책 197–199쪽 / PDF 199–201쪽). |
| 상품 | 상점, 상점 상품, 랜덤 상점 | 상점의 노출 조건·목록 갱신 주기·랜덤 풀과 상품의 진열·가격·수량·구매 제한을 분리한다. 랜덤 상점은 슬롯별 등장 확률을 나누기 위해 슬롯 열을 둔다(책 200–203쪽 / PDF 202–205쪽). |
| 확률 | 가챠 상품, 등급별 등장 확률, 랜덤 풀, 장비 랜덤 옵션 풀 | 등급 확률과 구성품 비중을 분리해 새 구성품 추가 시 전체 확률을 다시 수작업 조정하는 부담을 낮춘다(책 203–206쪽 / PDF 205–208쪽). 장비 랜덤 옵션은 장비 등급·타입별 풀을 정의하고, 획득 시 풀에서 옵션을 무작위로 고른 뒤 그 범위 안에서 수치를 다시 랜덤으로 정하는 2단계다(책 206–207쪽 / PDF 208–209쪽). |
| 전투·성장 | 레벨별 스테이터스, 캐릭터, 스킬, 스킬 효과, 필요 경험치, 강화 | 공통 성장 곡선·개별 비율·스킬 효과·단계별 비용/확률을 각각의 책임으로 둔다(책 207–213쪽 / PDF 209–215쪽). |
| 콘텐츠·설정 | 퀘스트, 게임 설정 | 퀘스트 테이블은 업적·이벤트 미션·시즌 패스 미션·튜토리얼 가이드까지 함께 관리하는 경우가 많아 확장성과 유연성이 가장 중요하다(책 213쪽 / PDF 215쪽). 개방·달성 조건이 여러 개인 퀘스트는 테이블을 쪼개고, 작은 범용 값은 키-값 설정으로 모은다(책 213–215쪽 / PDF 215–217쪽). |

### 2. 키로 연결하고, 값의 해석 규칙을 함께 쓴다

스트링 테이블은 키 하나를 다른 테이블이 참조하고, 플레이어 언어에 따라 같은 키의 문자열을 출력한다. 다이얼로그는 챕터 ID가 대사 행을 묶고, 대사 행은 스트링 키·캐릭터·표정·음성 리소스를 참조한다. 상품 테이블은 상점 ID를, 랜덤 상점은 랜덤 풀 그룹과 슬롯을, 가챠 상품은 등급 확률 그룹과 랜덤 풀을 참조한다. 이때 ID만 연결한다고 규칙이 완성되지는 않는다는 점, 그리고 ENUM의 허용값·대상 타입에 따른 참조 테이블·순서·기간·갱신·조건의 작동을 함께 명세해야 한다는 점은 이 장의 사례를 묶은 스킬 정리다. 원문 근거는 아래 각 사례의 쪽 표기를 따른다.

상점 테이블의 상품 목록 갱신 주기는 방랑 상인처럼 목록 전체가 바뀌는 상점에 쓰고, 상품의 갱신 주기는 구매 횟수 제한이 초기화되는 주기다. 둘을 구분한다. 구매 가능 횟수가 비어 있으면 제한 없음으로 간주하고, 노출 조건은 `NEWBIE_30`(가입 30일 이내)처럼 ENUM으로 정의한다. 상품 ID는 보통 `상점ID_번호`로 발번한다(책 200–202쪽 / PDF 202–204쪽). 원문은 구매 가능 횟수를 "하루에 몇 번"으로 설명하면서 별도의 갱신 주기 열도 두므로, 두 값의 관계는 원문만으로 확정되지 않는다.

**가챠는 세 테이블로 나눈다.** 원문은 상품마다 가격·판매 기간·구성품이 다름, 등급별 확률 분리, 픽업 대상 별도 설정, 천장(일정 횟수만큼 픽업 대상 뽑기에 실패하면 다음 뽑기에서 픽업 대상 확정 등장), 구성품이 아이템 또는 캐릭터인 경우를 지원하려면 가챠 상품·등급별 등장 확률·랜덤 풀 테이블이 필요하다고 설명한다. 가챠 상품은 단일 뽑기와 10회 뽑기 가격을 나눠 둘 수 있다(책 203–204쪽 / PDF 205–206쪽). 원문 예시 표의 상품은 골드로 뽑는 일반(GACHA_NORMAL), 크리스털로 뽑는 에픽(GACHA_EPIC), 오픈·종료 일시가 있는 기간 한정 픽업(GACHA_YURIRING) 세 가지이며, 각 상품이 NORMAL·EPIC·PICKUP 등급 확률 그룹과 자기 랜덤 풀을 참조한다(책 204쪽 / PDF 206쪽). 등급별 등장 확률 테이블은 `PICKUP_RATE`를 따로 두어 픽업 대상의 확률을 일반 SSR 확률과 구분한다. 원문 예시의 PICKUP 그룹은 PICKUP 0.5, SSR 0.5, SR 9, R 40, N 50이다(책 204–205쪽 / PDF 206–207쪽, 렌더 확인).

**비중의 분모는 같은 등급 구성품의 비중 합이다.** 랜덤 풀의 비중은 합이 100일 필요가 없다. 원문 예시에서 Bear·SpecialSword·Lion·SpecialArmor가 캐릭터·아이템 테이블에서 SSR로 정의되어 있으면, 같은 SSR 구성품의 비중 합 4를 분모로, 개별 비중 1을 분자로 한 뒤 PICKUP 그룹의 SSR_RATE 0.5를 곱한다. 즉 Bear는 (1/4)×0.5 = 0.125%로 등장한다(책 206쪽 / PDF 208쪽). 원문 예시에서 구성품의 등급은 랜덤 풀이 아니라 캐릭터·아이템 테이블의 정의를 따른다. 원문 계산은 같은 풀의 다섯 구성품 중 위 네 개만 SSR로 가정해 분모 4를 쓰며, 픽업 대상(Yuriring, 픽업 대상 여부 TRUE)의 등급과 분모 포함 여부는 밝히지 않는다. 사용자의 풀에 적용할 때는 픽업 대상의 분모 포함 여부를 결정 질문으로 남긴다. 픽업 대상 여부 열은 천장을 쳤을 때 확정 등장할 구성품을 지정한다(책 206쪽 / PDF 208쪽).

장비 옵션의 최솟값~최댓값도 이상~미만인지 이상~이하인지 프로그래머와 약속해야 한다(책 207쪽 / PDF 209쪽). 필요 경험치도 누적값인지 다음 레벨까지의 단일값인지에 따라 경험치 바·UI·레벨 결정 방식이 달라지므로 기획 단계에서 명확히 정의한다. 원문 예시에서 3레벨 필요 경험치 600은 누적이면 1→3레벨 총 600, 단일이면 2→3레벨 600이다. 단일 기준이면 레벨 열은 도달 대상 레벨이다(책 212쪽 / PDF 214쪽).

**캐릭터 스탯은 비율 분배 방식을 쓸 수 있다.** 등급별 레벨 스탯 총합은 레벨별 스테이터스 테이블에, 캐릭터별 성장 비율은 캐릭터 테이블에 두고 '등급 + 현재 레벨 + 비율'로 실시간 계산한다. 체력은 산출값에 10~15배를 한 번 더 곱하는 경우가 많다. 원문 예시는 SSR 1레벨 총합 130, 유리링 비율 체력 50%·공격력 15%·방어력 35%로 체력 130×50%×10 = 650, 공격력 19.5, 방어력 45.5다(책 208쪽 / PDF 210쪽). 저자는 이 방식이 라이브 밸런싱에 실용적이지만 모든 게임에 맞지는 않으며, 소수 정예 캐릭터 RPG는 레벨별 수치를 수동 관리하기도 한다고 밝힌다(책 208쪽 / PDF 210쪽).

스킬 효과 테이블에서 효과 발동 확률은 항상 발동이면 100이다. '공격력의 100% 대미지'는 연관 스테이터스 `ATK`와 효과 값 100으로 쓰고, 고정값 대미지·치유는 연관 스테이터스를 비운 채 효과 값만 쓰도록 규칙을 정의한다(책 211쪽 / PDF 213쪽). 강화 실패 시 페널티가 비어 있으면 재료만 소모되고, 파괴는 `DESTROY_ITEM` 같은 ENUM 작동 규칙을 정의한 뒤 입력한다(책 213쪽 / PDF 215쪽).

**새 설계의 참조 검증 — 적용 지침:** 고유 행 ID와 여러 행이 공유하는 그룹 ID는 다른 역할이다. 행 외래 키라면 대상 행을 식별할 키와 유일성을 확인한다. CSV에서 그룹값으로 여러 행을 찾는 구조라면 이를 논리적 그룹 조회로 표시하고, 대상 그룹의 성립·비어 있는 그룹·조회 결과의 사용 규칙을 정의한다. 복수 보상은 상위 회차의 키를 여러 보상 행이 참조하도록 설계할 수 있다. 공유 보상 세트가 필요하다면 별도 그룹 정의를 두는 등 식별 계약을 명확히 한다. 이는 10장의 키 설명과 이 장의 랜덤 풀 구분을 새 산출물에 적용한 점검이며, 특정 DB 구조를 강제하지 않는다.

### 3. 반복과 복합성은 분리 신호로 본다

- 제작 재료가 많아지면 `재료1/재료2` 열만 늘리지 말고 제작 재료 테이블의 1:N 분리를 검토한다.
- 스킬당 효과가 하나면 단일 테이블로 관리해도 큰 문제가 없지만, 여러 효과·조건·트리거가 얽히면 스킬과 스킬 효과를 나누는 것이 유지 보수와 확장에 유리하다(책 209–210쪽 / PDF 211–212쪽). 효과는 대상·범위·종류·발동 확률·지속 시간·연관 스테이터스·발동 조건을 가진다(책 210–211쪽 / PDF 212–213쪽).
- 퀘스트의 개방 조건·달성 조건이 여러 개면 테이블을 쪼갠다. 기간 한정 퀘스트는 시작일·종료일 칼럼을, 동시 발생 시 표시 순서가 필요하면 우선순위 칼럼을 추가한다. 원문의 단순형 퀘스트에서는 캐릭터도 보상으로 줄 수 있으면 보상 타입 칼럼이 추가로 필요하고, 보상이 여럿이면 보상 칼럼 수가 비례해 늘어난다(책 213–214쪽 / PDF 215–216쪽). 이 단순형을 언제 분리할지 12.2의 확장성 기준으로 판단하라는 것은 스킬의 적용 지침이다.
- 작은 설정값은 값마다 테이블을 만들지 않고, 문자열 ID와 Value의 키-값 테이블로 관리할 수 있다(책 215쪽 / PDF 217쪽). Value가 숫자만이 아니라 Boolean·문자열로 확장될 가능성도 고려한다.

### 4. 편의성·일관성·확장성으로 최종 검토한다

| 기준 | 원문의 규칙 | 실무상 효과 |
| --- | --- | --- |
| 편의성 | 명확한 칼럼명, 반복 입력의 규칙화/분리, 자료형·범위·빈값 방지(책 216쪽 / PDF 218쪽) | 사람이 입력·검토하고 도구가 읽기 쉽다. |
| 일관성 | ID 규칙 문서화, 모든 테이블의 기본 키·명확한 외래 키, 칼럼 순서·자료형·동작 통일(예: 테이블 맨 앞은 항상 ID → 이름·설명 → 기능 관련 필드 순서)(책 217쪽 / PDF 219쪽) | 공동 관리에서 검색·검증·커뮤니케이션 비용을 줄인다. |
| 확장성 | 추가 기능을 예상, 복잡해질 가능성이 높은 영역은 처음부터 테이블 분리를 고려, 폐지 데이터는 삭제 대신 비활성화 고려. 예: 스킬 레벨업으로 쿨타임이 줄어들게 할 예정이면 쿨타임 칼럼을 캐릭터 테이블이 아닌 스킬 테이블에 둔다(책 217쪽 / PDF 219쪽) | 업데이트가 기존 참조를 깨지 않고 최소 수정으로 늘어난다. |

원문의 종료일 24시 같은 경계 시각은 ‘모든 프로젝트가 반드시 이 값을 써야 한다’가 아니라, 같은 목적의 칼럼은 같은 방식으로 동작하도록 정해 문서화하라는 일관성 사례다.

## 주요 개념

- **스트링 키:** 다국어 텍스트를 직접 복사하지 않고 참조하는 고유 식별자.
- **챕터–대사 관계:** 챕터는 대사 묶음, 대사 행은 재생 순서와 연출 정보를 가진다.
- **랜덤 풀과 비중:** 후보 집합과 같은 등급 구성품 안의 상대 비율. 등급 확률과 역할이 다르며, 개별 확률은 비중/같은 등급 비중 합 × 등급 확률이다(책 206쪽 / PDF 208쪽).
- **천장:** 일정 횟수만큼 픽업 대상 뽑기에 실패하면 다음 뽑기에서 픽업 대상이 확정 등장하는 보장 로직(책 203쪽 / PDF 205쪽).
- **효과 테이블:** 스킬 하나에 여러 효과가 걸릴 때 효과를 스킬 효과 테이블의 별도 행으로 나누고, 스킬이 스킬 효과 ID로 참조하는 구조다(책 209–210쪽 / PDF 211–212쪽). 여러 스킬이 효과를 공유·재사용한다는 관점은 스킬 해석이다.
- **키-값 설정:** 소규모 범용 옵션을 `ID`와 `Value`로 관리하는 방식.
- **레거시 비활성화:** 폐지된 아이템·스킬을 즉시 삭제하지 않고 활성 상태로 관리하는 확장성 선택지.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **사례 구조를 범용 정답으로 복제하기:** 원문도 프로젝트별 통합·분리 형태가 달라질 수 있다고 밝힌다.
- **확률 하나에 모든 책임 넣기:** 등급 확률, 후보 비중, 픽업 여부, 보장 규칙을 같은 값에 섞으면 추가·조정이 어려워진다.
- **문자열을 각 테이블에 직접 쓰기:** 번역·수정·UI 일관성의 관리 지점이 분산된다.
- **복합 스킬을 단일 행에 계속 덧붙이기:** 효과·조건·트리거 증가에 따라 열이 폭발하고 재사용이 사라진다.
- **경험치·범위·확률 단위 미정:** 누적/단일 경험치나 범위 경계, 비중/확률의 해석이 구현마다 달라진다.
- **폐지 데이터를 무조건 삭제하기:** 기존 참조·운영 이력·레거시 호환을 점검하지 않으면 연결이 끊길 수 있다.

## 작은 재구성 산출물

원문 가챠의 “상품 → 등급 확률 → 후보 풀” 분리를 구조만 보이는 **새 적용 예시**로 재구성했다. 아래 식과 값은 프로젝트 규칙이 아니다.

```text
DrawProduct[PK: DRAW_SPRING]
  ├─ GradeRateGroupID → GradeRate[PK: RATE_SPRING]
  └─ RandomPoolGroupID → PoolEntry[PK: POOL_SPRING_01...]
                              ├─ Type → 대상 테이블을 결정
                              ├─ ContentID → 실제 후보
                              ├─ Weight → 같은 등급 구성품 안의 상대 비중(등급은 대상 테이블에서 조회)
                              └─ IsPickup → 천장 시 확정 등장 대상 여부
```

검증할 결정표도 함께 둔다.

| 입력한 값 | 반드시 확인할 규칙 | 실패 시 다룰 문제 |
| --- | --- | --- |
| `Type` | 타입별로 어떤 테이블을 참조하는가 | 존재하지만 잘못된 종류의 ID 연결 |
| `ContentID` | 해당 대상 테이블에 실제 존재하는가 | 빈/고아 참조 |
| `Weight` | 0 허용, 분모가 같은 등급 구성품의 비중 합인지, 픽업 대상의 분모 포함 여부, 등급 확률과의 곱 | 합계를 100으로 잘못 강제, 풀 전체를 분모로 계산, 분모 0 |
| `IsPickup` | 천장 시 확정 등장 대상인지, `PICKUP_RATE`와의 관계 | 천장 시 대상 없음 또는 의도 밖 후보 |

## 연습 문제

원문 연습 문제(책 218쪽 / PDF 220쪽)는 몬스터 테이블과 랜덤 드롭 풀 테이블을 설계하게 한다. 조건은 다섯 가지다. 몬스터 테이블은 모든 몬스터의 메타 정보를 관리하고, 처치 시 드롭할 랜덤 드롭 풀을 참조할 수 있어야 한다. 드롭 풀 하나에 여러 드롭 아이템이 들어갈 수 있고, 아이템마다 등장 확률이 있으며, 드롭 풀 하나를 여러 몬스터가 공유할 수 있다. 원문은 정답 표를 주지 않는다. 같은 몬스터라도 드롭 확률이 다를 수 있다는 점, 보상이 없는 몬스터와 한 몬스터의 복수 보상도 문제 설명에 포함된다. 풀이 구조는 이 장의 랜덤 풀·외래 키 원칙을 적용한 스킬 제안으로 표시한다.

## 실무 점검 항목

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- [ ] 각 테이블이 소유하는 데이터와 다른 테이블에 위임할 데이터를 구분했는가?
- [ ] 텍스트·리소스·아이템·캐릭터·스킬을 중복 값이 아닌 키로 연결하는가?
- [ ] 반복되는 재료·보상·효과·조건이 열 증가 대신 행/별도 테이블 분리 신호인지 검토했는가?
- [ ] 확률, 비중, 누적/단일 수치, 범위 경계, 기간·리셋 시점의 해석을 명시했는가?
- [ ] ENUM과 타입 값마다 허용 목록·대상 참조·작동 규칙이 있는가?
- [ ] ID 규칙, 칼럼 순서, 자료형, 종료 시각 같은 공통 규약을 문서화했는가?
- [ ] 잘못된 자료형·범위·빈값·고아 외래 키를 막는 검증 장치가 있는가?
- [ ] 미래의 복합 스킬·추가 콘텐츠·폐지 데이터를 처리할 확장 경로를 검토했는가?
