# 12장: 데이터 테이블 사례

> **출처 범위:** 『유리링의 실전 게임 시스템 기획』 12장, 책 p.192–218 (PDF p.194–220).  
> 이 장의 테이블명·ID·값·확률·비율은 구조를 설명하는 원문 사례다. 예컨대 특정 캐릭터명, 가챠 확률, 성장 배수, 상점 값은 프로젝트 기본값으로 전용하지 않는다. OCR로 열 정렬이 흐린 표는 관계 설명이 본문에서 확인되는 경우에만 정리했다.

## 핵심 관점

테이블 목록은 정답 목록이 아니다. 저자는 장르, 서버 구조, 데이터 흐름, 협업 방식에 따라 스킬과 캐릭터를 합칠 수도, 효과·조건을 분리할 수도 있다고 명시한다. 이 장의 가치는 “어떤 시스템에 어떤 종류의 데이터가 필요하고, 반복·다국어·확률·공통 효과·운영 설정을 어떤 단위로 나누어 키로 연결할지”를 판단하는 감각에 있다. 좋은 테이블은 동작만 하는 표가 아니라 여러 직군이 읽고 수정하며 자동화와 서비스 확장을 견디는 구조다.

## 저자의 절차와 규칙

### 1. 데이터 성격으로 테이블 책임을 정한다

| 영역 | 원문의 테이블 구성 | 분리/연결 이유 |
| --- | --- | --- |
| 텍스트 | 스트링, 다이얼로그 챕터, 다이얼로그 | 문자열은 키+언어별 값으로 관리하고, 대사는 챕터 소속·재생 순서·화자·표정·음성으로 연결한다. |
| 아이템·제작 | 아이템, 장비, 제작(필요 시 제작 재료) | 아이템 기본 정보와 장비 성능을 나누며, 조합 재료가 늘면 반복 재료를 1:N으로 분리한다. |
| 상품 | 상점, 상점 상품, 랜덤 상점 | 상점의 노출·갱신·랜덤 풀과 상품의 진열·가격·수량·제한을 분리한다. |
| 확률 | 등급별 확률, 랜덤 풀, 장비 랜덤 옵션 풀 | 등급 확률과 구성품 비중을 분리해 새 구성품 추가 시 전체 확률을 다시 수작업 조정하는 부담을 낮춘다. |
| 전투·성장 | 레벨별 스테이터스, 캐릭터, 스킬, 스킬 효과, 필요 경험치, 강화 | 공통 성장 곡선·개별 비율·공통 효과·단계별 비용/확률을 각각의 책임으로 둔다. |
| 콘텐츠·설정 | 퀘스트, 게임 설정 | 복합 퀘스트는 조건·보상·트리거의 분리를 고려하고, 작은 범용 값은 키-값 설정으로 모은다. |

### 2. 키로 연결하고, 값의 해석 규칙을 함께 쓴다

스트링 테이블은 키 하나를 다른 테이블이 참조하고, 플레이어 언어에 따라 같은 키의 문자열을 출력한다. 다이얼로그는 챕터 ID가 대사 행을 묶고, 대사 행은 스트링 키·캐릭터·표정·음성 리소스를 참조한다. 상품 테이블은 상점 ID를, 랜덤 상점은 랜덤 풀 그룹과 슬롯을, 가챠 상품은 등급 확률 그룹과 랜덤 풀을 참조한다. 이때 ID만 연결한다고 규칙이 완성되지는 않는다. ENUM의 허용값, 대상 타입에 따른 참조 테이블, 순서·기간·갱신·조건의 작동을 명세해야 한다.

특히 원문은 랜덤 풀의 **비중**은 합이 100일 필요가 없고 같은 등급 내부 비율을 나누는 데 쓰인다고 설명한다. 등급별 확률과 비중을 분리하면 등급 전체 확률을 유지하면서 구성품을 추가할 수 있다. 장비 옵션의 최솟값~최댓값도 범위의 포함 여부를 프로그래머와 약속해야 한다. 필요 경험치도 누적값인지 다음 레벨까지의 단일값인지에 따라 UI·레벨 계산이 달라지므로 반드시 먼저 확정한다.

**새 설계의 참조 검증 — 적용 지침:** 고유 행 ID와 여러 행이 공유하는 그룹 ID는 다른 역할이다. 행 외래 키라면 대상 행을 식별할 키와 유일성을 확인한다. CSV에서 그룹값으로 여러 행을 찾는 구조라면 이를 논리적 그룹 조회로 표시하고, 대상 그룹의 성립·비어 있는 그룹·조회 결과의 사용 규칙을 정의한다. 복수 보상은 상위 회차의 키를 여러 보상 행이 참조하도록 설계할 수 있다. 공유 보상 세트가 필요하다면 별도 그룹 정의를 두는 등 식별 계약을 명확히 한다. 이는 10장의 키 설명과 이 장의 랜덤 풀 구분을 새 산출물에 적용한 점검이며, 특정 DB 구조를 강제하지 않는다.

### 3. 반복과 복합성은 분리 신호로 본다

- 제작 재료가 많아지면 `재료1/재료2` 열만 늘리지 말고 제작 재료 테이블의 1:N 분리를 검토한다.
- 스킬에 여러 효과·조건·트리거가 붙으면 스킬과 스킬 효과를 나눈다. 효과는 대상·범위·종류·발동 확률·지속 시간·연관 스테이터스·발동 조건을 가진다.
- 퀘스트에 개방 조건·달성 조건·보상·기간·우선순위가 복수로 생기면 한 행의 반복 열을 늘리기보다 구조 분리를 검토한다.
- 작은 설정값은 값마다 테이블을 만들지 않고, 문자열 ID와 Value의 키-값 테이블로 관리할 수 있다. Value가 숫자만이 아니라 Boolean·문자열로 확장될 가능성도 고려한다.

### 4. 편의성·일관성·확장성으로 최종 검토한다

| 기준 | 원문의 규칙 | 실무상 효과 |
| --- | --- | --- |
| 편의성 | 명확한 칼럼명, 반복 입력의 규칙화/분리, 자료형·범위·빈값 방지 | 사람이 입력·검토하고 도구가 읽기 쉽다. |
| 일관성 | ID 규칙 문서화, 모든 테이블의 기본 키·명확한 외래 키, 칼럼 순서·자료형·동작 통일 | 공동 관리에서 검색·검증·커뮤니케이션 비용을 줄인다. |
| 확장성 | 추가 기능을 예상, 복잡해질 영역은 초기에 분리, 폐지 데이터는 삭제 대신 비활성화 고려 | 업데이트가 기존 참조를 깨지 않고 최소 수정으로 늘어난다. |

원문의 종료일 24시 같은 경계 시각은 ‘모든 프로젝트가 반드시 이 값을 써야 한다’가 아니라, 같은 목적의 칼럼은 같은 방식으로 동작하도록 정해 문서화하라는 일관성 사례다.

## 주요 개념

- **스트링 키:** 다국어 텍스트를 직접 복사하지 않고 참조하는 고유 식별자.
- **챕터–대사 관계:** 챕터는 대사 묶음, 대사 행은 재생 순서와 연출 정보를 가진다.
- **랜덤 풀과 비중:** 후보 집합과 집합 내부 상대 비율. 등급 확률과 역할이 다르다.
- **효과 테이블:** 스킬의 공통 효과를 별도 행으로 정의해 복합 스킬을 조합하는 구조.
- **키-값 설정:** 소규모 범용 옵션을 `ID`와 `Value`로 관리하는 방식.
- **레거시 비활성화:** 폐지된 아이템·스킬을 즉시 삭제하지 않고 활성 상태로 관리하는 확장성 선택지.

## 안티패턴

- **사례 구조를 범용 정답으로 복제하기:** 원문도 프로젝트별 통합·분리 형태가 달라질 수 있다고 밝힌다.
- **확률 하나에 모든 책임 넣기:** 등급 확률, 후보 비중, 픽업 여부, 보장 규칙을 같은 값에 섞으면 추가·조정이 어려워진다.
- **문자열을 각 테이블에 직접 쓰기:** 번역·수정·UI 일관성의 관리 지점이 분산된다.
- **복합 스킬을 단일 행에 계속 덧붙이기:** 효과·조건·트리거 증가에 따라 열이 폭발하고 재사용이 사라진다.
- **경험치·범위·확률 단위 미정:** 누적/단일 경험치나 범위 경계, 비중/확률의 해석이 구현마다 달라진다.
- **폐지 데이터를 무조건 삭제하기:** 기존 참조·운영 이력·레거시 호환을 점검하지 않으면 연결이 끊길 수 있다.

## 작은 재구성 산출물

원문 가챠의 “상품 → 등급 확률 → 후보 풀” 분리를 구조만 보이는 **새 적용 예시**로 재구성했다. 아래 식과 값은 프로젝트 규칙이 아니다.

```text
DrawProduct[PK: DRAW_SPRING]
  ├─ GradeRateGroupID → GradeRate[PK: RATE_SPRING]
  └─ RandomPoolGroupID → PoolEntry[PK: POOL_SPRING_01...]
                              ├─ Type → 대상 테이블을 결정
                              ├─ ContentID → 실제 후보
                              ├─ Weight → 같은 그룹 내 상대 비중
                              └─ IsPickup → 보장 로직의 후보 여부
```

검증할 결정표도 함께 둔다.

| 입력한 값 | 반드시 확인할 규칙 | 실패 시 다룰 문제 |
| --- | --- | --- |
| `Type` | 타입별로 어떤 테이블을 참조하는가 | 존재하지만 잘못된 종류의 ID 연결 |
| `ContentID` | 해당 대상 테이블에 실제 존재하는가 | 빈/고아 참조 |
| `Weight` | 0 허용, 그룹 내 계산 방식, 등급 확률과의 관계 | 합계를 100으로 잘못 강제하거나 분모 0 |
| `IsPickup` | 보장 조건이 참조하는 후보인지 | 보장 시 대상 없음 또는 의도 밖 후보 |

## 실무 점검 항목

- [ ] 각 테이블이 소유하는 데이터와 다른 테이블에 위임할 데이터를 구분했는가?
- [ ] 텍스트·리소스·아이템·캐릭터·스킬을 중복 값이 아닌 키로 연결하는가?
- [ ] 반복되는 재료·보상·효과·조건이 열 증가 대신 행/별도 테이블 분리 신호인지 검토했는가?
- [ ] 확률, 비중, 누적/단일 수치, 범위 경계, 기간·리셋 시점의 해석을 명시했는가?
- [ ] ENUM과 타입 값마다 허용 목록·대상 참조·작동 규칙이 있는가?
- [ ] ID 규칙, 칼럼 순서, 자료형, 종료 시각 같은 공통 규약을 문서화했는가?
- [ ] 잘못된 자료형·범위·빈값·고아 외래 키를 막는 검증 장치가 있는가?
- [ ] 미래의 복합 스킬·추가 콘텐츠·폐지 데이터를 처리할 확장 경로를 검토했는가?
