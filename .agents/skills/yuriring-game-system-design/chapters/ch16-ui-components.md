# 16장 — UX/UI 구성 요소

> 출처: 정윤지(유리링), 『유리링의 실전 게임 시스템 기획』. 위치는 `책 인쇄 쪽 / PDF 쪽`으로 함께 적는다(이 책은 PDF 쪽 = 인쇄 쪽 + 2). 핵심 근거: 책 264–288쪽 / PDF 266–290쪽(연습 문제 포함). PDF 291쪽은 PART 07 표지다.

## 핵심 관점

입력 UI는 값의 신뢰성·안정성·실수 없는 경험을 설계하는 장치이며, 입력은 시스템 상태를 바꾼다(책 266쪽 / PDF 268쪽). 알림 UI는 메시지의 중요도·유지 시간·조작 차단 여부에 맞춰 고르고, 탐색 UI는 콘텐츠 양과 이용 패턴에 맞춰 선택한다(책 278–284쪽 / PDF 280–286쪽). 끝으로 원문은 시인성·직관성·일관성·확장성·피드백·감정·역방향 점검을 UI 설계 시 반드시 고려해야 할 점으로 든다(책 285–287쪽 / PDF 287–289쪽). 이를 모든 구성요소의 품질 기준으로 쓰라는 것은 스킬의 적용 지침이다.

## 적용 절차 — 스킬의 재구성

아래 다섯 단계는 16.1–16.4 절을 작업 순서로 정리한 것이다. 각 단계의 근거는 괄호의 원문 컴포넌트 절에 있다. 단계 문장은 스킬 정리이고, 각 단계 끝의 '참고 원문 절'은 그 단계가 참고한 원문 범위다. 책의 말로 인용할 때는 아래 '핵심 판단 규칙'이나 원문 사례 문장의 쪽을 쓴다.

1. **상태 변화와 입력 목적을 정한다.** 직접 입력, 단일 선택, 복수 선택, 지속 ON/OFF, 정밀/대략 수치 중 무엇인지 구분해 컴포넌트를 고른다(참고 원문 절: 책 266쪽 / PDF 268쪽, 책 271–274쪽 / PDF 273–276쪽).
2. **입력 유형에 해당하는 계약을 명세한다.** 공통으로 역할·선택 결과·오류 피드백을 정하고, 텍스트에는 허용 문자·길이, 수치에는 범위·단위·보정, 선택 UI에는 선택 모델·기본값, 토글에는 현재 상태·저장 시점처럼 관련 항목만 붙인다. 직접 입력·키 입력·포커스도 지원하는 경우에 명세한다(참고 원문 절: 책 267–271쪽 / PDF 269–273쪽, 책 273–274쪽 / PDF 275–276쪽).
3. **지원하는 상태와 결과를 보인다.** 원문은 Default/Focus/Disabled/Hover/Pressed를 설명한다. 실제 적용은 플랫폼과 입력 장치에서 가능한 상태를 구분하고, 토글의 현재 상태, 즉시 실행/재확인, 필요한 저장 여부를 정한다(참고 원문 절: 책 274–275쪽 / PDF 276–277쪽).
4. **알림 UI를 목적에 맞게 고른다.** 완료·실패 같은 일시적인 안내는 토스트, 단어만으로 뜻이 드러나지 않는 요소의 보조 설명은 툴팁, 확인이 필요한 이벤트는 팝업(배경 조작을 막고 행동을 강제해야 하면 모달), 확인하지 않은 신규 항목은 배지, 진행 중임은 인디케이터(진행률을 잴 수 있으면 프로그레스 바)로 구분한다(참고 원문 절: 책 278–281쪽 / PDF 280–283쪽).
5. **탐색과 장기 운영을 검증한다.** 스크롤·캐러셀·아코디언의 콘텐츠 양·방향·정렬·확장 방식을 정하고, 복잡한 UI는 시스템 규칙의 신호로 역점검한다(참고 원문 절: 책 282–287쪽 / PDF 284–289쪽).

## 핵심 판단 규칙

|판단 규칙|조건·방법·이유|
|---|---|
|텍스트 입력은 문자 종류·길이 초과 처리·금칙어·플레이스홀더·키 동작을 정의한다.|이름/쿠폰 등은 허용 문자와 검증이 다르고, IME 조합 입력도 길이 차단에 영향을 준다(책 267쪽 / PDF 269쪽).|
|드롭다운/콤보박스에는 정렬 의도·기본값·선택 뒤 행동·저장·불일치 대응을 적는다.|콤보 입력 불일치는 안내와 자동 완성 여부가 필요하다(책 268–269쪽 / PDF 270–271쪽).|
|정밀 수치는 스피너, 대략 수치는 슬라이더, 자주 조정하는 수량은 스테퍼를 우선 검토한다.|입력 의도와 환경에 따라 적합한 방식이 다르다(책 269–271쪽 / PDF 271–273쪽). 원문 사례 값은 스피너(강화 자동 시도) 최솟값 1·최댓값 10·기본값 1, 슬라이더 기본값 80·단위 5·0/50/100 스냅이다(책 270–271쪽 / PDF 272–273쪽). 스테퍼는 최솟값·최댓값과 증감 단위를 반드시 정의하고, 기본값을 직전 사용값과 시스템 기본값 중 무엇으로 할지, 1회 조작 때 어떤 연산(예: 1개 사용에 자원 10 소모)이 일어나는지 정한다(책 271쪽 / PDF 273쪽).|
|수치 조절에는 범위·단위·기본값·직접 입력·보정 규칙을 묶어 명세한다.|스피너는 숫자 외/음수 방지, 슬라이더는 범위·스냅·값 표시, 스테퍼는 끝값에서 버튼 비활성이 필요하다(책 270–272쪽 / PDF 272–274쪽).|
|라디오는 정확히 하나, 체크박스는 복수, 토글은 지속 ON/OFF에 쓴다.|원문은 비슷한 형태라도 여러 개를 동시에 선택할 수 있으면 라디오가 아닌 체크박스를 써야 한다고 한다(책 272–274쪽 / PDF 274–276쪽). 같은 외형을 섞으면 상태를 오해한다는 이유는 스킬 해석이다. 라디오는 기본값이 반드시 있어야 하고(선택 없음 불가), 선택을 초기화할 수 없는 구조면 '선택 안 함'을 하나의 옵션으로 둔다. 체크박스에 선택 수 제한이 있으면 제한 수를 명시하고 초과 시 안내하며, 전체 선택/해제는 상황별로 판단한다(책 273쪽 / PDF 275쪽).|
|토글은 현재 상태와 저장 시점을 분명히 한다.|색·위치·텍스트로 상태를 구분하고 즉시 저장인지 저장 버튼 반영인지 정한다(책 274쪽 / PDF 276쪽).|
|버튼은 지원하는 상태를 구분하고, Disabled가 눌리지 않음을 확실히 보인다.|원문은 버튼 상태로 Default(기본)·Focus(포커스)·Disabled(비활성)·Hover(호버)·Pressed(눌림)를 들고, 상태별 시각 구분이 명확해야 하며 특히 Disabled는 색상·투명도·그림자 등으로 눌리지 않음이 확실히 인식되게 하라고 한다(책 274–275쪽 / PDF 276–277쪽). 이 목록을 입력 환경에 맞게 골라 적용하고 Hover(마우스 커서 상태)를 터치 전용 화면의 필수 상태로 강제하지 않는다는 것은 스킬의 적용 지침이며 원문 문장이 아니다.|
|긍정/부정 버튼의 위치와 즉시성을 기획 단계에서 정한다.|최근에는 확인 같은 긍정 버튼을 오른쪽, 취소 같은 부정 버튼을 왼쪽에 두는 방식이 보편적이지만 반대인 환경도 있으므로 UI 전체에서 방향을 통일한다. 삭제처럼 즉시 실행하지 않고 재확인할 행동인지도 설계에 포함한다(책 275쪽 / PDF 277쪽).|
|햄버거 버튼에 핵심 기능을 숨기지 않는다.|햄버거는 메뉴가 많거나 공간이 부족할 때의 대체 UI이므로 기본 메뉴 구조가 숨으면 안 되고, 자주 쓰는 주요 기능은 바깥에 둔다. 드로어 방식과 풀 스크린 메뉴는 메뉴 수·시각 간섭·터치 편의로 고르고, 메뉴에 무엇을 넣을지(필터·기능 목록·설정) 의도도 정한다(책 275–277쪽 / PDF 277–279쪽).|
|모달은 최소화하고 닫기 동선을 명시한다.|모달은 조작을 막고 특정 행동을 강제하므로 최소한으로 쓰고, 기존 화면과 겹치지 않게 배치하며 '닫기' 동선을 반드시 명시하고, 긍정/부정 버튼의 위치·색 대비도 결정해야 한다(책 279–280쪽 / PDF 281–282쪽).|
|알림은 차단성과 정보 수명에 맞춘다.|토스트는 주로 완료·실패 안내에 쓰며, 조작할 수 없는 영역이므로 긴 정보·반복 정보에는 부적합하고 여러 개가 겹치면 우선순위를 조정한다(책 278쪽 / PDF 280쪽). 툴팁은 과도하게 길거나 복잡한 정보는 담지 않는 것이 원칙이고, 모바일에서는 사용이 제한되므로 대안이 필요하다(책 279쪽 / PDF 281쪽). 배지는 숫자 표기 여부와 갱신 기준(서버/클라이언트)을 정하고, 너무 많이 띄우지 않게 우선순위를 둔다(책 280쪽 / PDF 282쪽). 무한 로딩은 인디케이터, 진행률을 알 수 있으면 프로그레스 바를 쓰고, 체감 속도를 위해 프레임이 적은 영역에 배치한다(책 281쪽 / PDF 283쪽).|
|탐색 UI는 콘텐츠 양·방향·조작 충돌·우선순위를 함께 검토한다.|스크롤 단서, 캐러셀 순환/정렬, 아코디언 단일/다중 확장을 정해야 한다(책 282–284쪽 / PDF 284–286쪽). 원문은 스크롤 안에 드래그 기능을 함께 넣으면 충돌 위험이 있고, 캐러셀 이미지에 버튼을 겹치면 시인성이 떨어지며, 모바일에서는 오작동을 막도록 접기/펼치기 버튼의 터치 영역을 충분히 확보하라고 한다(책 283–284쪽 / PDF 285–286쪽).|
|UI 설계 시 16.4의 일곱 관점(시인성·직관성·일관성·확장성·명확한 피드백·감정 설계·역방향 점검)으로 점검한다. 역방향 점검은 다음 행에 따로 적는다.|**시인성**은 기능의 중요도에 비례하고 자주 쓰는 기능일수록 접근성이 좋아야 한다(우편 보상 받기 버튼이 회색·작으면 보상이 있는 줄 모른다). **직관성**은 "이 버튼을 처음 본다면 뜻을 알까?"를 묻는다(사람 실루엣 + 기호). **일관성**은 버튼 위치·정렬·색·필터·팝업·확인/취소 순서를 프로젝트 전체에서 통일한다. **확장성**은 리스트·복합 필터를 처음부터 늘어날 것을 전제로 설계한다(거래소 필터 추가 사례). **명확한 피드백**은 모든 조작에 시각·청각 반응을 준다. **감정 설계**는 연출로 감정을 남기되, 가챠 연출이 너무 짧으면 감정이 남지 않고 길고 스킵이 불가능하면 피로만 쌓인다(책 285–287쪽 / PDF 287–289쪽).|
|UI가 복잡하면 규칙을 줄일 수 있는지 되묻는다(역방향 점검).|네 단계 입력 창은 예쁜 재배치보다 단계 통합·자동화가 더 나은 해법일 수 있다(책 287쪽 / PDF 289쪽).|

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- 입력 필드에 길이만 두고 허용 문자·오류·IME·엔터/탭 포커스를 미정으로 둔다.
- 끝값에서도 수량 증가/감소 버튼을 활성화하거나, 토글이 ‘현재 상태’인지 ‘누르면 될 상태’인지 모호하게 한다.
- 비활성 버튼을 활성 버튼과 비슷하게 그려 누를 수 있다고 오해하게 한다.
- 짧은 토스트에 긴 설명을 넣거나, 모든 알림을 조작 차단 모달로 처리한다.
- 햄버거 메뉴 안에 자주 쓰는 핵심 기능까지 숨기고(책 275쪽 / PDF 277쪽), 스크롤 가능·아코디언 확장 상태를 알리지 않는다.
- 가챠/강화 연출을 너무 짧게 만들어 감정이 남지 않거나, 길고 스킵이 불가능하게 만들어 피로만 쌓이게 한다(책 287쪽 / PDF 289쪽).

## 사례 재구성

**원문 사례 — 아이템 사용 수량 스테퍼(책 271–272쪽 / PDF 273–274쪽).** 최솟값 1, 최댓값 보유 수량, 단위 1, 사용 가능한 최대치를 기본값으로 두며, 최댓값에서는 `+`를 비활성화한다. 직접 입력의 잘못된 값은 보정하고 보유량 초과는 메시지로 알려 준다. 수치·상태·예외·피드백을 함께 정의한 사례다.

**새 적용 예시 — 덱 편성의 자동 추천 토글.** 토글은 ON/OFF 중 현재 상태를 색·위치·문구로 보이고, 누르면 즉시 추천 슬롯을 갱신할지 `저장` 후 적용할지를 명세한다. 이미 편성한 캐릭터는 선택 불가 상태와 이유를 보여 주며, 추천 결과가 바뀌면 짧은 피드백을 준다. 구성요소 명세를 상태 변화와 오조작 방지로 확장한 예시다.

## 연습 문제

원문 연습 문제(책 288쪽 / PDF 290쪽)는 보유 캐릭터 중 5명을 골라 전투 덱을 편성하고 캐릭터 간 시너지·특성을 쉽게 비교하게 한다는 기획 의도로 덱 편성 UI를 설계하게 한다. 질문은 다섯 가지다. 레이아웃(목록·슬롯·상세 정보 등)을 어떻게 구성할까, 시너지·추천 조합을 어떻게 제안할까, 이미 슬롯에 든 캐릭터를 다시 고르지 않게 하는 인터랙션은 무엇일까, 한 번에 편성을 끝내는 UX 장치(자동 편성·최근 편성 불러오기)는 무엇일까, 능력 비교를 어떤 UI로 구현할까. 위 '새 적용 예시'의 자동 추천 토글은 이 연습 문제의 정답이 아니라 별도 예시다.

## 점검 항목

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- [ ] 각 입력 유형에 해당하는 타입·범위/단위·기본값·검증·오류 피드백을 정했는가? 직접 입력과 저장 시점은 지원·필요 여부에 맞게 명세했는가?
- [ ] 필수 입력과 선택 입력, 단일/복수 선택, 즉시 ON/OFF가 UI 유형과 맞는가?
- [ ] 플랫폼과 입력 장치에서 지원하는 버튼 상태와 비활성 사유가 정의됐는가?
- [ ] 팝업/모달의 차단 여부, 닫기 행동, 긍정·부정 버튼의 라벨·위치·색 대비가 정해졌는가?
- [ ] 토스트·툴팁·배지·인디케이터·프로그레스 바의 사용 목적과 우선순위가 분리됐는가?
- [ ] 스크롤 가능 단서, 캐러셀 순환/정렬, 아코디언 확장 규칙과 터치 영역이 있는가?
- [ ] 시인성·직관성·일관성·확장성·명확한 피드백·감정선으로 검토했는가?
- [ ] UI 복잡성이 규칙/단계 통합 또는 자동화로 해결될 문제는 아닌가?

## 용어 및 관련 장

- **스피너/슬라이더/스테퍼**: 각각 정밀 수치, 대략 수치, 빈번한 수량 조정에 쓰는 입력 UI(책 269–272쪽 / PDF 271–274쪽).
- **모달**: 배경 조작을 차단해 특정 행동을 요구하는 팝업(책 279–280쪽 / PDF 281–282쪽).
- **배지**: 미확인 신규 항목을 점·숫자로 알리는 표시(책 280쪽 / PDF 282쪽).
- **역방향 점검**: 복잡한 UI를 시스템 구조의 문제 신호로 보고 규칙을 재검토하는 방법(책 287쪽 / PDF 289쪽).

## 원문/OCR 한계

본문으로 컴포넌트의 역할과 설계 고려사항을 정리했다. OCR로 일부 도판 텍스트가 깨진 부분은 수치나 화면 좌표로 재구성하지 않았고, 원문이 실제 예시로 제시한 값은 사례 범위에서만 언급했다.
