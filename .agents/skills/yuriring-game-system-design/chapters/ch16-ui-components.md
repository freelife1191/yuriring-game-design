# 16장 — UX/UI 구성요소

> 출처: 정윤지(유리링), 『유리링의 실전 게임 시스템 기획』. 이 문서는 **PDF 쪽수**를 쓴다(책 인쇄 쪽수는 PDF보다 2쪽 작음). 핵심 근거: PDF 266~289쪽.

## 핵심 관점

입력 UI는 값의 신뢰성·안정성·실수 없는 경험을 설계하는 장치이며, 입력은 시스템 상태를 바꾼다(PDF 268쪽). 알림 UI는 메시지의 중요도·유지 시간·조작 차단 여부에 맞춰 고르고, 탐색 UI는 콘텐츠 양과 이용 패턴에 맞춰 선택한다(PDF 280~286쪽). 끝으로 시인성·직관성·일관성·확장성·피드백·감정·역방향 점검은 모든 구성요소에 적용하는 품질 기준이다(PDF 287~289쪽).

## 저자 프레임워크/절차

1. **상태 변화와 입력 목적을 정한다.** 직접 입력, 단일 선택, 복수 선택, 지속 ON/OFF, 정밀/대략 수치 중 무엇인지 구분해 컴포넌트를 고른다(PDF 268, 273~276쪽).
2. **입력 유형에 해당하는 계약을 명세한다.** 공통으로 역할·선택 결과·오류 피드백을 정하고, 텍스트에는 허용 문자·길이, 수치에는 범위·단위·보정, 선택 UI에는 선택 모델·기본값, 토글에는 현재 상태·저장 시점처럼 관련 항목만 붙인다. 직접 입력·키 입력·포커스도 지원하는 경우에 명세한다(PDF 269~273, 275~276쪽).
3. **지원하는 상태와 결과를 보인다.** 원문은 Default/Focus/Disabled/Hover/Pressed를 설명한다. 실제 적용은 플랫폼과 입력 장치에서 가능한 상태를 구분하고, 토글의 현재 상태, 즉시 실행/재확인, 필요한 저장 여부를 정한다(PDF 276~277쪽).
4. **알림 강도를 고른다.** 일시 안내는 토스트, 보조 설명은 툴팁, 주의/결정은 팝업·모달, 미확인은 배지, 진행 여부는 인디케이터/프로그레스 바로 목적을 분리한다(PDF 280~283쪽).
5. **탐색과 장기 운영을 검증한다.** 스크롤·캐러셀·아코디언의 콘텐츠 양·방향·정렬·확장 방식을 정하고, 복잡한 UI는 시스템 규칙의 신호로 역점검한다(PDF 284~289쪽).

## 핵심 판단 규칙

|판단 규칙|조건·방법·이유|
|---|---|
|텍스트 입력은 문자 종류·길이 초과 처리·금칙어·플레이스홀더·키 동작을 정의한다.|이름/쿠폰 등은 허용 문자와 검증이 다르고, IME 조합 입력도 길이 차단에 영향을 준다(PDF 269쪽).|
|드롭다운/콤보박스에는 정렬 의도·기본값·선택 뒤 행동·저장·불일치 대응을 적는다.|콤보 입력 불일치는 안내와 자동 완성 여부가 필요하다(PDF 270~271쪽).|
|정밀 수치는 스피너, 대략 수치는 슬라이더, 자주 조정하는 수량은 스테퍼를 우선 검토한다.|입력 의도와 환경에 따라 적합한 방식이 다르다(PDF 271~273쪽).|
|수치 조절에는 범위·단위·기본값·직접 입력·보정 규칙을 묶어 명세한다.|스피너는 숫자 외/음수 방지, 슬라이더는 범위·스냅·값 표시, 스테퍼는 끝값에서 버튼 비활성이 필요하다(PDF 272~274쪽).|
|라디오는 정확히 하나, 체크박스는 복수, 토글은 지속 ON/OFF에 쓴다.|선택 모델이 다르므로 같은 외형을 섞으면 상태를 오해한다(PDF 274~276쪽).|
|토글은 현재 상태와 저장 시점을 분명히 한다.|색·위치·텍스트로 상태를 구분하고 즉시 저장인지 저장 버튼 반영인지 정한다(PDF 276쪽).|
|버튼은 지원하는 상태를 구분하고, Disabled가 눌리지 않음을 확실히 보인다.|원문의 기본·포커스·비활성·호버·눌림 목록을 입력 환경에 맞게 적용한다. Hover는 마우스 커서 상태이므로 터치 전용 화면의 필수 상태로 강제하지 않는다(PDF 276~277쪽·적용 지침).|
|모달은 최소화하고 닫기 동선을 명시한다.|모달은 조작을 막고 특정 행동을 강제하며, 긍정/부정 버튼의 위치·색 대비도 결정해야 한다(PDF 281~282쪽).|
|알림은 차단성과 정보 수명에 맞춘다.|짧은 완료/실패는 토스트, 긴 설명은 툴팁이 부적합하며, 진행률을 알 수 있으면 프로그레스 바를 쓴다(PDF 280~283쪽).|
|탐색 UI는 콘텐츠 양·방향·조작 충돌·우선순위를 함께 검토한다.|스크롤 단서, 캐러셀 순환/정렬, 아코디언 단일/다중 확장을 정해야 한다(PDF 284~286쪽).|
|UI가 복잡하면 규칙을 줄일 수 있는지 되묻는다.|네 단계 입력 창은 예쁜 재배치보다 단계 통합·자동화가 더 나은 해법일 수 있다(PDF 289쪽).|

## 안티패턴

- 입력 필드에 길이만 두고 허용 문자·오류·IME·엔터/탭 포커스를 미정으로 둔다.
- 끝값에서도 수량 증가/감소 버튼을 활성화하거나, 토글이 ‘현재 상태’인지 ‘누르면 될 상태’인지 모호하게 한다.
- 비활성 버튼을 활성 버튼과 비슷하게 그려 누를 수 있다고 오해하게 한다.
- 짧은 토스트에 긴 설명을 넣거나, 모든 알림을 조작 차단 모달로 처리한다.
- 햄버거 메뉴 안에 자주 쓰는 핵심 기능까지 숨기고, 스크롤 가능·아코디언 확장 상태를 알리지 않는다.
- 가챠/강화 연출은 길게만 만들고 스킵·피로·감정 보상의 균형을 보지 않는다.

## 사례 재구성

**원문 사례 — 아이템 사용 수량 스테퍼(PDF 273~274쪽).** 최솟값 1, 최댓값 보유 수량, 단위 1, 사용 가능한 최대치를 기본값으로 두며, 최댓값에서는 `+`를 비활성화한다. 직접 입력의 잘못된 값은 보정하고 보유량 초과는 메시지로 알려 준다. 수치·상태·예외·피드백을 함께 정의한 사례다.

**새 적용 예시 — 덱 편성의 자동 추천 토글.** 토글은 ON/OFF 중 현재 상태를 색·위치·문구로 보이고, 누르면 즉시 추천 슬롯을 갱신할지 `저장` 후 적용할지를 명세한다. 이미 편성한 캐릭터는 선택 불가 상태와 이유를 보여 주며, 추천 결과가 바뀌면 짧은 피드백을 준다. 구성요소 명세를 상태 변화와 오조작 방지로 확장한 예시다.

## 점검 항목

- [ ] 각 입력 유형에 해당하는 타입·범위/단위·기본값·검증·오류 피드백을 정했는가? 직접 입력과 저장 시점은 지원·필요 여부에 맞게 명세했는가?
- [ ] 필수 입력과 선택 입력, 단일/복수 선택, 즉시 ON/OFF가 UI 유형과 맞는가?
- [ ] 플랫폼과 입력 장치에서 지원하는 버튼 상태와 비활성 사유가 정의됐는가?
- [ ] 팝업/모달의 차단 여부, 닫기 행동, 긍정·부정 버튼의 라벨·위치·색 대비가 정해졌는가?
- [ ] 토스트·툴팁·배지·인디케이터·프로그레스 바의 사용 목적과 우선순위가 분리됐는가?
- [ ] 스크롤 가능 단서, 캐러셀 순환/정렬, 아코디언 확장 규칙과 터치 영역이 있는가?
- [ ] 시인성·직관성·일관성·확장성·명확한 피드백·감정선으로 검토했는가?
- [ ] UI 복잡성이 규칙/단계 통합 또는 자동화로 해결될 문제는 아닌가?

## 용어 및 관련 장

- **스피너/슬라이더/스테퍼**: 각각 정밀 수치, 대략 수치, 빈번한 수량 조정에 쓰는 입력 UI(PDF 271~274쪽).
- **모달**: 배경 조작을 차단해 특정 행동을 요구하는 팝업(PDF 281~282쪽).
- **배지**: 미확인 신규 항목을 점·숫자로 알리는 표시(PDF 282쪽).
- **역방향 점검**: 복잡한 UI를 시스템 구조의 문제 신호로 보고 규칙을 재검토하는 방법(PDF 289쪽).

화면의 정보·배치·표현은 [14장](ch14-visual-interaction.md), IA·플로·와이어프레임·저장 명세는 [15장](ch15-ux-ui-design.md), 기획 의도와 UX/UI 관계는 [13장](ch13-ux-ui-foundations.md)을 함께 참조한다.

## 원문/OCR 한계

본문으로 컴포넌트의 역할과 설계 고려사항을 정리했다. OCR로 일부 도판 텍스트가 깨진 부분은 수치나 화면 좌표로 재구성하지 않았고, 원문이 실제 예시로 제시한 값은 사례 범위에서만 언급했다.
