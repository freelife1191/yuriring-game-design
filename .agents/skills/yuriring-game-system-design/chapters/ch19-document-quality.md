# 19장: 시스템 기획서의 완성도를 결정하는 요소들

> **원문 범위:** 책 324–336쪽 / PDF 326–338쪽. 마지막 PART 08 안내(PDF 339쪽)는 제외했다. 글자 10pt, 정보 밀도 60~70%, 복합 기능 약 40쪽·UX 중심 50쪽 이상은 이 책의 현장 권고와 사례이지 보편 의무값이 아니다(책 326–327쪽 / PDF 328–329쪽). 원문은 AI에 출석 미션의 필요성을 '기획 의도' 문단에 인용할 4~5개 논리 근거로 요청하는 예를 보이며(책 333–335쪽 / PDF 335–337쪽), 그 답변 속 ‘일반적 데이터 패턴’, ‘도파민’, ‘LTV’ 같은 주장에 검증 단서를 따로 달지 않는다. 이런 주장을 검증된 사실·지표 정의로 승격하지 않는 것은 스킬의 적용 지침이다.

## 핵심 관점

원문은 좋은 기획서는 화려한 문서가 아니라 편안한 문서라고 한다(책 326쪽 / PDF 328쪽). 문서 품질을 **결정을 빠르게 하고 같은 구현을 재현하게 하는 전달 품질**로 보는 것은 스킬 정리다. 좋은 시스템이라도 독자가 읽기 어렵거나 Why를 찾을 수 없으면 신뢰와 개발 속도를 잃는다(책 326쪽 / PDF 328쪽). 저자는 가독성, 필요한 만큼의 분량, 기능 단위 배치, Why→What→How의 논리 흐름을 품질 기준으로 제시하고(책 326–328쪽 / PDF 328–330쪽), AI는 기획을 대체하는 작성기가 아니라 기획자의 사고를 확장·정리·검토·교정하는 보조자로 둔다(책 329쪽 / PDF 331쪽).

## 저자 절차와 판단 기준

### 1. 먼저 읽을 수 있게 만든다

저자는 가독성 점검 질문에서 꽉 찬 문단으로 본문을 촘촘하게 채우기보다 여백을 두고, 배경과 글자 대비를 확보하라고 하며(회색 배경에 흰 글씨는 '절대 금물'이라고 쓴다), 표·플로 차트·와이어프레임은 보조 수단으로 쓰라고 한다. 또한 플로 차트만 있고 텍스트 설명이 없으면 맥락이 전달되지 않는다고 쓴다(책 326쪽 / PDF 328쪽, 렌더 확인). 원문의 10pt 이하 지양 및 페이지 정보 밀도 60~70%는 저자의 현장 권고다. 원문 표현은 ‘10pt 이하의 글씨, 꽉 찬 문단은 피로감을 유발함’이라 10pt 자체가 피할 범위에 들어간다(책 326쪽 / PDF 328쪽). 팀 가이드 문구로 옮길 때 ‘10pt 이상 권장’처럼 원문 경계를 바꿔 쓰지 않으며, 경계를 바꾼 팀 기준에는 책의 권고라는 출처를 달지 않는다는 것은 스킬의 적용 지침이다. 원문은 너무 꽉 채운 문서는 답답하고 읽기 어려운 반면 너무 비운 문서는 무성의하게 느껴질 수 있다며 양쪽을 함께 경계한다(책 326쪽 / PDF 328쪽). 이를 특정 문서·도구·독자를 전제한 휴리스틱으로 보는 것은 스킬 해석이다. 팀의 템플릿, 화면 크기, 접근성, 표 복잡도에 따라 달라질 수 있으므로, 숫자를 맞추기보다 실제 독자가 핵심 규칙과 예외를 빠르게 찾는지로 검증하라는 것은 스킬의 적용 지침이다.

분량에 대해 저자는 짧은 기획서는 무성의하고 긴 기획서는 비효율적이라는 오해를 받는다고 하며, 필요한 정보를 빠짐없이 담되 불필요한 반복과 과잉 서술을 피하는 것이 중요하다고 한다. 저자는 복합 기능에 약 40쪽, 이미지·와이어프레임 비중이 큰 UX 콘텐츠에는 50쪽 이상도 가능하다고 예시한다(책 327쪽 / PDF 329쪽). 이 쪽수를 견적·품질의 절대 기준으로 쓰지 않고 기능 수, 상태 수, 예외, 플랫폼, 로컬라이징, 이미 존재하는 공통 명세를 기준으로 적정 범위를 판단하라는 것은 스킬의 적용 지침이다.

### 2. 탐색 비용이 적은 구조로 배치한다

단일 기능은 개요→흐름 요약→상세 규칙→예외→데이터→UI→리소스/로컬라이징/로그 순서를 기본형으로 제시한다(책 327쪽 / PDF 329쪽). 복합 시스템이라면 작은 단위 시스템별로 이 배치를 반복하고, UI를 모두 모은 뒤 테이블을 모두 모으는 식의 배치 대신 기능 단위 모듈 안에 UI·테이블·로직을 함께 다룬다(책 327쪽 / PDF 329쪽). 원문이 든 이유는 개발자가 필요한 내용을 찾으려고 페이지를 자주 옮겨 다녀야 하는 비효율이다(책 327쪽 / PDF 329쪽). 이를 ‘이 기능의 버튼은 어떤 테이블 값을 쓰는가?’를 찾는 상황으로 풀어 쓴 것은 스킬 해석이다.

### 3. AI에는 검토 가능한 산출물을 요청한다

- **브레인스토밍:** 막힌 일일 보상 설계에서 복수 콘셉트와 각 메커니즘·심리적 동기 구조·리스크를 받는다(책 329–330쪽 / PDF 331–332쪽). 결과는 후보이지 기획 확정안이 아니다(스킬 적용 지침).
- **구조화:** 섞인 메모를 의도, 트리 구조, 규칙, UX, 밸런스, 누락 데이터·로그 같은 섹션으로 재분류한다(책 331–333쪽 / PDF 333–335쪽). 원본 항목이 빠지거나 의미가 바뀌지 않았는지 사람이 대조한다(스킬 적용 지침).
- **논리 보강:** 원문은 AI에 '기획 의도' 문단에 인용할 4~5개의 논리 근거를 (1) 주장 (2) 논리 근거 (3) 기대 효과로 정리해 달라고 요청하는 예를 든다(책 333–335쪽 / PDF 335–337쪽). AI가 제시한 시장·심리·지표 주장을 출처, 실제 게임 데이터, 사용자 조사로 별도 검증한 뒤에만 문서 근거로 채택하라는 것은 스킬의 적용 지침이다.
- **문장 교정:** 능동형, 한 문장 한 의미, 중복 제거를 요청한다. 저자는 기획서가 완성된 뒤 마지막 다듬기 단계에서 쓰면 효과적이라고 한다(책 335–336쪽 / PDF 337–338쪽). 수치·조건·예외·용어는 축약 중 손실될 수 있으므로 교정 전후 의미를 검토한다(스킬 적용 지침).

## 주요 개념

- **가독성:** 글꼴 크기만이 아니라 대비, 여백, 정보 밀도, 시각 자료의 목적성까지 포함한다.
- **기능 단위 모듈:** 기능의 규칙·UI·데이터·예외를 함께 두어 탐색 비용을 줄이는 문서 단위다.
- **논리 전개:** Why(지금 필요한 이유)→What(만들 것)→How(플레이어·개발 관점의 작동)이다. 이 3단계 흐름이 없으면 세부가 화려해도 '기능 설명서'일 뿐이다(책 328쪽 / PDF 330쪽).
- **AI 보조 범위:** 원문이 든 활용은 발상·구조화·논리 보강·문장 교정이다(책 329–336쪽 / PDF 331–338쪽). 사실 검증, 목표 결정, 책임 있는 명세 승인을 AI에 위임하지 않는다는 것은 스킬의 적용 지침이다.

## 안티패턴과 대응

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **예쁜 문서 우선:** 어두운 저대비·과도한 그래픽이 명세를 가린다. 독해와 검색을 먼저 시험한다.
- **페이지 수 목표화:** 내용이 반복되거나 예외가 빠진다. 질문·상태·결정 기준으로 완결성을 판정한다.
- **복합 시스템의 수직 배치:** 한 기능을 이해하려 여러 장을 오간다. 기능 단위 모듈과 공통 참조로 재구성한다.
- **AI 답변을 검증 없이 근거로 인용(스킬 적용 지침):** 그럴듯한 심리학·시장·지표 문구를 사실처럼 싣지 않는다. 출처, 데이터 정의, 비교 기간을 확인하거나 가설로 표기한다. 원문 예시는 AI 답변을 기획 의도에 인용하는 방식이므로, 이 경고를 저자의 말로 인용하지 않는다.
- **교정 중 명세 손실:** 짧게 만들다 예외·단위·주체가 사라진다. diff 검토와 QA 관점 재독을 한다.

## 사례 재구성: 스킬트리 초안의 AI 보조 안전 적용

`레벨업 시 포인트 지급`, `선행 스킬`, `초기화 비용`, `전투 중 재배치 불가`가 뒤섞인 메모를 AI에 주고 섹션 분류와 누락 후보를 요청한다. 결과를 기획자가 원본과 비교해 ‘규칙’, ‘UI’, ‘밸런스 리스크’, ‘데이터’, ‘로그’로 배치한다. “초기화가 이탈을 줄인다” 같은 AI 문장은 가설 칸에만 두고, 실제 초기화 로그와 이탈 정의·비교 집단이 있어야 근거로 승격한다. 마지막에 “버튼이 작동되는 용도”를 “버튼을 누르면 초기화 확인 창을 연다”로 고치되, 발동 조건과 취소 결과가 남아 있는지 확인한다. 이는 원문의 구조화·설득 보강·문장 교정을 검증 가능한 작업으로 좁힌 예시다.
