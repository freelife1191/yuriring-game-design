# 06. 시스템의 구성: 규칙의 데이터 흐름을 연결하고 모듈로 재조립한다

**참고 범위:** 책 92–103쪽 / PDF 94–105쪽. 마지막 PART 04 안내(PDF 105쪽)는 제외했다.

## 핵심 관점

분해는 출발점이다. 완성된 시스템에서는 각 규칙이 앞 규칙의 결과를 받아 다음 규칙의 조건으로 사용한다. 기획자는 적어도 **어떤 규칙이 어떤 정보를 생성해 어디로 전달하고, 전달받은 쪽이 어떤 판정을 하는지**를 추적할 수 있어야 한다(책 94–97쪽 / PDF 96–99쪽). 이 관점은 모든 연결을 기획서에 구현 명세로 적으라는 뜻이 아니라, 누락·충돌·버그의 위치를 구조적으로 찾는 사고 훈련이다.

## 규칙 연결 절차

1. **하나의 플레이 행동을 시작점으로 잡는다.** 예: 타워 공격.
2. **독립 규칙으로 나눈다.** 공격 적중, 대미지 계산, 체력 갱신, 사망/승패 판정, UI 표시를 분리한다.
3. **규칙마다 입력·출력·다음 수신자를 쓴다.** 공격 규칙은 적중 사실을, 대미지 규칙은 피해량을, 체력 규칙은 갱신 체력을 다음 규칙에 전달한다(책 94–95쪽 / PDF 96–97쪽).
4. **시스템 경계를 넘는 트리거를 표시한다.** 타워 체력이 0 이하가 되면 전투가 아니라 디펜스 승패 시스템의 패배 조건을 작동시킨다. 데이터의 생성 위치와 해석 위치를 혼동하지 않는다(책 96쪽 / PDF 98쪽).
5. **UI도 수신자 중 하나로 취급한다.** 갱신된 체력값은 표시 규칙을 거쳐 UI에 출력된다. UI가 체력을 독자적으로 계산하거나, 규칙 결과와 다른 값을 표시하지 않게 한다(책 95–96쪽 / PDF 97–98쪽).

## 원문 사례를 실무 형식으로 재구성: 타워 파괴에서 승패까지

**원문 사례 재구성** — 저자의 전투·타워·승패 예시를 설계 점검표로 바꾼다(책 94–96쪽 / PDF 96–98쪽).

| 단계 | 생성 정보 | 수신 규칙과 결정 | UI/예외 점검 |
| --- | --- | --- | --- |
| 공격 | 적중 여부, 대상 | 대미지 계산이 적중일 때만 피해를 계산한다. | 빗맞음/무효 대상을 동일하게 처리하지 않는지 확인 |
| 대미지 | 피해량 | 타워 체력 계산이 현재 체력을 갱신한다. | 음수·상한 등 체력 규칙을 한곳에서 해석 |
| 체력 | 갱신 체력 | 표시 규칙은 UI를 갱신하고, 0 이하이면 승패 규칙을 트리거한다. | 표시값과 실제 판정값이 같은 출처인지 확인 |
| 승패 | 파괴 사실 | 패배 조건이 결과를 결정한다. | 결과 결정 후 추가 공격·중복 종료가 가능한지 점검 |

보스를 처치했는데 보상이 오지 않는 문제도 ‘버그’로 뭉뚱그리지 않는다. 처치 판정 → 보상 분배 → 우편 발송 중 어느 규칙에서 정보가 끊겼는지 따라가면 조사 범위가 줄어든다(책 97쪽 / PDF 99쪽).

## 모듈화: 같게 작동하는 것을 다시 조립한다

모듈화는 분해한 기능·속성을 재활용 가능한 규칙 묶음으로 만들고, 필요한 곳에 조합하는 설계다. 마을·길드·아레나·암거래 상점은 UI와 재화가 달라도 구매, 판매물품 설정, 구매 횟수 제한, 무작위 갱신 모듈의 조합으로 볼 수 있다(책 98–99쪽 / PDF 100–101쪽). 일일·주간·업적·튜토리얼 미션도 ‘목표 조건 충족 후 보상 수령’이라는 공통 구조를 공유한다.

모듈을 만들 때는 이름만 공통화하지 말고 다음 규칙을 확정한다.

- 판매물품 설정: 목록·가격·해금 조건을 어디서 읽고 어떻게 설정하는가?
- 구매 제한: 일/주 같은 단위, 초기화 시점, 한도 소진 시 처리와 UI가 무엇인가?
- 무작위 물품: 후보·확률·갱신 조건·동일 물품 중복 허용 여부는 무엇인가?

이렇게 해야 운영자가 기존 모듈 조합으로 기간 한정 상점을 구성할 수 있고, 개발도 같은 로직을 반복 작성하지 않는다(책 99–100쪽 / PDF 101–102쪽).

## 안티패턴

- **규칙을 독립 기능으로만 본다:** 공격이 끝난 뒤 대미지·체력·사망/승패로 어떤 사실이 전달되는지 없으면, 연결부 누락을 찾기 어렵다.
- **한 시스템 안의 UI만 본다:** 체력 표시를 별도 계산하면 판정값과 화면값이 갈라질 수 있다. UI는 갱신 결과의 소비자로 둔다.
- **이름·UI가 다르면 새 시스템으로 만든다:** 상점마다 구매·한도·갱신 로직을 새로 만들면 규칙 불일치와 운영 비용이 늘어난다.
- **모듈화를 규칙 생략으로 쓴다:** ‘제한 모듈 적용’만으로는 초기화·한도 소진·예외가 정의되지 않는다.

## 실무 점검

- 플레이어 행동 하나를 시작으로 규칙별 입력·출력·수신자를 그릴 수 있는가?
- 시스템 경계를 넘는 데이터와 트리거가 누구의 책임인지 명확한가?
- 계산값, 상태값, UI 표시가 같은 결과를 참조하는가?
- 보상·승패 같은 종결 결과가 중복으로 실행되거나 실패 후 유실되지 않는가?
- 이름만 다른 기능 중 공통 규칙을 모듈로 뽑을 대상이 있는가?
- 각 모듈에 설정 데이터, 제한/초기화, 실패 처리, 운영 시 변경 지점이 명시되어 있는가?
