# 06. 시스템의 구성: 규칙의 데이터 흐름을 연결하고 모듈로 재조립한다

**참고 범위:** 책 92–102쪽 / PDF 94–104쪽. 마지막 PART 04 안내(PDF 105쪽)는 제외했다.

## 핵심 관점

분해는 출발점이다. 완성된 시스템에서는 각 규칙이 앞 규칙의 결과를 받아 다음 규칙의 조건으로 사용한다. 기획자는 적어도 **어떤 규칙이 어떤 정보를 생성해 어디로 전달하고, 전달받은 쪽이 어떤 판정을 하는지**를 추적할 수 있어야 한다(책 94–97쪽 / PDF 96–99쪽). 저자는 실무에서 이런 연결 구조를 엔지니어가 설계하거나 이미 정해진 프레임워크에서 작동하는 경우가 많아 기획서에 모든 상호 작용을 명시할 일은 많지 않다고 한다. 그래도 이해해야 하는 이유는 두 가지다. 시스템이 꼬이는 이유를 구조적으로 파악할 수 있고, 길드 레이드·거래소·점령전 같은 복합 시스템을 설계하는 발판이 된다(책 97쪽 / PDF 99쪽).

## 규칙 연결 절차

아래 1~5단계는 스킬이 만든 사고·점검 절차다. 원문은 규칙 사이에서 무엇을 어디로 전달하는지 명시해야 한다고 하면서도(책 95쪽 / PDF 97쪽), 이런 연결을 기획서에 모두 적으라는 뜻이 아니라 시스템을 구조로 보는 연습이라고 한다(책 97쪽 / PDF 99쪽). 단계에 붙은 쪽은 해당 사례의 근거 위치다.

1. **하나의 플레이 행동을 시작점으로 잡는다.** 예: 타워 공격.
2. **독립 규칙으로 나눈다.** 공격 적중, 대미지 계산, 체력 갱신, 사망/승패 판정, UI 표시를 분리한다.
3. **규칙마다 입력·출력·다음 수신자를 쓴다.** 공격 규칙은 적중 사실을, 대미지 규칙은 피해량을, 체력 규칙은 갱신 체력을 다음 규칙에 전달한다(책 94–95쪽 / PDF 96–97쪽).
4. **시스템 경계를 넘는 트리거를 표시한다.** 타워 체력이 0 이하가 되면 전투가 아니라 디펜스 승패 시스템의 패배 조건을 작동시킨다. 데이터의 생성 위치와 해석 위치를 혼동하지 않는다(책 96–97쪽 / PDF 98–99쪽).
5. **UI도 수신자 중 하나로 취급한다.** 갱신된 체력값은 표시 규칙을 거쳐 UI에 출력된다(책 95–96쪽 / PDF 97–98쪽). UI가 체력을 독자적으로 계산하거나 규칙 결과와 다른 값을 표시하지 않는지 확인하는 것은 스킬의 점검 항목이다.

## 원문 사례를 실무 형식으로 재구성: 타워 파괴에서 승패까지

**원문 사례 재구성** — 저자의 전투·타워·승패 예시를 설계 점검표로 바꾼다(책 94–96쪽 / PDF 96–98쪽).

| 단계 | 생성 정보 | 수신 규칙과 결정 | UI/예외 점검 |
| --- | --- | --- | --- |
| 기본 체력 | 최초 기본 체력 값 | 체력 계산 규칙이 이 값을 기준으로 대미지를 반영한다(책 95쪽 / PDF 97쪽). | 초기값의 출처가 데이터 한곳인지 확인 |
| 공격 | 적중 여부, 대상 | 대미지 계산이 적중일 때만 피해를 계산한다. | 빗맞음/무효 대상을 동일하게 처리하지 않는지 확인 |
| 대미지 | 피해량 | 타워 체력 계산이 현재 체력을 갱신한다. | 음수·상한 등 체력 규칙을 한곳에서 해석 |
| 체력 | 갱신 체력 | 표시 규칙이 갱신값을 UI에 출력한다. 별도로 0 이하이면 디펜스 승패 규칙의 패배 조건이 작동한다. | 표시값과 실제 판정값이 같은 출처인지 확인(스킬 점검) |
| 승패 | 파괴 사실 | 패배 조건이 결과를 결정한다. | 결과 결정 후 추가 공격·중복 종료가 가능한지 점검 |

보스를 처치했는데 보상이 오지 않는 문제도 ‘버그’로 뭉뚱그리지 않는다. 처치 판정 → 보상 분배 → 우편 발송 중 어느 규칙에서 정보가 끊겼는지 따라가면 조사 범위가 줄어든다(책 97쪽 / PDF 99쪽).

## 모듈화: 같게 작동하는 것을 다시 조립한다

모듈화는 분해한 기능·속성을 재활용 가능한 규칙 묶음으로 만들고, 필요한 곳에 조합하는 설계다. 마을·길드·아레나·암거래 상점은 UI와 재화가 달라도 구매, 판매물품 설정, 구매 횟수 제한, 판매물품 랜덤 모듈의 조합으로 볼 수 있다(책 98–99쪽 / PDF 100–101쪽). 원문 조합표에서 마을 상점은 구매+판매물품 설정, 길드·아레나 상점은 여기에 구매 횟수 제한을 더하고, 암거래 상점은 네 모듈을 모두 쓴다(책 99쪽 / PDF 101쪽, 렌더 확인). 일일·주간·업적·튜토리얼·시즌 패스 미션도 ‘목표 달성 조건을 만족하면 보상을 수령한다’는 공통 규칙의 조합이다(책 99쪽 / PDF 101쪽).

원문은 모듈화의 장점으로 "이 상점에는 어떤 모듈이 적용된다"는 요약 기획이 가능한 간결한 설계, 새 상점마다 코드를 새로 쓰지 않는 개발 리소스 절감, 기존 모듈 조합만으로 이벤트·기간 한정 상점을 꾸리는 유연한 운영을 든다. 예를 들어 '강화 주문서만 파는 일일 상점'은 구매·판매물품 설정·구매 횟수 제한 모듈만 골라 바로 쓴다(책 99–100쪽 / PDF 101–102쪽). 모듈화 기획에서 시스템 기획자는 시스템을 각각 기획하기보다 **어떤 모듈로 구성할지 판단하고 각 모듈의 작동을 설계한다**(책 100쪽 / PDF 102쪽).

모듈을 만들 때는 이름만 공통화하지 말고 원문의 규칙 질문을 확정한다(책 100쪽 / PDF 102쪽).

- 판매물품 설정: 판매 목록·가격은 어디서 불러오고 기획자가 어떻게 세팅하는가?
- 구매 제한: 일간/주간 단위를 어떻게 지정하고, 횟수는 언제·어떻게 회복되며, 한도를 다 쓴 상품을 구매 시도하면 어떻게 처리하는가?
- 랜덤 판매: 등장 목록·확률은 어디서 불러오고, 동일 아이템 중복 등장을 허용하는가?

해금 조건, 한도 소진 시 UI처럼 위 질문 밖의 항목은 스킬이 덧붙인 확장 점검이다. 원문은 기획 초기에는 기능을 단독으로 설계하는 데 집중하지만 실무에서는 비슷한 구조를 얼마나 효율적으로 재활용하느냐가 중요하며, 이후 더 복잡한 시스템도 '쪼개기 → 조립하기'의 반복이라고 정리한다(책 100쪽 / PDF 102쪽).

원문은 모듈 단위 규칙 설계가 명확해야 프로그래머가 효율적으로 구현하고 운영자도 문제없이 활용할 수 있다고 하며, 모듈화의 장점으로 기존 모듈 조합만으로 기간 한정 상점을 구성하고 새 코드를 쓰지 않아도 되는 점을 든다(책 99–100쪽 / PDF 101–102쪽).

## 연습 문제

원문 연습 문제(책 101쪽 / PDF 103쪽)는 캐릭터 숙소 커스터마이징 시스템을 구조화하게 한다. 숙소에 가구를 배치하면 가구의 호감도 상승 수치에 비례해 캐릭터 호감도가 오르고, 캐릭터가 좋아하는 가구면 효과가 상승한다는 조건이다. 과제는 세 가지다. 숙소 시스템을 기능 단위로 분해하기(가구 배치·저장·가구 효과 확인 등), 가구의 속성을 분리·정의하기(호감도 상승 수치·효과 상승 캐릭터 등), 가구 배치 → 호감도 상승 흐름을 규칙 연결 구조로 설명하기.

## 안티패턴

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **규칙을 독립 기능으로만 본다:** 공격이 끝난 뒤 대미지·체력·사망/승패로 어떤 사실이 전달되는지 적혀 있지 않으면, 연결부 누락을 찾기 어렵다.
- **한 시스템 안의 UI만 본다:** 체력 표시를 별도 계산하면 판정값과 화면값이 갈라질 수 있다. UI는 갱신 결과의 소비자로 둔다.
- **이름·UI가 다르면 새 시스템으로 만든다:** 상점마다 구매·한도·갱신 로직을 새로 만들면 규칙 불일치와 운영 비용이 늘어난다.
- **모듈화를 규칙 생략으로 쓴다:** ‘제한 모듈 적용’만으로는 초기화·한도 소진·예외가 정의되지 않는다.

## 실무 점검

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- 플레이어 행동 하나를 시작으로 규칙별 입력·출력·수신자를 그릴 수 있는가?
- 시스템 경계를 넘는 데이터와 트리거가 누구의 책임인지 명확한가?
- 계산값, 상태값, UI 표시가 같은 결과를 참조하는가?
- 보상·승패 같은 종결 결과가 중복으로 실행되거나 실패 후 유실되지 않는가?
- 이름만 다른 기능 중 공통 규칙을 모듈로 뽑을 대상이 있는가?
- 각 모듈에 설정 데이터, 제한/초기화, 실패 처리, 운영 시 변경 지점이 명시되어 있는가?
