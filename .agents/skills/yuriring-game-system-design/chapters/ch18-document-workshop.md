# 18장: 시스템 기획서 실습

> **원문 범위:** 책 300–323쪽 / PDF 302–325쪽. 캐릭터 수집형 RPG의 ‘파견 미션’은 설명용 사례다. 미션 5개 지역, 인원 3명, 1시간 모집, 보상 배율 등의 수치는 이 사례의 설계값이며 다른 게임의 기본값이 아니다(책 305–309쪽 / PDF 307–311쪽).

## 핵심 관점

좋은 시스템 문서는 개요에서 협업자가 **무엇을 왜 만들지** 합의하게 하고, 본문에서 개발자가 **어떻게 만들고 QA가 무엇을 검증할지** 재현 가능하게 만든다. 원문 사례는 한 장의 긴 기능 설명이 아니라, 목적·타깃·시나리오·구성요소에서 출발해 규칙·예외·데이터·행동 흐름·UI 상태로 내려간다(장 로드맵 책 301쪽 / PDF 303쪽, 실습 전체 책 302–323쪽 / PDF 304–325쪽). 문서의 순서를 독자가 시스템의 의미를 이해한 뒤 특정 상태와 입력의 결과를 찾도록 짜라는 것은 스킬의 적용 지침이다.

## 저자 절차와 판단 기준

아래 절 제목과 '각 요소는 다른 질문에 답한다' 같은 연결 설명은 스킬 정리이고, 괄호의 쪽에 있는 사례 내용이 원문이다.

### 1. 개요는 협업의 판단 재료로 쓴다

개요에 (a) 한 문단의 문제와 시스템 정의, (b) 간단 요약, (c) 개발 목적·배경·기대 효과·달성 목표, (d) 게임 내 포지션·타깃·방향, (e) 플레이 시나리오, (f) 구현 시스템 목록을 둔다(책 302–304쪽 / PDF 304–306쪽). 각 요소는 다른 질문에 답한다. 목적은 투자 이유, 타깃은 노출·난이도 판단, 시나리오는 실제 행동과 보상을, 목록은 파트별 작업 경계를 만든다. 원문 달성 목표는 세 가지다. (1) 보유 캐릭터 중 60% 이상이 한 주간 최소 1회 이상 파견에 사용되도록 유도, (2) 파견 UI 진입률이 일일 플레이어 중 40% 이상, (3) 특정 속성·희귀도 기반 미션으로 '파견 전략' 개념 안착(정성 목표)이다(책 303쪽 / PDF 305쪽). 이 값은 사례의 설계값이며 다른 프로젝트의 기본값이 아니다. 새 목표를 쓸 때 관측 대상·분모·기간을 함께 적으라는 것은 스킬의 적용 지침이다.

### 2. 본문은 기능을 상태·조건·결과·예외로 닫는다

각 규칙에서 먼저 설계 의도와 제약을 밝히고, 정상 흐름 다음에 실패·경계 흐름을 명시한다. 원문 파견 사례는 등장 갱신(보상 수령 시 같은 지역 그룹의 미션 1개가 새로 등장하고, 등장 시점부터 1시간 동안 편성할 수 있으며 마감 시간이 지나면 다른 미션으로 교체, 책 306쪽 / PDF 308쪽), 이미 파견 중인 캐릭터의 선택 불가, 정원 미달 시 시작 불가, 일반·특별·이벤트 유형, 중도 복귀 시 보상 미지급, 일괄 수령의 활성 조건까지 이어진다(책 305–308쪽 / PDF 307–310쪽). 중도 복귀해도 슬롯은 다른 미션으로 교체되지 않는데, 이는 무한 뽑기를 막기 위한 의도다. 미션마다 고유 파견 시간이 있어 짧은 미션을 자주 수행하는 것이 효율적이며 일일 접속 루틴과 연결된다(책 307쪽 / PDF 309쪽).

특별 미션의 조건 보너스는 수치 규칙 명세의 사례다. 특별 미션에는 조건이 최대 3개 설정되고, 캐릭터는 조건 1개 충족당 +1점이며, 파견 총합 점수에 따라 0점은 기본 보상, 1~3점은 +20%, 4~5점은 +50%, 6점 이상은 +100%를 준다. 보상 수량이 소수점이면 올림 처리하고, 슬롯을 채우면 받을 보상 배율을 미리 보여 준다(책 308쪽 / PDF 310쪽, 렌더 확인). 배율 구간은 사례 설계값이다. 이때 오류 메시지나 토스트도 사용자 피드백이자 QA 관찰점이므로 “어떤 조건에서 어떤 상태 변화와 문구가 나오는가”를 함께 적는다.

선택 자체가 의도한 재미인 시스템에서는 자동화가 그 판단을 전부 대체하지 않는지 검토한다. 원문의 자동 파견은 아직 편성되지 않았고 마감 시간이 지나지 않은 미션에만 가능하며, 파견 가능한 캐릭터가 최소 3명 이상 남아 있어야 한다. 부족하면 "파견 가능한 캐릭터 수가 부족합니다." 팝업을 띄우고 진행하지 않는다. 배치 순서는 **조건 점수(많이 충족하는 순)→등급→레벨→캐릭터 고유 ID**이며, 항상 수동 편성보다 최적이라고 보장하지 않아 전략 여지를 남긴다(책 309쪽 / PDF 311쪽). 원문은 조건 점수만 '많이 해당하는 순'으로 방향을 밝히고 등급·레벨·ID의 오름/내림 방향과 동점 처리는 적지 않는다(책 321쪽 / PDF 323쪽). 이 방향은 적용할 때 결정 질문으로 남긴다. 이는 자동화 일반의 목적을 제한하는 원칙은 아니다. 자동화 규칙에는 대상 가능 조건, 정렬/동점 기준, 필요한 실패 피드백과 결과 상태를 명세한다.

### 3. 데이터는 운영 규칙을 실행 가능한 열로 번역한다

원문은 미션의 등장 규칙·분류·조건·보상을 MissionTable 한 테이블에 정의하고, 이 테이블을 기반으로 클라이언트 UI와 서버 로직이 동기화되도록 설계했다고 한다(책 309–311쪽 / PDF 311–313쪽). 표의 모든 열을 복사하기보다 고유 ID와 문자열 키, 분류, 등장 그룹·확률, 기간, 조건 유형/값, 보상 ID/수량을 분리해 같은 원천을 보게 하는 것이 핵심이라는 것은 스킬 해석이다. 원문 예: `APPEAR_RATE`는 같은 그룹 안의 등장 확률(단위 만분율), `DURATION_HOURS`는 파견 시간(단위 시간), `END_DATE`는 이벤트 등장 종료일(24시)이다(책 310–311쪽 / PDF 312–313쪽). 조건 값 칼럼(`CONDITION_n_VALUE`)에 들어갈 수 있는 값은 앞선 조건 유형(TYPE) 칼럼에서 지정한 값에 따라 달라진다(책 310쪽 / PDF 312쪽). 각 열에 이름·자료형·의미를 쓰고 해당되면 허용값·단위·참조·사용처를 덧붙인다는 정리는 스킬 정리다. 원문 파견 사례에서는 서버가 조건 배율과 최종 보상 수량을 계산한다(책 310쪽 / PDF 312쪽). 일반 적용에서는 프로젝트 권한 모델과 부정 조작·일관성 요구에 따라 서버/클라이언트 책임을 정한다.

### 4. UI는 그림이 아니라 상태 전이 명세로 쓴다

레이아웃에는 정보 우선순위와 배치 이유를 적는다. 원문 UI 화면 이름은 '파트타임 미션'이며, 가장 큰 왼쪽 영역에 동적 파견 현황 지도를 두고, 오른쪽에는 파견 현황·보상 수령·자동 파견 같은 명령을 수행하는 상세 영역(정보·컨트롤 허브)을 둔다. 터치 정밀도를 위해 버튼을 리스트 형태로 배치하고, 보조·정적 정보를 오른쪽에 두어 메인 지도에 시각적 영향을 주지 않게 하며, 오른쪽이 조작의 연속성과 기능 버튼에 익숙한 위치라는 점을 이유로 든다(책 311–312쪽 / PDF 313–314쪽). 원문의 플레이어 행동 흐름 시나리오는 1단계 메인 맵 확인 → 2단계 미션 선택(인원 미배정) → 3단계 캐릭터 배치 → 4단계 파견 시작 → 보너스 경로 자동 파견 → 5단계 보상 수령 → 6단계 다음 루프다(책 312–314쪽 / PDF 314–316쪽). 원문의 컴포넌트 표는 UI 명칭, 역할, 구성 요소, 작동 규칙, 디자인 의도, 배치 이유를 정리하며, 구성 요소 칸은 `UI_BTN_STAFFING`·`UI_TITLE_MISSION_IN_PROGRESS` 같은 문자열 키와 MissionTable 열을 참조한다(책 315–322쪽 / PDF 317–324쪽). 원문 사례의 정렬·활성 규칙은 조건 보너스 대상 캐릭터는 아이콘 표시와 목록 전면 정렬, 선택 불가 캐릭터는 후면 정렬(책 306쪽 / PDF 308쪽), 자동 파견 버튼은 비어 있는 미션 슬롯이 있을 때만 활성(책 317–318쪽 / PDF 319–320쪽)이다. 이 값은 사례 설계값이다. 표시 데이터·활성 조건·클릭 결과·비활성 시 피드백·시각 상태를 필요한 요소에 명시한다는 정리는 스킬 정리다. 와이어프레임은 위치를, 규칙 표는 동작을 보완한다.

## 주요 개념

- **개요/본문 분리:** 개요는 합의용, 본문은 구현·테스트용이다.
- **조건 기반 보너스:** 캐릭터의 속성·배경·등급 등이 미션 조건과 맞을 때 보상을 다르게 하여 수집과 선택을 연결하는 사례 구조다(책 308쪽 / PDF 310쪽).
- **데이터 주도 설계:** 등장·기간·조건·보상을 코드 분기 대신 검증 가능한 데이터 행으로 관리한다.
- **상태 기반 UI(스킬 정리):** 원문 컴포넌트 명세가 미션 슬롯의 미배정·진행 중·완료 상태(책 315–316쪽 / PDF 317–318쪽)와 캐릭터 파견 슬롯의 선택 중 상태(책 319쪽 / PDF 321쪽)를 따로 정의한 사례를 일반화해, 화면에서 구분되는 상태마다 입력 가능 여부와 결과를 정의한다.

## 안티패턴과 대응

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **개요 없이 상세부터 작성:** 파트가 왜 필요한지와 범위를 다르게 이해한다. 문제·목표·타깃·구성요소부터 합의한다.
- **정상 흐름만 설명:** 모집 마감, 중복 배정, 정원 부족, 보상 없음, 중도 취소가 QA에서 뒤늦게 발견된다. 각 입력의 불가 조건과 피드백을 붙인다.
- **데이터 표만 제시:** 열의 단위·참조·소비처가 없으면 데이터 입력과 런타임 해석이 갈린다.
- **UI 그림에 동작을 맡김:** 버튼 활성 조건, 서버 동기화, 정렬, 상태 갱신을 텍스트로 명시한다.

## 사례 재구성: ‘길드 의뢰’ 문서 뼈대

새 `길드 의뢰`를 만들 때 개요에는 “전투 외 협동 기여처 부족”이라는 문제, 길드 활동을 원하는 타깃, `의뢰 확인→인원 배정→진행→공동 보상 수령` 시나리오, 의뢰 관리·참여 조건·기여도 계산·보상·로그·예외 처리 목록을 둔다. 본문에서는 동시 참여 가능 수, 마감·갱신 규칙, 탈퇴·정원 초과·보상 수령 실패의 결과를 정한다. `GuildRequestTable`에는 ID, 기간, 참여 조건, 목표, 보상, 노출 그룹을 두고 각 열의 타입·단위·참조를 적는다. UI에는 빈 의뢰/참여 중/완료/마감 상태와 각 버튼의 활성 조건을 붙인다. 수치와 보상 곡선은 별도 밸런스 결정이며, 이 장에서 가져올 것은 이러한 **명세의 연결 방식**이다.
