# 18장: 시스템 기획서 실습

> **원문 범위:** PDF 302~325쪽 / 책 300~323쪽. 캐릭터 수집형 RPG의 ‘파견 미션’은 설명용 사례다. 미션 5개 지역, 인원 3명, 1시간 모집, 보상 배율 등의 수치는 이 사례의 설계값이며 다른 게임의 기본값이 아니다(PDF 307~311쪽).

## 핵심 관점

좋은 시스템 문서는 개요에서 협업자가 **무엇을 왜 만들지** 합의하게 하고, 본문에서 개발자가 **어떻게 만들고 QA가 무엇을 검증할지** 재현 가능하게 만든다. 원문 사례는 한 장의 긴 기능 설명이 아니라, 목적·타깃·시나리오·구성요소에서 출발해 규칙·예외·데이터·행동 흐름·UI 상태로 내려간다(PDF 304~307쪽). 문서의 순서는 독자가 시스템의 의미를 이해한 뒤 특정 상태와 입력의 결과를 찾도록 해야 한다.

## 저자 절차와 판단 기준

### 1. 개요는 협업의 판단 재료로 쓴다

개요에 (a) 한 문단의 문제와 시스템 정의, (b) 간단 요약, (c) 개발 목적·배경·기대 효과·달성 목표, (d) 게임 내 포지션·타깃·방향, (e) 플레이 시나리오, (f) 구현 시스템 목록을 둔다(PDF 304~306쪽). 각 요소는 다른 질문에 답한다. 목적은 투자 이유, 타깃은 노출·난이도 판단, 시나리오는 실제 행동과 보상을, 목록은 파트별 작업 경계를 만든다. 목표 수치를 쓸 때는 원문 예시처럼 “활용률·UI 진입률”처럼 관측 방법을 붙이고, 측정 기간·분모·성공 기준은 프로젝트에서 별도로 확정한다.

### 2. 본문은 기능을 상태·조건·결과·예외로 닫는다

각 규칙에서 먼저 설계 의도와 제약을 밝히고, 정상 흐름 다음에 실패·경계 흐름을 명시한다. 원문 파견 사례는 등장 갱신, 이미 파견 중인 캐릭터의 선택 불가, 정원 미달 시 시작 불가, 일반·특별·이벤트 유형, 중도 복귀 시 보상 미지급, 일괄 수령의 활성 조건까지 이어진다(PDF 307~310쪽). 이때 오류 메시지나 토스트도 사용자 피드백이자 QA 관찰점이므로 “어떤 조건에서 어떤 상태 변화와 문구가 나오는가”를 함께 적는다.

선택 자체가 의도한 재미인 시스템에서는 자동화가 그 판단을 전부 대체하지 않는지 검토한다. 원문의 파견 사례는 **조건 점수→등급→레벨→캐릭터 고유 ID** 순으로 자동 배치하며, 항상 수동 편성보다 최적이라고 보장하지 않아 전략 여지를 남긴다(PDF 311쪽). 이는 자동화 일반의 목적을 제한하는 원칙은 아니다. 자동화 규칙에는 대상 가능 조건, 정렬/동점 기준, 필요한 실패 피드백과 결과 상태를 명세한다.

### 3. 데이터는 운영 규칙을 실행 가능한 열로 번역한다

MissionTable 사례의 핵심은 표의 모든 열을 복사하는 데 있지 않다. 고유 ID와 문자열 키, 분류, 등장 그룹·확률, 기간, 조건 유형/값, 보상 ID/수량을 분리해 클라이언트 UI와 서버 계산이 같은 원천을 보게 하는 것이다(PDF 311~313쪽). 각 열에는 이름·자료형·의미를 쓰고, 해당되는 경우 허용값·단위·참조·사용처를 덧붙인다. 원문 파견 사례에서는 서버가 조건 배율과 최종 보상 수량을 계산한다(PDF 312쪽). 일반 적용에서는 프로젝트 권한 모델과 부정 조작·일관성 요구에 따라 서버/클라이언트 책임을 정한다.

### 4. UI는 그림이 아니라 상태 전이 명세로 쓴다

레이아웃에는 정보 우선순위와 배치 이유를, 행동 흐름에는 화면 진입→대상 선택→조건 확인→편성→실행→진행→수령→다음 루프를 적는다(PDF 313~316쪽). 원문의 컴포넌트 표는 UI 명칭, 역할, 구성 요소, 작동 규칙, 디자인 의도, 배치 이유를 정리한다. 표시 데이터·활성 조건·클릭 결과·비활성 시 피드백·시각 상태는 해당 요소에 필요한 경우 명시한다(PDF 317~324쪽). 와이어프레임은 위치를, 규칙 표는 동작을 보완한다.

## 주요 개념

- **개요/본문 분리:** 개요는 합의용, 본문은 구현·테스트용이다.
- **조건 기반 보너스:** 캐릭터의 속성·배경·등급 등이 미션 조건과 맞을 때 보상을 다르게 하여 수집과 선택을 연결하는 사례 구조다(PDF 310쪽).
- **데이터 주도 설계:** 등장·기간·조건·보상을 코드 분기 대신 검증 가능한 데이터 행으로 관리한다.
- **상태 기반 UI:** 미배정·진행·완료·선택 중처럼 화면에서 구분되는 상태마다 입력 가능 여부와 결과를 정의한다.

## 안티패턴과 대응

- **개요 없이 상세부터 작성:** 파트가 왜 필요한지와 범위를 다르게 이해한다. 문제·목표·타깃·구성요소부터 합의한다.
- **정상 흐름만 설명:** 모집 마감, 중복 배정, 정원 부족, 보상 없음, 중도 취소가 QA에서 뒤늦게 발견된다. 각 입력의 불가 조건과 피드백을 붙인다.
- **데이터 표만 제시:** 열의 단위·참조·소비처가 없으면 데이터 입력과 런타임 해석이 갈린다.
- **UI 그림에 동작을 맡김:** 버튼 활성 조건, 서버 동기화, 정렬, 상태 갱신을 텍스트로 명시한다.

## 사례 재구성: ‘길드 의뢰’ 문서 뼈대

새 `길드 의뢰`를 만들 때 개요에는 “전투 외 협동 기여처 부족”이라는 문제, 길드 활동을 원하는 타깃, `의뢰 확인→인원 배정→진행→공동 보상 수령` 시나리오, 의뢰 관리·참여 조건·기여도 계산·보상·로그·예외 처리 목록을 둔다. 본문에서는 동시 참여 가능 수, 마감·갱신 규칙, 탈퇴·정원 초과·보상 수령 실패의 결과를 정한다. `GuildRequestTable`에는 ID, 기간, 참여 조건, 목표, 보상, 노출 그룹을 두고 각 열의 타입·단위·참조를 적는다. UI에는 빈 의뢰/참여 중/완료/마감 상태와 각 버튼의 활성 조건을 붙인다. 수치와 보상 곡선은 별도 밸런스 결정이며, 이 장에서 가져올 것은 이러한 **명세의 연결 방식**이다.

## 점검 항목

- [ ] 개요만 읽고 문제, 타깃, 기대 효과, 시스템 경계를 판단할 수 있는가?
- [ ] 각 규칙이 조건→입력→처리→결과→예외 피드백까지 닫히는가?
- [ ] 자동화의 대상·우선순위·동점·실패·완료 상태가 명시됐는가?
- [ ] 데이터 열마다 이름·타입·의미가 있고, 해당되는 단위·허용값·참조·소비처를 명세했는가?
- [ ] UI의 각 상태와 버튼 활성·비활성·서버 동기화·오류 메시지가 검증 가능한가?
