# 17장: 시스템 기획서의 역할과 범위

> **원문 범위:** 책 290–299쪽 / PDF 292–301쪽. 아래의 단계·독자·서술 구조는 이 범위의 저자 제안이다. 특히 아이디어가 기획서로 발전할 가능성이 약 10%라는 표현은 현장의 불확실성을 설명한 예시이지, 프로젝트 KPI나 일반 비율이 아니다(책 293쪽 / PDF 295쪽).

## 핵심 관점

시스템 기획서는 한 번 완성해 넘기는 산출물이 아니라, 아이디어에서 유지보수까지 실제 구현과 함께 자라는 **살아 있는 문서**다(책 292–294쪽 / PDF 294–296쪽). 초안의 목적은 승인과 방향 판단이고, 상세 기획서의 목적은 구현과 검증이다. 원문은 기획서를 나를 위한 메모가 아니라 타인을 움직이게 만드는 설명서라고 한다(책 295–297쪽 / PDF 297–299쪽). 같은 문서라도 단계에 따라 요구하는 정보 밀도가 달라지고, 독자가 다음 행동을 정확히 결정하거나 수행하게 하는 것이 목표라는 것은 스킬 정리다. 동시에 저자는 기획서가 고정된 설계도는 아니지만 본격 개발 전에 완성도를 높여야 변경 가능성을 줄일 수 있고, 기획 변경이 잦을수록 개발 품질이 떨어지고 팀 신뢰가 흔들릴 수 있으므로 기획 의도를 명확히 하고 사전 검토를 철저히 하라고 한다(책 294쪽 / PDF 296쪽).

## 저자 절차와 판단 기준

### 1. 불확실성에 맞춰 문서의 질문을 바꾼다

1. **아이디어 제안서 — Why:** 해결할 문제, 목표, 지금 해야 하는 이유를 짧게 적는다. 원문은 이 단계를 기획서로 발전할 가능성이 10% 정도인, 아이디어 공유를 위한 가벼운 문서로 설명한다(책 292–293쪽 / PDF 294–295쪽). 구현 상세를 확정하는 문서로 쓰지 않는다는 점은 초안 단계에 대한 원문 설명(책 293쪽 / PDF 295쪽)을 이 단계에 적용한 스킬 해석이다.
2. **기획서 초안 — What:** 만들려는 시스템, 가치, 기존 시스템과의 차별성을 보여 준다. 원문 도표는 그 방법이 효과적인 이유와 '다른 방법은 또 없는가?'도 묻는다(책 292쪽 / PDF 294쪽). 이 단계의 성공 조건은 “이 방향으로 진행할까?”라는 의사결정을 돕는 것이며, 확정 명세인 척하지 않는 것이다(책 293쪽 / PDF 295쪽).
3. **상세 기획서 — How:** 승인이 나거나 개발 우선순위에 반영되면(둘 중 하나) 작성한다. 구조·규칙·UI·데이터·입출력 리소스·예외를 명세한다. 프로그래머, 아티스트, QA, 로컬라이징이 각자 구현·제작·검증할 수 있어야 한다(책 293–294쪽 / PDF 295–296쪽).
4. **개발·유지보수 — Review & Update:** 개발 중 바뀐 사항, 변경 사유, 추가 개선 포인트를 명시적 근거와 함께 문서에 반영한다. 그렇지 않으면 기획서가 실제와 달라져 QA·런칭 단계에서 문제가 생긴다(책 294쪽 / PDF 296쪽). 변경 이력을 문서와 빌드의 동기화 수단으로 본다는 표현은 스킬 정리다.

### 2. 독자의 결정을 먼저 적는다

문서를 열기 전 “누가 읽고 무엇을 결정·작업하는가”를 적는다. 원문은 PM·사업팀·운영팀·외부 퍼블리셔에게는 시스템의 역할과 출시 일정·마케팅 영향을 전달하고(책 295쪽 / PDF 297쪽), 채용심사자는 사고력과 커뮤니케이션 역량을 본다고 한다(책 296쪽 / PDF 298쪽). 디렉터·PM에는 가치, 비용 대비 효과, 부작용을; 프로그래머에는 누락 없는 규칙과 상태를; 아티스트에는 화면·애니메이션·이펙트 요구를; QA·로컬라이징에는 예외와 텍스트·다국어 조건을; 다른 기획자에게는 기존 시스템과의 중복·충돌 지점을 제공한다(책 295–296쪽 / PDF 297–298쪽). 독자별 사본이 아니라 공통 본문 안에서 각 직군의 질문이 답을 찾게 연결한다는 해석은 스킬 정리다.

원문은 신입 기획자가 '무엇을 만들고 싶은지'에 치우치기 쉽지만 실무에서는 '왜 지금 해야 하는지'의 설득이 더 중요하다고 하며, 기획서에 반드시 포함할 핵심 내용으로 세 가지를 든다. 이 기획을 실현해야 하는 이유, 실현했을 때의 기대 효과와 파급력(플레이어 경험·리텐션·콘텐츠 완성도), 기획 의도를 만족시키기 위한 개발 요소의 구체화(UI·UX·데이터 테이블·예외 처리)다(책 296–297쪽 / PDF 298–299쪽).

### 3. Why → What → How를 역순 없이 전개한다

- **Why:** 개발팀 관점의 구조·콘텐츠 흐름 개선, 플레이어 관점의 경험·동기·불편 해결, 기대 효과, 유사 사례를 제시한다(책 298쪽 / PDF 300쪽).
- **What:** 핵심 개념과 기능, 전체 플레이 사이클 안의 위치, 타깃 플레이어와 유도 행동, 플레이어의 선택·피드백을 정의한다(책 299쪽 / PDF 301쪽).
- **How:** 규칙·예외·플로, 데이터 구조, 화면의 입력과 피드백, 아트·번역·로그·치트 같은 리소스를 명세한다(책 299쪽 / PDF 301쪽).

이 순서가 세부 기능이 좋아 보여서 필요성을 나중에 끼워 맞추는 일을 막는다는 설명과, Why가 바뀌면 What과 How도 함께 재검토한다는 점검은 스킬 정리다.

## 주요 개념

- **설득 자료와 실행 명세의 분리:** 승인 전에는 문제와 가치의 판단 재료, 승인 후에는 구현 가능한 공통 기준이 중심이다.
- **문서-구현 일치:** 원문은 변경을 명시적 근거와 함께 문서에 업데이트하라고 한다(책 294쪽 / PDF 296쪽). 변경된 실제 사양과 문서가 서로 참조 가능해야 하고 “구두로 합의했다”는 상태가 장기 기준선이 될 수 없다는 판단은 스킬의 적용 지침이다.
- **기획 의도:** 기능 목록이 아니라 어떤 문제를 어떤 플레이어 경험으로 바꾸려는지 설명하는 연결 고리다.
- **필요 리소스:** UI·UX만이 아니라 아트, 번역, 로그, 개발 확인 수단까지 포함한다(책 299쪽 / PDF 301쪽).

## 안티패턴과 대응

> 이 절은 원문의 기준을 실패 사례로 정리한 스킬 정리다. `책 X쪽 / PDF Y쪽`이 붙은 항목만 그 쪽에 원문 근거가 있고, 나머지는 저자의 말로 인용하지 않는다.

- **처음부터 완성본을 요구:** 탐색 단계의 가설까지 구현 확정처럼 쓰면 논의 비용이 커진다. 현재 단계와 미확정 항목을 표시한다.
- **“무엇”부터 나열:** 필요성과 성공 효과가 빠지면 승인자는 가치 판단을, 구현자는 우선순위 판단을 할 수 없다.
- **변경 후 문서 방치:** 기획서와 실제 동작이 달라진다. 원문의 기준은 변경 사항·사유·개선점과 근거를 반영하는 것이다(책 294쪽 / PDF 296쪽). 일시·영향 범위·결정자는 별도 이슈 추적이 없다면 추가할 수 있는 프로젝트 적용 항목이며, 중복 기록을 강제하지 않는다.
- **독자 무시:** “랜덤”, “적절히”, “필요 시” 같은 표현은 직군마다 다른 구현을 낳는다. 상태, 조건, 출력, 예외로 풀어 쓴다.

## 사례 재구성: 장비 프리셋 제안에서 명세까지

신규 `장비 프리셋`을 제안한다고 하자. **Why**에는 “세팅 전환의 반복 조작이 특정 콘텐츠 진입을 늦춘다”와 목표 경험(짧은 준비, 상황별 선택)을 쓴다. **What**에는 전투 유형별 저장 슬롯, 타깃(다수의 장비를 보유한 중후반 이용자), 플레이 사이클에서의 진입 위치를 둔다. 승인 뒤 **How**에는 저장 가능 슬롯 수, 전환 가능 화면·시점, 장비가 잠겼거나 보유하지 않을 때의 처리, UI 피드백, 저장 데이터, 번역 키, 전환 로그를 명세한다. 개발 중 전투 화면 전환이 기술상 불가하다고 확인되면 “전투 전 편성 화면에서만 전환”으로 범위를 바꾸고 사유와 영향(튜토리얼·QA 케이스)을 같이 갱신한다. 이는 원문의 Why→What→How 및 개발 단계 수정 원칙을 새 기능에 적용한 예시다.

## 점검 항목

> 스킬이 만든 점검 목록이다. 근거는 위 절들의 쪽 표기를 따른다.

- [ ] 문서 단계가 제안·초안·상세·변경 반영 중 어디인지 드러나는가?
- [ ] Why에 현재 문제, 플레이어 경험, 기대 효과가 있고 What/How와 모순되지 않는가?
- [ ] 각 직군이 필요한 결정·입력·검증 기준을 찾을 수 있는가?
- [ ] 규칙, UI, 데이터, 예외, 리소스, 로그/확인 수단이 빠지지 않았는가?
- [ ] 변경 사항·사유·새 기준이 반영되어 빌드와 문서가 일치하는가? 영향·결정자 등 추가 이력은 프로젝트의 추적 방식에 맞는가?
