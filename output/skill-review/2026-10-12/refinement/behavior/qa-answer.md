# 가상 출석 보상 기획 메모 검토 및 QA 시나리오

## 입력·형식 확인

- 요청 형식: 메모 원문은 변경하지 않고, 문제 → 영향 → 수정 제안과 QA 시나리오를 작성했다.
- 적용 범위: 수령 규칙(R1~R2), 수령 상태 데이터(D1), 수령 UI(U1~U2), 표시 전용 제목, 명시된 미정 정책을 검토했다.
- QA의 `필수 결과`는 메모에서 확정한 R1·R2·D1·U1만 근거로 한다. 응답 문구, 오류 표시, 재시도와 저장·갱신의 세부 동작은 단정하지 않고 조건부 결과 또는 결정 질문으로 남긴다.

## 검토 결과

### 1. 수령 버튼 활성 조건이 수령 규칙과 충돌한다

**문제**: R1은 `완료 && 미수령`일 때만 보상을 수령할 수 있다고 정한다. 반면 U2는 완료한 회차라면 이미 수령했더라도 수령 버튼을 활성화한다.

**영향**: 수령 완료 상태에서 활성화된 버튼을 누르면 실제 지급은 R2 때문에 한 번으로 막히더라도, 플레이어는 재수령 가능으로 이해할 수 있다. 실패 응답과 화면 갱신 방식도 미정이어서 재접속·다중 기기에서 UI가 실제 상태와 어긋날 수 있다.

**수정 제안**: `수령 가능` 버튼의 활성 조건을 `완료 && 미수령`으로 통일하고, 성공 뒤에는 버튼을 비활성화한 `수령됨` 상태로 전환한다. 완료 회차를 계속 강조해야 한다면 수령 버튼을 활성화하는 대신 완료/수령 상태 표기를 분리한다.

### 2. 수령 여부 데이터의 행 의미·중복 금지 범위가 부족하다

**문제**: D1은 계정·이벤트·회차별 수령 여부를 저장한다고만 하며, 한 기록이 무엇을 의미하는지와 같은 계정·이벤트·회차에 대한 중복 기록을 어떻게 막는지 정하지 않았다.

**영향**: 요청 ID가 각각 달라도 같은 회차의 수령 기록이 둘 이상 생길 수 있다. 동시 요청이나 재시도 시 R2의 “한 번만 지급”을 저장 데이터만으로 증명하거나 복구하기 어렵다.

**수정 제안**: 수령 기록의 한 행을 `한 계정의 한 이벤트 한 회차에 대한 수령 상태`로 정의한다. 해당 범위의 중복 금지 규칙(예: 계정 ID + 이벤트 ID + 회차의 유일성)과 보상 반영·수령 상태 저장을 한 번의 확정 처리로 묶는 방식을 명세한다. 보상 아이템 상세 정보는 기존 아이템 정의를 참조하고 수령 기록에 복제하지 않는다.

### 3. 중복 요청에 대한 보상 안전성은 있으나 결과 계약과 복구 계약이 비어 있다

**문제**: R2는 반복 요청의 추가 지급을 금지하지만, 이미 처리된 요청에 성공을 재전달할지, 이미 수령됨을 안내할지, 일시 오류 뒤 어떤 상태를 다시 조회할지 정하지 않았다. 저장 성공 뒤 응답 유실 또는 앱 종료 같은 실패 시점의 처리도 없다.

**영향**: 보상은 중복 지급되지 않아야 하지만, 플레이어는 보상 수령 여부를 알 수 없거나 계속 재시도할 수 있다. 저장과 지급의 일부만 반영되면 중복 지급 또는 보상 누락 위험이 생긴다.

**수정 제안**: 서버(또는 권한 있는 처리 주체)가 요청 시점에 완료·미수령 상태를 다시 판정하고, 보상 반영과 수령 상태 확정을 분리되지 않게 처리한다. 재시도는 확정 상태를 조회한 뒤 동일한 최종 상태를 반환하도록 설계하고, 중복 요청의 표현 정책은 별도 결정한다.

### 4. 수령 성공 UI만 있고 실패·동기화 상태가 없다

**문제**: U1은 성공 시 `수령됨` 표시만 정의한다. 미완료, 이미 수령, 통신·저장 오류, 다른 기기에서 먼저 수령한 뒤의 갱신 상태가 정의되지 않았다.

**영향**: 버튼이 눌렸지만 변화가 없을 때 버그처럼 보이며, 클라이언트의 오래된 활성 상태를 신뢰하면 R1·R2가 UI에서 보장되지 않는다.

**수정 제안**: 버튼은 서버 판정 전에는 중복 탭을 막는 진행 상태를 제공하고, 결과를 받은 뒤 최신 수령 상태로 다시 그린다. 오류 알림의 형태와 재시도 동선은 결정 후 명세한다. 표시 전용 제목 `출석 보상`에는 입력·저장·활성 조건을 부여하지 않는다.

## 결정 질문

1. 수령 완료 회차에서 U2의 “수령 버튼 활성화”는 정말 재수령 시도용인가, 아니면 완료 회차를 강조하려는 표현인가? 전자라면 R1의 예외 조건과 재요청 UX를, 후자라면 버튼 외 상태 표기를 정해야 한다.
2. 동일 요청 또는 이미 수령한 회차의 응답은 최초 성공 재전달, `이미 수령` 안내, 최신 상태 조회 중 무엇으로 할 것인가?
3. 저장·지급·응답 중 일부가 실패하거나 응답이 유실됐을 때, 언제 재시도를 허용하고 어떤 복구 절차로 최종 상태를 확정할 것인가?
4. 수령 기록의 정확한 유일성 범위는 `계정 + 이벤트 + 회차`인가? 이벤트 버전, 시즌, 서버/캐릭터 등 추가 식별자가 필요한가?
5. 완료 여부는 어느 시스템이 언제 확정하는가? 이벤트 종료·회차 초기화·보상 변경 뒤에도 미수령 보상을 받을 수 있는가?
6. 미완료·이미 수령·일시 오류·서버 오류 각각에 사용할 안내 방식(토스트, 팝업, 인라인 문구)과 재시도 동선은 무엇인가?
7. 수령 버튼을 누른 뒤 결과 수신 전 중복 탭을 막을 진행 상태와, 다른 기기 수령 뒤 화면을 갱신할 시점은 어떻게 할 것인가?

## 검토 기준

- 규칙: 입력 시점과 실행 시점의 상태를 구분하고, 중복 요청·상태 불일치·실패 경로를 정상 흐름과 함께 명세했다.
- 데이터: 수령 기록의 행 의미, 키 조합의 중복 금지 범위, 다른 시스템 데이터의 참조 분리를 점검했다.
- UI: 버튼의 활성·수령됨·진행·오류 상태와 표시 전용 제목의 역할을 분리했다.
