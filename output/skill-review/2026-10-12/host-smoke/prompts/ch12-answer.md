# 주말 랜덤 상점 데이터 설계 검토

> [!IMPORTANT]
> 아래 상점 조건은 **가상 프로젝트 가정**이며, 책의 사례·실제 서비스 정책·관찰 결과가 아닙니다. 12장의 랜덤 풀·비중·타입별 참조 분리 원칙을 이 가정에 적용한 제안입니다.

## 1. 확정 가정·제안·미확정

| 구분 | 내용 | 검증·결정 책임 |
| --- | --- | --- |
| 확정 가정 | 주말 랜덤 상점이 있고 하루 두 번 갱신한다. 후보 타입은 소비품·장비·재료다. | 기획자가 가상 입력의 범위를 확인한다. |
| 제안 | 상점 정의, 진열 상품 행, 랜덤 풀, 타입별 대상, 운영 제한을 별도 책임으로 둔다. | 기획자가 구조를 승인하고, 데이터 담당자와 개발자가 키·조회 구현을 맞춘다. |
| 미확정 | 슬롯별 독립 추출 여부, 동일 상품 중복 허용, 갱신 후 구매 이력 보존, 두 갱신의 정확한 시각이다. | 시스템 기획자와 서버/백엔드 담당자가 정책·저장 범위를 결정한다. |

## 2. 결정 질문

| 질문 | 결정 전 보류 사유 | 결정 책임 |
| --- | --- | --- |
| `추출 단위`는 슬롯마다 독립인가, 앞 슬롯 결과를 제외하는가? | 중복 규칙·분모·재시도 로직이 달라진다. | 시스템 기획자 |
| 같은 `ContentID`의 동시 진열을 허용하는가? | 허용 여부에 따라 풀 중복 검증과 UI 표시가 달라진다. | 시스템 기획자·UI 담당 |
| 갱신 후 구매 이력과 잔여 재고를 보존하는가? | 계정별 저장 키·재구매 제한의 기준 회차가 달라진다. | 시스템 기획자·백엔드 담당 |
| 값은 절대 확률인가, 풀 내부 상대 비중인가? | 계산식과 합계 검증이 다르다. | 시스템 기획자 |
| 타입별 상품 상세는 어디를 참조하는가? | 잘못된 종류의 ID를 막을 대상 테이블 계약이 필요하다. | 데이터 담당자·개발자 |
| 기간·재고·구매 제한은 정의 행, 상품 행, 계정 상태 중 어디가 소유하는가? | 전역 설정과 개별 상품·플레이어별 상태를 혼합하면 갱신·동시 구매 처리 기준이 불명확해진다. | 시스템 기획자·백엔드 담당 |
| 하루 두 번의 실제 갱신 시각과 시간대는 무엇인가? | 입력에 시각이 없으며, 임의의 시각을 데이터 기본값으로 정할 근거가 없다. | 라이브 운영·시스템 기획자 |

## 3. 키 관계와 책임 분리

| 데이터 단위 | 핵심 키·참조 | 책임 |
| --- | --- | --- |
| `WeekendShop` | `ShopID`(PK), `PoolGroupID`(논리적 그룹 조회) | 상점 활성 기간·갱신 정책 식별. 실제 갱신 시각은 미정 값으로 남긴다. |
| `ShopOffer` | `OfferID`(PK), `ShopID`(FK), `PoolEntryID` 또는 `PoolGroupID` | 진열될 상품의 가격·기간·공용 재고·구매 제한 같은 **상품별 운영 규칙**. 여러 슬롯/반복 진열이 필요하면 행으로 늘린다. |
| `RandomPoolEntry` | `PoolEntryID`(PK), `PoolGroupID`, `Type`, `ContentID`, `Weight` | 후보 한 건과 같은 풀 안의 상대 비중. `PoolGroupID`는 여러 행을 조회하는 그룹 키이며 단일 행 외래 키와 구분해 문서화한다. |
| `Consumable` / `Equipment` / `Material` | 각 테이블의 고유 `ContentID`(PK) | 타입별 실제 상품 상세. 랜덤 풀은 상세 값을 복제하지 않고 `Type + ContentID`로만 연결한다. |
| `AccountShopState` *(정책 확정 시)* | `AccountID + ShopID + RefreshCycleID + OfferID` | 계정별 구매 이력·잔여 구매 가능 횟수·갱신 뒤 보존 여부. 구매 이력 보존 정책이 미확정이므로 도입 여부도 미확정이다. |

기간은 상점 전체에 공통이면 `WeekendShop`, 특정 상품만 다르면 `ShopOffer`가 소유한다. 공용 재고는 `ShopOffer`, 계정별 구매 제한과 그 사용량은 정책이 확정되면 `AccountShopState`가 소유한다. 한 열에 전역 기간·상품 재고·계정별 이력을 함께 저장하지 않는다.

## 4. 검증 규칙과 반례

| 검증 대상 | 규칙 | 반례·영향 | 결정 책임·보류 사유 |
| --- | --- | --- | --- |
| 타입 참조 | `Type`은 `CONSUMABLE`, `EQUIPMENT`, `MATERIAL`만 허용하고, 각 값은 대응 테이블의 활성 `ContentID`만 참조한다. | `Type=EQUIPMENT`, `ContentID=재료 ID` 또는 존재하지 않는 ID면 고아/잘못된 종류의 상품이 된다. | 데이터 담당자·개발자: 타입→테이블 매핑과 비활성 콘텐츠 처리 계약이 필요하다. |
| 랜덤 풀 | `PoolGroupID` 조회 결과가 한 건 이상이어야 하며, 상점이 참조하는 그룹이 존재해야 한다. | 빈 풀 또는 없는 그룹이면 갱신할 후보가 없다. | 시스템 기획자: 빈 풀일 때 상점 닫기·재시도·대체 풀 중 어떤 결과인지 미정이다. |
| 비중 | `Weight`는 수치·허용 범위·0 허용 여부를 명시하고, 추출 대상 가중치 합계가 0이면 실패 처리한다. | 모든 후보 비중이 0이면 분모가 0이라 추출할 수 없다. | 시스템 기획자: 0 비중을 비활성 후보로 쓸지, 입력 오류로 막을지 미정이다. |
| 확률 | 값이 `Probability`라면 단위와 합계 규약(예: 풀/등급 단위의 합)을 검증한다. 값이 `Weight`라면 같은 풀 내부의 상대 비율로 계산하며 **합계 100을 강제하지 않는다**. | 비중 30·70·20을 ‘확률 합계 100 위반’으로 거절하면 정상 풀도 막는다. 반대로 확률 행의 합계 규약이 없으면 구현마다 해석이 달라진다. | 시스템 기획자·데이터 담당자: 현재 값의 의미가 미확정이다. |
| 중복 | 독립 추출이면 각 슬롯의 후보 집합이 동일할 수 있다. 비중복 추출이면 선택된 항목을 제외한 뒤 다시 분모를 계산한다. | 중복 금지인데 제외·재계산을 하지 않으면 같은 상품이 다시 뽑힌다. | 시스템 기획자: 독립/비복원 여부가 미확정이다. |
| 기간·갱신 | 시작/종료의 시간대·경계 포함 여부와 `RefreshCycleID` 생성 규칙을 명시한다. | ‘하루 두 번’만으로는 같은 날짜 경계와 갱신 뒤 이력 귀속을 판정할 수 없다. | 라이브 운영·시스템 기획자: 갱신 시각이 미정이다. |
| 재고·구매 제한 | 공용 재고는 원자적으로 감소하고 0 미만을 막는다. 계정 제한은 계정·상점·회차·상품 범위를 키로 명시한다. | 동시 구매에서 마지막 재고가 둘에게 판매되거나, 갱신 뒤 제한이 잘못 초기화될 수 있다. | 백엔드 담당·시스템 기획자: 동시성 처리와 이력 보존 정책이 미확정이다. |

## 5. 가데이터 검토 순서

1. `WeekendShop` 가데이터에 `ShopID`, 활성 기간, `PoolGroupID`를 넣고 실제 갱신 시각은 `미정`으로 둔다.
2. 각 `RandomPoolEntry`에 세 타입을 최소 한 행씩 넣고, 타입별 `ContentID`가 대응 상품 테이블에 존재하는지 확인한다.
3. 같은 풀에 `Weight`가 30·70·20인 행을 넣어 상대 비중으로 계산되는지 확인한다. 합계 120이라는 이유만으로 오류 처리하지 않는다.
4. 별도 가데이터로 빈 `PoolGroupID`, 존재하지 않는 `ContentID`, 타입과 맞지 않는 `ContentID`, 모든 `Weight=0`을 넣고 각각의 검증 오류·보류 정책이 분리되어 보고되는지 확인한다.
5. 독립/비복원 추출을 아직 결정하지 않은 상태에서는 두 결과를 모두 기대값으로 기록한다. 한 쪽을 기본 동작으로 가정해 중복 검증을 고정하지 않는다.
6. 기간·재고·구매 제한 가데이터를 `WeekendShop`·`ShopOffer`·`AccountShopState` 후보 책임에 각각 넣어 중복 소유가 없는지 확인한다. 구매 이력 보존·갱신 시각이 정해지기 전에는 실제 초기화 결과를 확정하지 않는다.

> [!NOTE]
> 이 검토는 구조·키·값 해석의 확인용 가데이터 절차입니다. 실제 서비스의 갱신 시간, 중복 허용, 이력 보존, 빈 풀 처리 정책을 결정하거나 실행한 결과는 아닙니다.
