# 자동 원정 편성 기능 협업 기획서

## 0. 적용 범위

| 구분 | 내용 |
|---|---|
| **책의 사실** | 18장 파견 미션 사례의 자동 배치는 `조건 점수 → 등급 → 레벨 → 캐릭터 고유 ID` 순으로 비교한다. 자동화에는 대상 가능 조건, 우선순위·동점 처리, 실패 피드백, 결과 상태가 필요하다. |
| **가상 프로젝트 가정** | 정원은 4명이다. 같은 캐릭터의 중복 배정은 금지한다. 휴식 중 캐릭터는 후보에서 제외한다. |
| **이 문서의 제안** | 상태 전이, 데이터 구조, UI와 QA 형식은 협업을 위한 초안이다. 미정 정책은 임의로 확정하지 않는다. |

> [!IMPORTANT]
> 네 비교 기준의 **순서만** 참조 범위다. 조건 점수·등급·레벨·캐릭터 고유 ID의 오름차순/내림차순은 프로젝트 미확정이므로, 현재 문서는 특정 후보의 최종 순위를 단정하지 않는다.

---

## 1. 개요

### 문제

출전 후보가 여러 명일 때 플레이어가 매번 후보 상태와 우선순위를 비교해 원정 인원을 채워야 한다. 자동 편성은 이 반복을 줄이되, 선택 기준과 실패 원인을 이해할 수 있어야 한다.

### 목표

가능한 후보를 확인하고, 정렬 방향이 확정되었을 때 최대 4명의 결과를 제시한다. 정원 부족·후보 없음·상태 변경·취소 상황에서는 잘못된 편성을 확정하지 않고 원인과 다음 행동을 안내한다.

### 타깃

원정 인원을 빠르게 편성하려는 플레이어와, 후보 상태·정렬·결과를 같은 규칙으로 구현·검증해야 하는 기획·개발·UI/UX·QA 담당자.

### 구성 요소

1. 후보 수집과 가능/제외 사유 판정
2. 조건 점수·등급·레벨·캐릭터 고유 ID 비교
3. 최대 4명 선택 및 중복 배정 검증
4. 결과 표시, 상태 재검증, 취소 안내
5. 후보·선택·검증 데이터를 연결하는 테이블과 QA 케이스

## 2. 본문

### 2.1 상태와 입력

| 상태 | 진입 조건 | 표시 | 입력 가능 여부 | 결과 |
|---|---|---|---|---|
| 후보 조회 중 | 자동 편성 요청 시작 | 후보를 불러오는 상태 | 자동 편성 재요청은 처리 중으로 보이게 하는 방안이 제안이다. | 최신 후보로 판정 진행 |
| 편성 가능 | 중복 배정이 아니고 휴식 중이 아닌 후보가 4명 이상 | 후보별 비교값과 가능 상태 | 자동 편성 실행을 허용하는 방안이 제안이다. | 정렬 방향 확정 후 상위 4명 결과 생성 |
| 정원 부족 | 가능한 후보가 1~3명 | 가능한 인원·제외 사유 | 자동 확정은 불가로 표시하는 방안이 제안이다. | 결과를 확정하지 않음 |
| 후보 없음 | 가능한 후보가 0명 | 후보 없음·제외 사유 | 자동 확정 불가 | 결과를 확정하지 않음 |
| 결과 검증 중 | 자동 선택 결과 생성 후 확정 전 | 선택된 후보와 재검증 진행 상태 | 취소 가능 시점은 미정 | 최신 후보 상태 확인 |
| 결과 무효 | 검증 중 선택 후보가 휴식·중복 배정 등으로 바뀜 | 변경 후보와 재실행 필요 여부 | 재실행 입력은 제공할 수 있으나 방식은 제안 | 결과를 확정하지 않고 후보 조회로 복귀 |
| 취소됨 | 취소 요청 수신 | 취소 결과 및 영향 범위 | 확정 전/후 취소 허용 여부는 미정 | 되돌림·보상·동기화 정책은 미정 |

### 2.2 조건·판정·결과·예외

| 순서 | 조건 및 판정 | 결과 | 예외/피드백 |
|---|---|---|---|
| 1 | 후보가 이미 배정되었는지 확인한다. | 배정 중이면 후보에서 제외한다. | `AlreadyAssigned` 사유를 표시한다. 이는 가상 프로젝트 가정이다. |
| 2 | 후보가 휴식 중인지 확인한다. | 휴식 중이면 후보에서 제외한다. | `Resting` 사유를 표시한다. 이는 가상 프로젝트 가정이다. |
| 3 | 가능한 후보 수를 확인한다. | 0명이면 후보 없음, 1~3명이면 정원 부족으로 종료한다. | 정원 4명은 가상 프로젝트 가정이다. 부분 편성 허용 여부는 미정이다. |
| 4 | 가능한 후보를 조건 점수로 비교한다. | 다음 비교 기준 또는 순위 결정으로 진행한다. | 정렬 방향 미정 |
| 5 | 조건 점수가 같으면 등급, 다시 같으면 레벨, 다시 같으면 캐릭터 고유 ID를 비교한다. | 정렬 방향이 확정된 경우에만 최종 순위를 얻는다. | 각 기준의 정렬 방향 미정 |
| 6 | 상위 4명을 결과로 만든 뒤 후보 상태를 다시 확인한다. | 모두 유효하면 결과를 제시한다. | 재검증은 이 문서의 제안이며, 불가 후보가 있으면 결과 무효·재실행 안내를 표시한다. |

> [!WARNING]
> 캐릭터 고유 ID는 마지막 동점 해소 기준이지만 방향이 미정이다. 따라서 조건 점수·등급·레벨이 같은 두 후보 중 누가 앞서는지는 현 시점에 결정할 수 없다.

## 3. 데이터 명세 제안

아래 테이블은 구현을 강제하는 스키마가 아니라, 행의 책임·기본 키·참조·중복 검증 범위를 합의하기 위한 제안이다.

| 테이블 | 한 행의 의미 | 기본 키 | 주요 값 | 단일 행 참조 | 그룹 조회 | 중복 검증 범위 |
|---|---|---|---|---|---|---|
| `FormationRequest` | 자동 편성 요청 1건 | `FormationRequestID` | `RequestState`, `ValidationState` | 해당 없음 | `FormationCandidateSnapshot`에서 같은 `FormationRequestID`를 가진 후보 행 전체를 조회한다. 이는 후보 **그룹 조회**다. | 요청 ID는 유일해야 한다. |
| `FormationCandidateSnapshot` | 요청 시점 후보 캐릭터 1명 | `CandidateSnapshotID` | `FormationRequestID`, `CharacterID`, `CandidateState`, `IsResting`, `AssignmentState`, `ConditionScore`, `Grade`, `Level` | `CharacterID`는 캐릭터 정의의 **단일 행**을 참조한다. `FormationRequestID`는 이 후보가 속한 요청 1건을 참조한다. | 같은 `FormationRequestID`로 여러 후보 행을 모아 후보 집합을 만든다. 이는 단일 캐릭터 참조와 다른 **역방향 그룹 조회**다. | 같은 요청 안에서는 `CharacterID`가 한 번만 존재해야 한다. |
| `FormationSelection` | 요청 결과로 선택된 후보 1명 | `FormationSelectionID` | `FormationRequestID`, `CandidateSnapshotID`, `Rank`, `ValidationState` | `CandidateSnapshotID`는 선택된 후보 스냅샷 **단일 행**을 참조한다. | 같은 `FormationRequestID`의 선택 행 전체를 조회해 최대 4명 결과를 얻는다. | 같은 요청 안에서 `Rank`와 `CandidateSnapshotID`는 각각 유일해야 하며, 선택 행은 최대 4개다. |
| `CandidateExclusion` | 요청에서 제외된 후보 1명과 사유 1건 | `CandidateExclusionID` | `FormationRequestID`, `CandidateSnapshotID`, `ReasonCode` | `CandidateSnapshotID`는 제외 후보 스냅샷 **단일 행**을 참조한다. | 같은 `FormationRequestID`의 제외 행을 후보별 사유 목록으로 조회한다. | 동일 후보·동일 사유의 중복 기록 허용 여부는 미정이다. |

### 참조와 검증 규칙

| 구분 | 규칙 |
|---|---|
| 후보 상태 | `CandidateState`, `IsResting`, `AssignmentState`를 이용해 가능 여부를 판정한다. 실제 ENUM 값과 상태 전이 책임은 미정이다. |
| 조건 점수 | `ConditionScore`는 우선순위 첫 기준이다. 산식·범위·동점 값과 정렬 방향은 미정이다. |
| 단일 행 참조 | `CharacterID`, `CandidateSnapshotID`처럼 하나의 대상 행을 가리키는 키는 대상 존재와 유일한 식별을 검증한다. |
| 그룹 조회 | `FormationRequestID`로 여러 후보·선택·제외 행을 찾는 것은 반복 행의 집합 조회다. 비어 있는 후보 집합과 최대 4명 선택 결과를 별도로 검증한다. |
| 최종 검증 | 같은 요청에서 동일 캐릭터가 둘 이상 선택되지 않고, 선택 수가 4를 넘지 않으며, 결과 확정 전 후보 상태가 여전히 가능한지 확인한다. 재검증 시점과 서버 권한은 미정이다. |

## 4. UI 명세 제안

| 요소 | 상태별 표시 | 입력 가능 여부 | 결과/피드백 |
|---|---|---|---|
| 후보 목록 | 조건 점수·등급·레벨·고유 ID, 가능/제외 사유, 정렬 방향 미확정을 표시한다. | 목록은 표시 전용이다. | 선택 기준과 제외 이유를 확인할 수 있다. |
| 자동 편성 버튼 | 편성 가능, 정원 부족, 후보 없음, 결과 검증 중, 결과 무효를 구분한다. | 편성 가능일 때 실행 가능하게 하는 방안이 제안이다. | 실행 결과 또는 실패 안내로 전환한다. |
| 결과 영역 | 선택 후보 최대 4명, 순위, 제외 사유, 검증 상태를 표시한다. | 확정 및 취소 입력의 활성 조건은 미정이다. | 상태 변경 시 결과 무효와 재실행 안내를 보여 준다. |
| 취소 입력 | 취소 가능 여부와 취소 영향 범위를 표시한다. | 확정 전/후 각각의 허용 여부는 미정이다. | 취소 처리 성공/실패와 되돌림 범위를 안내한다. |
| 안내 메시지 | 정원 부족·후보 없음·상태 변경·취소를 구분한다. | 정적 안내 문구는 입력·저장 규칙이 필요 없다. | 문구, 노출 시간, 차단 여부는 프로젝트에서 결정한다. |

## 5. QA 케이스

| ID | 사전 조건/입력 | 기대 확인 | 미정 확인 사항 |
|---|---|---|---|
| QA-01 정원 부족 | 가능한 후보가 3명이고 나머지는 중복 배정 또는 휴식 중 | 4명 결과를 확정하지 않고 가능한 인원·제외 사유를 보인다. | 부분 편성 허용 여부 |
| QA-02 동점 | 조건 점수·등급·레벨이 같고 고유 ID가 다른 후보 둘 | 고유 ID가 마지막 비교 기준으로 전달됨을 확인한다. | 고유 ID 정렬 방향과 실제 앞선 후보 |
| QA-03 후보 없음 | 모든 후보가 중복 배정 또는 휴식 중 | 후보 없음으로 종료하고 각 제외 사유를 보인다. | 추가 제외 사유의 허용 목록 |
| QA-04 편성 중 상태 변경 | 결과 생성 뒤 확정 전, 선택 후보 하나가 휴식 또는 중복 배정으로 변경됨 | 재검증에서 결과가 무효화되고 재실행 안내가 나온다. | 변경 감지 시점, 재시도, 서버 동기화 방식 |
| QA-05 취소 | 자동 편성 결과가 표시된 상태에서 취소 요청 | 취소 요청의 성공/실패와 영향 범위를 표시한다. | 취소 가능 시점, 배정·보상·서버 반영의 되돌림 정책 |

## 6. 미확정 질문

1. 조건 점수·등급·레벨·캐릭터 고유 ID는 각각 어느 방향으로 정렬하는가?
2. 자동 편성 또는 원정 완료에 보상이 있는가? 있다면 지급·수량·취소/실패 시 처리는 무엇인가?
3. 후보 조회·결과 확정·상태 변경·취소는 어느 시점과 권한으로 서버에 동기화하며, 재시도·충돌은 어떻게 처리하는가?

## 7. 협업 인계

- **기획:** 정렬 방향, 부분 편성, 취소·보상 정책을 확정한다.
- **개발:** 확정된 상태 모델과 참조 계약을 바탕으로 후보 그룹 조회·중복 검증·재검증·동기화 책임을 구현한다.
- **UI/UX:** 실제 플랫폼에서 버튼 상태와 취소 피드백을 확정한다.
- **QA:** 다섯 QA 케이스에 미정 정책을 채운 뒤 실제 상태 전이와 데이터 무결성을 검증한다.

근거: 18장 시스템 기획서 실습의 자동 편성 우선순위·상태 기반 문서 구조, 12장의 단일 행 참조와 반복 그룹 조회 구분, 16장의 상태별 입력·피드백 명세 원칙.
