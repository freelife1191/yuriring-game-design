# 보상 수령 명세 기획 검토

아래는 **기획 검토용 시나리오**다. 실제 테스트를 실행한 결과가 아니다.

## 자료에서 확인되는 기준과 현재 명세의 범위

자료는 출석 이벤트 메타와 회차별 보상 행을 분리하고, 보상 행이 이벤트와 아이템을 키로 참조하는 구조를 제시한다. 또한 규칙은 상황·필요 정보·판단·결과·예외를 모두 써야 하며, 실행 직전에 실제 상태를 다시 검증해야 한다. UI는 버튼의 역할·상태·결과·갱신을 정의해야 하지만 정적 제목은 입력·저장 조건을 가질 필요가 없다. [11장: 데이터 테이블 설계](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md), [7장: 규칙 구성](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md), [15장: UX/UI 설계](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md), [16장: UX/UI 구성요소](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md)를 적용했다.

다만 자료가 이 시스템의 고유한 **수령 자격**, `ClaimRecord`의 상태값, 중복 요청 식별 방식, 자동 수령·만료 정책을 직접 정의하지는 않는다. 다음 항목은 사용자 명세의 R1·R2·D1·D2·U1·U2를 검토한 결과이며, 미정 값은 예상 결과로 확정하지 않는다.

| 실패 UI | 실패 시 UI 처리와 실제 기록 조회 시점이 미정이다. | 버튼을 유지·비활성 중 어느 쪽인지, 재시도 가능 여부가 구현자마다 달라진다. | 실패 원인별 안내, 버튼 상태, 재조회/재시도 조건을 명세한다. 일반 조건 미충족은 이유를 알리고, 비정상 접근은 필요한 범위만 안내한다. |
| 정적 제목 | ‘화면 제목은 정적 텍스트’다. | 입력·기본값·저장 조건을 억지로 추가하면 문서만 복잡해진다. | 제목에는 역할·표기 문구만 명세하고, 입력·저장 규칙은 수령 버튼·상태 표시에만 적용한다. |

## 결과 판정 기준

**확정 정책에서 반드시 지켜야 할 결과**는 R1·R2·U1이 서로 양립하는 범위에서만 정한다. 즉, 완료·미수령 보상을 버튼으로 성공적으로 수령했다면 수령 완료가 되어야 하고(R1), 같은 요청은 한 번만 반영되어야 하며(R2), 성공 시 완료 안내가 보여야 한다(U1). `RewardEvent`와 `RewardRow`, `ClaimRecord`의 필드는 D1·D2가 정한 범위에서 기록되어야 한다.

반면 정확한 상태값, 중복 요청의 응답, 참조 오류 처리, 상태 재검증 시점, 재접속 조회 시점은 명세에 없다. U2의 ‘미수령 여부와 무관한 활성화’는 R1과 충돌하므로, 이 부분은 현재 **반드시 지켜야 할 단일 결과를 만들 수 없다.** 아래 표에서 이를 조건부 결과로 분리한다.

| 누락되었거나 잘못된 참조 | 대상 `RewardRow`의 이벤트 ID 또는 아이템 ID가 비어 있거나 참조 대상에 존재하지 않는 상태에서 수령을 시도한다. | 현재 명세에는 이 오류의 저장·UI 결과를 확정한 규칙이 없다. 따라서 이를 정상 수령 성공으로 판정하면 안 된다. | 참조 오류를 수령 불가로 처리한다면 지급·수령 완료 기록을 만들지 않고 현재 상태를 보존하며 사유를 안내하는 정책을 명시한다. 운영 보정으로 처리한다면 보정의 주체·기준·지급 시점을 별도로 정한다. | D1, R1 |
| 수령 직전 상태 변경 | 화면에는 수령 가능으로 보였지만, 클릭 직전에 만료·다른 경로의 수령·자격 상실이 발생했다. | R1은 성공 후에만 완료 상태가 된다고 하므로, 이미 유효하지 않은 수령을 성공으로 확정해서는 안 된다. | 실행 순간 재검증을 채택하면 새 지급 없이 변경된 실제 상태를 반환한다. 화면 표시 시점을 그대로 신뢰하는 방식은 경합 결과를 처리할 정책이 추가로 필요하다. 재시도 가능 여부와 안내 문구도 미정이다. | R1, R2, U1 |
| 재접속 | 이전 세션의 성공·실패·진행 중 상태가 있을 수 있는 계정이 화면에 다시 들어온다. | U2는 완료 상태 버튼을 다시 활성화하라고 하지만, R1은 미수령 보상만 직접 수령하게 하므로 두 규칙을 동시에 만족하는 단일 합격 결과는 없다. | R1을 우선하면 실제 지급 기록을 조회해 미수령일 때만 활성화하고, 이미 완료면 완료 상태를 보인다. U2를 문자 그대로 유지하면 이미 완료된 보상도 활성화되므로 클릭 결과·중복 지급 방지·오류 안내를 추가 정의해야 한다. | R1, D2, U2 |

## 합격 조건을 확정하기 위한 질문

1. ‘완료 상태’는 어떤 이벤트 진행 조건을 만족한 상태이며, 보상 행 단위와 이벤트 단위 중 어디까지 수령 자격을 판정하는가?
2. `ClaimRecord`의 한 행은 무엇을 뜻하는가? 계정별 보상 행 1회 기록인지, 시도 이력인지, 두 역할을 분리할지 정해야 한다.
3. `RewardRow`의 기본 키와 발번 규칙은 무엇이며, `(계정 ID, 보상 행 ID)`에 중복을 허용하는가?
4. 동일 요청의 식별자는 무엇이고, 네트워크 재전송·연속 클릭·서로 다른 요청의 중복 수령을 각각 어떻게 처리하는가?
5. 지급 반영과 수령 완료 기록이 한쪽만 성공했을 때의 복구 기준은 무엇인가?
6. 자동 수령, 만료, 보관함 가득 참, 참조된 이벤트/아이템의 비활성화는 각각 어떤 상태 전이를 만드는가?
7. 재접속/화면 재진입 때 언제 실제 지급 기록을 조회하며, 조회 실패 중 버튼·안내·재시도는 어떻게 보이는가?

> [!NOTE]
> 이 시나리오는 규칙·데이터·UI의 연결을 검토하기 위한 것이다. 자료의 출석 보상 테이블 사례는 이벤트와 반복 보상 행의 분리·참조 원칙을 보여 주며, 이 프로젝트의 `ClaimRecord` 스키마나 중복 요청 프로토콜을 확정하지 않는다.
