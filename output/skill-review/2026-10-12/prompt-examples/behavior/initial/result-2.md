# 보상 수령 명세 기획 검토

아래는 **기획 검토용 시나리오**다. 실제 테스트를 실행한 결과가 아니다.

## 자료에서 확인되는 기준과 현재 명세의 범위

자료는 출석 이벤트 메타와 회차별 보상 행을 분리하고, 보상 행이 이벤트와 아이템을 키로 참조하는 구조를 제시한다. 또한 규칙은 상황·필요 정보·판단·결과·예외를 모두 써야 하며, 실행 직전에 실제 상태를 다시 검증해야 한다. UI는 버튼의 역할·상태·결과·갱신을 정의해야 하지만 정적 제목은 입력·저장 조건을 가질 필요가 없다. [11장: 데이터 테이블 설계](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md), [7장: 규칙 구성](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md), [15장: UX/UI 설계](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md), [16장: UX/UI 구성요소](/Users/freelife/ai/yuriring-game-design/.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md)를 적용했다.

다만 자료가 이 시스템의 고유한 **수령 자격**, `ClaimRecord`의 상태값, 중복 요청 식별 방식, 자동 수령·만료 정책을 직접 정의하지는 않는다. 다음 항목은 사용자 명세의 R1·R2·D1·D2·U1·U2를 검토한 결과이며, 미정 값은 예상 결과로 확정하지 않는다.

## 모순·누락표

| 구분 | 발견 사항 | 플레이·구현 영향 | 보완 방향 |
| --- | --- | --- | --- |
| 규칙 ↔ UI | R1은 ‘미수령’일 때만 직접 수령인데, U2는 재접속 후 미수령 여부와 무관하게 완료 상태 버튼을 다시 활성화한다. | 이미 지급된 보상을 다시 받을 수 있는 것처럼 보이거나, 클릭 뒤 오류가 난다. | 재접속 때 실제 지급 기록과 현재 수령 자격을 조회한 뒤 버튼을 활성화한다. 지급 완료면 비활성/완료 표기로 갱신한다. |
| 중복 요청 | R2의 ‘같은 요청은 한 번만’에 요청 식별자, 적용 범위, 응답 정책이 없다. | 동일 요청 재전송과 별도 중복 클릭을 구분할 수 없고, 중복 지급 또는 모호한 오류 응답이 생긴다. | 수령 시도 단위와 중복 판정 키를 정한다. 중복일 때 기존 성공을 반환할지, 현재 상태를 반환할지도 결정한다. |
| 데이터 키 | D2가 참조하는 보상 행 ID의 발번 규칙·중복 금지·빈값 금지가 미정이다. | `ClaimRecord`가 어느 보상 행을 가리키는지, 동일 회차를 한 번만 수령했는지 검증할 수 없다. | `RewardRow` 한 행의 기본 키 의미와 발번 규칙을 정의하고, 계정 ID와 보상 행 ID의 관계에서 필요한 유일성 규칙을 정한다. |
| 참조 무결성 | D1에는 이벤트 ID·아이템 ID의 참조 대상과 존재 검증이 명시되지 않았다. | 존재하지 않는 이벤트/아이템을 가진 보상 행이 만들어질 수 있다. | 각 외래 키의 대상 테이블·칼럼·존재 검증 시점을 명시한다. 아이템 이름·아이콘 등은 보상 행에 복사하지 않고 기존 정의를 참조한다. |
| 상태 전이 | R1은 성공 뒤 ‘수령 완료’로 바꾼다고만 하며, 완료/미수령/지급 중/실패/만료 등 필요한 상태와 전이 순서가 없다. | 지급 성공과 기록 변경 사이에 오류가 나면 중복 또는 누락을 판단하기 어렵다. | 최소 상태 집합과 각 상태의 진입·종료 조건, 지급 반영과 기록 변경의 일관성 기준을 정한다. 상태 수와 구현 방식은 프로젝트 기술 제약에 맞춰 결정한다. |
| 실패 UI | 실패 시 UI 처리와 실제 기록 조회 시점이 미정이다. | 버튼을 유지·비활성 중 어느 쪽인지, 재시도 가능 여부가 구현자마다 달라진다. | 실패 원인별 안내, 버튼 상태, 재조회/재시도 조건을 명세한다. 일반 조건 미충족은 이유를 알리고, 비정상 접근은 필요한 범위만 안내한다. |
| 정적 제목 | ‘화면 제목은 정적 텍스트’다. | 입력·기본값·저장 조건을 억지로 추가하면 문서만 복잡해진다. | 제목에는 역할·표기 문구만 명세하고, 입력·저장 규칙은 수령 버튼·상태 표시에만 적용한다. |

| --- | --- | --- | --- | --- | --- |
| 정상 수령 | 계정이 완료 상태이고 미수령이며, 보상 행·이벤트·아이템 참조가 유효하다. | 수령 버튼 1회 선택 | 지급 반영과 수령 완료 기록이 같은 수령 대상으로 일관되게 남는다. 구체 상태명·트랜잭션 방식은 미정이다. | 성공 안내를 표시하고 해당 보상의 버튼을 완료/비활성 상태로 갱신한다. | R1, D1, D2, U1 |
| 같은 요청 재전송 | 첫 요청이 이미 반영되었거나 반영 결과를 반환 중이다. | 같은 요청 식별자로 재전송 | **정책 확정 전에는 결과를 단정할 수 없다.** 중복을 기존 성공으로 응답한다면 지급 기록은 추가되지 않고 기존 완료 상태를 반환한다. 오류로 처리한다면 그 실패 응답과 재조회 규칙이 필요하다. | 선택한 중복 정책에 맞춰 완료 상태 또는 명확한 안내를 보인다. | R2, D2, U1 |
| 누락되었거나 잘못된 참조 | 대상 `RewardRow`의 이벤트 ID 또는 아이템 ID가 비어 있거나, 참조 대상에 존재하지 않는다. | 수령 시도 | 지급·수령 완료 기록을 만들지 않고 기존 상태를 보존한다. | 수령 불가 이유를 안내하고, 현재 상태를 재조회한다. | D1, R1 |
| 수령 직전 상태 변경 | 화면에서는 수령 가능으로 보였지만 실행 직전에 만료·다른 경로의 수령·자격 상실 등으로 실제 상태가 바뀌었다. | 수령 버튼 선택 | 실행 시점 재검증에 실패하면 새 지급을 만들지 않는다. 변경된 실제 상태를 보존한다. | 이전 화면 상태를 믿지 말고 최신 결과를 반영한다. 재시도 가능 여부와 안내 문구는 정책으로 정한다. | R1, R2, U1 |
| 재접속 | 이전 세션에서 성공·실패·진행 중 어느 상태인지 가능하며, 로컬 표시가 최신이라는 보장이 없다. | 화면 재진입 또는 재접속 | 실제 지급 기록과 수령 자격을 조회한 결과를 기준으로 한다. U2의 무조건 활성화는 적용하지 않는다. | 미수령일 때만 활성화하고, 이미 완료면 완료 상태를 보여 준다. 조회 실패 상태의 표시·재시도는 미정이다. | R1, D2, U2 |

## 합격 조건을 확정하기 위한 질문

1. ‘완료 상태’는 어떤 이벤트 진행 조건을 만족한 상태이며, 보상 행 단위와 이벤트 단위 중 어디까지 수령 자격을 판정하는가?
2. `ClaimRecord`의 한 행은 무엇을 뜻하는가? 계정별 보상 행 1회 기록인지, 시도 이력인지, 두 역할을 분리할지 정해야 한다.
3. `RewardRow`의 기본 키와 발번 규칙은 무엇이며, `(계정 ID, 보상 행 ID)`에 중복을 허용하는가?
4. 동일 요청의 식별자는 무엇이고, 네트워크 재전송·연속 클릭·서로 다른 요청의 중복 수령을 각각 어떻게 처리하는가?
5. 지급 반영과 수령 완료 기록이 한쪽만 성공했을 때의 복구 기준은 무엇인가?
6. 자동 수령, 만료, 보관함 가득 참, 참조된 이벤트/아이템의 비활성화는 각각 어떤 상태 전이를 만드는가?
7. 재접속/화면 재진입 때 언제 실제 지급 기록을 조회하며, 조회 실패 중 버튼·안내·재시도는 어떻게 보이는가?

> [!NOTE]
> 이 시나리오는 규칙·데이터·UI의 연결을 검토하기 위한 것이다. 자료의 출석 보상 테이블 사례는 이벤트와 반복 보상 행의 분리·참조 원칙을 보여 주며, 이 프로젝트의 `ClaimRecord` 스키마나 중복 요청 프로토콜을 확정하지 않는다.
