# 유리링 게임 시스템 기획 스킬: 챕터별 고급 활용

이 가이드는 프로젝트에 생성된 [`yuriring-game-system-design`](../.agents/skills/yuriring-game-system-design/SKILL.md) 스킬을 실제 기획 작업에 깊게 쓰는 방법이다. 스킬은 정윤지(유리링)의 『유리링의 실전 게임 시스템 기획』 8부 21장을 장별 자료로 보관한다. 모든 장을 한 번에 읽기보다, 현재 결정해야 하는 질문에 맞는 장을 먼저 호출하는 편이 정확하고 효율적이다.

아래의 사용 전략, 요청문, 산출물 양식과 실무 시나리오는 책의 원문을 재현한 것이 아니라 스킬의 장별 내용을 바탕으로 만든 **새 응용 예시**다. 저자의 공식 절차나 프로젝트의 확정 사양으로 취급하지 않는다. 책 속 사례의 수치·ID·확률·기간도 기본값으로 복사하지 않는다. 출처 범위와 OCR·도식의 한계는 [스킬 출처 정보](../.agents/skills/yuriring-game-system-design/source.json)와 각 장의 첫머리에서 확인한다.

아래의 8개 `활용 영역`은 21장을 읽기 순서와 업무 주제로 묶은 **이 가이드의 편집 분류**다. 원본 책의 공식 부 제목을 재현하거나 대체하지 않는다.

## 호출과 요청문 작성법

생성된 스킬 이름으로 다음처럼 요청한다. **아래 코드 블록은 대화창에 입력할 프롬프트이며 터미널 명령이 아니다.** 장별 고급 예시는 Codex 형식으로 작성했다. Claude Code에서는 첫 호출을 `/yuriring-game-system-design`으로, Antigravity에서는 `yuriring-game-system-design 스킬을 사용해`로 바꾼다. 자연어로 작성된 기본 요청은 그대로 사용할 수도 있다.

| 호스트 | 호출 형식 | 예시 |
| --- | --- | --- |
| Codex | `$yuriring-game-system-design` | `$yuriring-game-system-design 장비 프리셋의 규칙과 예외를 설계해줘.` |
| Claude Code | `/yuriring-game-system-design` | `/yuriring-game-system-design 장비 프리셋의 규칙과 예외를 설계해줘.` |
| Antigravity | 스킬명을 자연어로 언급 | `yuriring-game-system-design 스킬을 사용해 장비 프리셋의 규칙과 예외를 설계해줘.` |

좋은 요청에는 다음 다섯 가지를 가능한 범위에서 넣는다.

1. **결정할 기능과 문제:** 예: “초보자가 장비를 매번 갈아 끼워 콘텐츠 진입을 포기한다.”
2. **대상과 맥락:** 장르, 플레이어 단계, 기존 시스템, 플랫폼, 현재 흐름.
3. **제약:** 일정, 서버/클라이언트 제약, 재사용할 UI·데이터, 운영 정책.
4. **원하는 산출물:** 의도문, 규칙표, 플로 차트 초안, 테이블, 와이어프레임 명세, 리뷰 중 무엇인지.
5. **확정·미확정의 구분:** 모르는 값은 가정으로 표시하고, 사실 근거가 필요한 주장은 검증 후보로 남기라고 요청한다.

스킬 답변은 곧바로 확정 사양이 아니다. 특히 구현, 확률, 경제, 보안, 접근성, 로그, 실제 이용자 효과는 프로젝트의 기술 제약·데이터·테스트 결과로 별도 확인한다.

### 프롬프트를 적용하는 순서

1. **장 선택:** 해결할 문제와 가장 가까운 장의 바로가기를 연다.
2. **예시 선택:** A/B는 두 가지 적용 상황의 구분이다. 제목과 첫 요청을 읽고 설계·분석·비교·검토 중 현재 목적에 맞는 예시를 고른다.
3. **입력 교체:** 가상 상황·수치를 실제 프로젝트의 정보로 바꾸고, 확정 정책과 미정 정책을 구분한다.
4. **결과 확인:** 예시 아래의 기대 결과와 해당 장의 검토 기준으로 답변을 읽는다.
5. **후속 요청:** 선택한 예시에서 실제로 만든 결과를 이어서 보완한다. 해당되지 않는 항목은 빼거나 현재 기능의 이름으로 바꾼다. 새 대화라면 [새 대화 인계 형식](#handover)으로 기존 산출물, 확정·미정 정책, 이어받을 조건 판정을 함께 제공한다.

### 새 대화 인계 형식

후속 요청은 같은 대화에서 쓰는 것이 가장 간단하다. 새 대화에서 이어 갈 때는 앞 대화의 답변을 기억하지 못하므로, 판단에 필요한 결과·조건·근거를 요청에 직접 붙인다. 이전 평가나 기대 답안이 아니라 실제로 받은 결과와 선택만 넣는다.

```text
$yuriring-game-system-design [장]장 고급 예시 [A/B]의 결과 중 [검토할 부분]을 보완해줘.
선행 결과·선택안: [실제로 받은 결과 요약과 선택 이유]
유지할 확정 조건 / 미정 사항: [정책과 아직 결정하지 않은 축]
이어받을 조건·예외: [성립·불성립·미확인·해당 없음 판정 / 책 쪽·입력·관측 근거 / 미확인 항목]
판정이 유지되거나 바뀌는 이유, 새 반례와 다음 확인 자료를 남겨줘.
```

'성립·불성립·미확인·해당 없음'은 이어받는 조건의 적용 판단을 적는 칸이다. 해당하지 않는 조건은 짧게 이유만 적고 새 시스템이나 정책을 억지로 추가하지 않는다.

장 번호가 떠오르지 않으면 [참조 자료 색인](../.agents/skills/yuriring-game-system-design/references/index.md)에서 구체적인 사례·테이블·UI 이름으로 찾는다. 예를 들어 **다국어 NPC 대사 → 12장**, **수량 스테퍼 → 16장**, **자동 파견 → 18장**으로 시작하고, 필요한 구조·규칙·화면 장을 추가한다. 색인의 장 연결 표와 UX/UI 세부 PDF 위치도 활용할 수 있다.

> **장을 연결하는 방법**
>
> 전체 설계를 한 번에 요청할 수 있지만, 복잡한 기능은 **의도 → 구조 → 규칙 → 데이터 → UI → 협업 문서** 순으로 산출물을 이어받으면 앞 단계의 결정과 뒤 단계의 불일치를 찾기 쉽다. 미확정 사항은 다음 단계로 넘길 때도 그대로 표시한다.

> [!NOTE]
> **완성된 부분은 유지하고 현재 필요한 산출물만 요청한다**
>
> 아래 순서는 이 가이드의 활용 예시다. 이미 의도나 규칙이 확정되어 있다면 필요한 데이터·UI·검토 단계부터 시작할 수 있다. 예시의 QA 개수·가데이터 행 수는 연습용 요청량이며 책의 필수 규격이 아니다.

```text
정의 → 한 행의 의미 → 연결 예시 → 흔한 오해 순으로 정리해줘.
책의 개념과 설명을 위해 새로 만든 데이터는 구분해줘.
마지막에 이해 확인 문제 3개만 내고, 정답은 내가 답한 다음에 알려줘.
```

**적용 예시 — 필요한 패턴을 고르고 산출물을 연결하기**

```text
$yuriring-game-system-design 실무 패턴을 참조해 길드 기부 시스템에 맞는
패턴 3개를 고르고, 선택 이유와 적용할 장을 알려줘.
가상 전제: 재료를 기부하면 개인 기여도와 길드 진행도가 함께 증가한다.
기부 취소와 탈퇴 후 보상 정책은 아직 미정이다.
선택한 패턴별 입력·결정·산출물·다음 패턴에 넘길 정보를 표로 작성해줘.
새 규칙은 제안으로 표시하고, 같은 정책을 여러 표에 중복 정의하지 마.
```

**검토 예시 — 판단표로 중요한 수정부터 고르기**

```text
$yuriring-game-system-design 판단표를 사용해 아래 가상 기획 메모를 검토해줘.

접속하면 보상을 지급하고 버튼을 누르면 수령한다. 이벤트 기간은 미정이다.”
결정 전 해결할 문제, 구현을 막는 누락, 문서 개선을 구분해줘.
각 지적에 메모의 근거 문장, 관련 장, 필요한 결정, 최소 수정안을 붙여줘.
자동 지급과 수동 수령의 충돌을 임의 정책으로 채우지 마.
```

### 자료 선택과 개념 확인

```text
$yuriring-game-system-design 참조 색인에서 다국어 NPC 대사 설계에 필요한 자료를 골라 설명해줘.
가상 입력: UI 문구와 NPC 대사를 한 표에 한글로 직접 적고, 같은 대사를 여러 장면에서 재사용한다.
관련 장과 필요한 보조 자료를 읽고 선택 이유를 짧게 알려줘.
스트링·챕터·대사 행의 책임과 참조를 정리하고, 현재 방식의 수정·번역 비용을 비교해줘.
책의 설명, 새 적용 예시, 결정이 필요한 정책을 구분해줘.
원문의 정확한 전체 칼럼명은 자료에서 확인되는 범위만 말하고 부족하면 확인할 PDF 쪽을 알려줘.
산출물: 책임·연결 표, 실제 읽은 자료와 쪽 근거, 미정 질문.
```

**기대 결과:** 12장을 중심으로 필요한 자료만 연결하고, 문자열과 재생 정보를 구분한 책임표. 정확한 원문 헤더를 추정하거나 프로젝트의 반복 재생 정책을 임의로 확정하지 않았는지 확인한다.

### 같은 조건에서 대안 비교

```text
$yuriring-game-system-design 출석 보상의 자동 지급안과 직접 수령안을 비교해줘.
가상 목표: 접속 뒤 보상을 쉽게 확인하고 첫 콘텐츠로 자연스럽게 이동하게 한다.
확정: 두 안의 보상 종류·수량·참여 자격은 동일하다. 지급 방식만 비교한다.
미정: 가득 찬 보관함의 처리, 미수령 보상의 만료, 접속 직후 노출 방식.
기획 의도와 관련 규칙의 장을 읽고 행동 단계·성취 피드백·피로·오류 복구·운영 비용을 비교해줘.
관측 데이터가 없으므로 유지율이나 매출 증가를 확정하지 마.
선택지를 지지하는 조건과 반례, 우선 확인할 정책을 표로 정리해줘.
산출물: 동일 기준의 비교표, 조건부 추천, 검증할 질문.
```

**기대 결과:** 보상 크기까지 바꿔 비교하지 않는 대안표. 추천은 목표·제약에 따른 제안으로 표시하고, 효과는 가설과 검증 방법으로 남긴다.

### 변경 영향과 문서 보완

```text
$yuriring-game-system-design 아래 길드 기부 문서에서 취소 허용안을 검토해줘.
[자료: 현재 기획서 또는 기존 답변]
가상 변경안: 서버 처리 전의 기부 요청만 취소할 수 있게 한다.
기존 확정 정책: 처리 완료 후 기여도·보상은 취소하지 않는다. 같은 요청은 한 번만 반영한다.
변경되는 규칙·데이터·UI·QA와 유지할 항목을 구분하고, 현재 명세의 위치 또는 식별자를 연결해줘.
파일은 수정하지 말고 변경 전·후 제안과 영향표를 작성해줘.
취소와 처리 완료가 경쟁할 때의 판정 주체·시점·실패 안내는 미정 질문으로 남겨줘.
산출물: 변경 영향표, 수정 문장 초안, 회귀 테스트와 남은 결정 사항.
```

**기대 결과:** 현재 문서의 확정 정책을 보존하는 변경안. 문서에 없는 위치·규칙 ID를 만들지 않고, 신규 ID가 필요하면 새 제안으로 표시한다. 문서가 제공되지 않았다면 실제 대조가 불가능한 부분을 밝혀야 한다.

### 규칙·데이터·UI를 연결한 QA

```text
$yuriring-game-system-design 아래 보상 수령 명세를 규칙·데이터·UI 관점에서 검토해줘.
[자료: 규칙표, 테이블 관계, 화면 명세 또는 기존 답변]
자료에서 실제로 정의된 수령 자격·기록·상태를 먼저 추출해줘.
정상 수령, 중복 요청, 누락되었거나 잘못된 참조, 수령 직전 상태 변경, 재접속을 검토 후보로 삼고 해당되는 경우만 검사해줘.
각 케이스를 사전 조건·입력·기대 저장 상태·기대 UI·관련 규칙으로 연결해줘.
확정 정책에서 반드시 지켜야 할 결과와 미정 응답·구현 방식에 따른 조건부 결과를 구분해줘.
명세가 부족하면 정책별 가능한 결과를 나누고, 미정 값을 예상 결과로 확정하지 마.
테스트를 실제 실행한 것처럼 쓰지 말고 기획 검토용 시나리오로 표시해줘.
산출물: 모순·누락표, QA 시나리오, 합격 조건을 확정하기 위한 질문.
```

**기대 결과:** 규칙·참조 관계·화면이 같은 조건과 상태를 쓰는지 확인하는 QA 표. 확정된 중복 지급 금지 등의 조건은 유지하고 미정 응답·구현 방식만 조건부로 남긴다. 실제 테스트 결과와 설계된 시나리오도 구분한다.

## 전체 작업을 연결하는 실무 시나리오

### 시나리오 A: 새 기능을 제안에서 구현 기준선까지 만들기

`ch03 → ch04 → ch05 → ch07 → ch09 → ch10~12 → ch15~16 → ch17~18`을 작업 순서의 한 예로 사용한다. 이미 완성한 산출물은 유지하고 필요한 단계만 이어 간다. 예를 들어 장비 프리셋이라면 먼저 대상·문제·경험을 의도문으로 고정하고, 저장/불러오기/삭제를 기능으로 나눈다. 각 기능의 조건·판정·예외를 쓴 뒤 분기가 많은 불러오기 흐름만 플로 차트로 검증한다. 이어 프리셋, 슬롯, 장비 참조의 행 의미와 키 관계를 잡고, 화면 요소의 상태·입력·저장 여부를 명세한다. 마지막으로 의도·규칙·데이터·UI·미결정을 한 기능 문서에 묶는다.

**완료 기준:** 승인자는 왜 필요한지와 범위를 판단할 수 있고, 개발·QA·UI 담당자는 정상 흐름, 실패 흐름, 참조 데이터, 화면 상태를 각각 같은 의미로 찾을 수 있어야 한다.

**복사할 프롬프트**

```text
$yuriring-game-system-design 03~07, 09~12, 15~18장을 필요한 범위에서 연결해
장비 프리셋 기능의 구현용 기획서 초안을 만들어줘.
가상 전제: 수집형 RPG에서 저장·적용·이름 변경·삭제를 지원한다.
확정 요구: 적용 전 소유 여부와 착용 가능 조건을 다시 확인한다.
미정 정책: 슬롯 수, 유료 확장, 일부 장비만 적용할 수 있는지 여부.
의도·기능 분해·규칙과 예외·테이블·UI·QA 시나리오 순으로 구성해줘.
각 규칙에 식별자를 붙여 데이터와 UI에서 같은 규칙을 참조하게 해줘.
데이터 부족은 미결정으로 남기고, 미정 정책별 선택지와 영향을 제시해줘.
문서 끝에 의도→규칙→데이터→UI→테스트 연결표를 작성해줘.
```

### 시나리오 B: 기존 기능의 문제를 재설계하기

`ch02 → ch03 → ch06 → ch07~09 → ch13~16 → ch21`을 사용한다. 먼저 플레이어가 겪는 결과를 조건·상태·피드백으로 되짚고, 문제가 감정·루프·이해 중 어디에 있는지 정의한다. 다음으로 기존 규칙과 연결부를 추적해 실제 상태와 UI 표시가 갈리는 지점을 찾는다. 실패·동시성·빈 대상까지 포함한 흐름을 다시 그리고, UI가 복잡한 이유가 화면 배치인지 규칙 자체인지 검토한다.

**완료 기준:** “버튼을 바꾼다”가 아니라 어떤 조건·판정·표시·연결을 바꾸며, 무엇을 보존하고 어떤 회귀를 테스트할지가 명확해야 한다.

**복사할 프롬프트**

```text
$yuriring-game-system-design 02, 06~09, 13~16, 21장을 연결해
길드 보상 수령 문제를 재설계해줘. 아래는 가상 테스트 관찰이다.
“버튼을 누른 직후 탈퇴하면 지급 여부를 알 수 없다.
재접속 후 버튼은 다시 활성화되지만 보유 재화는 증가해 있다.”
현재 구현과 로그는 제공되지 않았으므로 원인을 확정하지 마.
관찰 사실·원인 가설·추가 증거·정책 결정을 각각 분리해줘.
상태 전이, 요청 중 UI, 실패 안내, 재접속 복구를 연결한 수정안을 제안해줘.
기존 지급 정책을 유지할 수 있는 최소안과 정책 변경이 필요한 안을 비교해줘.
중복 지급·미지급·탈퇴 경계의 회귀 시나리오와 합격 조건을 작성해줘.
```

### 시나리오 C: 라이브 지표를 보고 운영 변경을 결정하기

`ch04 → ch08 → ch12 → ch19 → ch20 → ch21`을 사용한다. 지표 하나로 원인을 단정하지 말고, 대상 세그먼트·기간·튜토리얼·이벤트·정성 피드백을 함께 적는다. 변경하려는 제한·확률·보상·표시가 의도와 어떤 관계인지 검토하고, 조정할 값과 설정 데이터의 책임을 분리한다. 문서의 사실·가설을 나눈 뒤, 핵심/옵션/후속 범위와 로그·테스트 계획을 정한다.

**완료 기준:** 변경 전후 비교 지표, 분석 기간, 대상, 예상 부작용, 되돌릴 기준과 패치 노트에 설명할 이유가 준비되어야 한다.

**복사할 프롬프트**

```text
$yuriring-game-system-design 04, 08, 12, 19~21장을 연결해
파견 미션의 보상·UI 변경안을 검토해줘. 아래 수치는 가상 연습 데이터다.
최근 7일: 대상 계정 300개, 화면 진입 계정 90개, 미션 시작 계정 60개.
관측 범위 밖의 유지율·매출·이전 기간 수치는 없고, 세그먼트도 미분리다.
제안은 “보상 증가”와 “조건 비교 UI 개선”이며 원인은 아직 모른다.
현재 데이터로 말할 수 있는 것과 말할 수 없는 것을 먼저 구분해줘.
제안별 의도, 필요한 추가 로그, 예상 부작용, 검증 계획을 비교해줘.
관측 기간·분모·대상과 변경 범위는 명시하고, 효과나 성공 임계값은 지어내지 마.
일정 제약에서 핵심·옵션·후속으로 나누고 검토 가능한 결정 기록을 만들어줘.
```

## 공통 산출물 검수 기준

전체 구현 명세를 검토할 때 아래 기준 중 해당 기능에 적용되는 항목을 확인한다. 개념 학습이나 도입안 작성에서는 현재 필요한 산출물만 선택한다.

- [ ] **의도:** KPI 이름 외에 대상·문제·행동·감정·전체 흐름을 설명한다.
- [ ] **규칙:** 주체, 적용 범위, 입력, 판정 시점, 성공·실패 결과, 예외와 플레이어 안내가 있다.
- [ ] **데이터:** 행의 의미, 기본 키, 참조 대상, 타입·범위·시간 경계, 가데이터 검증이 있다.
- [ ] **UI:** 요소의 역할과 표시를 설명하고, 해당 요소에 필요한 활성 조건·입력·피드백·저장·동기화 여부를 명세한다. 정적 제목·설명에 동작 항목을 요구하지 않는다.
- [ ] **근거:** 출처 있는 사실, 프로젝트 결정, 가정, AI가 제안한 가설이 구분되어 있다.
- [ ] **변경:** 관련 규칙·테이블·화면·테스트 케이스에 미치는 영향을 기록한다.

### 01. [시스템 기획이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch01-system-planning.md)

- **활용 시점:** 아이디어가 “퀘스트를 추가한다”, “보상을 준다”처럼 기능명만 있고 실제 작동 계약이 없을 때 사용한다. 콘텐츠 값과 시스템 규칙의 책임을 나누는 출발점에도 맞다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 01장을 중심으로 [기능]을 시스템으로 설계해줘. 해결할 문제는 [문제]이고, 플레이어 행동을 시도 조건 → 판정 → 성공/실패 결과 → 상태·보상 반영으로 나눠줘. 중복 입력, 취소, 연결 종료, 재접속에서 보존할 상태와 UI 안내도 포함해줘.`
- **기대 산출물과 확인:** 기능의 역할 한 문장, 행동별 조건·판정·결과 표, 시스템/콘텐츠 데이터의 책임표, 실패 경로를 받는다. 새 콘텐츠를 추가할 때 코드 수정 대신 데이터 추가로 확장 가능한 부분과, 차단 시 다음 행동을 안내하는 UI가 있는지 확인한다.
- **연계 장:** 결과를 설계 언어로 바꾸려면 [02장 — 시스템 기획자의 시야](../.agents/skills/yuriring-game-system-design/chapters/ch02-designer-perspective.md), 구조 분해는 [05장 — 시스템 구조 분할](../.agents/skills/yuriring-game-system-design/chapters/ch05-system-decomposition.md), 예외 명세는 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md)로 잇는다.

<a id="example-01-a"></a>

#### 고급 예시 A — 퀘스트 계약을 예외까지 설계하기

```text
$yuriring-game-system-design 01장을 중심으로 협동 생존 게임의 ‘난파선 구조 요청’ 퀘스트 계약을 설계해줘.
가상 입력: 2~4인 파티가 구조 신호기 3개를 활성화하면 보급 상자를 받는다. 이 명칭과 수치는 책 사실이나 확정 사양이 아니다.
확정: 보상은 참여자별로 수령하며 파티장 전용이 아니다. 기여 판정은 서버가 처리한다.
제약: 재접속과 동시 상호작용 뒤에도 보상이 중복되거나 누락되면 안 된다.
수락 조건 → 신호기 인정 → 완료 판정 → 보상 지급 → 완료 표시를 규칙 표로 써줘.
중복 입력, 수락 전 기여, 파티 탈퇴, 보상 지급 중 연결 종료를 예외 표에 별도로 넣어줘.
콘텐츠 값과 시스템 규칙·상태·참조 데이터의 책임을 분리해줘.
미확정인 기여 기준·보상 보관 정책은 결정 질문과 가정으로 표시해줘.
UI가 차단 사유와 다음 행동을 어떻게 안내하는지도 제안해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**

#### 고급 예시 B — 라이브 퀘스트 구조의 반례 검토

```text
확정: 오프라인 중 처치 이벤트는 기록되지 않으며, 동일 계정의 동시 접속을 허용하지 않는다.
제약: 운영팀은 보상량만 데이터로 바꾸고 싶고, 개발 변경은 최소화해야 한다.
정상 흐름을 먼저 조건·판정·상태 변화·결과로 분해해줘.
그 뒤 빠른 재수락, 일일 경계 시각, 목표 변경, 우편함 가득 참을 반례로 테스트해줘.
각 반례에서 보존할 상태, 재시도 기준, 플레이어 메시지, 운영 로그를 나눠줘.
책의 사례나 수치를 정답으로 복사하지 말고, 미확정 정책을 질문으로 남겨줘.
마지막에 데이터화할 항목과 코드 또는 전용 처리로 남길 항목을 구분해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

### 02. [시스템 기획자의 시야](../.agents/skills/yuriring-game-system-design/chapters/ch02-designer-perspective.md)

- **활용 시점:** 레퍼런스나 플레이 테스트에서 “먹으면 회복된다”, “돌리면 보상을 얻는다” 같은 결과만 보일 때, 그 결과를 만드는 상태·판정·연출을 역추적한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 02장을 중심으로 [관찰한 플레이 결과]를 시스템 시야로 역분석해줘. 조건, 입력, 상태 변화, 데이터 참조, 결과 결정 시점, UI/사운드 피드백, 연속 입력·실패 복구를 분리하고, 플레이어 감정 목표가 어느 규칙과 피드백에서 구현되는지도 표로 보여줘.`
- **기대 산출물과 확인:** 플레이어 시야/시스템 시야 대응표와 처리 순서를 받는다. 연출의 멈춤 지점과 실제 결과 결정·지급·확인 시점이 구분됐는지, 표시값과 실제 판정값이 같은 출처를 보는지 검토한다.
- **연계 장:** 감정과 선택 기준은 [03장 — 기획 의도란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch03-design-intent.md), 다른 규칙으로 전달되는 정보는 [06장 — 시스템의 구성](../.agents/skills/yuriring-game-system-design/chapters/ch06-system-composition.md)에서 구체화한다.

<a id="example-02-a"></a>

#### 고급 예시 A — 관찰된 뽑기 연출을 시스템으로 역분석하기

```text
$yuriring-game-system-design 02장을 중심으로 모바일 RPG의 상자 열기 연출을 역분석해줘.
가상 관찰: 열기 버튼 뒤 3초 연출이 나오고 마지막에 장비 카드가 1장 공개된다. 이는 실제 서비스 분석이 아니다.
확정: 결과 판정과 보상 지급은 서버 권한이며, 클라이언트는 재시도 요청을 할 수 있다.
제약: 연출 중 앱이 종료되어도 결과가 사라지거나 중복되면 안 된다.
플레이어 시야의 행동·감정·피드백과 시스템 시야의 입력·판정·상태를 대응표로 만들어줘.
연출 시작, 결과 결정, 지급 반영, 공개 확인의 시점을 각각 분리해줘.
중복 탭, 응답 지연, 공개 전 재접속, 인벤토리 한도 초과를 반례로 검토해줘.
표시 등급과 실제 지급 데이터가 어긋나는 위험 및 점검 로그를 적어줘.
가상 관찰에서 추론한 항목과 확정 조건을 구분해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 연출과 실제 처리 책임을 분리한 처리 순서 및 실패 복구 표. 결과 결정 시점이 UI 연출에 종속되지 않아야 한다.

<a id="example-02-b"></a>

#### 고급 예시 B — 피격 체험의 상태·피드백 감사

```text
$yuriring-game-system-design 02장을 중심으로 보스 돌진 피격 체험을 설계 감사해줘.
가상 입력: 돌진에 맞으면 체력이 15% 줄고 0.6초 경직 애니메이션이 재생된다. 수치와 명칭은 예시일 뿐이다.
확정: 피해 판정은 서버가 확정하고, 무적 상태는 다른 스킬에서도 재사용한다.
제약: 연속 충돌로 한 프레임에 여러 번 피해를 주지 않아야 한다.
충돌 인식 → 피해 계산 → 생존/사망 판정 → 경직·무적 → UI·사운드 갱신의 순서를 써줘.
화면 흔들림과 체력 감소가 같은 결과를 가리키는지 검증 항목을 제시해줘.
동시 피격, 지연 패킷, 체력 0 경계, 무적 만료 직전 충돌을 반례로 다뤄줘.
재사용 효과와 개별 보스 데이터의 책임을 분리해줘.
미확정인 무적 지속·중첩 규칙은 결정 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>

### 03. [기획 의도란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch03-design-intent.md)

- **활용 시점:** “리텐션을 올린다”, “편의성을 높인다”처럼 지표나 기능명만 있는 제안을, 실제 플레이 경험을 고르는 판단 기준으로 바꿀 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 03장을 중심으로 [기능 제안]의 기획 의도를 작성해줘. [대상 플레이어]가 [문제 상황]에서 [원하는 감정/행동]을 경험하도록 [핵심 상호작용]이 [전체 흐름 변화]를 만든다는 형식으로 정리하고, 각 규칙이 의도를 지지하는 이유와 편의 개선이 의도를 훼손할 수 있는 지점도 표시해줘.`
- **기대 산출물과 확인:** 대상·문제·경험·행동 흐름을 담은 의도문, 의도-규칙 연결표, 변경 요청의 판단 근거를 받는다. KPI를 경험 정의로 오인하지 않았는지, 피드백 없이 감정만 선언하지 않았는지 확인한다.
- **연계 장:** 의도를 설득 가능한 구조로 넓히려면 [04장 — 기획 의도 설계란?](../.agents/skills/yuriring-game-system-design/chapters/ch04-intent-design.md), 실제 규칙으로 내리려면 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md)를 사용한다.

<a id="example-03-a"></a>

#### 고급 예시 A — 복귀 기능의 의도와 규칙을 정렬하기

```text
$yuriring-game-system-design 03장을 중심으로 협동 레이드의 전투 중 복귀 기능 의도를 설계해줘.
가상 입력: 사망한 플레이어는 동료가 구조 토큰을 전달하면 다음 안전 구역에서 복귀한다. 명칭과 흐름은 가상이다.
확정: 조기 사망자의 이탈감을 줄이되, 사망의 긴장감은 유지해야 한다.
제약: 보스 전투의 난이도와 팀 역할 분담을 무력화하는 자동 복귀는 피한다.
대상 플레이어·문제 상황·원하는 감정/행동·핵심 상호작용·전체 흐름 변화를 한 문장으로 써줘.
토큰 회수, 전달, 복귀 대기, 재합류 규칙이 의도를 어떻게 지지하는지 연결표로 보여줘.
‘즉시 무료 복귀’ 제안을 의도 기준으로 찬반 검토해줘.
확정 사항, 가정, 플레이 테스트로 검증할 가설을 구분해줘.
KPI 이름만으로 효과를 단정하지 말고 측정 후보와 해석 한계를 적어줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

### 04. [기획 의도 설계란?](../.agents/skills/yuriring-game-system-design/chapters/ch04-intent-design.md)

- **활용 시점:** 도입 이유가 있으나 문제·역할·감정·플레이 흐름·근거가 흩어져 승인 또는 우선순위 판단이 어려울 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 04장을 중심으로 [기능]의 도입안을 문제 정의 → 시스템 역할 → 감정 설계 → 플레이 흐름 설계로 작성해줘. 필요성·미도입 시 문제·기대 결과·기존 기능과 차이·리스크/대응·근거의 여섯 질문에 답하되, 검증되지 않은 효과는 가설로 표시해줘. [레퍼런스]에서 표면 기능이 아니라 역할만 비교해줘.`
- **기대 산출물과 확인:** 제안 개요, 의도-설계 기준, 레퍼런스 차이, 리스크와 검증 계획을 받는다. 레퍼런스의 기간·보상·UI를 복사하지 않았는지, 자동/수동 수령이나 노출 시점처럼 경험을 바꾸는 선택마다 이유가 있는지 검토한다.
- **연계 장:** 기능·속성으로 내리려면 [05장 — 시스템 구조 분할](../.agents/skills/yuriring-game-system-design/chapters/ch05-system-decomposition.md), 라이브 효과 검증은 [20장 — 디자인부터 런칭까지, 시스템 기획의 여정](../.agents/skills/yuriring-game-system-design/chapters/ch20-production-lifecycle.md)으로 이어 간다.

<a id="example-04-a"></a>

#### 고급 예시 A — 길드 의뢰 제안안을 설득 구조로 만들기

```text
$yuriring-game-system-design 04장을 중심으로 길드 공동 의뢰 도입안을 작성해줘.
가상 입력: 길드원이 주간 목표에 기여하면 공동 보급 상자가 열리는 기능이다. 이름과 구조는 가상 예시다.
확정 목표: 개인 기여를 확인할 수 있게 하되, 과도한 경쟁은 피한다. 불만 감소 효과는 검증할 가설이다.
제약: 기존 길드 채팅과 길드 상점은 유지하며, 신규 화면은 최대 두 개다.
문제 정의 → 시스템 역할 → 감정 설계 → 플레이 흐름 설계의 네 단계로 정리해줘.
필요성, 미도입 시 손실, 기존 기능과 차이, 리스크/대응, 검증 방법을 표로 써줘.
기여 공개 방식 두 가지를 제안하고 심리적 부작용을 비교해줘.
가상 사례의 보상·기간은 확정값처럼 제시하지 말고 조정 근거를 적어줘.
미확정인 기여 인정 범위와 보상 수령 조건은 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

>

### 05. [시스템 구조 분할](../.agents/skills/yuriring-game-system-design/chapters/ch05-system-decomposition.md)

- **활용 시점:** 길드·퀘스트·성장처럼 큰 시스템을 시작할 때, 화면이나 명사 목록이 먼저 나오고 행동·속성·상태의 책임이 섞여 있을 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 05장을 중심으로 [시스템]을 기능 단위와 속성 단위로 분해해줘. 각 기능에 대상, 입력, 조건, 처리 결과, 예외, 연동 대상을 적고, 고정 기획 데이터와 플레이 중 변하는 상태는 의미·변경 조건·보존·복구 요구로 구분해줘. UI를 먼저 확정하지 말고 필요한 화면 상태를 마지막에 도출해줘.`
- **기대 산출물과 확인:** 기능 맵, 객체/속성 목록, 상태 수명표, UI 후보를 받는다. 단순 명사 목록이 아닌 동작 단위까지 내려갔는지, 속성값에 지속·중첩·상한·해제 규칙이 붙었는지, 저장 구현 방식은 프로젝트 기술 결정과 구분됐는지 확인한다.
- **연계 장:** 기능 사이의 정보 전달은 [06장 — 시스템의 구성](../.agents/skills/yuriring-game-system-design/chapters/ch06-system-composition.md), 데이터 모델은 [10장 — 데이터 테이블이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch10-table-foundations.md)~[12장 — 데이터 테이블 사례](../.agents/skills/yuriring-game-system-design/chapters/ch12-table-cases.md)로 확장한다.

#### 고급 예시 A — 동료 파견 시스템을 기능·속성으로 분해하기

```text
$yuriring-game-system-design 05장을 중심으로 방치형 RPG의 동료 파견 시스템을 분해해줘.
가상 입력: 동료 3명을 지역에 보내면 일정 시간이 지난 뒤 재료를 가져온다. 명칭·인원·시간은 가상이다.
확정: 한 동료는 동시에 하나의 파견에만 배정되고, 서버 시간이 완료 판정 기준이다.
제약: 화면 설계보다 규칙·상태·데이터 책임을 먼저 확정한다.
등록, 편성, 시작, 진행 조회, 완료 수령, 취소를 기능 단위로 나눠줘.
동료·파견·지역·보상 각각의 속성, 변경 조건, 보존 수명, 복구 요구를 표로 써줘.
고정 기획 데이터와 플레이어별 상태를 구분하고 참조 관계를 적어줘.
동료 중복 배정, 완료 직전 취소, 지역 잠금, 보상 수령 실패의 예외를 포함해줘.
미확정인 완료 시간·보상 계산 방식은 가정과 결정 질문으로 표시해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> **기대 결과**

```text
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

### 06. [시스템의 구성](../.agents/skills/yuriring-game-system-design/chapters/ch06-system-composition.md)

- **활용 시점:** 개별 기능 명세는 있으나 공격→피해→체력→승패처럼 결과가 다음 규칙으로 어떻게 전달되는지, 또는 유사 기능을 어디까지 공통 모듈로 만들지 판단해야 할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 06장을 중심으로 [시스템 흐름]의 규칙 연결도를 작성해줘. 각 단계가 생성하는 정보, 그 정보를 받는 규칙, 다음 상태 변화, UI 소비자, 중복 처리·표시 불일치 예외를 표로 정리해줘. [유사 기능 목록] 중 공통화할 규칙과 개별로 남길 규칙을 이유와 함께 제안해줘.`
- **기대 산출물과 확인:** 이벤트/데이터 흐름표와 모듈 경계안을 받는다. UI가 별도로 값을 계산하지 않고 판정 결과를 소비하는지, 공통 모듈 이름만 있고 초기화·한도·예외가 빠지지 않았는지 확인한다.
- **연계 장:** 개별 규칙의 빈칸은 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md), 분기가 복잡한 연결은 [09장 — 규칙의 도식화](../.agents/skills/yuriring-game-system-design/chapters/ch09-flowcharts.md), 장기 영향은 [21장 — 시스템 기획자 레벨 업](../.agents/skills/yuriring-game-system-design/chapters/ch21-designer-growth.md)에서 검토한다.

<a id="example-06-a"></a>

#### 고급 예시 A — 전투 보상 연동도를 설계하기

```text
$yuriring-game-system-design 06장을 중심으로 협동 보스 처치 뒤 보상 연동도를 작성해줘.
가상 입력: 보스 처치 시 기여 등급에 따라 개인 보상 상자가 생성된다. 명칭과 등급은 가상이다.
확정: 처치 판정은 전투 서버가 소유하고, 보상 수령은 별도 인벤토리 시스템이 처리한다.
제약: UI가 기여도나 보상 내용을 독자 계산하면 안 되며, 한 번만 수령할 수 있다.
처치 이벤트부터 기여 계산, 보상 생성, 수령 가능 표시, 지급 완료까지 정보 흐름을 표로 써줘.
각 단계의 생산 정보, 소비 규칙, 상태 변화, UI 소비자, 로그 책임을 적어줘.
동시 수령, 인벤토리 부족, 지연된 처치 이벤트, 중복 이벤트를 반례로 검토해줘.
공통 보상 지급 모듈과 보스별 개별 규칙의 경계를 제안해줘.
미확정인 기여 산식은 가정으로 분리하고 구현 사실처럼 단정하지 마.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> **기대 결과**

```text
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

### 07. [규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md)

- **활용 시점:** 구매·제작·강화·보상처럼 실패, 동시 요청, 대상 소진, 비정상 접근이 생기는 기능의 기본 명세를 작성할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 07장을 중심으로 [기능]의 규칙 명세를 작성해줘. 상황·적용 범위·필요 정보·입력·판단·성공/실패 결과·예외 처리로 나누고, 이 기능에 해당하는 조건 미충족·실행 중 상태 변경·대상 없음·자동 처리 빈 대상·비정상 요청을 다뤄줘. 실패 시 보존할 상태와 플레이어 메시지, 내부 기록 정책을 분리해줘.`
- **기대 산출물과 확인:** 규칙 표와 예외 매트릭스를 받는다. 화면에 보인 값만 믿지 않고 실행 직전에 실제 상태를 재검증하는지, 일반 실패의 안내와 비정상 접근의 기록·노출 정책을 구분했는지 확인한다.
- **연계 장:** 의도와 제한의 균형은 [08장 — 규칙의 설계](../.agents/skills/yuriring-game-system-design/chapters/ch08-rule-design.md), 팀 해석을 맞출 분기 도식은 [09장 — 규칙의 도식화](../.agents/skills/yuriring-game-system-design/chapters/ch09-flowcharts.md)로 이어 간다.

<a id="example-07-a"></a>

#### 고급 예시 A — 제작 요청의 규칙과 예외 매트릭스

```text
$yuriring-game-system-design 07장을 중심으로 대장간 제작 요청의 규칙 명세를 작성해줘.
가상 입력: 재료와 도면을 제출하면 장비 한 개를 제작하며, 일부 도면은 제작 대기열을 사용한다. 모두 가상 설정이다.
확정: 제작 시작 직전에 서버가 재료 소유와 수량을 재검증한다.
제약: 재료 소모와 제작 결과 생성은 서로 어긋나면 안 되고, 클라이언트 입력은 신뢰하지 않는다.
상황·적용 범위·필요 정보·입력·판단·성공/실패 결과를 규칙 표로 작성해줘.
재료 부족, 도면 잠김, 대기열 가득 참, 중복 요청, 제작 중 연결 종료를 예외 매트릭스로 써줘.
일반 실패 안내와 비정상 요청의 내부 기록·노출 정책을 구분해줘.
취소 가능 여부와 완료 결과 보관은 미확정으로 두고 결정 질문을 적어줘.
가상 재료명·시간·확률을 기본 사양처럼 제시하지 마.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 판정 주체와 시점이 명확한 규칙·예외 표. 소모와 결과가 하나의 일관된 처리 단위로 보이는지가 검토 기준이다.

<a id="example-07-b"></a>

#### 고급 예시 B — 자동 보상 수령의 실패 경로 검토

```text
$yuriring-game-system-design 07장을 중심으로 시즌 미션의 자동 보상 수령 규칙을 검토해줘.
가상 입력: 목표 달성 후 다음 로그인 때 보상이 자동 지급된다고 가정한다. 명칭과 지급 방식은 가상이다.
확정: 계정당 보상은 한 번만 받을 수 있고, 보상 인벤토리에는 용량 제한이 있다.
제약: 자동 처리 대상이 비어 있거나 이미 처리된 경우에도 오류 팝업을 남발하지 않는다.
적용 범위, 입력 또는 트리거, 판정 시점, 성공·실패 결과, 상태 보존을 구조화해줘.
미달성, 이미 수령, 보상 공간 부족, 시즌 종료 직전, 다중 기기 로그인 반례를 포함해줘.
플레이어에게 보여 줄 메시지와 운영 로그를 어떤 경우에 남길지 분리해줘.
공간 부족 시 대체 보관 정책은 확정하지 말고 선택지와 영향으로 제시해줘.
자동 수령이 의도한 경험에 주는 이점과 예상 혼란도 짧게 검토해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 자동 처리의 무음 종료와 사용자 안내가 구분된 명세. 중복 지급 방지와 보관 실패 처리의 책임이 분명해야 한다.

### 08. [규칙의 설계](../.agents/skills/yuriring-game-system-design/chapters/ch08-rule-design.md)

- **활용 시점:** 거래·경제·경쟁·제한처럼 편의, 신뢰, 악용 방지가 충돌하는 복합 시스템에서 세부 규칙의 목적과 우선순위를 검토할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 08장을 중심으로 [복합 기능]을 기획 의도 → 설계 기준 → 기능 단위 → 정상/예외 흐름 → 검토·보완 순서로 설계해줘. [자원 흐름/신뢰/악용 방지] 중 목표를 명시하고, 등록·변경·취소·구매·정산 등 책임을 분리해줘. 제한값은 확정값으로 만들지 말고 조정 주체와 검증 근거를 제안해줘.`
- **기대 산출물과 확인:** 의도-설계 기준표, 기능별 흐름, 제한·충돌 우선순위, 운영 검토 항목을 받는다. 사례의 시간·수수료·건수·허용 범위를 기본값으로 전용하지 않았는지, 대금의 생성·보관·지급 시점이 하나의 정의로 일관되는지, 제한이 정상 행동까지 과도하게 막지 않는지 확인한다.

> [!IMPORTANT]
> **원문을 적용할 때의 한계**
>
> 거래소 사례에는 구매 완료 뒤 판매자에게 금액을 전송한다는 설명과 정산 버튼으로 지급한다는 설명이 함께 있다. 자동·수동 정산 중 하나를 책의 확정 사양으로 단정하지 않는다. 프로젝트에서는 지급 방식을 결정하고 대금의 상태·수령·실패 처리를 같은 정의로 연결한다.

- **연계 장:** 흐름 검증은 [09장 — 규칙의 도식화](../.agents/skills/yuriring-game-system-design/chapters/ch09-flowcharts.md), 조정값과 참조 데이터는 [11장 — 데이터 테이블 설계](../.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md)에서 설계한다.

> [!TIP]
> **구현 명세와 플레이어 설명의 깊이를 구분한다**
>
> 구현용 문서에는 필요한 판정·예외를 남기되, 플레이어 안내는 기존 게임에서 예측 가능한 부분을 간결하게 쓰고 오해하기 쉬운 적용 범위를 명확히 한다. 설명의 분량보다 플레이어의 기대와 실제 결과가 일치하는지를 검토한다. 근거는 8장, 책 126–127쪽이다.

<a id="example-08-a"></a>

#### 고급 예시 A — 거래소 구매·정산 정책의 미결정 관리

```text
$yuriring-game-system-design 08장을 중심으로 플레이어 거래소의 구매와 판매 대금 흐름을 설계해줘.
가상 입력: 판매자는 장비를 등록하고 구매자는 재화로 구매하며, 거래 완료 후 판매 대금이 발생한다. 모든 명칭은 가상이다.
확정: 재고 확인과 재화 차감은 서버 권한이고, 동일 매물은 한 번만 판매돼야 한다.
제약: 원문 사례의 자동 전송과 정산 버튼 설명은 모호하므로 자동·수동 정산 중 하나를 책의 정답으로 단정하지 않는다.
등록, 가격 변경, 취소, 구매, 대금 발생, 수령 또는 지급 실패의 책임을 기능별로 분리해줘.
자동 정산·수동 정산 두 정책을 상태·UI·복구·악용 방지 관점에서 비교해줘.
구현용 상세 명세와 플레이어 안내 문구를 나누고, 안내에는 오해하기 쉬운 지급 시점·실패 상태를 명확히 적어줘.
동시 구매, 잔액 부족, 매물 취소 경쟁, 지급 중 연결 종료의 예외를 넣어줘.
수수료·등록 기간·횟수 제한은 가상 기본값을 만들지 말고 조정 주체와 검증 질문만 제시해줘.
확정·가정·미결정 정책을 명확히 태그로 구분해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 대금 상태와 지급 책임이 일관된 거래소 설계안. 자동/수동 정산은 선택지로 남고, 수치 기본값이 제시되지 않아야 한다.

#### 고급 예시 B — 경제 악용 방지와 정상 행동의 균형

```text
$yuriring-game-system-design 08장을 중심으로 친구 간 희귀 재료 거래의 악용 방지 정책을 검토해줘.
가상 입력: 신규 계정이 고가 재료를 반복 이동시키는 패턴을 운영팀이 우려한다. 관찰과 데이터는 가상이다.
확정: 거래 기록은 감사 가능해야 하며, 정상 이용자의 즉시 거래 경험도 중요하다.
제약: 제한 수치·차단 기간·수수료는 근거 없이 확정하지 않고, 차단만으로 문제를 해결했다고 판단하지 않는다.
보호하려는 신뢰·경제·사회적 경험을 설계 기준으로 우선순위화해줘.
등록, 가격 검증, 구매, 취소, 신고 또는 감사의 흐름별 위험을 표로 정리해줘.
강한 제한, 단계적 제한, 사후 탐지의 장단점과 정상 행동 부작용을 비교해줘.
내부 검증·감사 명세와 플레이어 안내를 구분하고, 제한이 적용되는 조건·실패 이유를 얼마나 설명할지 제안해줘.
가상 징후와 실제 검증이 필요한 지표를 분리하고 오탐 반례를 포함해줘.
미확정인 제재 주체·이의 처리·임계값은 결정 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 악용 위험과 정상 사용성을 함께 보는 정책 비교. 수치 대신 근거·운영 책임·되돌림 조건이 제시돼야 한다.

### 09. [규칙의 도식화](../.agents/skills/yuriring-game-system-design/chapters/ch09-flowcharts.md)

- **활용 시점:** 판정 순서, 성공/실패 분기, 반복, 하위 프로세스가 자연어만으로 여러 해석을 낳는 경우에 사용한다. 모든 화면 이동을 그리는 용도는 아니다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 09장을 중심으로 [기능]의 [특정 범위]를 플로 차트 설계안으로 만들어줘. 먼저 정상 흐름을 텍스트로 검증한 뒤 입력·처리·판단·출력을 구분하고, 재고/잔액/상태 변경/서버 오류/중복 요청 같은 예외 분기를 포함해줘. 차트에서 생략할 상세 값은 별도 명세 항목으로 분리해줘.`
- **기대 산출물과 확인:** 도식 대상과 목적, 단계별 텍스트 흐름, Mermaid 또는 도형용 노드 목록, 분기별 종료 상태를 받는다. 한 장에 모든 시스템을 넣어 가독성을 잃지 않았는지, 반복 화살표와 하위 프로세스의 입·출구가 명확한지, 차트가 상세 수치·문구의 유일한 근거가 되지 않았는지 확인한다.
- **연계 장:** 판단 항목의 정의는 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md), UI 화면 흐름은 [15장 — UX/UI 설계](../.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md)와 분리해 작성한다.

<a id="example-09-a"></a>

#### 고급 예시 A — 매물 구매 플로 차트를 반례까지 그리기

```text
$yuriring-game-system-design 09장을 중심으로 거래소 매물 구매의 플로 차트 설계안을 작성해줘.
가상 입력: 플레이어가 매물 상세에서 구매를 누르면 서버가 재고와 재화를 확인한다. 이는 가상 흐름이다.
확정: 실제 재고와 실제 잔액은 실행 직전에 서버가 판단한다.
제약: 차트는 UI 메뉴 탐색이 아니라 거래 확정 규칙만 다루며, 상세 수치·문구는 별도 명세로 뺀다.
먼저 입력·판단·처리·출력으로 정상 텍스트 흐름을 작성해줘.
그다음 Mermaid 초안 또는 노드 목록으로 조건 분기와 종료 상태를 표현해줘.
매물 소진, 잔액 부족, 동시 구매, 요청 재전송, 내부 처리 실패를 각각 분기해줘.
성공 처리의 원자성 요구와 실패 뒤 재시도 가능 여부를 차트 밖 주석으로 적어줘.
가상 데이터, 프로젝트 확정 사항, 미확정 복구 정책을 구분해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 범위가 제한된 규칙 플로와 완결된 모든 분기. 차트가 수치·문구·정산 정책의 유일한 근거가 되지 않아야 한다. 플로 차트로 그리는 이유가 '조건 판정이 중요하고 예외가 많다'는 책의 기준(9장, 책 153쪽)과 연결되는지도 확인한다.

#### 고급 예시 B — 매칭 재시도 루프의 종료 조건 감사

```text
$yuriring-game-system-design 09장을 중심으로 협동 던전 자동 매칭의 재시도 흐름을 설계 감사해줘.
가상 입력: 4인 파티를 찾고 제한 시간 안에 인원이 모이지 않으면 조건을 완화해 다시 찾는다. 수치와 규칙은 가상이다.
확정: 플레이어는 언제든 취소할 수 있고, 입장 확정 뒤에는 중복 방 배정을 막아야 한다.
제약: 반복 화살표만 그리지 말고 재진입 조건, 종료 조건, 상태 복구를 텍스트로도 명시한다.
입력·대기·후보 탐색·확정·실패·취소의 상태와 전이를 먼저 정리해줘.
조건 완화, 취소와 확정의 경합, 파티원 이탈, 서버 응답 지연을 반례로 넣어줘.
공통 매칭 검증과 던전별 입장 조건을 하위 프로세스로 분리할지 판단해줘.
차트에 넣지 않을 대기 시간·우선순위 값은 별도 데이터 명세로 분리해줘.
미확정인 완화 정책은 가정과 결정 질문으로 표시해줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

### 10. [데이터 테이블이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch10-table-foundations.md)

- **활용 시점:** 어떤 값을 테이블로 관리해야 하는지, 기본 키·외래 키·자료형·설정 데이터와 플레이어 상태를 어떻게 구분할지 막힐 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 10장을 중심으로 [기능]의 데이터 후보를 분류해줘. 테이블·코드 상수·전용 도구·플레이어 상태 후보를 나누고, 조정·추가·검증·참조할 값의 테이블 적합성을 비교해줘. 테이블 후보에는 한 행의 의미, 기본 키, 참조 대상, 자료형, 범위·빈값·ENUM·시간 경계, 게임에서의 사용 규칙을 적어줘. 기획 설정 데이터와 플레이어별 저장 상태는 책임과 변경 주체로 구분해줘.`
- **기대 산출물과 확인:** 테이블화 판단표, 열 사전 초안, 키/참조 목록, 저장 상태 구분을 받는다. 테이블이 코드나 전용 도구보다 적절한지, 외래 키가 실제 단일 행을 가리키는지 또는 그룹 조회인지, 값의 단위와 경계가 정의됐는지 확인한다.
- **연계 장:** 객체와 반복 데이터의 구체 분리는 [11장 — 데이터 테이블 설계](../.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md), 도메인별 사례 비교는 [12장 — 데이터 테이블 사례](../.agents/skills/yuriring-game-system-design/chapters/ch12-table-cases.md)에서 한다.

> [!IMPORTANT]
> **분리·통합의 선택 이유를 남긴다**
>
> 테이블 분리 자체가 좋은 설계를 보장하지 않는다. **사용 빈도·업데이트 빈도·수정 범위·재사용성**으로 통합안과 분리안을 비교하고, 선택한 구조의 이유를 설명한다. 또한 운영자가 수동으로 바꿀 값과 자동으로 갱신·초기화할 규칙을 구분한다. 근거는 10장, 책 171–172쪽이며 초기화 시각·시간대는 프로젝트 정책으로 정한다.

<a id="example-10-a"></a>

#### 고급 예시 A — 제작 데이터의 테이블화 판단과 키 설계

```text
$yuriring-game-system-design 10장을 중심으로 요리 제작 기능의 데이터 구조를 설계해줘.
가상 입력: 요리법마다 필요한 재료와 수량, 결과 아이템, 해금 조건이 다르다. 명칭과 구조는 가상이다.
확정: 아이템 이름·아이콘·등급은 기존 아이템 데이터가 소유하고, 플레이어 보유 재료는 개인 상태다.
제약: 반복 조정할 조건은 테이블 후보로 삼되, 복잡한 조리 연출 타이밍은 전용 도구 또는 코드 후보로 검토한다.
테이블·코드 상수·전용 도구로 나눌 후보와 이유를 표로 써줘.
레시피와 반복 재료의 통합안·분리안을 사용 빈도·업데이트 빈도·수정 범위·재사용성으로 비교하고 선택 이유를 적어줘.
각 테이블의 한 행 의미, 기본 키, 외래 키 대상, 타입·빈값·범위·시간 경계를 명세해줘.
외래 키가 단일 행을 가리키는 경우와 ‘등급별 목록’ 같은 그룹 조회 조건을 혼동하지 않게 구분해줘.
레시피에 아이템 상세를 중복 저장하지 않는 참조 예시를 넣어줘.
가상 ID와 수치는 예시임을 표시하고, 포맷·스키마는 미확정 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 테이블화 판단과 참조 무결성이 분명한 열 사전 초안. 그룹 조회 조건을 단일 행 외래 키처럼 선언하지 않아야 한다.

<a id="example-10-b"></a>

#### 고급 예시 B — 시즌 설정과 플레이어 상태의 분리 감사

```text
$yuriring-game-system-design 10장을 중심으로 시즌 패스 데이터 모델의 책임을 감사해줘.
가상 입력: 시즌마다 보상 단계, 공개 기간, 임무 목록이 바뀌고 플레이어마다 현재 단계와 수령 이력이 다르다. 모두 가상이다.
확정: 시즌 설정 변경은 운영 데이터로 관리하고, 플레이어 진행은 계정별 저장 상태다.
제약: 기획 테이블을 개인 진행 데이터 저장소로 쓰지 않으며, 변경 전후 검증 가능한 값만 테이블로 둔다.
기획 데이터, 플레이어 상태, 코드 또는 전용 처리 후보를 세 열로 분류해줘.
시즌 정의와 반복 보상 데이터를 나누거나 합칠 때의 사용·업데이트 빈도, 수정 범위, 재사용성을 비교해줘.
수동 데이터 교체와 자동 전환·초기화 규칙을 구분하고, 미정인 기준 시각·시간대는 결정 질문으로 남겨줘.
각 데이터의 행 의미, 소유 주체, 키, 자료형, 시간 경계, 사용 규칙을 적어줘.
시즌 ID가 하나의 시즌 행을 가리킬 때와 보상 그룹을 조회할 때의 조건을 구분해줘.
종료 시즌 데이터 참조, 새 시즌 전환, 중복 수령 기록의 반례를 검토해줘.
미확정인 보관 기간·마이그레이션 방식은 결정 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 설정·개인 상태·처리 로직이 분리된 책임표. 키의 단일 행 참조와 그룹 필터가 명확히 구별돼야 한다.

### 11. [데이터 테이블 설계](../.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md)

- **활용 시점:** 출석, 이벤트, 보상처럼 메타 정보와 회차·보상·조건이 반복되어 열이 계속 늘거나, 여러 표에 같은 이름·아이콘·상세값이 중복될 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 11장을 중심으로 [기능]의 테이블을 설계해줘. 한 행이 의미하는 객체를 먼저 선언하고, 반복되는 메타/보상/조건을 분리해 기본 키와 외래 키로 연결해줘. 각 칼럼에 이름, 타입, 입력 형식, 게임 동작, 사용 규칙을 넣고, 관계를 검증할 가데이터와 경계 사례 3개를 작성해줘.`
- **기대 산출물과 확인:** 객체별 테이블 초안, ERD 텍스트, 열 사전, 가데이터를 받는다. 다른 시스템이 소유한 이름·아이콘·성능을 복사하지 않았는지, 반복 정보의 행 분리가 관계 없는 고립 테이블을 만들지 않았는지, 기본 키의 중복·빈값과 외래 키의 존재 검증이 있는지 확인한다.
- **연계 장:** 규칙에서 필요한 값은 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md), 확률·상품·스킬 등 확장 사례는 [12장 — 데이터 테이블 사례](../.agents/skills/yuriring-game-system-design/chapters/ch12-table-cases.md)에서 확인한다.

<a id="example-11-a"></a>

#### 고급 예시 A — 출석 이벤트의 반복 보상을 정규화하기

```text
$yuriring-game-system-design 11장을 중심으로 14일 출석 이벤트의 테이블을 설계해줘.
가상 입력: 이벤트마다 제목·기간·배너가 있고, 일차별로 아이템 보상과 수량이 반복된다. 명칭·기간은 가상이다.
확정: 아이템 상세는 기존 아이템 테이블이 소유하고, 출석 이벤트는 그 ID만 참조한다.
제약: 하루별 보상을 Item1~Item14 열로 늘리지 않으며, 한 행이 무엇인지 먼저 선언한다.
이벤트 메타, 일차 보상, 아이템 참조의 객체·행 의미·기본 키·외래 키를 표로 설계해줘.
각 칼럼에 영문 또는 프로젝트 규약형 이름, 타입, 입력 형식, 게임 동작, 사용 규칙을 써줘.
이벤트 키가 이벤트 정의 한 행을 참조하는 관계와, 보상 테이블에서 같은 이벤트 키의 여러 행을 조회하는 동작을 구분해줘.
기간 경계, 중복 일차, 존재하지 않는 아이템, 리셋 규칙을 가데이터 3개로 검증해줘.
가상 ID는 예시로 표시하고, 시간대·리셋 시각은 미확정 결정 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 메타와 반복 보상이 분리된 ERD 텍스트·열 사전·가데이터. 테이블마다 한 행의 객체 의미가 일관돼야 한다. 책의 출석부 사용 규칙(시작일·종료일 선후, 참조 키 존재, 회차·수량 0/NULL 불가, 11장 책 188쪽)이 사용 규칙 열에 반영됐는지 확인한다. 기간 제한이 없는 이벤트의 날짜 칸 처리도 본다.

<a id="example-11-b"></a>

#### 고급 예시 B — 복수 이벤트 보상 관계의 반례 검토

```text
$yuriring-game-system-design 11장을 중심으로 주간 출석과 신규 유저 출석이 함께 있는 데이터 설계를 검토해줘.
가상 입력: 두 출석부는 서로 다른 기간·보상 회차를 가지지만 같은 아이템을 보상으로 쓸 수 있다. 모두 가상이다.
확정: 같은 아이템의 이름·아이콘·등급을 각 출석부에 복사하지 않는다.
제약: 이벤트별 보상 행은 소속 이벤트 없이 고립되면 안 되며, 개인 수령 이력은 기획 데이터와 분리한다.
각 테이블의 객체, 반복 구조, 소유 책임, 키 관계를 먼저 설명해줘.
잘못된 단일 테이블안과 분리안의 변경 비용·오류 가능성을 비교해줘.
이벤트 키로 보상 행을 그룹 조회하는 관계와 단일 보상 행을 참조하는 외래 키를 구별해줘.
동일 회차 중복, 이벤트 종료, 아이템 삭제, 잘못된 참조의 반례 가데이터를 작성해줘.
미확정인 보상 중복 수령 규칙과 종료 후 보관 기간은 질문으로 남겨줘.
확정된 내용, 설명을 위해 둔 가정, 추가 검증이 필요한 내용을 구분해줘.
아직 정하지 않은 수치·정책은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
표에는 항목, 선택지, 각 선택지가 미치는 영향, 담당자에게 확인할 질문을 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 반복·참조·개인 이력이 분리된 검토안. 관계 없는 테이블 분리나 상세 속성 중복을 찾을 수 있어야 한다.

선행: [고급 예시 A — 출석 이벤트의 반복 보상을 정규화하기](#example-11-a) 또는 [고급 예시 B — 복수 이벤트 보상 관계의 반례 검토](#example-11-b)의 답변. 같은 대화에서 이어서 쓰고, 새 대화라면 [새 대화 인계 형식](#handover)으로 선행 결과·조건 판정·미확인 항목을 함께 붙인다.

```text
판정이 유지되거나 바뀌는 이유, 새 반례, 아직 확인하지 못한 항목을 남겨줘.
```

### 12. [데이터 테이블 사례](../.agents/skills/yuriring-game-system-design/chapters/ch12-table-cases.md)

- **활용 시점:** 다국어 텍스트, 아이템·제작, 상점·랜덤 상점, 가챠·확률, 스킬·성장, 퀘스트, 범용 설정처럼 복합 데이터의 분리/통합 선택을 비교할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 12장을 중심으로 [도메인: 예 가챠/스킬/퀘스트]의 데이터 책임을 설계해줘. 반복 재료·보상·효과·조건은 열 증가와 별도 행/테이블 분리를 비교하고, 텍스트·리소스·콘텐츠 참조와 ENUM의 해석 규칙을 명시해줘. 확률과 비중, 추출이 독립인지·중복 허용/복원인지, 누적/단일 수치, 범위 포함 여부, 기간·리셋 경계는 계산 전에 질문 목록으로 남겨줘.`
- **기대 산출물과 확인:** 도메인별 책임표, 연결 관계, 공통 규약, 확장성·레거시 처리 선택지를 받는다. 등급 확률과 동일 등급 내부 비중을 섞지 않았는지, ID와 그룹 ID의 역할을 혼동하지 않았는지, 사례의 확률·값·테이블명이 프로젝트 정답처럼 제시되지 않았는지 확인한다.
- **연계 장:** 기초 키 규칙은 [10장 — 데이터 테이블이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch10-table-foundations.md), 관계와 가데이터는 [11장 — 데이터 테이블 설계](../.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md), 운영 조정은 [20장 — 디자인부터 런칭까지, 시스템 기획의 여정](../.agents/skills/yuriring-game-system-design/chapters/ch20-production-lifecycle.md)과 연결한다.

<a id="example-12-a"></a>

#### 고급 예시 A — 확률 배너의 등급 확률과 후보 비중 분리

```text
$yuriring-game-system-design 12장을 중심으로 ‘별빛 소환’ 배너의 확률 데이터를 설계해줘.
가상 입력: SSR 3%, SR 17%, R 80%라는 등급 확률과 SSR 후보 루나·카일의 상대 비중 3:1이 있다.
이 수치와 캐릭터명은 책의 사실이나 실제 운영 데이터가 아닌 가상 예시라고 명시해줘.
10회 뽑기는 각 회차가 독립 추출이고, 동일 캐릭터 중복과 복원을 허용한다고 가정한다.
등급 확률 그룹, 등급별 후보 풀, 후보 행, 픽업 플래그의 책임과 키 연결을 표로 작성해줘.
확률과 비중을 섞지 말고, 비중 합계가 100일 필요가 없는 이유와 0 비중·빈 풀 검증도 적어줘.
10회 보장, 천장, 유료 재화 가격은 미확정으로 남기고 임의의 규칙을 만들지 마.
산출물은 테이블 초안, 계산 순서, 가데이터 3행, QA 경계 사례 5개로 제한해줘.
확정 가정·근거·미확정을 별도 표기해줘.
각 판단의 검증 책임자와 남은 질문도 짧게 구분해줘.
```

> [!NOTE]
> **기대 결과**
>
> 등급 확률과 후보 비중의 책임이 분리된 테이블·검증안. 독립/복원 가정과 미확정 보장 규칙이 섞이지 않아야 한다. 개별 확률이 등급 확률 × (후보 비중 ÷ 같은 등급 후보 비중 합)의 순서로 계산되는지 확인한다(12장, 책 206쪽 방식). 가상 입력에서는 루나 3% × 3/4 = 2.25%, 카일 3% × 1/4 = 0.75%다.

<a id="example-12-b"></a>

#### 고급 예시 B — 랜덤 상점 갱신 데이터의 반례 검토

```text
$yuriring-game-system-design 12장을 중심으로 주말 랜덤 상점의 데이터 설계를 반례까지 검토해줘.
가상 입력: 상점은 하루 두 번 갱신하며, 상품 후보는 소비품·장비·재료 세 타입으로 나뉜다.
이 설정은 가상 프로젝트 가정이며 책의 사례, 실제 서비스 정책, 관찰 결과가 아님을 먼저 표시해줘.
각 슬롯은 독립 추출인지, 같은 상품 중복을 허용하는지, 갱신 뒤 구매 이력을 보존하는지는 미확정이다.
상점 정의, 상품 행, 랜덤 풀, 타입별 참조 대상, 기간·재고·구매 제한의 책임을 분리해줘.
타입 값마다 참조 테이블을 어떻게 검증하는지와 고아 ID·빈 풀·분모 0 반례를 포함해줘.
값이 확률인지 비중인지 구분하고, 확률 합계 규약을 검증하되 비중 합계 100은 강제하지 마. 갱신 시각은 미정으로 남겨줘.
산출물은 결정 질문, 키 관계, 검증 규칙, 가데이터 검토 순서만 제시해줘.
확정 가정·제안·미확정을 분리하고 검증 책임도 표시해줘.
반례별로 누가 결정해야 하는지와 보류 사유를 짧게 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> 랜덤 상점의 데이터 책임과 참조 검증이 드러난 설계안. 미결정 추출 정책을 임의로 확정하지 않는지가 판단 기준이다.

<a id="followup-12"></a>

#### 후속 요청 — 가데이터로 확률 검산과 참조·빈 풀 QA

선행: [고급 예시 A — 확률 배너의 등급 확률과 후보 비중 분리](#example-12-a) 또는 [고급 예시 B — 랜덤 상점 갱신 데이터의 반례 검토](#example-12-b)의 답변. 같은 대화에서 이어서 쓰고, 새 대화라면 [새 대화 인계 형식](#handover)으로 선행 결과·조건 판정·미확인 항목을 함께 붙인다.

```text
판정이 유지되거나 바뀌는 이유, 새 반례, 아직 확인하지 못한 항목을 남겨줘.
```

### 13. [UX/UI란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch13-ux-ui-foundations.md)

- **활용 시점:** 화면을 예쁘게 만드는 문제와 플레이어가 목표를 이해하고 행동할 수 있게 만드는 문제를 구분해야 할 때, 또는 기능의 경험 목표를 UI 방향으로 번역할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 13장을 중심으로 [기능]의 UX와 UI를 분리해 설계해줘. 플레이어가 도달해야 할 목표, 이해해야 할 정보, 선택·행동 순서, 성공/실패 후 피드백을 먼저 정의하고, 그 경험을 지원할 화면/표시 요소를 제안해줘. 접근성이나 플랫폼 제약은 [제약]으로 반영하되 미확정은 가정으로 표시해줘.`
- **기대 산출물과 확인:** 사용자 목표-행동-피드백 흐름과 UI 역할 목록을 받는다. UI 구성요소가 목적 없이 먼저 선택되지 않았는지, 경험 목표를 절대적인 완료 조건처럼 단정하지 않았는지, 규칙의 차단 이유와 다음 행동이 보이는지 확인한다.
- **연계 장:** 표현과 상호작용 방식은 [14장 — UX/UI 기획을 위한 구성 요소와 표현 기법](../.agents/skills/yuriring-game-system-design/chapters/ch14-visual-interaction.md), 화면·요소 명세는 [15장 — UX/UI 설계](../.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md)~[16장 — UX/UI 구성 요소](../.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md)로 구체화한다.

<a id="example-13-a"></a>

#### 고급 예시 A — 길드 해산의 고비용 행동 UX 목표 설계

```text
$yuriring-game-system-design 13장을 중심으로 길드장 전용 ‘길드 해산’ 경험 목표를 설계해줘.
가상 입력: 해산하면 길드명·가입 상태·공용 보관함 접근이 사라지고 7일 재생성 제한이 생긴다.
이 조건은 가상 프로젝트 가정이며 실제 정책이나 책의 확정 사례가 아니라고 표기해줘.
목표는 오조작을 줄이되, 권한 있는 사용자가 결과를 이해하고 완료할 수 있게 하는 것이다.
플레이어 목표, 알아야 할 정보, 선택·확인·완료 후 행동, 실패·취소 피드백을 먼저 정의해줘.
그다음 UI 요소를 제안하되, 장식 제안과 행동 이해에 필수인 요소를 구분해줘.
실제 오조작률 개선 효과는 미확정 가설로 두고 관찰 이벤트와 사용성 검증 질문을 제안해줘.
버튼 색만으로 위험을 구분하지 않는 접근 가능한 대체 피드백도 포함해줘.
확정 가정과 검증 가설·책임을 분리해줘.
실패한 사용성 결과가 나오면 재검토할 규칙도 짧게 적어줘.
```

> [!NOTE]
> **기대 결과**
>
> UX 목표에서 UI로 이어지는 흐름과 검증 가설. UI 예쁨이 아니라 결과 이해·취소·피드백이 명세되어야 한다.

<a id="example-13-b"></a>

#### 고급 예시 B — 초보자 장비 추천의 발견성 분석

```text
$yuriring-game-system-design 13장을 중심으로 초보자 장비 추천 기능의 UX 가설을 분석해줘.
가상 입력: 레벨 15에 첫 보스 패배 뒤 추천 배너를 한 번 노출하고, 수락 시 장비 3개를 비교한다.
이 노출 규칙과 수치는 가상 예시이며 실제 플레이 로그나 책의 권장값이 아니라고 밝혀줘.
플레이어가 무엇을 이해하고 어떤 선택을 해야 하는지, 추천을 거절해도 다음 행동이 보이는지 설계해줘.
추천 근거 표시, 비교 부담, 보상 오해, 재노출 여부를 UX 질문과 UI 역할로 나눠줘.
‘추천이 이탈을 줄인다’는 문장은 사실이 아니라 검증 대상 가설로만 기록해줘.
A/B 테스트가 필요할 수 있는 변수와 성공·실패를 해석할 때의 주의점을 제시해줘.
장비 수치·알고리즘·재화 비용은 미확정으로 유지하고 채우지 마.
결과를 경험 흐름 표와 검증 책임으로 정리해줘.
관찰값이 가설을 반박할 때 바꿀 다음 질문도 제시해줘.
```

> [!NOTE]
> **기대 결과**
>
> 발견·이해·선택·피드백을 분리한 경험 설계. 가설과 관찰 지표가 사실처럼 단정되지 않아야 한다.

<a id="chapter-14"></a>

### 14. [UX/UI 기획을 위한 구성 요소와 표현 기법](../.agents/skills/yuriring-game-system-design/chapters/ch14-visual-interaction.md)

- **활용 시점:** 정보의 우선순위, 레이아웃, 시각적 깊이, 아이콘·색·메타포가 플레이어의 이해와 조작에 미치는 영향을 검토할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 14장을 중심으로 [화면/기능]의 정보 위계와 표현 전략을 검토해줘. 사용자가 가장 먼저 봐야 할 정보, 그다음 선택할 행동, 상태 변화 피드백을 정하고, 레이아웃·대비·그룹화·아이콘/텍스트·메타포가 각각 어떤 오해를 줄이는지 설명해줘. 장식 제안과 기능상 필수 요소를 구분해줘.`
- **기대 산출물과 확인:** 정보 위계표, 표현 옵션별 장단점, 오해 가능성 목록을 받는다. 색상만으로 상태를 구별하게 하지 않았는지, 익숙한 메타포가 실제 게임 규칙과 어긋나지 않는지, 중요한 행동의 우선순위가 시각적으로 묻히지 않는지 확인한다.
- **연계 장:** 실제 정보 구조·화면 전환은 [15장 — UX/UI 설계](../.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md), 버튼·입력·알림의 조건은 [16장 — UX/UI 구성 요소](../.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md)에서 명세한다.

<a id="example-14-a"></a>

#### 고급 예시 A — 레이드 HUD 정보 위계와 표현 검토

```text
$yuriring-game-system-design 14장을 중심으로 4인 레이드 전투 HUD의 정보 위계를 설계해줘.
가상 입력: 중앙에는 보스 패턴, 좌측에는 파티 체력, 하단에는 스킬 6개와 쿨다운이 표시된다.
이 화면 구성은 가상 시나리오이며 책의 도판이나 실제 게임 UI를 재현한 것이 아니라고 명시해줘.
전투 중 1초 안에 봐야 할 정보, 다음 행동 전에 확인할 정보, 필요 시 열어볼 정보를 구분해줘.
각 정보의 위치·대비·그룹화·아이콘과 텍스트 병기 이유를 행동 목표와 연결해줘.
색상만으로 위험·상태를 구분하지 않는 대체 표현과 시야를 가리는 반례를 포함해줘.
보스 패턴을 더 잘 보이게 하려면 UI 장식 대신 규칙·동시 정보량을 줄여야 할 조건도 제시해줘.
폰트 크기·색상값·애니메이션 시간은 미확정으로 두고 임의 수치를 넣지 마.
필수 요소와 선택 요소를 분리해줘.
```

> [!NOTE]
> **기대 결과**
>
> 현재 맥락의 정보 우선순위와 표현 이유가 있는 HUD 방안. 시야·접근성·규칙 복잡성 반례가 포함되어야 한다.

#### 고급 예시 B — 수집 도감의 메타포와 오해 가능성 리뷰

```text
$yuriring-game-system-design 14장을 중심으로 몬스터 수집 도감 화면의 표현 전략을 비판적으로 검토해줘.
가상 입력: 실루엣 카드는 미발견, 컬러 카드는 발견, 금테 카드는 최고 희귀도 획득을 뜻한다.
이 상태 규칙은 가상 입력이며 실제 제품 정책이나 책의 권장 표현이 아니라고 밝혀줘.
사용자가 ‘발견’과 ‘획득’, 최고 희귀도와 강화 완료를 혼동할 가능성을 정보 위계로 분석해줘.
카드 배치, 필터 진입 깊이, 아이콘·텍스트 보조, 색 외의 구분 방법을 제안해줘.
수집 진행률을 항상 상단에 고정할지, 필요 시 열람할지의 장단점을 사용 맥락으로 비교해줘.
이 화면의 세계관 연출과 기능상 필수 상태 표시를 분리해서 명세해줘.
정확한 카드 수·색상 코드·정렬 방식은 미확정으로 남기고 채우지 마.
오해 사례별 완화안을 표로 작성해줘.
```

> [!NOTE]
> **기대 결과**
>
> 상태 의미와 시각 표현을 연결한 검토표. 메타포가 실제 규칙과 어긋나는 반례를 다뤄야 한다.

### 15. [UX/UI 설계](../.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md)

- **활용 시점:** 기능의 규칙은 정해졌지만 화면 범위, 정보 구조, 화면 전환, 와이어프레임, 정렬·필터·검색의 동작을 구현자가 같은 의미로 읽게 해야 할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 15장을 중심으로 [기능]의 UX/UI 명세 초안을 만들어줘. 정보 구조도, 필요한 화면과 전환 조건, 화면별 목표, 와이어프레임 영역을 구분해줘. 정적 요소는 역할·표시를, 상호작용 요소는 해당되는 입력·기본값·변경 결과·저장 여부를 명세해줘. [정렬/필터/검색/탭]이 있다면 초기 상태, 변경 결과, 서버/클라이언트 동기화 가정도 명시해줘.`
- **기대 산출물과 확인:** 화면 목록, 전환표, 영역 설계, 요소 명세표를 받는다. 정보 구조도·UI 플로 차트·와이어프레임을 같은 산출물로 혼동하지 않았는지, 선택/정렬/필터의 초기값과 저장 범위가 정해졌는지, 화면 그림에 동작 규칙을 맡기지 않았는지 확인한다.
- **연계 장:** 복잡한 규칙 분기는 [09장 — 규칙의 도식화](../.agents/skills/yuriring-game-system-design/chapters/ch09-flowcharts.md), 공통 UI 구성요소의 상세 동작은 [16장 — UX/UI 구성 요소](../.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md), 문서 모듈화는 [18장 — 시스템 기획서 실습](../.agents/skills/yuriring-game-system-design/chapters/ch18-document-workshop.md)으로 잇는다.

<a id="example-15-a"></a>

#### 고급 예시 A — 우편함 정렬·필터·검색의 화면 흐름 명세

```text
$yuriring-game-system-design 15장을 중심으로 게임 우편함의 정렬·필터·검색 흐름을 UX/UI 명세로 작성해줘.
가상 입력: 탭은 전체·미수령·공지이고, 필터는 보상 포함 여부, 검색은 제목만 대상으로 한다.
이 기능 범위는 가상 프로젝트 가정이며 실제 제품 요구나 책의 사례가 아니라고 표시해줘.
초기 탭, 초기 정렬, 필터 중첩, 검색어 적용·해제, 결과 없음, 읽음/수령 뒤 목록 갱신을 분리해줘.
화면 목표, 전환 조건, 영역, 요소별 역할·입력·변경 결과·저장 여부를 표로 작성해줘.
정렬/필터/검색 상태를 서버와 동기화할지 기기 로컬에 보존할지는 미확정 질문으로 남겨줘.
정렬 기준의 동점 처리와 새 우편 도착 시 목록 위치도 결정 질문으로 제시해줘.
정확한 API, 데이터베이스, UI 스타일은 제안하지 말고 기능 계약에 집중해줘.
확정 가정과 미확정을 구분해줘.
```

> [!NOTE]
> **기대 결과**
>
> 초기 상태부터 결과 갱신까지 끊기지 않는 화면·요소 명세. 저장 범위와 동점 규칙을 임의 확정하지 않는지가 기준이다.

<a id="example-15-b"></a>

#### 고급 예시 B — 장비 인벤토리 필터 흐름의 반례 설계

```text
$yuriring-game-system-design 15장을 중심으로 장비 인벤토리 필터 흐름의 반례를 포함한 명세를 만들어줘.
가상 입력: 등급·부위·장착 가능 여부 필터와 공격력 정렬이 있으며, 장비는 0개일 수 있다.
이 조건과 장비 속성은 가상 예시이며 책의 실제 데이터나 확정 사양이 아니라고 밝혀줘.
필터를 하나도 선택하지 않은 상태, 상충 선택, 결과 0개, 장비 장착 직후, 필터 초기화를 분기해줘.
정보 구조도와 UI 플로 차트의 역할을 구분하고, 각 화면 영역이 답하는 질문을 써줘.
필터 선택 순서가 결과에 영향을 주는지, 적용 즉시 갱신인지 확인 버튼이 필요한지는 미확정으로 유지해줘.
공격력 동점, 숨김 장비, 로딩 실패는 규칙·표시·재시도 관점에서 별도 표기해줘.
정적 제목이나 설명 문구에는 입력 조건을 강제하지 말고, 동작 요소만 명세해줘.
QA 가능한 흐름 표와 미결정 질문을 제공해줘.
```

> [!NOTE]
> **기대 결과**
>
> 필터·정렬의 정상/예외 흐름과 화면 산출물의 역할이 분리된 명세. 정적 요소를 동작 요소처럼 다루지 않아야 한다.

### 16. [UX/UI 구성 요소](../.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md)

- **활용 시점:** 입력, 선택, 알림, 진행 표시, 탐색 UI를 선택하고 버튼/모달/툴팁/배지/스크롤 등 구성요소의 상태와 행동을 구체적으로 정할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 16장을 중심으로 [사용자 과업]에 맞는 UI 구성 요소를 설계해줘. 각 요소의 명칭과 역할을 쓰고, 상태나 동작이 필요한 요소에만 표시 조건, 입력 방식, 기본/비활성/로딩/오류 상태, 확인·취소 결과, 저장 여부와 접근 가능한 대체 피드백을 표로 작성해줘. 화면이 복잡하면 배치를 꾸미기 전에 줄일 수 있는 규칙·단계를 함께 제안해줘.`
- **기대 산출물과 확인:** 요소별 상태 명세와 선택 이유를 받는다. 정적 표시 요소에 활성 조건·입력·저장을 억지로 요구하지 않았는지, 진행률을 알 수 있는 작업에 모호한 로딩만 쓰지 않았는지, 확인이 필요한 행동에 취소·되돌리기 결과가 있는지, 탐색 UI의 콘텐츠 양·방향·우선순위가 맞는지, UI 복잡성이 규칙 과잉 신호는 아닌지 검토한다.
- **연계 장:** 사용자 경험 목표는 [13장 — UX/UI란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch13-ux-ui-foundations.md), 시각적 위계는 [14장 — UX/UI 기획을 위한 구성 요소와 표현 기법](../.agents/skills/yuriring-game-system-design/chapters/ch14-visual-interaction.md), 전체 화면 명세는 [15장 — UX/UI 설계](../.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md)에서 확인한다.

<a id="example-16-a"></a>

#### 고급 예시 A — 제작 완료 수령 모달의 조건부 UI 명세

```text
$yuriring-game-system-design 16장을 중심으로 제작 완료 수령 모달의 구성 요소와 상태를 명세해줘.
가상 입력: 제작품은 완료·수령됨·보관함 가득·제작 중단 상태를 가질 수 있다.
이 상태명은 가상 프로젝트 가정이며 책의 실제 상태 모델이나 제품 정책이 아니라고 표시해줘.
수령 버튼, 닫기, 제작품 정보, 남은 시간, 오류 안내 각각의 역할과 필요한 상태만 정의해줘.
동작 요소에는 표시 조건, 입력 방식, 기본·비활성·로딩·오류, 확인 결과, 저장 여부를 표로 작성해줘.
정적 제목과 설명에는 입력·저장·활성 조건을 억지로 붙이지 말고 표시 목적만 쓰게 해줘.
보관함 가득일 때 보존되는 제작 상태, 안내 문구, 재시도 경로는 규칙과 UI로 나눠줘.
재화 환불, 자동 수령, 네트워크 구현 방식은 미확정으로 남기고 임의 결론을 내리지 마.
접근 가능한 대체 피드백도 함께 제시해줘.
```

> [!NOTE]
> **기대 결과**
>
> 요소마다 필요한 상태만 담긴 UI 명세. 정적 정보와 상호작용·오류 복구의 책임이 혼합되지 않아야 한다. 오류 안내를 토스트·팝업·모달 중 어디에 둘지 고를 때 토스트는 긴·반복 정보에 부적합하고 모달은 최소한으로 쓴다는 책의 기준(16장, 책 278–280쪽)과 맞는지 확인한다.

### 17. [시스템 기획서의 역할과 범위](../.agents/skills/yuriring-game-system-design/chapters/ch17-document-purpose.md)

- **활용 시점:** 제안, 승인, 프리 프로덕션, 개발 중 변경 등 문서의 단계가 바뀌었는데 같은 형식의 문서를 계속 쓰고 있거나, 독자별 필요한 결정을 정리해야 할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 17장을 중심으로 [기능] 문서의 현재 단계가 [탐색/승인/구현/변경 관리]일 때 필요한 목차를 설계해줘. 독자별로 내려야 할 결정과 미확정 항목을 먼저 적고, Why → What → How 순서로 의도·기대 효과·기능 범위·규칙·예외·데이터·UI·리소스·로그를 배치해줘. 변경된 사양과 문서를 동기화할 항목도 포함해줘.`
- **기대 산출물과 확인:** 단계별 문서 목차와 독자-결정 매트릭스를 받는다. 탐색 가설을 구현 확정처럼 쓰지 않았는지, Why 없이 기능 목록부터 시작하지 않았는지, 실제 사양과 문서가 서로 참조 가능한지 확인한다.
- **연계 장:** 기능 단위 본문 작성은 [18장 — 시스템 기획서 실습](../.agents/skills/yuriring-game-system-design/chapters/ch18-document-workshop.md), 가독성과 AI 보조 검수는 [19장 — 시스템 기획서의 완성도를 결정하는 요소들](../.agents/skills/yuriring-game-system-design/chapters/ch19-document-quality.md), 라이프사이클 반영은 [20장 — 디자인부터 런칭까지, 시스템 기획의 여정](../.agents/skills/yuriring-game-system-design/chapters/ch20-production-lifecycle.md)에서 한다.

```text
$yuriring-game-system-design 17장을 중심으로 ‘길드 원정’ 기능의 승인 단계 문서 목차를 설계해줘.
가상 입력: 주 1회 20명 협동 콘텐츠이며, 보상은 기여도에 따라 달라질 수 있다는 제안만 있다.
이 기능·주기·인원은 가상 프로젝트 가정이며 실제 서비스 사양이나 책의 사례가 아니라고 밝혀줘.
기획 리드, 개발 리드, UI 담당, QA 담당이 지금 내려야 할 결정을 독자별로 나눠줘.

승인에 필요한 근거와 승인 뒤 구현 문서로 넘길 결정 항목을 구분해줘.
문서가 탐색 가설을 확정 사양처럼 보이게 하는 반례도 검토해줘.
독자-결정 매트릭스와 변경 동기화 항목을 산출해줘.
```

```text
$yuriring-game-system-design 17장을 중심으로 라이브 중 장비 강화 비용 변경 문서의 범위를 설계해줘.
가상 입력: 비용을 낮추자는 제안이 있고, 기존 이용자 보상 여부와 적용 시점은 미확정이다.

운영, 경제 기획, 클라이언트, 서버, QA, CS가 각각 알아야 할 사실·결정·미확정을 나눠줘.

정확한 할인율, 일정, 보상 방식은 임의로 채우지 말고 결정 질문으로 남겨줘.
```

>

#### 후속 요청 — 독자별 결정 필요·참고·미확정 표

<a id="chapter-18"></a>

### 18. [시스템 기획서 실습](../.agents/skills/yuriring-game-system-design/chapters/ch18-document-workshop.md)

- **활용 시점:** 하나의 기능을 개요부터 규칙·데이터·UI·예외·테스트 가능한 상태까지 완결된 협업 문서로 만들어야 할 때 사용한다. 파견 미션 같은 상태 기반 시스템에 특히 잘 맞는다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 18장을 중심으로 [기능]의 기능 단위 기획서를 작성해줘. 개요에는 문제·목표·타깃·구성요소를, 본문에는 상태·조건·결과·예외를, 데이터에는 기간·조건·보상·참조·검증 규칙을, UI에는 미배정/진행/완료 등 상태별 입력 가능 여부와 동기화 규칙을 포함해줘. 이 기능에 해당하는 모집 마감·중복 배정·정원 부족·보상 없음·취소 등의 반례만 테스트 케이스로 넣어줘.`
- **기대 산출물과 확인:** 개요, 규칙표, 상태 전이, 데이터 표, UI 요소 명세, 예외·QA 표를 한 묶음으로 받는다. 개요와 상세가 다른 범위를 말하지 않는지, 데이터 열에 단위·참조·소비처가 있는지, 정렬이 필요하면 조건 점수·등급·레벨·고유 ID처럼 사용할 우선 기준을 명시하되 원문이 밝히지 않은 등급·레벨·고유 ID의 오름/내림 방향을 확정하지 않았는지, UI 그림이 버튼 활성 조건·서버 갱신을 대신하고 있지 않은지 확인한다.

> [!IMPORTANT]
> **자동 편성 사례의 참조 범위**
>
> 책의 우선순위는 조건 점수 → 등급 → 레벨 → 캐릭터 고유 ID다. 원문이 방향을 밝힌 것은 조건 점수(많이 충족하는 순)뿐이고 등급·레벨·고유 ID의 오름차순·내림차순 방향은 원문에서 확정하지 않으므로 프로젝트 정책으로 명시한다. 다른 자동화 기능에 이 순서를 그대로 적용하지 않는다.

- **연계 장:** 규칙의 기본 틀은 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md), 데이터 관계는 [11장 — 데이터 테이블 설계](../.agents/skills/yuriring-game-system-design/chapters/ch11-table-design.md), UI 명세는 [15장 — UX/UI 설계](../.agents/skills/yuriring-game-system-design/chapters/ch15-ux-ui-design.md)~[16장 — UX/UI 구성 요소](../.agents/skills/yuriring-game-system-design/chapters/ch16-ui-components.md)와 함께 쓴다.

<a id="example-18-a"></a>

#### 고급 예시 A — 자동 원정 편성의 기능 단위 명세와 정렬 미확정

```text
$yuriring-game-system-design 18장을 중심으로 자동 원정 편성 기능의 협업 기획서를 작성해줘.
가상 입력: 출전 후보 중 조건 점수 → 등급 → 레벨 → 캐릭터 고유 ID 순으로 우선순위를 비교한다.
이 순서만 스킬의 참조 범위이며, 각 기준의 오름·내림 방향은 프로젝트 미확정으로 유지해줘.
정원 4명, 중복 배정 금지, 휴식 중 캐릭터 제외는 가상 프로젝트 가정이라고 별도 표시해줘.
개요에는 문제·목표·타깃·구성요소를, 본문에는 상태·조건·판정·결과·예외를 작성해줘.
데이터에는 후보 상태·조건 점수·참조·검증 규칙을, UI에는 상태별 표시와 입력 가능 여부를 포함해줘.
각 테이블은 한 행의 의미·기본 키·중복 검증 범위를 명시하고, 단일 행 참조와 그룹 조회를 구분해줘.
정원 부족, 동점, 후보 없음, 편성 중 상태 변경, 취소를 QA 케이스로 넣어줘.
정렬 방향, 보상, 서버 동기화 방식은 미확정 질문으로 남기고 임의로 정하지 마.
사실·가상 가정·제안을 명확히 나눠줘.
```

> [!NOTE]
> **기대 결과**
>
> 규칙·데이터·UI·QA가 한 기능 단위로 연결된 문서. 정렬 순서는 보존하되 오름/내림을 단정하지 않아야 한다.

<a id="example-18-b"></a>

#### 고급 예시 B — 파견 미션 상태 문서의 입력 조건 반례

```text
$yuriring-game-system-design 18장을 중심으로 파견 미션의 상태 기반 기획서를 검토해줘.
가상 입력: 미배정·진행·완료·보상 수령 상태가 있으며, 완료 뒤 수령해야 재파견할 수 있다.
이 상태 흐름은 가상 예시이고 책의 실제 기능 사양이나 프로젝트 확정 정책이 아니라고 밝혀줘.
상태별로 가능한 입력, 불가능한 입력, 전이 조건, 결과, 플레이어 안내를 표로 작성해줘.
모집 마감, 중복 배정, 정원 부족, 보상 없음, 취소, 재접속을 예외·QA 케이스로 포함해줘.
UI 공통 필드와 상태에 따라 필요한 동작 필드를 구분하고, 정적 제목에는 입력 조건을 강제하지 마.
보상 지급 시점, 자동 수령, 시간 기준, 데이터 저장 방식은 미확정 항목으로 남겨줘.
문서의 개요·규칙·데이터·UI가 서로 다른 상태명을 쓰는 반례도 찾아줘.
불일치 검수표와 수정 우선순위를 제시해줘.
```

> [!NOTE]
> **기대 결과**
>
> 상태별 계약과 문서 간 명칭 일관성 검토. 정적 UI에 동작 조건을 부여하지 않고 미확정 지급 정책을 보존해야 한다.

### 19. [시스템 기획서의 완성도를 결정하는 요소들](../.agents/skills/yuriring-game-system-design/chapters/ch19-document-quality.md)

- **활용 시점:** 문서가 길거나 여러 사람이 수정해 규칙·UI·테이블이 흩어졌을 때, 또는 AI로 브레인스토밍·구조화·문장 교정을 하되 근거와 책임을 지켜야 할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 19장을 중심으로 아래 기획 메모를 검토 가능한 문서 구조로 재구성해줘: [메모]. Why/What/How, 규칙, 예외, 데이터, UI, 밸런스 리스크, 로그, 미결정으로 분류하고 원문 항목을 누락하지 마. 사실 주장·수치·인과는 출처 확인 필요 또는 가설로 표시하고, 문장 교정 전후에 조건·단위·예외·책임 주체가 사라졌는지 검수표도 만들어줘.`
- **기대 산출물과 확인:** 기능 단위 문서 구조, 누락 후보, 사실/가설 구분, 문장 수정안과 보존 검수표를 받는다. AI의 시장·심리·지표 주장을 근거로 인용하지 않았는지, 페이지 수나 디자인보다 탐색성·가독성·명세 완결성을 우선했는지, 축약 과정에서 예외가 사라지지 않았는지 확인한다.
- **연계 장:** 문서의 목적과 독자는 [17장 — 시스템 기획서의 역할과 범위](../.agents/skills/yuriring-game-system-design/chapters/ch17-document-purpose.md), 기능 문서의 실습 틀은 [18장 — 시스템 기획서 실습](../.agents/skills/yuriring-game-system-design/chapters/ch18-document-workshop.md), 출시 후 검증은 [20장 — 디자인부터 런칭까지, 시스템 기획의 여정](../.agents/skills/yuriring-game-system-design/chapters/ch20-production-lifecycle.md)과 연결한다.

<a id="example-19-a"></a>

#### 고급 예시 A — AI 보조 문서 재구성과 귀속 보존 검수

```text
$yuriring-game-system-design 19장을 중심으로 아래 가상 기획 메모를 검토 가능한 문서로 재구성해줘.
메모: ‘주간 보스는 어려워야 하고 보상은 좋게, 참가자는 많을수록 재미있다, 나중에 조정한다.’
이 메모는 가상 입력이며 실제 사용자 조사·지표·책의 주장·확정 사양이 아니라고 먼저 표기해줘.
Why/What/How, 규칙, 예외, 데이터, UI, 밸런스 리스크, 로그, 미결정으로 분류하되 원문 문장을 삭제하지 마.
‘어려워야’, ‘좋게’, ‘많을수록’ 같은 모호한 표현은 질문 또는 테스트 가능한 명세 후보로 바꿔줘.
AI가 새로 제안한 문장에는 AI 제안이라고 귀속을 표시하고, 사실·수치·인과는 근거 확인 필요로 남겨줘.
축약·문장 교정 전후에 주체·조건·단위·예외·책임이 사라지지 않았는지 검수표를 작성해줘.
보상 수치, 인원 제한, 난이도 알고리즘은 미확정으로 유지하고 발명하지 마.
문서 탐색성과 완결성 기준으로 결과를 정리해줘.
```

> [!NOTE]
> **기대 결과**
>
> 원문 메모·AI 제안·검증 필요 사실이 구분된 문서와 보존 검수표. AI의 가설을 근거처럼 쓰지 않아야 한다.

<a id="example-19-b"></a>

#### 고급 예시 B — 긴 강화 문서의 누락·모순 감사

```text
$yuriring-game-system-design 19장을 중심으로 장비 강화 문서의 품질 감사를 설계해줘.
가상 입력: 규칙 표에는 실패 시 재료 소모라고 쓰였지만 UI 문구에는 재료 보존이라고 적혀 있다.
이 충돌은 가상 문서 결함이며 실제 프로젝트 사실이나 책의 사례가 아니라고 밝혀줘.
독자가 기획·개발·QA일 때 각자가 빠르게 찾아야 할 질문을 기준으로 문서 모듈을 나눠줘.
Why/What/How와 규칙·예외·데이터·UI·로그 사이에서 찾을 모순과 누락을 체크리스트로 작성해줘.
표·플로·와이어프레임이 각각 답해야 할 질문을 분리하고, 한 그림이 규칙을 대신하는 위험을 지적해줘.
AI가 제안한 수정은 제안자·근거 상태를 보존하고, 원문 조건을 조용히 바꾸지 말아줘.
실패 확률, 재료 수량, UI 문구 최종안은 미확정으로 두고 결정 담당자를 제시해줘.
수정 우선순위와 재검수 절차를 산출해줘.
```

> [!NOTE]
> **기대 결과**
>
> 모순을 추적 가능한 위치로 연결한 감사안. 문장 미화보다 조건·예외·귀속 보존이 우선이어야 한다.

<a id="followup-19"></a>

#### 후속 요청 — AI 제안·프로젝트 결정·검증 필요 사실의 라벨 규칙

선행: [고급 예시 A — AI 보조 문서 재구성과 귀속 보존 검수](#example-19-a)의 답변. 같은 대화에서 이어서 쓰고, 새 대화라면 [새 대화 인계 형식](#handover)으로 선행 결과·조건 판정·미확인 항목을 함께 붙인다.

```text
$yuriring-game-system-design 19장 고급 예시 A의 답변을 이어서 보완해줘.
위 문서에 AI 제안·프로젝트 결정·검증 필요 사실을 구분하는 라벨 규칙과 예시 5개를 추가해줘.
AI 답변의 통계·심리·시장 주장을 검증 전 근거로 쓰지 않는 것은 이 스킬의 검증 지침이며 책의 경고 문장이 아니라는 점을 라벨 설명에 밝혀줘.
판정이 유지되거나 바뀌는 이유, 새 반례, 아직 확인하지 못한 항목을 남겨줘.
```

### 20. [디자인부터 런칭까지, 시스템 기획의 여정](../.agents/skills/yuriring-game-system-design/chapters/ch20-production-lifecycle.md)

- **활용 시점:** 기능을 디자인·프리 프로덕션·프로덕션·라이브의 연속 과정으로 관리하거나, 구현 제약·일정 지연·지표 해석 때문에 원래 사양을 조정해야 할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 20장을 중심으로 [기능]의 제작 라이프사이클 계획을 만들어줘. 디자인 단계의 핵심 재미, 프리 프로덕션의 핵심/선택/후속 범위와 기준선, 프로덕션 이슈의 원인·영향·우회안·문서 반영, 라이브의 로그·지표·정성 피드백·폴리싱 계획을 구분해줘. 제약 [제약]에서 의도를 보존하는 대안도 비교해줘.`
- **기대 산출물과 확인:** 단계별 의사결정표, 기준선·미결정 목록, 이슈 기록 양식, 로그 계획, 변경 전후 평가 계획을 받는다. 기능 목록을 핵심 재미로 오인하지 않았는지, QA 결과만으로 기획 의도까지 검증됐다고 보지 않는지, 지표 하나나 첫 주 단면만으로 원인을 단정하지 않는지 확인한다.
- **연계 장:** 핵심 경험의 출발은 [03장 — 기획 의도란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch03-design-intent.md)~[04장 — 기획 의도 설계란?](../.agents/skills/yuriring-game-system-design/chapters/ch04-intent-design.md), 문서 기준선은 [17장 — 시스템 기획서의 역할과 범위](../.agents/skills/yuriring-game-system-design/chapters/ch17-document-purpose.md)~[19장 — 시스템 기획서의 완성도를 결정하는 요소들](../.agents/skills/yuriring-game-system-design/chapters/ch19-document-quality.md), 영향도와 범위 판단은 [21장 — 시스템 기획자 레벨 업](../.agents/skills/yuriring-game-system-design/chapters/ch21-designer-growth.md)으로 이어진다.

<a id="example-20-a"></a>

#### 고급 예시 A — 장비 프리셋의 제작·라이브 기준선 계획

```text
$yuriring-game-system-design 20장을 중심으로 장비 프리셋 기능의 디자인부터 라이브까지 계획을 작성해줘.
가상 입력: 콘텐츠 전 빠른 준비와 세팅 선택이 목표이며, 전투 중 전환은 1차 범위에서 제외한다.
이 목표와 범위는 가상 프로젝트 가정이며 책의 확정 사례나 실제 출시 계획이 아니라고 밝혀줘.
디자인 단계에서는 핵심 재미를 플레이어 행동·판단·감정으로 정의하고, 프리 프로덕션에서는 핵심·선택·후속을 나눠줘.
프로덕션 제약으로 저장 공간이 부족할 때 프리셋 수 축소·기존 UI 재사용 등 우회안을 의도 보존 기준으로 비교해줘.
이슈마다 원인·영향·재현·결정·문서 반영을 추적하는 기록 양식을 만들어줘.
라이브에서는 생성률·전환률·저장 실패와 정성 피드백을 함께 읽는 로그·검증 계획을 제안해줘.
정확한 프리셋 개수, 기간, 성공 지표 임계값은 미확정으로 남기고 임의 수치를 넣지 마.
확정 가정·가설·결정 필요 항목을 분리해줘.
```

> [!NOTE]
> **기대 결과**
>
> 단계별 기준선과 제약 대응·운영 검증이 연결된 계획. QA 통과와 경험 검증을 같은 것으로 취급하지 않아야 한다. 사양이 바뀔 때 이유·범위·파급력을 정리하고 실시간, 적어도 당일 문서에 반영하는 책의 원칙(20장, 책 350쪽)이 계획에 들어 있는지 확인한다.

<a id="example-20-b"></a>

#### 고급 예시 B — 이벤트 보상 변경의 라이브 분석 반례

```text
$yuriring-game-system-design 20장을 중심으로 2주 이벤트 보상 변경 제안의 라이브 검증 계획을 비판적으로 작성해줘.
가상 입력: 첫 주 완료율이 낮아 보상 상향 의견이 나왔고, 동시에 튜토리얼 문구도 바뀌었다.
이 관찰은 가상 시나리오이며 실제 지표·인과·책의 권장 운영 결론이 아니라고 명시해줘.
완료율 하나로 보상 부족을 단정하지 않고, 기간·세그먼트·튜토리얼·이벤트 노출·정성 피드백을 분리해줘.
변경 전 확인할 질문, 가능한 원인, 최소 변경안, 예상 부작용, 되돌림 기준을 표로 작성해줘.
핵심 재미를 보존하는 안내 개선·보상 조정·진입 조건 조정의 차이를 비교해줘.
패치 노트에 공개할 변경 이유와 미공개로 남길 운영 정보의 경계를 결정 질문으로 남겨줘.
정확한 보상량·분석 기간·통계 결론은 미확정으로 유지하고 만들어내지 마.
사실·가설·검증 결과의 기록 양식을 제공해줘.
```

> [!NOTE]
> **기대 결과**
>
> 단일 지표 단정을 피한 라이브 분석·변경 계획. 원인 가설과 실제 관찰을 분리하고 되돌림 기준이 있어야 한다.

#### 후속 요청 — 지금 확정·실험·다음 단계로 넘길 항목 정리

```text
현재 작성한 제작 계획 또는 라이브 변경 검토안에서 ‘지금 확정할 것’, ‘실험할 것’, ‘다음 단계로 넘길 것’을 표로 정리해줘.
결정이 바뀌면 이유·범위·파급력과 함께 실시간, 적어도 당일 문서에 반영한다는 책의 원칙(20장, 책 350쪽)에 맞춰 갱신할 문서 항목과 기한을 열로 추가해줘.
판정이 유지되거나 바뀌는 이유, 새 반례, 아직 확인하지 못한 항목을 남겨줘.
```

### 21. [시스템 기획자 레벨 업](../.agents/skills/yuriring-game-system-design/chapters/ch21-designer-growth.md)

- **활용 시점:** 새 기능을 제안하기 전 기존 루프·경제·UI·신규 유저 경험까지 영향도를 검토하거나, 레퍼런스 분석과 모호한 자연어 명세를 실무적으로 훈련할 때 사용한다.
- **다른 기능에 응용할 기본 요청:** `yuriring-game-system-design 스킬에서 21장을 중심으로 [새 기능]의 사전 설계 리뷰를 해줘. 조건 → 입력 → 처리 → 출력과 실패/예외를 먼저 작성하고, 기존 [루프/재화/UI/콘텐츠]에 미칠 영향도를 표로 분석해줘. [레퍼런스]는 표면 기능이 아니라 역할·제약·보완 수단으로 분해하고, 모호한 표현을 주체·범위·시점·고정/가변값·해당되는 정렬·동점 기준·오류 결과가 있는 테스트 가능한 문장으로 바꿔줘. [일정] 안에서 핵심·옵션·후속을 나눠줘.`
- **기대 산출물과 확인:** 기능 계약, 영향도 표, 레퍼런스 패턴 기록, 명세 교정안, 범위 대안을 받는다. 고립 기능으로 설계하지 않았는지, ‘랜덤’·‘적절히’·‘필요 시’가 검증 가능한 조건으로 바뀌었는지, 플레이어의 시간·기대·부담을 실제 관찰 또는 테스트로 확인할 계획이 있는지 검토한다.
- **연계 장:** 규칙과 플로는 [07장 — 규칙이란 무엇인가?](../.agents/skills/yuriring-game-system-design/chapters/ch07-rule-components.md)~[09장 — 규칙의 도식화](../.agents/skills/yuriring-game-system-design/chapters/ch09-flowcharts.md), 협업 문서화는 [17장 — 시스템 기획서의 역할과 범위](../.agents/skills/yuriring-game-system-design/chapters/ch17-document-purpose.md)~[19장 — 시스템 기획서의 완성도를 결정하는 요소들](../.agents/skills/yuriring-game-system-design/chapters/ch19-document-quality.md), 실제 출시·운영 판단은 [20장 — 디자인부터 런칭까지, 시스템 기획의 여정](../.agents/skills/yuriring-game-system-design/chapters/ch20-production-lifecycle.md)에서 확인한다.

<a id="example-21-a"></a>

#### 고급 예시 A — 장비 조각 성장 기능의 전방위 영향도 훈련

```text
$yuriring-game-system-design 21장을 중심으로 장비 조각 성장 기능의 사전 설계 리뷰를 훈련 형식으로 작성해줘.
가상 입력: 조각 보유와 장비 해금 뒤 강화를 누르면 조각·골드를 소모하고 단계가 오른다는 아이디어가 있다.
이 아이디어와 재화명은 가상 예시이며 실제 게임 데이터, 레퍼런스 관찰, 책의 확정 사양이 아니라고 밝혀줘.
조건 → 입력 → 처리 → 출력과 실패·예외를 먼저 작성하고, 미정 부분은 질문으로 남겨줘.
기존 장비 강화·스킬 강화·일일 재화·인벤토리·신규 유저 경로·로그에 대한 영향도를 표로 분석해줘.
각 영향에 중복·대체·경쟁 관계와 제거·통합·단계 공개·보완 UX 대안을 연결해줘.
‘성장 동기가 늘어난다’는 문장은 관찰 또는 테스트가 필요한 가설로만 다뤄줘.
조각 획득처, 비용, 상한, 확률, 출시 일정은 미확정으로 두고 발명하지 마.
확정 가정·가설·결정 필요 항목을 구분해줘.
```

> [!NOTE]
> **기대 결과**
>
> 기능 계약과 기존 루프 영향이 연결된 사전 리뷰. 고립 기능처럼 보지 않고 검증할 가설을 남겨야 한다.

<a id="example-21-b"></a>

#### 고급 예시 B — 랜덤 상점 레퍼런스 분석과 모호한 명세 교정

```text
$yuriring-game-system-design 21장을 중심으로 랜덤 상점 아이디어의 분석·명세 교정 훈련을 해줘.
가상 입력: ‘매일 랜덤 상품이 적절히 갱신되고 필요한 사람에게 좋은 물건이 나온다’라는 메모가 있다.
이 메모는 가상 문장이고 실제 레퍼런스 관찰·운영 데이터·책의 확정 문구가 아니라고 먼저 표시해줘.
표면 UI가 아니라 사용 경로, 소비 시점, 반복 루프 역할, 보완 수단, 플레이어 부담을 묻는 분석 질문을 만들어줘.
주체·범위·시점·고정/가변값·정렬·동점·실패 결과가 보이게 메모를 테스트 가능한 문장 후보로 고쳐줘.
상품 목록이 전 플레이어 공통인지 개인별인지, 슬롯 수·중복·갱신 기준은 미확정 질문으로 보존해줘.
기존 재화·상점·신규 유저·운영 일정에 미칠 영향을 표로 쓰고, 2주 일정의 핵심·옵션·후속을 구분해줘.
구체 상품, 확률, 갱신 시각, 가격은 임의로 채우지 마.
레퍼런스 관찰·가설·프로젝트 결정을 명확히 분리해줘.
```

> [!NOTE]
> **기대 결과**
>
> 레퍼런스 외형 복제를 피하고 모호한 문장을 테스트 가능한 계약으로 바꾼 분석안. 미확정 운영값을 보존해야 한다.
