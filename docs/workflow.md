# 게임 시스템 기획 실무 워크플로

[가이드 홈](index.md) · 관련: [고급 활용법](advanced-usage.md), [검수와 테스트](validation.md)

이 워크플로는 새 게임 기능을 기획하거나 기존 기획서를 반복 보완할 때 `yuriring-game-system-design`을 적용하는 순서입니다. 결과물의 크기에 맞게 단계를 줄일 수 있지만, **의도 → 구조 → 규칙 → 데이터 → UX/UI → 검토**의 연결은 유지합니다.

> [!TIP]
> **작은 기능도 의도부터 시작하세요**
>
> 버튼 하나를 추가하는 요청이라도 어떤 행동과 경험을 바꾸는지 먼저 정하면 규칙, 데이터, UI가 서로 어긋나는 일을 줄일 수 있습니다.

장 번호를 모르면 [참조 자료 색인](../.agents/skills/yuriring-game-system-design/references/index.md)에서 현재 질문의 사례·테이블·UI 이름을 찾아 먼저 읽을 장을 고릅니다. 설계 양식은 실무 패턴, 초안 점검은 판단표를 함께 적용합니다.

---

## 1. 기획 의도 정리 — 3~4장

| 확인할 것 | 산출물 | 요청 예시 |
|---|---|---|
| 누구의 어떤 문제를 해결하는가 | 대상·문제 정의 | `신규 길드원의 기부 참여가 낮은 이유와 해결할 문제를 정의해줘.` |
| 플레이어가 어떤 역할과 감정을 경험하는가 | 역할·감정 설계 | `기부 후 즉시 보상을 받는 경험이 협동감과 어떤 관계인지 설명해줘.` |
| 언제, 어떤 행동으로 이어지는가 | 플레이 흐름 | `가입 → 기부 발견 → 참여 → 보상 확인의 흐름을 설계해줘.` |

> [!IMPORTANT]
> **목표 지표와 기획 의도를 구분합니다**
>
> “참여율을 올린다”는 측정 목표입니다. 기획 의도에는 대상 이용자, 해결할 경험 문제, 기능이 제공할 역할을 함께 적습니다.

---

## 2. 기능과 연결점 분해 — 5~6장

기능이 할 수 있는 행동과 관리해야 할 속성을 분리하고, 기존 시스템과의 연결을 표시합니다.

```text
기능: 길드 기부
행동: 기부하기 / 보상 확인하기 / 기록 보기
속성: 기부 가능 횟수 / 사용 재화 / 누적 기여도 / 보상 상태
연결: 길드 / 재화 / 우편함 / 업적 / 랭킹
```

```text
$yuriring-game-system-design 5~6장을 적용해 길드 기부 기능을
행동, 상태, 관리 속성, 연결 시스템으로 분해해줘.
기존 재화·우편함·업적에 미치는 영향도 함께 표로 작성해줘.
```

> [!WARNING]
> **화면부터 고정하지 마세요**
>
> 기능의 목적·행동·상태가 결정되기 전에 화면을 확정하면 예외 처리와 데이터 구조가 바뀔 때 UI를 다시 그릴 가능성이 커집니다.

---

## 3. 규칙과 예외 정의 — 7~9장

각 행동을 조건, 처리, 결과, 실패·취소·충돌로 나누어 작성합니다.

| 항목 | 예시 질문 |
|---|---|
| 적용 조건 | 누가 언제 기부할 수 있는가? |
| 필요 정보 | 길드 ID, 이용자 ID, 재화 종류·수량, 일일 횟수가 필요한가? |
| 처리와 결과 | 재화 차감과 기여도 반영은 어떤 순서로 일어나는가? |
| 실패 | 재화 부족, 길드 탈퇴, 이미 처리된 요청이면 무엇을 안내하는가? |
| 취소·충돌 | 처리 중 연결이 끊기거나 요청이 중복되면 무엇을 보장하는가? |

```text
$yuriring-game-system-design 7~9장을 적용해 아래 행동의 규칙을 작성해줘.
각 행동을 적용 조건 → 필요 정보 → 판정·처리 → 결과 → 실패·취소·충돌 순서로 쓰고,
플로 차트로 표현해야 할 분기와 문장 명세로 충분한 항목을 구분해줘.
구현용 명세의 조건·예외와 플레이어용 안내 문구는 구분해줘.
플레이어 안내는 기존 게임의 관습과 기대를 고려해 오해하기 쉬운 지점을 구체적으로 설명해줘.
```

**설명 깊이의 기준:** 구현자가 알아야 할 예외는 명세에 남기고, 플레이어에게는 예측 가능한 동작까지 장황하게 나열하지 않습니다. 같은 ‘공격 시’ 효과라도 지속 피해·다단히트의 적용 방식이 기존 규칙과 다르면 그 차이를 명확히 알려야 합니다. [8장](../.agents/skills/yuriring-game-system-design/chapters/ch08-rule-design.md)의 설명 밀도 기준을 적용합니다.

## 4. 데이터 테이블 설계 — 10~12장

행이 무엇을 뜻하는지 먼저 정의한 뒤 열·타입·키·참조를 결정합니다. 설정 데이터와 플레이 중 변하는 기록도 구분합니다.

한 행의 의미·기본 키·업무상 중복 금지 범위를 함께 적습니다. 행 ID가 서로 달라도 같은 요청의 선택 대상이나 같은 회차의 보상이 중복될 수 있습니다. 단일 행 참조와 여러 행의 그룹 조회를 구분하는 [실무 패턴](../.agents/skills/yuriring-game-system-design/patterns.md#객체반복-정보참조-분리)을 적용해 검증 범위를 명시합니다.

테이블을 나누거나 합칠 때는 **사용 빈도·업데이트 빈도·수정 범위·재사용성**으로 대안을 비교하고 선택 이유를 남깁니다. 분리 자체가 정답은 아닙니다. [10장](../.agents/skills/yuriring-game-system-design/chapters/ch10-table-foundations.md)의 기준에 따라, 운영자가 값을 언제 어떻게 바꾸고 초기화할지도 작동 규칙으로 명세합니다. 초기화 시각·시간대가 미정이면 임의로 확정하지 않습니다.

| 테이블 역할 | 예시 | 점검 기준 |
|---|---|---|
| 설정 | 기부 종류별 비용·기여도·보상 | 운영자가 바꾸는 기준값인가? |
| 상태·기록 | 이용자별 오늘 기부 횟수·누적 기여도 | 언제 생성·갱신·초기화되는가? |
| 보상 이력 | 지급 ID·상태·지급 시각 | 중복 지급을 어떻게 막는가? |

> [!IMPORTANT]
> **참조와 중복을 구분합니다**
>
> 다른 시스템이 이미 관리하는 아이템 상세 정보나 이용자 기본 정보는 그대로 복제하지 않습니다. 이 기능에 필요한 식별자와 참조 조건, 존재 여부 검증을 명세합니다.

## 5. UX/UI 명세 — 13~16장

정보 구조 → 화면 이동 → 와이어프레임 수준의 구성 → 요소별 명세 순으로 작성합니다. **각 요소에 필요한 항목만** 명세하며, 정적 제목·설명에는 입력·저장 조건을 강제하지 않습니다.

| 요소별로 적을 것 | 예시 |
|---|---|
| 이름·역할 | `기부하기 버튼`: 선택한 기부를 요청한다 |
| 입력·상호 작용 | 탭, 확인 모달, 재시도 |
| 상태 | 기본, 비활성, 처리 중, 성공, 실패 |
| 피드백 | 재화 부족 사유, 성공한 기여도 변화 |
| 저장 여부 | 마지막 선택, 확인 팝업 표시 여부 |

```text
$yuriring-game-system-design 13~16장을 적용해
길드 기부 화면의 정보 구조와 화면 흐름을 작성해줘.
각 UI 요소에 필요한 역할, 입력, 상태, 피드백, 저장 여부만 붙이고,
정적 제목·설명에는 입력·저장 조건을 강제하지 마.
규칙 문서와 충돌하는 항목은 별도로 표시해줘.
```

## 6. 기획서 완성·반복 검토 — 17~21장

기획서는 읽는 사람에 따라 필요한 정보가 다릅니다. 개발에는 판정·데이터·오류 처리, 아트에는 필요한 리소스·상태, QA에는 재현 조건·기대 결과가 드러나야 합니다.

QA에는 **확정 정책의 필수 결과**와 **미정 정책별 조건부 결과**를 나눕니다. “같은 요청은 한 번만 지급”이 확정이라면 중복 지급 금지는 유지하고, 재요청 응답·오류 안내는 결정 질문으로 남깁니다. 규칙과 UI가 충돌하는 경우에는 하나의 합격 결과를 임의로 정하지 않습니다. [QA 적용 양식](../.agents/skills/yuriring-game-system-design/patterns.md#정상-흐름과-예외를-함께-명세)을 참고하세요.

1. 현재 기획안과 변경 목적을 제공합니다.
2. 관련 장을 지정해 누락·모순·영향을 검토합니다.
3. 수정안을 반영한 뒤 같은 조건으로 재검토합니다.
4. 미결정 정책은 결정 전까지 표에 남깁니다.

```text
$yuriring-game-system-design 17~21장을 기준으로 이 기획서를 검토해줘.
개발·아트·QA·라이브 운영이 각각 알아야 할 정보가 빠졌는지 확인하고,
변경이 재화·보상·기록·UI·운영에 미치는 영향을 표로 정리해줘.
확정 근거가 없는 정책은 임의로 채우지 마.
```

> [!NOTE]
> **반복 검토의 종료 조건**
>
> 모든 가능성을 나열하는 것이 목적은 아닙니다. 현재 출시 범위에서 구현·QA·운영이 판단할 수 있고, 남은 결정 사항의 담당자와 시점이 보이면 한 차례의 기획 검토를 마칠 수 있습니다.

장별 세부 프롬프트와 고급 조합은 [고급 활용법](advanced-usage.md)을 참조하세요.
