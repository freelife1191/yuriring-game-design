# 검수와 테스트

[가이드 홈](index.md) · 관련: [실무 워크플로](workflow.md)

`yuriring-game-system-design`의 답변과 기획안을 검수할 때는 **원문 근거, 프로젝트 가정, 실제 답변**을 분리합니다. 파일이 존재하거나 형식이 좋아 보인다는 사실만으로 기획의 정확성이 보장되지는 않습니다.

> [!TIP]
> **먼저 검수할 항목**
>
> 플레이 경험을 크게 바꾸거나 구현 비용이 큰 수치·조건·예외·데이터 참조부터 확인하세요.

---

## 1. 원문과 스킬 범위 확인

스킬의 [source.json](../.agents/skills/yuriring-game-system-design/source.json)에는 원본 제목·판본·PDF 페이지 수·21개 장·추출 방식·확인 한계가 기록되어 있습니다.

| 확인 대상 | 확인 방법 | 주의할 점 |
|---|---|---|
| 장 제목·범위 | `source.json`의 `chapters`와 장 파일 | 소절을 별도 장으로 취급하지 않기 |
| 질문별 자료 선택 | [참조 자료 색인](../.agents/skills/yuriring-game-system-design/references/index.md)과 실제 읽은 파일 | 색인만 읽고 장의 상세 조건·한계를 생략하지 않기 |
| 책 쪽 인용 | `page_convention`과 원본 PDF | 이 스킬의 PDF쪽은 책 인쇄쪽보다 2 크지만 다른 자료에 일반화하지 않기 |
| 수치·확률·순서 | 원본의 해당 본문·표·도식 | 사례 수치를 현재 서비스 기본값으로 승격하지 않기 |
| 책의 예시 | 장 파일의 출처·적용 조건 | 특정 프로젝트 전제를 보편 규칙으로 바꾸지 않기 |
| 추출 한계 | `limitations` | 전체 도식·이미지·표가 전수 시각 검증된 것으로 해석하지 않기 |

> [!WARNING]
> **원문 확인이 필요한 판단**
>
> 확률 계산, 시간·수량, 정렬 방향, 테이블 열의 연결, 플로 차트 분기는 원본 PDF의 해당 페이지를 다시 확인하세요. 스킬의 요약은 판단을 돕지만 원문의 시각 정보 전체를 대체하지 않습니다.

> [!NOTE]
> **참조 자료 구성 검수**
>
> 21장 핵심 지식의 원문 대조, 참조 색인 보완과 단독 사용 검증 범위는 [참조 자료 검수 기록](../output/skill-review/2026-10-12/references/report.md)에 있습니다. 해당 검수 시점의 파일을 대상으로 한 기록이며, 모든 소절·문장·도판을 포함하거나 전수 검증한 결과는 아닙니다.

## 2. 기획안 검수 체크리스트

### 의도와 구조

- [ ] 대상 이용자와 해결할 경험 문제가 보이는가?
- [ ] 기능의 행동, 상태, 속성, 연결 시스템이 분리되어 있는가?
- [ ] 성과 지표만 있고 플레이어 경험의 이유가 빠지지 않았는가?

### 규칙과 데이터

- [ ] 행동마다 적용 조건, 처리, 결과, 실패·취소·충돌이 있는가?
- [ ] 구현용 명세의 예외와 플레이어용 설명을 구분했는가? 플레이어가 예측 가능한 부분은 간결하게, 오해하기 쉬운 조건은 구체적으로 설명했는가? (8장)
- [ ] 설정값과 플레이 기록이 구분되어 있는가?
- [ ] 테이블 분리·통합의 이유를 사용·업데이트 빈도, 수정 범위, 재사용성으로 설명하는가? 갱신·초기화의 작동 규칙과 미정 시각·시간대도 구분했는가? (10장)
- [ ] 행의 의미, 기본 키, 참조 대상, 존재·유일성 검증이 실제 관계와 맞는가?
- [ ] 행 ID 유일성과 업무상 중복 금지 범위를 구분했는가? 같은 요청·회차의 반복 행과 그룹 조회가 실제 산출물과 맞는가?
- [ ] 중복 요청·중복 보상·동시 처리의 대응이 필요한가?

### UX/UI와 협업

- [ ] 상호 작용하는 요소에 필요한 역할, 입력, 상태, 피드백, 저장 여부가 있는가? 정적 제목·설명에 입력·저장 조건을 강제하지 않았는가?
- [ ] 실패 안내가 규칙 문서의 실패 조건과 일치하는가?
- [ ] 개발·아트·QA·운영이 각각 필요한 정보를 찾을 수 있는가?
- [ ] QA에서 확정 정책의 필수 결과를 보존하고 미정 응답·복구 정책의 조건부 결과와 구분했는가? 문서가 충돌하면 미결정 사항으로 표시했는가?
- [ ] 변경의 영향 범위와 미결정 정책의 담당자가 표시되어 있는가?

## 3. 실제 답변 평가

```text
$yuriring-game-system-design 아래 기획안을 검토해줘.
원문 근거, 현재 프로젝트를 위한 제안, 아직 미결정인 정책을 구분하고,
규칙·예외·데이터·UI의 모순을 문제 → 영향 → 수정안 순서로 적어줘.

[기획안]
```

| 평가 기준 | 통과의 예 | 실패 신호 |
|---|---|---|
| 요청 이해 | 장르·제약·목적을 결과에 반영 | 입력에 없는 플랫폼·정책을 단정 |
| 근거 구분 | 책의 설명과 새 제안을 구분 | 새 아이디어를 책의 결론처럼 서술 |
| 참조와 링크 | 질문에 맞는 장을 읽고 실제 파일·쪽 범위를 인용 | 색인만 보고 답하거나 존재하지 않는 경로를 근거 링크로 제공 |
| 조건 보존 | 미정 수치·정책을 표로 남김 | 보상·확률·시간을 근거 없이 확정 |
| 설계 연결 | 규칙·데이터·UI의 참조 관계가 이어짐 | UI 성공 안내가 실제 처리 조건과 불일치 |
| 행·중복·QA | 행과 키의 책임이 맞고 확정·조건부 기대 결과가 분리됨 | 행 ID만으로 중복 방지를 보장하거나 확정된 결과까지 미정으로 처리 |
| 범위 인식 | 다루지 않은 내용과 확인 필요성을 밝힘 | 원문에 없는 세부 사실을 단정 |

> [!IMPORTANT]
> **답변 문구가 아니라 내용으로 판단합니다**
>
> “검토 완료”나 “통과”라는 표현이 있어도 조건·단위·참조·예외가 빠졌다면 통과가 아닙니다. 실제 산출물에서 확인한 근거와 누락 항목을 기록하세요.

## 4. 결과 기록과 수정 요청

검수 결과에는 범위, 확인한 장·원문 페이지, 실제 요청과 답변, 발견한 문제, 수정 파일 또는 문서, 재검수 결과를 남깁니다.

초기 실패·부분 통과도 보존하고 수정 후 무엇을 다시 확인했는지 적습니다. **기존 답변의 링크만 수정한 검사**, **새 독립 세션에서 답변을 다시 생성한 검사**, **앱에서 실제 호출한 검사**는 서로 다른 검증 범위입니다. 한 결과를 다른 범위의 통과로 표현하지 않습니다.

> [!NOTE]
> **실제 호스트 호출과 프롬프트 표본 검사**
>
> Codex CLI의 새 세션에서 README의 수량 스테퍼 예시를 호출하고, 고급 예시의 랜덤 상점·자동 원정 편성 답변을 별도로 평가한 [검수 기록](../output/skill-review/2026-10-12/host-smoke/report.md)을 참고하세요. 요청·답변·실제 자료 읽기 로그와 초기 결과를 보존합니다. CLI 호출, 독립 답변 평가, 같은 평가자의 재생성 범위를 구분하며, GUI나 다른 호스트에서 실행한 결과로 해석하지 않습니다.
>
> 이 검사와 앞선 QA 검사에서 드러난 보완점을 스킬·실무 패턴에 반영한 내용은 [검증 기반 보완과 재검수 기록](../output/skill-review/2026-10-12/refinement/report.md)에 정리했습니다. 행·키·중복 범위, 확정·조건부 QA 결과, 책과 적용 지침의 출처 구분을 확인하세요.

| 판정 | 의미 | 다음 행동 |
|---|---|---|
| 통과 | 정한 범위의 조건을 충족 | 기획서에 반영하고 변경 이력 기록 |
| 부분 통과 | 근거·조건·예외 일부가 부족 | 부족한 항목만 좁게 보완 요청 |
| 실패 | 핵심 규칙·수치·연결이 잘못됨 | 원문과 입력을 다시 대조해 수정 |
| 확인 불가 | 원문·결정권자·프로젝트 정보가 없음 | 필요한 자료 또는 담당자 확인 요청 |

```text
$yuriring-game-system-design 이전 검토에서 지적된 아래 항목만 다시 보완해줘.
확인된 사실과 새 제안을 구분하고, 해결되지 않은 항목은
‘결정이 필요한 사항’ 표에 항목·선택지·영향·확인할 담당자를 적어줘.

[검수 기록]
```

## 5. 원문과 공유 시 유의할 점

원문 PDF, 추출 텍스트, 이미지·표를 외부에 공유할 때는 해당 자료의 저작권과 공유 권한을 확인하세요. 검수 기록에는 필요한 페이지·근거·요약만 남기고, 원문 전체를 기획 문서에 복제하지 않는 편이 안전합니다.
