# 시작하기

[가이드 홈](index.md) · 다음: [에이전트별 사용](agents.md)

`yuriring-game-system-design`은 게임 시스템 기획의 **학습·설계·검토**에 사용합니다. 설치 절차는 [README의 설치하기](../README.md#설치하기)를 따르고, 이 문서는 설치가 끝난 뒤 바로 쓸 수 있는 요청을 안내합니다.

> [!TIP]
> **가장 짧은 시작**
>
> 대화창에 아래 문장을 입력한 뒤, 대괄호만 현재 프로젝트 정보로 바꾸면 됩니다.

```text
$yuriring-game-system-design [기능 이름]을 설계해줘.
장르는 [장르], 대상 이용자는 [대상], 기존 관련 기능은 [기능],
제약은 [일정·플랫폼·기술 제약]이야.
기획 의도, 규칙·예외, 필요한 데이터, UI 흐름을 구분하고
아직 정하지 않은 항목은 답변 마지막의 ‘결정이 필요한 사항’ 표에 정리해줘.
```

---

## 1. 요청 목적 고르기

| 목적 | 언제 쓰는가 | 요청 첫 문장 예시 |
|---|---|---|
| 개념 학습 | 책의 장이나 개념을 이해할 때 | `11장의 데이터 테이블 설계 원칙을 설명해줘.` |
| 새 기능 설계 | 기능을 처음 정의할 때 | `길드 기부 기능을 처음부터 설계해줘.` |
| 기획안 검토 | 초안의 누락·모순을 찾을 때 | `아래 기획안을 규칙·예외·데이터 관점에서 검토해줘.` |
| 문서 보완 | 작성 중인 문서를 구현 가능한 명세로 만들 때 | `이 화면 명세에 입력·상태·저장 규칙을 보완해줘.` |
| 변경 영향 분석 | 라이브 기능을 바꾸기 전일 때 | `보상 수량 변경이 기존 시스템에 미치는 영향을 분석해줘.` |

> [!IMPORTANT]
> **목적을 먼저 말하세요**
>
> “기획해줘”만으로는 학습용 설명, 초기 설계, 문서 검토 중 무엇을 원하는지 알기 어렵습니다. 목적과 현재 산출물의 상태를 함께 알려주면 관련 장과 결과 형식이 좁혀집니다.

### 장 번호를 모를 때

[참조 자료 색인](../.agents/skills/yuriring-game-system-design/references/index.md)에서 사례 이름을 찾거나, 대화창에 구체적인 기능을 바로 적습니다. 아래는 Codex 예시이며 다른 호스트의 호출 표기는 [에이전트별 사용](agents.md)을 따릅니다.

| 요청 예시 | 먼저 읽을 장 | 확인할 결과 |
|---|---|---|
| `$yuriring-game-system-design 다국어 NPC 대사와 UI 문구의 데이터 책임을 나눠줘.` | 12장 | 스트링·챕터·대사 행의 책임과 참조 |
| `$yuriring-game-system-design 보유 수량 12인 아이템 수량 스테퍼를 명세해줘. 기본 선택 수량은 미정이야.` | 16장 | 경계·오류·버튼 상태와 미정 기본값 |
| `$yuriring-game-system-design 책의 자동 파견 선정 기준과 확정할 수 없는 부분을 설명해줘.` | 18장 | 비교 우선순위와 미정 정렬 방향 |

> [!TIP]
> **찾은 뒤 필요한 자료만 읽습니다**
>
> 상세 조건과 사례는 장 파일, 용어의 짧은 뜻은 용어집, 작성 양식은 실무 패턴, 초안 검토는 판단표를 사용합니다. 정확한 원문 칼럼명·수치·도판이 필요하면 해당 PDF쪽을 추가로 확인합니다.

## 2. 최소 입력 정보

다음 네 가지가 있으면 실무에 쓸 수 있는 초안을 만들기 쉽습니다.

| 정보 | 예시 | 없을 때의 처리 |
|---|---|---|
| 기능 목표 | 신규 이용자의 첫 주 이탈을 줄인다 | 가설로 표시 |
| 대상과 맥락 | 모바일 수집형 RPG, 길드 가입 후 | 확인 질문 또는 가정 |
| 기존 연결점 | 재화, 우편함, 길드 레벨 | 영향 범위를 미결정으로 표시 |
| 제약 | 2주, 서버 개발 1명, 실시간 갱신 불가 | 구현 선택지와 영향 제시 |

원문 PDF를 함께 제공하면 책의 수치·도식·예시 조건을 재확인하는 데 도움이 됩니다. 다만 기본적인 질문이나 기존 스킬의 장별 학습에는 원문 파일을 함께 제공할 필요가 없습니다.

## 3. 바로 쓰는 요청

### 개념을 배우기

```text
$yuriring-game-system-design 7장과 8장을 바탕으로
‘규칙’과 ‘예외’의 차이를 초보 기획자에게 설명해줘.
길드 기부를 예시로 들되, 책의 설명과 새 예시를 구분해줘.
```

### 기능 초안을 만들기

```text
$yuriring-game-system-design 모바일 수집형 RPG의 길드 기부 기능을 설계해줘.
목표는 협동 참여를 늘리는 것이고, 하루 1회 참여, 재화 2종이 있어.
기획 의도 → 기능·속성 분해 → 규칙·예외 → 데이터 → UI 흐름 순서로 작성해줘.
확정할 수 없는 정책은 ‘결정이 필요한 사항’ 표로 남겨줘.
```

### 초안을 검토하기

```text
$yuriring-game-system-design 아래 기획안을 검토해줘.
규칙 충돌, 실패·취소 처리, 중복 지급 가능성, 데이터 참조, UI 피드백을 확인하고
각 항목을 문제 → 영향 → 수정안 순서로 작성해줘.

[기획안 붙여넣기]
```

### 특정 장을 적용하기

```text
$yuriring-game-system-design 15장과 16장을 우선 적용해서
상점 구매 확인 화면의 요소별 역할, 입력, 기본 상태, 실패 안내, 저장 여부를 명세해줘.
각 요소에 필요한 상태와 동작만 명세하고, 정적 제목에는 입력·저장 조건을 강제하지 마.
```

## 4. 결과 확인

좋은 결과에는 다음이 구분되어 있습니다.

- 사용자의 입력과 프로젝트 제약
- 책의 원칙 또는 참조 장
- 실제 읽은 자료와 확인한 쪽 범위. 파일 링크가 있으면 해당 경로가 존재하는지 확인
- 현재 프로젝트를 위한 제안과 가정
- 아직 정하지 않은 정책과 확인할 담당자

> [!WARNING]
> **수치와 정책은 자동 확정되지 않습니다**
>
> 보상 수량, 확률, 제한 시간, 재화 차감 시점, 취소 가능 여부는 서비스 정책입니다. 근거가 없으면 확정값으로 채우지 말고 선택지와 영향을 요청하세요.

장별 프롬프트가 필요하면 [고급 활용법](advanced-usage.md), 기획서의 반복 작성 순서는 [실무 워크플로](workflow.md)를 보세요.
